# 第 54 章 · 构建工具

**简体中文** ｜ [English](./54-build-tool.en-US.md)

---

> 第 53 章把依赖管好了，代码怎么变成能跑的东西？答案听起来只有一句「编译一下」，但真实的构建系统要同时做对三件互相拉扯的事：**少做**（增量）、**同时做**（并行）、**别人做过就别做**（缓存）——而这三件事各自都有一个能让你**静默产出错误产物**的陷阱。
>
> 本章的**钥匙实验**先手写一个增量构建系统，实测时间戳判断的两种失效。**假阳性**：`touch` 一个内容没变的头文件，白白重建 3 个目标（`git checkout` 每天制造成千上万次）。**假阴性更致命**：改了头文件内容但 mtime 被拨回一小时前（时钟漂移、解压旧档、缓存恢复都会造成），构建系统报告「重建 0 个」，而**产物里还是旧版本**——你以为修了，其实没有。换成 Bazel 式的**内容哈希**，同样四个实验全部正确。
>
> Java 版把这个抽象陷阱变成了可运行的翻车现场：`static final int MAX_RETRIES = 3` 改成 10，按「哪个文件变了重编哪个」只重编 `Config.java`——运行 `App.run()` 打印的**仍然是 3**。因为常量在编译期被**内联进了 App.class 的字节码**，App 根本没有对 Config 的运行时引用。第二个翻车更直接：方法签名改了只重编被改的类，下游拿到 **`NoSuchMethodError`**。两次翻车同一个根因：**增量的正确性取决于依赖图的完整性**，而文件级 mtime 看不见字节码级的依赖。
>
> C++ 版调用真实的 `g++ -E` 量出了另一笔账：一个两行的加法函数，`#include <iostream>` 之后预处理器吐出 **66293 行——膨胀 8286 倍**。这就是「改一个头文件要重编一片」的物理原因，也是 C++ 编译慢的第一大来源。
>
> JS 版手写了一个微型打包器：从入口构建依赖图 → 生成可运行的 bundle → **tree-shaking**。没人 import 的 `matrixMultiply`/`sub`/`formatCsv` 被整块摇掉，bundle 从 972 字节降到 662 字节（**瘦身 32%**），而运行结果逐字符相同。它能成立的唯一前提是 ESM 的 `import/export` **静态可分析**——CommonJS 的 `require(变量)` 摇不动。
>
> C# 版实测了并行的天花板：同一个任务图串行 670 ms、8 个 worker 并行 460 ms，而**关键路径**（`core → data → api → bundle`）正好是 460 ms——给 999 个 worker 仍然是 460 ms。**优化构建速度的第一步不是加机器，是缩短关键路径**。而缓存的前提——**确定性构建**——被实测证明极易破坏：产物里写个时间戳，同样的输入两次构建哈希就不同，所有缓存瞬间失效。

## 1. 学习目标

学完本章，你将能够：

- 说清构建系统的三块基石（**依赖图 + 拓扑排序 + 变更判定**），并手写一个增量构建器；
- 复现时间戳判断的**假阳性与假阴性**（实测），并解释内容哈希为什么同时消灭两者；
- 识别**增量编译的正确性陷阱**（常量内联、过期类文件——实测静默产出错误程序）；
- 解释 **tree-shaking 为什么依赖静态模块结构**（实测瘦身 32%），以及 CommonJS 为何摇不动；
- 用**关键路径**判断构建还能不能靠并行加速（实测 999 worker 也追不上），并说清**确定性构建**是缓存的前提。

## 2. 为什么会出现这个概念

### 一个 make 就能解决的问题？

```text
最朴素的构建: 一条命令把所有源文件编一遍
问题在【规模】: 十万行代码、五千个文件、改一行要等二十分钟——没人受得了
→ 于是有了增量: 只重建受影响的部分
→ 但「受影响」这三个字，就是本章全部难度的来源
```

### 构建系统的三块基石

```text
① 依赖图（DAG）: 谁依赖谁——这是一切的前提
② 拓扑排序:     先建依赖，再建目标
③ 变更判定:     哪些目标【过期】了需要重建 ← 三块里最难的一块
```

### 一句话定义

```text
构建系统 = 一个把「源码 → 产物」的转换过程建模成 DAG，
          并尽可能【少做、并行做、复用别人做过的】执行引擎
```

> **一句话总结**：构建工具的全部难度不在「怎么编译」，而在**「什么可以不编译」**——而这个判断一旦出错，代价不是构建失败（那反而幸运），是**静默产出一个与源码不符的产物**（本章用三种语言各实测了一次）。

## 3. 底层原理

### 钥匙实验一：手写增量构建，实测时间戳的两种失效

**依赖图与拓扑序**（Python 实测）：

```text
规则: a.obj ← [a.src, common.hdr]   b.obj ← [b.src, common.hdr]
      c.obj ← [c.src]               app.bin ← [a.obj, b.obj, c.obj]
拓扑序: ['a.obj', 'b.obj', 'c.obj', 'app.bin']
首次构建（全量）: 重建 4 个
```

**增量生效时的样子**：

```text
什么都没改，再构建: 重建 0 个 ✓
改 c.src:           重建 2 个 → ['c.obj', 'app.bin']（a.obj/b.obj 没动）✓
改 common.hdr:      重建 3 个 → ['a.obj', 'b.obj', 'app.bin']
→ 一个头文件牵动两个 obj——【依赖图的扇出决定改动的爆炸半径】
```

**失效一：假阳性**（内容没变却重建）：

```text
touch common.hdr（内容一个字没改）: 重建 3 个
→ 白白重建——git checkout / 分支切换会大量制造这种假阳性
```

**失效二：假阴性**（内容变了却不重建——真正危险的那个）：

```text
改了 common.hdr 但 mtime 被拨回一小时前: 重建 0 个
产物里的头文件版本: 【还是旧的 v2】✗
→ 改动【没进产物】——时钟漂移、解压旧档、构建缓存恢复都会造出这种局面
→ 假阳性只是浪费时间，假阴性是【产物悄悄过期】——你以为修了，其实没有
```

**Bazel 的答案：内容哈希**（同样四个实验重跑，Python 实测）：

```text
无改动:                 重建 0 个 ✓
touch（假阳性场景）:     重建 0 个 ✓ 内容没变就不重建
改内容 + 回拨 mtime:     重建 3 个 ✓ 哈希变了就重建
→ 内容哈希同时消灭两种失效——代价是每次都要读文件算哈希（用缓存摊薄）
```

### 钥匙实验二：增量编译的正确性陷阱（Java 实测）

**陷阱一：常量内联**——Java 增量编译最著名的坑：

```java
public class Config { public static final int MAX_RETRIES = 3; }
public class App { public static String run() { return "重试上限 = " + Config.MAX_RETRIES; } }
```

```text
把 MAX_RETRIES 改成 10，按增量策略【只重编 Config.java】:
运行 App.run() → 重试上限 = 3   ← 还是 3！
→ 原因: static final 常量在编译期被【内联进 App.class 的字节码】
  App.class 里存的是字面量 3，根本没有对 Config 的运行时引用
→ 「哪个文件变了重编哪个」在这里【静默产出错误的程序】——比编译失败糟得多
重编 App.java 之后 → 重试上限 = 10 ✓
```

**陷阱二：过期的类文件**：

```text
Util.greet 加了个参数，只重编 Util.java:
运行 Caller.run() → ✗ NoSuchMethodError: 'String Util.greet(String)'
→ 第 53 章的运行时炸弹，这次的成因是【过期的 Caller.class】
```

**两次翻车的共同根因**：

```text
增量的正确性取决于【依赖图的完整性】
而文件级 mtime 看不见「常量被内联」「签名被引用」这些【字节码级】依赖
→ 增量构建的黄金法则: 增量的结果必须与全量重建【逐字节一致】
→ 排查诡异行为的第一招永远是 clean build——
  如果 clean 后问题消失，说明你的增量系统漏了一条依赖边
```

### 钥匙实验三：头文件展开的真实代价（C++ 调用 g++ -E 实测）

```text
一行加法函数，预处理后:
  不含任何头文件:               8 行
  #include <iostream>:      66293 行（膨胀 8286x）
  #include <vector/string/map>: 63839 行（膨胀 7979x）
→ 你写的两行代码，编译器实际要处理【几万行】——每个 .cpp 都重新处理一遍
→ 这是 C++ 编译慢的第一大来源，也是「改一个头文件要重编一片」的物理原因
```

**真实编译的增量对比**（同一实验里调用 g++ 实测）：

```text
全量编译 3 个 .cpp:              77 ms
改 c.cpp（无共享头）→ 重编 1 个:  28 ms（省了 64%）
改 common.hpp → 重编 2 个:       50 ms（省了 35%）
→ 改动落在依赖图哪个节点，决定了增量能省多少——头文件是最贵的改动
```

### 钥匙实验四：打包与 tree-shaking（JS 手写打包器实测）

**三步走**：

```text
① 从入口解析 import，递归建依赖图:
   main.js → ./format.js{formatSum}
   format.js → ./math.js{add}
   math.js → （无依赖）
② 把模块图改写成注册表 + __require 运行时，合成单文件 → 真实运行输出「结果: 42」
③ tree-shaking: 从入口出发标记「谁被用到」，其余整块删除
```

```text
format.js 被用到的导出: {formatSum}   （formatCsv 没人用）
math.js   被用到的导出: {add}         （sub、matrixMultiply 没人用）
体积: 972 → 662 字节（瘦身 32%），运行结果逐字符一致 ✓
```

**为什么 CommonJS 摇不动而 ESM 可以**：

```text
CommonJS: require(变量)、module.exports[key] = ... —— 【运行时】才知道导入导出什么
ESM:      import { add } from './math.js' —— 【语法层面】固定，不执行就能分析
→ 这就是 ESM 坚持静态结构的原因: 不是为了好看，是为了让工具能做 tree-shaking
→ 第 47 章的既视感: 声明式（静态可分析）让优化器有牌可打——SQL 与 ESM 同一个道理
```

### 钥匙实验五：并行的天花板是关键路径（C# 实测）

```text
任务图: core(200) → {utils(80), data(120)} → {api(90), ui(70)} → bundle(50)；docs(60) 独立

串行执行:            670 ms（所有任务耗时之和）
并行（8 worker）:    460 ms（加速 1.46x）
  第 1 波: core, docs      第 2 波: utils, data
  第 3 波: api, ui         第 4 波: bundle
关键路径: core → data → api → bundle = 460 ms
给 999 个 worker:    460 ms   ← 完全追不上
```

```text
→ 就算给你无限个 CPU，构建也不可能快过关键路径
→ 优化构建速度的第一步不是加机器，是【缩短关键路径】:
  拆分 core 这种「谁都依赖」的巨型节点，比买 CPU 有效得多
```

### 缓存的前提：确定性构建（C# 实测）

```text
含时间戳的构建，同样输入两次: 492994B701CC vs 7407931BE6ED → 一致: False
去掉时间戳后:               E0C277E9CB07 vs E0C277E9CB07 → 一致: True

破坏确定性的三大常客:
  ① 时间戳（编译时间写进产物）
  ② 绝对路径（/Users/你的名字/...）
  ③ 并行/哈希遍历顺序（同样的输入，产物里符号顺序不同）
```

```text
→ 没有确定性，缓存命中率暴跌（action cache 的 key 每次都不同）
→ 也无法验证「这个二进制真的是这份源码编的吗」——第 53 章供应链的终局问题
→ 第 53 章的锁文件保证「装一样的依赖」，确定性构建保证「产出一样的产物」——
  供应链可验证性的两块基石
```

### 三者的关系

```text
增量: 少做事   —— 正确性最难（钥匙实验一、二各实测了一次翻车）
并行: 同时做   —— 上限是关键路径（实验五）
缓存: 别人做过 —— 需要确定性 + 内容哈希
→ 三者叠加才有现代构建体验；缺任何一个都会在某个规模上撞墙
```

## 4. JavaScript

JS 版手写打包器（数据见钥匙实验四），这里补充生态与机制。

### 打包器的运行时就是模块系统的用户态复刻

```javascript
const __modules = {}, __cache = {};
function __require(id) {
  if (__cache[id]) return __cache[id];
  const exports = {}; __cache[id] = exports;
  __modules[id](exports, __require);
  return exports;
}
```

**这就是第 14 章模块系统在浏览器里的手工实现**——浏览器当年没有模块，打包器就自己造一个。

### 现代构建器在比什么

```text
webpack : JS 写的，插件生态最全——大项目冷启动分钟级
esbuild : Go 写的，并行 + 少遍历——快 10~100x（本章算法的工业级实现）
vite    : 开发态干脆【不打包】——浏览器原生 ESM 按需加载，秒级启动
          生产态仍用 Rollup 打包（HTTP 请求数与压缩率的取舍又回来了）
→ 「打包」本身是 HTTP/1.1 时代的产物；工具在【更快】与【不做】之间演化
```

> **注意**：`sideEffects: false`（package.json）告诉打包器「这个包没有导入即执行的副作用，可以放心摇」——标错了会摇掉真正需要的初始化代码；code splitting 是 tree-shaking 的另一面（不是删掉，而是拆成按需加载的块）；source map 让压缩后的产物还能对回源码，是构建产物的调试基础设施。

## 5. Python

Python 版手写增量构建系统（数据见钥匙实验一），这里补充它的工程含义。

### 变更判定的三代方案

```text
一代（Make）:   mtime 比较 —— 快，但有实测的两种失效
二代（内容哈希）: sha256(输入) —— 正确，代价是读文件
三代（远程缓存）: key = hash(所有输入 + 命令行) → 查表
  → 同样的输入在【任何机器】上都算出同一个 key
  → 同事/CI 构建过的直接下载——「构建」退化成「查表」
```

### 为什么哈希的代价可以接受

```text
读文件算哈希 vs 重新编译: 前者是毫秒级 I/O，后者是秒级 CPU
→ 而且哈希结果可以按 (路径, mtime, size) 缓存 —— mtime 没变就不重算哈希
→ 于是变成: mtime 做【快速筛选】，哈希做【最终裁决】——两者结合而非二选一
```

> **注意**：Make 的隐式规则和 `.PHONY` 是几十年积累的约定；`ninja` 是「只做执行不做配置」的极简构建器（CMake/Meson 生成它的输入）；Python 自己的构建（PEP 517/518）把「构建后端」变成了可替换的组件——setuptools、hatchling、maturin 各有取舍。

## 6. Java

Java 版复现了两个增量陷阱（数据见钥匙实验二），这里补充工具的应对。

### 真实工具怎么解

```text
javac 本身:     不做增量——每次给它的文件全都重编（把难题交给上层）
Gradle 增量编译: 分析【类级依赖 + 常量依赖】，常量变了就重编所有引用者
Bazel:          内容哈希 + 沙箱 + header jar（只含签名）
```

**header jar 的思想值得单独说**：

```text
下游依赖的是你的【签名】，不是实现
→ 实现变了不必重编下游，签名变了才必须
→ 爆炸半径的精确化: 把「改了这个文件」细化成「改了这个文件的公开接口吗」
```

### 沙箱：把「漏掉的依赖」变成构建失败

```text
Bazel 在沙箱里执行每个动作: 只有【声明过的输入】才可见
→ 你漏声明一个头文件/依赖 → 沙箱里找不到它 → 构建立刻失败
→ 这把 Python 版 ④ 那种「悄悄用了没声明的东西」从运行时错误提前成了构建错误
→ 与第 53 章 pnpm 消灭幽灵依赖是同一个思路: 【物理上够不着没声明的东西】
```

> **注意**：Maven 的 `mvn clean install` 成为肌肉记忆，正是因为它的增量不够可信；Gradle 的构建缓存（`--build-cache`）和配置缓存是两回事，前者缓存任务输出、后者缓存构建脚本的求值结果；`--scan` 能生成构建性能报告，是找关键路径的第一手工具。

## 7. C++

C++ 版调用真实 g++ 测量（数据见钥匙实验三），这里补充它的完整流程与武器。

### 编译 vs 链接：两个截然不同的阶段

```text
编译: 每个 .cpp → .o（各自独立，可并行，可缓存——ccache 就缓存这一步）
链接: 所有 .o + 库 → 可执行文件（解析跨文件符号引用，第 53 章的符号世界）
→ 链接【不能增量】: 改一个 .o 就要重链整个可执行——大项目链接常是瓶颈
→ 所以有了 lld/mold 这样的并行链接器
```

### 减少重编的四种武器

```text
① 前置声明: 头文件里能不 #include 就不 include
   —— 少一条依赖边就少一片重编（Pimpl 是它的极致，第 53 章 ABI 也靠它）
② 预编译头(PCH): 把 <vector> 这类稳定大头文件预处理一次复用（治膨胀）
③ ccache: 编译结果按【预处理后内容的哈希】缓存（Python 版内容哈希的 C++ 版）
④ C++20 modules: 从根上取消文本展开——import 一次解析，产出二进制接口
```

**第 ④ 条才是治本**：让 C++ 终于有了 JS/Java 早就有的「模块」（第 14/53 章）——而模块化的直接红利就是**依赖精确、无需重复展开**。

> **注意**：`-MMD -MP` 让 gcc 自动生成依赖文件（Make 的自动依赖发现）；`include-what-you-use` 工具能找出「引了但没用」和「用了但没引」的头文件；分布式编译（distcc/icecc）把并行推到多机——但仍受关键路径限制（C# 版实测）。

## 8. C#

C# 版实测了并行的天花板与确定性（数据见钥匙实验五）。

### 调度算法的核心

```csharp
while (done.Count < Graph.Length) {
    // 找出所有「依赖都完成了」的任务
    var ready = Graph.Where(t => !done.Contains(t.Name) && t.Deps.All(done.Contains))
                     .Take(workers).ToList();
    elapsed += ready.Max(t => t.Ms);          // 一波的耗时 = 最慢的那个
    foreach (var t in ready) done.Add(t.Name);
}
```

**这就是所有构建工具的核心循环**：反复找出「就绪集合」，喂给 worker 池（第 45 章的线程池在这里变现）。

### 关键路径的实践含义

```text
实测: 8 worker 460 ms、999 worker 460 ms、关键路径 460 ms —— 三者相同
→ 诊断顺序: 先量关键路径，再决定加机器还是改结构
→ 缩短关键路径的手段: 拆分巨型节点、消除不必要的依赖边、把慢任务提前启动
→ 「构建慢」的答案往往不在构建工具里，而在【模块划分】里
```

### 确定性的工具支持

```text
.NET:  <Deterministic>true</Deterministic>（默认开）+ <PathMap> 消除绝对路径
gcc:   -ffile-prefix-map、-frandom-seed
通用:  SOURCE_DATE_EPOCH 环境变量约定（让工具用固定时间戳而非 now）
→ Reproducible Builds 项目在推动整个开源生态做到这件事
```

> **注意**：MSBuild 的 `Inputs`/`Outputs` 是 mtime 式判定（有实测过的两种失效）；`dotnet build` 的增量在跨项目引用时依赖 `.csproj` 的时间戳，改了 Directory.Build.props 常需 `--no-incremental`；NuGet 包的确定性还要求 `ContinuousIntegrationBuild=true`。

## 9. SQL

数据库里有一模一样的增量构建问题：**物化视图的刷新**。

### 视图 vs 物化视图 = 全量构建 vs 构建产物

```text
普通视图:   每次查询都【重新计算】——相当于每次 make 都 make clean
物化视图:   把结果【存成表】——就是构建产物，代价是会【过期】
```

### 增量刷新（实测）

```text
新到 2 笔订单（都在 2026-08-01）:
  全量刷新: 重算全部 28 天
  增量刷新: 只重算【受影响的那一天】
增量刷新后校验（与实时计算比对）: ✓ 一致
→ 「只重建受影响的部分」——与 Python 版增量构建是同一个算法
```

### 增量的翻车也一模一样（实测）

```text
改了 id=1 的【老】订单（属于 2026-08-02），而增量刷新只看「新插入的行」:
  物化表里 2026-08-02 的 total = 70855
  实时计算的 total            = 80853
→ 产物【悄悄过期】——与 Java 版的常量内联、Python 版的 mtime 假阴性完全同构
→ 三个例子，同一条教训: 增量的正确性 = 依赖追踪的完整性
```

### 用触发器做自动依赖发现（实测修复）

```sql
CREATE TRIGGER orders_au AFTER UPDATE OF amount ON orders BEGIN
  UPDATE daily_totals SET total = total - OLD.amount + NEW.amount WHERE day = NEW.day;
END;
```

```text
加了 INSERT/UPDATE 触发器后:
  2026-08-02 物化=78631 实时=78631 ✓
  2026-08-03 物化=71681 实时=71681 ✓
→ 触发器 = 构建系统的【自动依赖发现】: 不靠人记得声明，靠机制捕获每次变更
→ 代价也一样: 每次写入都变慢（第 49 章实测索引写放大，同一笔账）
```

### 同构对照表

```text
源文件       ↔ 基础表(orders)
构建产物     ↔ 物化视图(daily_totals)
依赖图       ↔ 视图定义里的表引用
增量构建     ↔ 增量刷新（只重算受影响分区）
自动依赖发现 ↔ 触发器 / CDC 变更捕获
clean build  ↔ 全量刷新（永远正确，永远慢）
→ dbt 把这套完整搬进了数据工程: 模型即目标、DAG 调度、增量物化策略
```

> **注意**：PostgreSQL 的 `MATERIALIZED VIEW` 只支持全量 `REFRESH`（并发刷新需要唯一索引），增量要靠 pg_ivm 之类扩展或手写触发器；sqlite 没有物化视图，本例用普通表 + 触发器手工实现；数据仓库里的「增量模型」（dbt 的 `incremental`）需要你显式提供「哪些行是新的」的判据。

## 10. 五语言横向对比

### ① 构建工具与机制对照

| 维度 | JavaScript | Python | Java | C++ | C# |
|------|-----------|--------|------|-----|-----|
| 主流工具 | webpack/vite/esbuild | setuptools/hatch + tox | Maven/Gradle | Make/CMake/Ninja/Bazel | MSBuild |
| 编译单元 | 模块（文件） | 模块（无编译） | 类（.java→.class） | **编译单元（.cpp）** | 项目（assembly） |
| 增量粒度 | 模块级 | — | 类级（+常量依赖） | 文件级（头文件扇出大） | **项目级**（粗） |
| 特有陷阱 | CommonJS 摇不动 | — | **常量内联**（实测） | **头文件展开 8286x**（实测） | 跨项目引用时间戳 |
| 死代码消除 | **tree-shaking**（实测 32%） | — | ProGuard/R8 | 链接器 --gc-sections | IL Linker/trimming |
| 缓存方案 | 各工具自带 | — | Gradle build cache | ccache/sccache | MSBuild 增量 |

### ② 钥匙实验数据汇总

```text
增量生效:     改 c.src → 重建 2 个；改 common.hdr → 重建 3 个（扇出决定爆炸半径）
mtime 假阳性: touch 未改内容的文件 → 白重建 3 个
mtime 假阴性: 改内容 + 回拨 mtime → 重建 0 个，产物【还是旧版本】
内容哈希:     同样四个场景全部判断正确
常量内联:     只重编 Config → App 仍打印 3（应为 10）——静默错误
过期类文件:   只重编 Util → Caller 抛 NoSuchMethodError
头文件展开:   8 行 → 66293 行（膨胀 8286x）
C++ 增量:     全量 77 ms；改 c.cpp 28 ms（省 64%）；改头文件 50 ms（省 35%）
tree-shaking: 972 → 662 字节（瘦身 32%），输出一致
并行天花板:   串行 670 ms、8 worker 460 ms、999 worker 460 ms = 关键路径 460 ms
确定性:       含时间戳两次构建哈希不同；去掉后一致
SQL 增量翻车: 物化 70855 vs 实时 80853；加触发器后完全一致
```

### ③ 共性与根因

**共性**：所有语言的构建系统都是「DAG + 拓扑序 + 变更判定」；所有增量方案的正确性都取决于依赖图的完整性（三种语言各实测了一次漏边的后果）；所有缓存方案都要求确定性。

**根因**：

- **增量的难点是「隐式依赖」**：常量内联（Java）、头文件展开（C++）、老行被更新（SQL）——这些依赖不在文件系统层面可见，必须由工具在**语言层面**理解；
- **C++ 编译最慢是模型决定的**：没有模块 → 头文件文本展开 → 每个编译单元重复解析几万行（实测 8286x）；
- **tree-shaking 只在静态模块系统里可行**：与第 47 章「声明式让优化器有牌可打」是同一条原理；
- **并行的上限是图的形状**：关键路径由**模块划分**决定，所以「构建慢」的答案常常在架构里而非工具里；
- **确定性是缓存与供应链的共同基础**：它把「构建」从一次计算变成一次**可验证的映射**。

## 11. 底层实现对比

| 工具 | 变更判定 | 并行/缓存 | 关键特点 |
|------|---------|----------|---------|
| **Make** | mtime | `-j` 并行 | 最小可用；两种失效都有（实测） |
| **Ninja** | mtime + 命令行哈希 | 高度并行 | 只执行不配置；命令变了也重建 |
| **Gradle** | 输入输出**内容哈希** | 本地/远程构建缓存 | 增量任务 + 增量编译（含常量依赖分析） |
| **Bazel** | 内容哈希 + **沙箱** | 远程缓存 + 远程执行 | 声明式依赖；漏声明即构建失败 |
| **esbuild** | 全量为主（够快） | Go 并行 | 用速度绕过增量复杂度 |
| **Vite（开发态）** | 不打包 | 浏览器原生 ESM | 把「构建」推迟到浏览器按需请求 |

**Bazel 的沙箱值得单独说**：

```text
每个动作在只含【声明过的输入】的沙箱里执行
→ 漏声明一个依赖 → 沙箱里找不到 → 构建立刻失败（而不是悄悄用了宿主机上的文件）
→ 这就是「hermetic build（封闭构建）」: 构建结果不依赖机器上碰巧存在的东西
→ 与第 53 章 pnpm 消灭幽灵依赖同构: 让没声明的东西【物理上够不着】
```

## 12. 性能分析

### 本章实测数字速查

```text
增量收益:     改无共享依赖的文件省 64%；改头文件只省 35%（C++ 真实编译）
头文件成本:   8 → 66293 行（8286x 膨胀）
tree-shaking: 瘦身 32%（本例规模；真实项目常见 30-70%）
并行:         串行 670 → 并行 460 ms（1.46x）；关键路径 460 ms 是硬下限
确定性:       破坏一次 → 缓存 key 每次都变 → 缓存命中率归零
```

### 构建速度的优化顺序

```text
① 量关键路径 —— 决定「加机器有没有用」（C# 版实测 999 worker 也追不上）
② 缩短关键路径 —— 拆分巨型节点、砍掉不必要的依赖边（架构问题）
③ 确保确定性 —— 否则缓存全废
④ 开缓存 —— 本地 → 远程（团队级复用）
⑤ 最后才是换更快的工具（esbuild 之于 webpack）
→ 反过来做（先换工具）常常收效甚微: 图的形状没变，天花板就没变
```

> ⚠️ **增量的正确性优先于速度**。本章三次实测的翻车（常量内联、mtime 假阴性、物化视图漏更新）都产出了**看起来正常但实际错误的产物**——这类问题的排查成本远高于多花两分钟做 clean build。任何增量优化都要能回答：**它与全量构建的结果逐字节一致吗？**

## 13. 工程实践

| 场景 | ✅ 推荐 | ❌ 避免 | 原因 |
|------|--------|--------|------|
| 变更判定 | 内容哈希（或 mtime 筛选 + 哈希裁决） | 纯 mtime | 实测两种失效，假阴性会静默出错 |
| Java 常量 | 用方法或非 final 静态字段暴露可变配置 | `public static final` 常量跨模块 | 实测内联导致改了不生效 |
| C++ 头文件 | 前置声明 + Pimpl + PCH | 头文件里随手 include | 实测展开 8286x，扇出决定重编范围 |
| 前端产物 | ESM + `sideEffects` 标注正确 | CommonJS 混用 | 实测只有静态结构能 tree-shake |
| 构建变慢时 | 先量关键路径 | 直接加 worker/机器 | 实测 999 worker 追不上关键路径 |
| 缓存 | 先做到确定性再开缓存 | 直接开缓存 | 不确定 → key 每次变 → 命中率 0 |
| 产物里的元信息 | 用 `SOURCE_DATE_EPOCH` 等固定值 | 写入构建时间/主机名 | 实测破坏确定性 |
| 依赖声明 | 沙箱化构建（Bazel）或显式声明 | 依赖「机器上碰巧有」 | 隐式依赖 = 换台机器就炸 |
| 诡异行为排查 | 第一招 clean build | 反复调试增量结果 | clean 后消失 = 漏了依赖边 |
| 数据物化 | 触发器/CDC 自动捕获变更 | 手写「只处理新行」 | 实测漏掉 UPDATE 导致产物过期 |

### 一句话决策

```text
构建慢时问三件事:
  ① 关键路径多长？    → 决定并行还有没有空间（不够就改模块划分）
  ② 增量对不对？      → clean build 与增量结果一致吗
  ③ 缓存能不能命中？  → 产物确定吗（时间戳/路径/顺序）
```

## 14. 最佳实践

- **变更判定用内容哈希**：实测 mtime 有假阳性（浪费）和假阴性（静默错误）两种失效，后者才是真正的敌人。
- **警惕语言层面的隐式依赖**：Java 常量内联、C++ 头文件展开、SQL 的老行更新——实测三种语言各翻车一次，共同根因是依赖图漏边。
- **增量的验收标准是「与全量逐字节一致」**：任何增量优化都要能回答这个问题；诡异行为的第一招永远是 clean build。
- **先量关键路径再谈并行**：实测 999 个 worker 也追不上 460 ms 的关键路径——「构建慢」的答案常在模块划分里。
- **做到确定性再开缓存**：实测一个时间戳就让哈希每次都变、缓存全废；确定性还是供应链可验证性的基础（第 53 章）。
- **前端坚持 ESM 并正确标注 `sideEffects`**：实测只有静态模块结构能 tree-shake（瘦身 32%）。
- **C++ 把「减少依赖边」当日常纪律**：前置声明、Pimpl、IWYU——实测头文件是最贵的改动点。
- **让漏声明的依赖构建失败而非静默通过**：沙箱化构建（Bazel）与 pnpm 消灭幽灵依赖是同一个思路。

## 18. 本章总结

**一句话**：构建工具把「源码 → 产物」建模成 DAG，并在**少做（增量）、同时做（并行）、别人做过就别做（缓存）**三条路上同时优化——而本章实测证明三条路各有一个能让你**静默产出错误产物**的陷阱：增量的判定用时间戳会同时有**假阳性**（`touch` 未改文件白重建 3 个）和更致命的**假阴性**（改内容但 mtime 回拨 → 重建 0 个，产物里还是旧版本），换成**内容哈希**才同时消灭两者；而语言层面的**隐式依赖**让翻车更隐蔽——Java 的 `static final` 常量被内联进调用方字节码，改了值只重编定义方，运行时**仍然打印旧值 3**（比编译失败糟得多），C++ 的头文件是**文本展开**（实测 8 行代码 `#include <iostream>` 后变成 66293 行，膨胀 8286 倍，这既是编译慢的第一来源也是「改一个头文件重编一片」的物理原因），SQL 的增量物化漏掉 `UPDATE` 老行同样让产物悄悄过期（70855 vs 80853）——三种语言，同一条教训：**增量的正确性等于依赖追踪的完整性**；并行方面，手写调度器实测串行 670 ms、8 worker 460 ms，而**关键路径正好是 460 ms**，给 999 个 worker 一毫秒也快不了——**优化构建的第一步不是加机器而是缩短关键路径**；缓存方面，其前提**确定性构建**被实测证明一个时间戳就能破坏（同样输入两次哈希不同），而它同时是第 53 章供应链可验证性的另一块基石；最后 JS 手写打包器完成了从依赖图到 **tree-shaking** 的全链路（瘦身 32%，输出一致），并揭示它成立的唯一前提是 ESM 的**静态可分析**——与第 47 章「声明式让优化器有牌可打」同一条原理。

**关键要点**

- **三块基石**：依赖图 + 拓扑排序 + 变更判定；难度全在第三块。
- **mtime 的两种失效**（实测）：假阳性浪费时间，**假阴性静默产出过期产物**。
- **内容哈希**（实测）：同时消灭两种失效；并让「构建」可退化成「查表」（远程缓存）。
- **隐式依赖的三次翻车**（实测）：Java 常量内联、C++ 头文件展开 8286x、SQL 漏捕获 UPDATE。
- **增量的黄金法则**：结果必须与全量重建逐字节一致；诡异行为第一招 clean build。
- **关键路径是并行的硬下限**（实测 999 worker = 8 worker = 460 ms）。
- **确定性是缓存的前提**（实测时间戳破坏哈希），也是供应链验证的基础。
- **tree-shaking 依赖静态模块结构**（实测 32%）——ESM 坚持静态语法正是为此。
