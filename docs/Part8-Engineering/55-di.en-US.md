# Chapter 55 · Dependency Injection

[简体中文](./55-di.md) ｜ **English**

---

> Chapter 52 kept repeating one sentence — "hard to test is almost always a design smell" — and the reason its C# example could slide a `FakeRepo` into `OrderService` was that the service depended on an **interface**, not a concrete class. This chapter answers the question that was deferred: **why hand your dependencies over?**
>
> The core is one sentence: **don't go looking for your dependencies; let them be handed to you**. When a class writes `new SqlRepo()` itself, the decision "which implementation" lives inside the class; turning it into a constructor parameter hands that decision to the caller — that is **inversion of control**.
>
> The **key experiment** hand-writes a DI container: reflect to find the constructor → recursively resolve each parameter type → `newInstance` to assemble, and **40 lines is Spring's skeleton** (Chapter 30's reflection merging with Chapter 51's object-graph construction). It also measures the container's two other core duties: **lifetimes** (a `@Singleton` `SqlRepo` injected in three places creates exactly 1 instance) and **cycle detection** (A needs B, B needs A → the container reports precisely `circular dependency: A → B → A`).
>
> That cycle experiment reveals an important criterion: **constructor injection makes circular dependencies impossible to construct**, so the container fails immediately; field injection (`@Autowired` on a field) instead creates an empty object and fills fields afterward — the cycle "starts successfully" but the object is momentarily a **half-built thing**, deferring the problem to runtime. **Constructor injection turns a design problem into a startup failure.**
>
> The C# example measured DI's most classic production incident — the **captive dependency**: a `Singleton` service depending on a `Scoped` repository leaves the second request still using the **first request's `RequestContext`** (measured: both show `Request#4`). The real consequences are database connections, transactions, and current-user identity leaking across requests — a correctness and security failure at once. The rule is hard: **long lifetimes must not depend on short ones**.
>
> The Python example offers the inverse view: in a dynamic language, a hard-wired dependency **can still be replaced** — assign the instance attribute directly, or use `mock.patch` to rebind the name in the module namespace (both measured working). That explains why "Python doesn't really need a DI container," but it also exposes the price: **a patch's string path hard-codes "who created what, where"**, coupling tests to implementation details.
>
> The C++ example priced the other road: runtime polymorphism (virtual calls) at 1.60 ns per call versus compile-time injection (templates) at 0.48 ns — **3.3× faster, and the entire gap is inlining**. And the reason C++ has almost no DI containers is exactly Chapter 51's ORM reason: **no runtime reflection**.

## 1. Learning Objectives

By the end of this chapter, you will be able to:

- State in one sentence how **inversion of control** relates to **dependency injection**, and distinguish **DI** from a **DI container**;
- Hand-write a DI container (reflective construction + autowiring + lifetimes + cycle detection);
- Compare the trade-offs of **constructor/property/method** injection (measured failure modes for each);
- Recognize the **captive dependency** (measured cross-request state leakage) and state the hard lifetime rule;
- Explain why the **service locator is considered an anti-pattern** — it differs from DI by exactly one direction.

## 2. Why This Concept Exists

### The question Chapter 52 left open

```text
Ch. 52 measured: OrderService could accept test doubles only because it depended on【interfaces】
                 "hard to test is almost always a design smell"
→ but why does depending on an interface make it replaceable? Who decides the implementation?
  —— this chapter's subject
```

### What happens when dependencies are hard-wired

```java
class UserService {
    private Repo repo = new SqlRepo();        // ⚠️ dependency hard-wired inside
    private Mailer mailer = new SmtpMailer(); // ⚠️ unreplaceable in tests
}
```

```text
Who decides the implementation?【The class itself】— control lives inside the class
Consequences: no test doubles (Ch. 52 measured), swapping databases means editing business code,
              no isolation under concurrency
```

### Inversion of control: hand the decision over

```java
class UserService {
    UserService(Repo repo, Mailer mailer) { ... }   // declares only【what it needs】
}
```

```text
Who decides now?【The caller/container】— control is【inverted】
→ "dependency injection" is one technique for achieving IoC: hand dependencies in as parameters
→ other techniques: template methods, event callbacks, service locators
  (§8 explains why the last is an anti-pattern)
```

### The one-sentence definition

```text
Dependency injection = don't go looking for your dependencies; let them be handed to you
It moves the decision "which implementation" from the【user】to the【assembler】
```

> **In one sentence**: DI's value isn't "using a framework" but that **dependencies become a public, compile-time-visible contract** — written in the constructor signature, mandatory in tests, obvious on reading. This chapter measures how that simple shift buys testability, replaceability, and **errors surfacing at startup**.

## 3. How It Works

### DI is not a DI container (dispelling the biggest misconception first)

**Manual injection (Poor Man's DI) is the purest form of dependency injection** (Java measured):

```java
Repo repo = new SqlRepo();
FakeMailer mailer = new FakeMailer();
UserService svc = new UserService(repo, mailer);
System.out.println(svc.notify(42));   // → 用户42, mail log: [用户42: 你好]
```

```text
→ no framework at all — this is DI
→ a container solves "manual assembly is tedious when the object graph is large," not DI itself
→ small projects and libraries【should not】pull in a container;
  C++ has essentially only this road (C++ §6)
```

### Key experiment one: hand-writing a DI container (Java, ~40 lines)

**The container does exactly three things**:

```java
<T> T get(Class<T> type) {
    Class<?> impl = bindings.getOrDefault(type, type);
    if (singletons.containsKey(impl)) return (T) singletons.get(impl);
    if (!building.add(impl)) throw new IllegalStateException("circular dependency: ...");  // ③ cycles
    Constructor<?> ctor = impl.getDeclaredConstructors()[0];                    // ① find the ctor
    Object[] args = new Object[ctor.getParameterCount()];
    for (int i = 0; i < args.length; i++)
        args[i] = get(ctor.getParameterTypes()[i]);                             // ② resolve recursively
    Object instance = ctor.newInstance(args);
    if (impl.isAnnotationPresent(Singleton.class)) singletons.put(impl, instance);
    return (T) instance;
}
```

**Measured**:

```text
container.get(UserService.class) — the container did three things:
  ① reflected to find the constructor UserService(Repo, Mailer)
  ② recursively resolved each parameter type (Repo→SqlRepo, Mailer→FakeMailer)
  ③ newInstance to assemble them
result: notify(7) → 用户7
```

**This is Spring/Guice's skeleton** — Chapter 30's reflection (asking a class for its constructors) merging with Chapter 51's object-graph construction.

### Key experiment two: lifetimes (Java + C# measured)

**Java measured singleton sharing**:

```text
SqlRepo is annotated @Singleton, shared by UserService and ReportService
SqlRepo instance count: 1 (three injections, one instance)
ReportService unannotated → new each time: r1 == r2 ? false
```

**C# measured the full three-lifetime semantics**:

```text
same scope, resolving IRepo twice: same instance? True
different scopes:                  same instance? False
  scope1 → 用户1 (from Request#2)
  scope2 → 用户1 (from Request#3)      ← each holds its own RequestContext
Singleton IClock across scopes: same instance? True
```

```text
Transient  new every time    —— stateless small objects
Scoped     one per request   —— connections, transactions, current user (web: scope = one HTTP request)
Singleton  one globally      —— configuration, connection pools, caches
```

### Key experiment three: the captive dependency (C# measured, DI's classic incident)

**A `Singleton` service depending on a `Scoped` repository**:

```text
request 1 resolving SingletonService → 用户1 (from Request#4)
request 2 resolving SingletonService → 用户1 (from Request#4)   ← still #4!
same SingletonService both times? True
```

```text
⚠️ the second request is【using the first request's RequestContext】— captured by the singleton
→ real consequences: connections/transactions/current user leaking across requests —
  a correctness and security failure at once
→ the rule: long lifetimes【must not】depend on short ones (Singleton ⊅ Scoped ⊅ Transient)
→ ASP.NET Core's ValidateScopes turns this combination into a startup error
→ when you truly need it: inject IServiceScopeFactory and open a scope on demand
```

### Key experiment four: cycles and the three injection styles

**Constructor injection makes cycles unconstructible** (Java measured):

```text
container.get(A.class) → ✗ circular dependency: A → B → A
→ A needs B and B needs A — under constructor injection it【cannot be built at all】,
  so the container fails immediately
```

**Versus field injection**:

```text
field injection (@Autowired on a field): create an empty object, then fill the fields
→ the cycle "starts successfully," but the object is momentarily a【half-built thing】—
  the problem is deferred to runtime
→ constructor injection's biggest advantage: it turns a【design problem】into a【startup failure】
```

**The three styles' failure modes** (C# measured):

| Style | Form | Failure mode (measured) | Trade-off |
|-------|------|------------------------|-----------|
| **Constructor** | `Svc(IRepo repo)` | forgot to pass → throws **at construction** ✓ | mandatory and immutable — **the recommended default** |
| **Property** | `svc.Repo = ...` | forgot to set → NullReference **at use** | optional and swappable, at the cost of half-built objects |
| **Method** | `Run(IRepo repo)` | the signature forces it | for dependencies serving a single method |

### The container's cost (C# measured)

```text
container resolving 200000 times: 71.5 ms (0.36 μs each)
manual new 200000 times:           1.5 ms (0.01 μs each)
→ 48× slower — reflective constructor lookup plus recursive resolution
→ but mind the denominator: microseconds each, against millisecond-scale HTTP requests — usually negligible
→ real containers【cache compiled construction delegates】(expression trees, Ch. 51), far faster than this
→ compile-time DI (Dagger/Micronaut/source generators) generates the assembly code outright: zero reflection
```

### DI versus the service locator: one direction apart

```text
DI:              UserService(Repo repo)                 —— dependencies are【pushed in】
Service locator: Repo repo = Locator.get(Repo.class);   —— dependencies are【pulled out】

Both avoid `new`-ing a concrete class, but:
  DI's dependencies live in the【constructor signature】— compile-time visible, mandatory in tests
  the locator's live in the【method body】— the signature tells you nothing, tests will miss them
→ why the latter is an anti-pattern: it【hides】dependencies, while DI【publishes】them
```

## 4. JavaScript

The JS example demonstrates **functional DI** — closures are the lightest container.

### Closure factories: assembly separated from use (measured)

```javascript
function makeGreeter({ clock, mailer }) {
  // dependencies are【captured by the closure】; the returned signature no longer shows them
  return function greet(user) {
    const stamp = clock();
    mailer.send(user, `你好 @${stamp}`);
    return stamp;
  };
}
```

```text
assembly: makeGreeter({...}) — done once (the equivalent of a container's Resolve)
use:      greet('甲') → 1000000, greet('乙') → 1000000
→ greet's signature is (user) — callers have【no idea】it depends on a clock and a mailer
→ this is constructor injection in functional form: the closure environment = an object's fields
→ Chapter 13 called a closure "a function plus its captured environment" —
  that environment is the【dependency container】
```

### Partial application: DI by another name (measured)

```javascript
const report = partial(sendReport, frozenClock(2_000_000), fakeMailer());
report('日报') → 日报@2000000
report('周报') → 周报@2000000
```

```text
"bind the dependencies, return a simpler function" — isomorphic to what a DI container does
→ in the functional world DI needs no special name; it is【partial application】
```

### The composition root: only one place knows the real dependencies

```javascript
function buildApp(env) {
  const deps = env === 'test'
    ? { clock: frozenClock(3_000_000), mailer: fakeMailer() }
    : { clock: realClock, mailer: realMailer };
  return { greet: makeGreeter(deps), deps };
}
```

```text
→ the composition root belongs at the【outermost layer】(main/entry); business code only receives
→ a signal that DI is done well: grep the project for `new Xxx()` — it should appear only there
```

### Why the JS ecosystem rarely uses DI containers

```text
① modules are already singleton containers: import { db } from "./db.js" — global assembly by default
② functions are first class: passing a function is lighter than passing an object
③ but the price: imported dependencies【cannot be swapped】— tests must use jest.mock on modules
→ the practice: write business logic as【dependency-receiving pure functions/factories】,
  importing real implementations only at the composition root
→ exceptions: Angular (a full DI container), NestJS (Spring's decorators and container ported over)
```

> **Note**: `jest.mock`/`vi.mock` share Python's `mock.patch` problem — tests coupled to "who imported what, where"; React's Context is UI-layer DI (passing dependencies across the tree without prop drilling); the most common DI failure in JS is `new`-ing a database connection at module top level — it makes the whole module unloadable in tests.

## 5. Python

The Python example offers the dynamic language's inverse view.

### A hard-wired dependency is still replaceable (two techniques measured)

**Technique one: assign the instance attribute**:

```text
after reassigning attributes, greet('甲') → 1000000, mail: [('甲', '你好 @1000000')]
→ impossible in static languages (private final fields), which is why they【must】design DI first
→ this is the technical root of "Python doesn't really need a DI container": everything is a writable attribute
```

**Technique two: `mock.patch` rebinding names in the module namespace**:

```python
with mock.patch(__name__ + ".SystemClock", lambda: FrozenClock(2_000_000)), \
     mock.patch(__name__ + ".Mailer", FakeMailer):
    svc2 = HardCodedService()      # what it news internally is now the double
```

```text
during the patch, internally created objects are doubles: greet → 2000000, mailer type: FakeMailer
after the with block, everything is restored ✓
→ it directly rebinds names in the【module namespace】(Ch. 13's scope)
⚠️ but this is not "better DI"; it is【a test coupled to implementation details】:
   the patch path hard-codes "who created what, where" — one refactor turns tests red
```

### Constructor injection remains the first choice in Python (measured)

```text
InjectedService(FrozenClock, FakeMailer).greet('丙') → 3000000
→ no patching, no knowledge of internals — the test depends only on the constructor signature
→ monkey patching can save you, but it shouldn't replace design
```

### Default-parameter injection: Python's lightweight option (measured)

```python
def greet_with_defaults(user, clock=None, mailer=None):
    clock = clock or SystemClock()      # ← the fallback must live in the body
    mailer = mailer or Mailer()
```

```text
production: greet_with_defaults('丁')                          uses real dependencies
tests:      greet_with_defaults('丁', FrozenClock(4e6), fake)  → 4000000
→ each function is its own injection point — no classes, no container
⚠️ trap: never write def f(mailer=Mailer()) — defaults are evaluated【once at definition】and shared
```

### Protocol: static checking plus duck typing

```text
Neither SystemClock nor FrozenClock implements any interface, yet both satisfy the Clock protocol
→ Protocol is【structural typing】: mypy checks it statically, runtime doesn't enforce it
  (Chapter 28's third road to interfaces)
→ so Python gets "DI with type hints" without the ceremony of interface inheritance
```

> **Note**: containers still have their place — deep object graphs, unified lifetime management, a web framework's request scope (FastAPI's `Depends()` is a lightweight DI container); `functools.partial` is the Python equivalent of the JS partial application; **DI is a design principle; a container is a tool you need only at scale**.

## 6. Java

The Java example is the key experiments' main stage (data in §3); here are two high-frequency Spring puzzles.

### Why `@Transactional` fails on self-invocation (proxy mechanism measured)

```text
what the container injects is often not the original object but a【proxy】:
  calling raw.find(1)     → 用户1
  calling proxied.find(1) → 【proxy intercepted】用户1
```

```text
transactions, logging, and caching are inserted by the proxy around the method
but this.method() inside the class goes to the original object, bypassing the proxy
→ Chapter 48's "@Transactional doesn't work on self-invocation" is not a bug but the proxy's nature
→ fixes: split into two beans injecting each other, or inject the proxy of yourself (AopContext)
```

### Constructor versus field injection (Spring officially recommends the former)

```java
// ✅ constructor: mandatory, final-able, cycles fail at startup (measured)
public UserService(Repo repo, Mailer mailer) { ... }

// ⚠️ field: not final, cycles start "fine", tests need reflection or a container
@Autowired private Repo repo;
```

```text
Spring 4.3+ lets a single constructor omit @Autowired — the default nudges you toward constructor injection
```

> **Note**: `@Component`/`@Service`/`@Repository` are semantic aliases of `@Component` with identical scanning; `@Lazy` can break a cycle but merely hides it; Guice and Dagger are the two alternatives — Dagger uses an **annotation processor to generate assembly code at compile time** (zero reflection, fast startup, the Android mainstream).

## 7. C++

The C++ example priced both roads.

### Runtime polymorphism versus compile-time injection (measured)

```cpp
// road one: virtual functions (Java/C# style)
class RuntimeService { std::shared_ptr<IClock> clock_; };

// road two: template parameters (the dependency is a【type】)
template <typename ClockT>
class CompileTimeService { ClockT clock_; };   // by value — no pointer, no vtable
```

```text
runtime polymorphism, 20000000 calls: 31.9 ms (1.60 ns each)
compile-time injection:                9.6 ms (0.48 ns each)
→ 3.3× faster — the entire gap is inlining
→ zero-overhead philosophy (Chs. 29/38) showing up in DI
```

### But compile-time injection costs three things

```text
① type explosion: Service<A,B> and Service<A,C> are【two unrelated types】
② no runtime switching: choosing an implementation from a config file? impossible
③ slower compiles and unreadable errors (Ch. 54 measured 8286× header expansion)
→ real projects mix: templates for stable hot dependencies, virtuals for configurable ones
```

### Why C++ has almost no DI containers

```text
Exactly Chapter 51's ORM reason:【no runtime reflection】
→ a Java container can call getDeclaredConstructors() (measured)
→ a C++ class doesn't know its own constructors or their parameter types — a container has nothing to work with
→ so C++'s answer is a【manual composition root】: build the object graph layer by layer in main()
   which is precisely Java's Poor Man's DI — for C++ it isn't the "poor" version, it's the only version
```

> **Note**: Boost.DI simulates autowiring with template metaprogramming, paying in compile-time magic and error-message hell; `std::function` is a lightweight way to "inject a behavior" without interface inheritance; C++20 concepts let template parameters declare contracts — a compile-time Protocol (Chapter 28).

## 8. C#

The C# example owns the lifetime measurements (data in key experiments two and three); here are the practical criteria.

### What to inject and what not to

```text
Inject:     things with【external side effects】or【multiple implementations】
            —— databases, HTTP clients, clocks, random sources, file systems, current user
            (Ch. 52 measured: time and randomness are flakiness's two big sources; injection tames both)
Don't:      pure data structures, value objects, pure utility functions — nothing to replace
→ the criterion: "do I need to swap this in tests?" — if not, don't add a layer of indirection
→ the smell of over-DI: every class has an interface, each interface has one implementation,
  named IFooService/FooService
```

### ASP.NET Core's lifetime conventions

```text
AddSingleton  —— configuration, connection pools, in-memory caches
AddScoped     —— DbContext, current user, per-request transactions (scope = one HTTP request)
AddTransient  —— stateless small services
→ ValidateScopes (on by default in development) catches "Singleton depends on Scoped" at startup
  (the incident measured in §3)
```

> **Note**: `IServiceScopeFactory` is the only correct way to use scoped services inside a singleton; `IOptions<T>` is the standard configuration-injection shape (with hot reload); source-generated DI (Jab, StrongInject) generates assembly code, combining a container's convenience with manual performance.

## 9. SQL

Databases face the same "replaceable implementation" question, and the answer is likewise **depend on contracts, not implementations**.

### A view is the database layer's interface (measured)

```text
The application queries the users view rather than the users_v1 table:
  querying users: 张三@北京, 李四@上海
after renaming the underlying column from full_name to name_text, the same query:
  张三@北京, 李四@上海
```

```text
→ isomorphic to Chapter 28's "depend on interfaces, not implementations": the view is that interface
→ the dependency-inversion principle in database form: the application doesn't depend on the table,
  the table doesn't depend on the application — both depend on the【view contract】
```

### CTE-parameterized data sources: SQL's dependency injection (measured)

```sql
WITH source_orders(id, user_id, amount) AS (
  VALUES (101, 1, 99), (102, 1, 1)          -- ← the injected "test double"
)
SELECT u.name, COUNT(s.id), SUM(s.amount)
FROM users u LEFT JOIN source_orders s ON s.user_id = u.id GROUP BY u.id;
```

```text
real source:   张三: 2 orders, 8000 total   李四: 1 order, 100 total
double source: 张三: 2 orders, 100 total    李四: 0 orders, 0 total
→ the same aggregation logic fed a different data source — logic decoupled from source
→ dbt's ref()/source() macros turned this into engineering practice (mentioned in Ch. 54)
```

### More replaceable points

```text
PRAGMA/SET parameters → runtime configuration injection (Ch. 46 synchronous, Ch. 48 isolation levels)
user-defined functions → the application【registers】a function into the database
                         (sqlite3's create_function)
foreign tables/FDW    → a "table" that is really another database or an API
→ the common thread: fix the【contract】, keep the【implementation】swappable
```

> **Note**: abstraction has costs too — deeply nested views hinder predicate pushdown (Chapter 47); over-abstracted repositories throw away SQL's JOIN and window-function power (Chapter 47); the criterion matches the application layer exactly: **an interface with one implementation is over-design at any layer**.

## 10. Cross-Language Comparison

### ① DI mechanisms

| Dimension | Java | C# | Python | JavaScript | C++ |
|-----------|------|-----|--------|-----------|-----|
| Mainstream container | Spring/Guice/Dagger | built-in `IServiceCollection` | usually none (FastAPI `Depends`) | usually none (Angular/NestJS excepted) | **almost none** |
| Assembly mechanism | **runtime reflection** | reflection + expression trees | everything is writable | closures/factories | **templates or manual** |
| Dominant style | constructor (official rec.) | constructor | constructor/default params | closure capture/partial application | constructor (manual) |
| Lifetimes | singleton/prototype/request | Singleton/Scoped/Transient | self-managed | self-managed | self-managed |
| Signature technique | AOP proxies (measured) | ValidateScopes | **monkey patching** (measured) | **partial application** (measured) | **compile-time injection** (measured 3.3×) |
| Without a container | manual assembly | manual assembly | default parameters | composition root | **composition root (the only road)** |

### ② Key experiment data summary

```text
hand-written container: reflect for ctor → resolve recursively → newInstance; 40 lines = Spring's skeleton
singleton sharing:      @Singleton SqlRepo injected in 3 places, 1 instance
lifetimes:              same scope IRepo identical True; across scopes False; Singleton across scopes True
captive dependency:     Singleton on Scoped → request 2 still uses Request#4 (cross-request leak)
cycle detection:        constructor injection → "circular dependency: A → B → A"
three styles:           constructor forgotten → throws at construction; property forgotten → NullReference at use
container cost:         0.36 μs per resolve vs 0.01 μs manual new (48× slower)
C++ two roads:          virtual 1.60 ns vs template 0.48 ns (3.3× faster)
Python patching:        attribute reassignment ✓; mock.patch rebinding ✓ (but couples to internals)
SQL views:              underlying column renamed, caller's query results unchanged
```

### ③ Common ground and root causes

**Common ground**: every language's DI core is identical — **don't go looking, let them be handed in**; every ecosystem recommends constructor injection (mandatory, immutable, cycles fail at startup); every language has the "composition root" concept (the one place that knows real implementations).

**Root causes**:

- **Whether a container exists is decided by reflection**: Java/C# have runtime reflection → powerful containers; C++ doesn't → manual assembly only (exactly Chapter 51's ORM isomorphism);
- **Dynamic languages need lighter DI**: Python's everything-is-writable and JS's first-class functions mean they don't need "design for replaceability first";
- **Lifetimes are the container's unique complexity**: manual assembly puts object lifecycles in your hands; delegating them requires explicit declarations — **the captive dependency is that complexity's bill**;
- **Proxies are AOP's implementation basis**, and the unified explanation for Spring's various "didn't take effect" puzzles (self-invocation bypasses the proxy);
- **The boundary of what to inject is "does it need replacing"**: the same criterion as Chapter 52's "what to mock," appearing twice.

## 11. Implementation Comparison

| Container | Assembly time | Mechanism | Traits |
|-----------|--------------|-----------|--------|
| **Spring** | runtime | reflection + CGLIB/JDK dynamic proxies | most complete; proxies bring the self-invocation trap (measured) |
| **Guice** | runtime | reflection + explicit Module bindings | no XML, no scanning; binding code is documentation |
| **Dagger** | **compile time** | annotation processor generating assembly code | zero reflection, fast startup, compile-time errors (Android mainstream) |
| **ASP.NET Core** | runtime | reflection + cached expression trees | built in; ValidateScopes catches captive dependencies |
| **FastAPI `Depends`** | runtime | function-signature introspection | dependencies are functions; nesting and caching come free |

**Dagger's compile-time road deserves a note**:

```text
It【generates】code identical to what you'd assemble by hand, at compile time
→ zero reflection at runtime (C# measured reflection 48× slower; here it's eliminated)
→ missing or circular dependencies error at【compile time】, earlier than startup
→ the price: slower builds (Ch. 54's annotation processors) and generated code to read when debugging
→ the same idea as Chapter 51's "C++ works around missing reflection with code generation"
```

## 12. Performance Analysis

### This chapter's numbers at a glance

```text
container resolve: 0.36 μs each vs manual new 0.01 μs (48× slower)
C++ two roads:     virtual 1.60 ns vs template 0.48 ns (3.3× faster)
singleton:         three injections, one instance (the payoff of correct lifetimes)
```

### When the container's overhead matters

```text
Doesn't matter: resolving dozens of objects per (millisecond-scale) web request —
                0.36 μs × 50 = 18 μs, negligible
Matters:        ① resolving inside a loop (resolve once outside it)
                ② startup-sensitive contexts (serverless cold starts, Android launch) → compile-time DI
                ③ virtual calls on a hot path (C++ measured 3.3×) → templates
```

> ⚠️ **DI's real cost is not performance but indirection.** Every added interface costs one more "jump to find the implementation" in a reader's head; an interface with a single implementation buys no replaceability while charging comprehension. Chapter 52's "what to mock" becomes "what to abstract" here, with an identical criterion: **do I need to swap it in tests?**

## 13. Engineering Practice

| Scenario | ✅ Recommended | ❌ Avoid | Why |
|----------|--------------|---------|-----|
| Default injection style | constructor | field | measured: cycles fail at startup; dependencies can be final |
| Small projects/libraries | manual assembly (Poor Man's DI) | pulling in a container | DI ≠ container; a library's container is forced on users |
| Lifetimes | never let long hold short | Singleton depending on Scoped | measured cross-request state leakage |
| Scoped inside a singleton | `IServiceScopeFactory` on demand | direct injection | same as above |
| What to inject | the external world (DB/HTTP/clock/random) | pure data structures, value objects | criterion: does it need swapping in tests |
| Number of interfaces | only when multiple implementations exist | one interface per class | one implementation = pure indirection |
| Where to assemble | a single composition root (main/entry) | `new` in business code | grep `new` — it should only appear there |
| Spring cross-cutting failures | split beans or inject your own proxy | wondering "why didn't it work" | measured: proxy bypass is inherent to self-invocation |
| Python testing | constructor injection | heavy `mock.patch` | patches couple to "who created what, where" |
| C++ hot paths | template compile-time injection | virtual functions | measured 3.3× |
| Startup-sensitive apps | compile-time DI (Dagger/source generators) | runtime reflection containers | zero reflection + compile-time errors |

### The rule of thumb

```text
When writing a class, ask three things:
  ① what does it `new` itself?       → that is the part that cannot be replaced
  ② do tests need to swap those?     → yes → promote them to constructor parameters
  ③ do I need a container?           → small graphs assemble by hand; add one when it grows
```

---

## 14. Best Practices

- **Default to constructor injection**: measured, it makes cycles fail at startup, lets dependencies be `final`, and forces tests to pass them explicitly.
- **Distinguish DI from a DI container**: measured, manual assembly is pure DI; small projects and libraries shouldn't pull one in.
- **Never let a long lifetime depend on a short one**: measured, the captive dependency leaves request two using request one's context — a security incident, not just a bug.
- **Create interfaces only for things that need replacing**: the same criterion as Chapter 52's "what to mock"; a single-implementation interface is pure indirection.
- **Confine `new` to the composition root**: grep for `new Xxx()`/`make_shared` — it should appear only near the entry point.
- **Prefer constructors or factories over monkey patching in Python/JS**: measured, patching works but couples tests to "who created what, where."
- **Use template injection on C++ hot paths**: measured 3.3× faster than virtuals; keep virtuals for configurable parts.
- **Use compile-time DI when startup matters**: Dagger/source generators emit the assembly code — zero reflection, errors at compile time.

## 15. Common Pitfalls

**Pitfall 1 · Singleton depending on Scoped (the captive dependency)**

```csharp
services.AddSingleton<MyService>();   // ⚠️ it depends on a Scoped DbContext
// measured: request 2 still uses request 1's RequestContext
// ✅ inject IServiceScopeFactory and open a scope on demand
```

**Pitfall 2 · Field injection masking cycles**

```java
@Autowired private B b;    // ⚠️ the cycle "starts fine"; the object is momentarily half-built
// ✅ constructor injection — measured, the container reports "circular dependency: A → B → A"
```

**Pitfall 3 · Spring self-invocation defeating cross-cutting concerns**

```java
public void outer() { this.inner(); }        // ⚠️ bypasses the proxy; @Transactional has no effect
@Transactional public void inner() { ... }
// ✅ split into two beans, or inject your own proxy
```

**Pitfall 4 · An interface for every class**

```text
⚠️ IUserService/UserService, IOrderService/OrderService … each interface with one implementation
✅ create interfaces only when there are multiple implementations or tests need to swap
```

**Pitfall 5 · Resolving inside a loop**

```csharp
for (int i = 0; i < 100000; i++) container.Resolve<IRepo>();   // ⚠️ measured 0.36 μs × 100k
// ✅ resolve once outside the loop
```

**Pitfall 6 · Python's mutable default parameters**

```python
def f(mailer=Mailer()):    # ⚠️ evaluated once【at definition】and shared globally
def f(mailer=None):        # ✅ fall back inside the body
```

**Pitfall 7 · A library pulling in a DI container**

```text
⚠️ your library depends on a container → users are forced into your choice
   (a common source of Chapter 53's dependency conflicts)
✅ expose constructors/factory functions and let users decide how to assemble
```

## 18. Chapter Summary

**One sentence**: dependency injection's core is a single sentence — **don't go looking for your dependencies; let them be handed to you** — moving the "which implementation" decision from the user to the assembler (**inversion of control**), and that simple shift simultaneously buys testability (Chapter 52's doubles can finally be inserted), replaceability, and **errors surfacing at startup**; the hand-written container reveals it does exactly three things — **reflect for the constructor → resolve parameters recursively → assemble the instance** (40 lines is Spring's skeleton, merging Chapter 30's reflection with Chapter 51's object-graph construction) — plus two duties: **lifetimes** (measured: a `@Singleton` injected three times creates one instance) and **cycle detection** (measured reporting `A → B → A` precisely, which is exactly **why constructor injection beats field injection** — it turns a design problem into a startup failure rather than a runtime half-built object); the C# example measured DI's classic production incident, the **captive dependency** (a `Singleton` holding a `Scoped` repository leaves request two using request one's `RequestContext`, leaking connections, transactions, and user identity across requests), and priced the container (0.36 μs per resolve versus 0.01 μs manual, 48× slower yet negligible against millisecond requests); the Python example gave the inverse view — a hard-wired dependency remains replaceable in a dynamic language (both attribute reassignment and `mock.patch` measured working), explaining why "Python doesn't need a container" while exposing the price: **patches couple tests to "who created what, where"**; the JS example showed functional DI (closures as containers, partial application as injection); the C++ example measured compile-time injection at **3.3×** the speed of virtual calls and identified its container-less state as Chapter 51's ORM reason — **no runtime reflection**; finally, DI and the **service locator** differ by exactly one direction: the former writes dependencies into the constructor signature (public, compile-time visible, mandatory in tests), the latter hides them in method bodies — **that is the entire basis for calling it an anti-pattern**.

**Key takeaways**

- **The core in one sentence**: don't look for dependencies, let them be handed in; DI ≠ a DI container.
- **A container does three things** (measured): reflect for the constructor, resolve recursively, assemble — plus lifetimes and cycle detection.
- **Constructor beats field injection** (measured): cycles fail at startup rather than producing half-built objects at runtime.
- **The hard lifetime rule** (measured): long lifetimes must not depend on short ones — otherwise you have a captive dependency.
- **Captive dependencies are security incidents** (measured reusing `Request#4`): connections, transactions, and identities leak.
- **The container's cost is negligible; indirection is not** (measured 48× slower at 0.36 μs): the real cost is comprehension.
- **Dynamic languages need lighter DI** (monkey patching measured working), but patches couple tests to internals.
- **DI vs service locator**: push versus pull, public versus hidden — the sole criterion behind the "anti-pattern" label.

**Checklist**

- [ ] I can distinguish inversion of control, dependency injection, and DI containers.
- [ ] I can hand-write a minimal container with autowiring and cycle detection.
- [ ] I know the three injection styles' failure modes and default to constructor injection.
- [ ] I can recognize a captive dependency and state the lifetime rule.
- [ ] I use "do I need to swap it in tests?" to decide what to abstract and inject.

**Next chapter**: DI answers "where do dependencies come from," but how dependencies are organized, how objects get created, and how behavior gets extended are recurring problems with proven solutions. Chapter 56 covers **design patterns**: we will measure the **equivalence of the strategy pattern and function pointers** (in languages with first-class functions, half the classic patterns collapse into a function), the observer pattern's relationship to the event loop (Chapter 43), the singleton's correct multithreaded implementation (why Chapter 41's double-checked locking was once wrong), and most importantly — **why a "pattern's" necessity varies wildly across languages**: what takes thirty lines of strategy pattern in C++ is passing a function in Python.
