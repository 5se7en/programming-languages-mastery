# 第 52 章 · 测试

**简体中文** ｜ [English](./52-testing.en-US.md)

---

> 前面五十一章写了几百个「实测示例」，每一个都在验证一个论断——其实那就是测试。本章把这件事正式化，回答一个此前所有章节都默认成立却从未论证的问题：**你怎么知道代码是对的？**
>
> 本章的**钥匙实验**先把测试金字塔从教条还原成**成本结构**：同样验证一段逻辑，单元测试（纯函数）**0.7 μs**，集成测试（真实数据库）**665 μs——慢 1022 倍**，端到端测试（启动进程）**10157 μs——慢 15608 倍**。一套 1000 个测试的套件，全单元 1 毫秒、全端到端 10 秒。金字塔的形状不是审美，是**每往上一层贵一到两个数量级**的直接推论。
>
> 然后是 mock 的两面。实测同一个用例「0 元订单结账」：mock 版**通过**（57 μs，绿灯），真实网关**拒绝**——因为真实网关有一条 mock 不知道的规则「金额必须为正」。**mock 测的是你以为依赖会怎样，集成测试测的是依赖实际怎样**。C# 版用另一个介质复现了同一教训：fake 仓储让带斜杠的订单号「2026/08/001」通过，真实文件系统直接失败——斜杠是路径分隔符。
>
> 覆盖率的误用也被实测钉死：一个 VIP 折扣函数埋着 bug（该打七折写成八折），测试调用了两个分支——**行覆盖率 100%**，测试全绿，bug 安然无恙。因为 VIP 分支的断言写成了 `assert result > 0` 这样的弱断言。**覆盖率度量的是「代码被执行过」，不是「行为被验证过」**。
>
> 两个手写实验揭示了框架的本质：Java 用反射手写微型 JUnit（自动发现、隔离运行、失败报告各约 10 行），并实测**共享实例时 t2 挂、每测试新实例时全过**——JUnit 每方法新实例是用隔离买确定性；C++ 没有反射，测试靠**静态注册器**发现（`TEST` 宏展开成全局对象，构造函数在 `main` 之前自动注册）——与第 51 章 ORM 同一个结论。
>
> 最精彩的是 C++ 的**属性测试**三层递进：手挑用例全过 → 10 万组随机输入抓出 `(a+b)/2` 溢出（**12433 个反例**）→ 教科书修法 `a+(b-a)/2` **也被抓住**（异号大数时 `b-a` 照样溢出，12600 个反例）→ `std::midpoint` 10 万组全过。「求两数中点」难到 2019 年才进标准库——**属性测试连修复的 bug 都能抓到**。JS 版则实测了最危险的一类测试 bug：**异步假通过**——忘了 await 的断言在测试判定之后才执行，失败被吞掉，测试永远是绿的。

## 1. 学习目标

学完本章，你将能够：

- 用**成本结构**解释测试金字塔（实测三层 1x / 1022x / 15608x），而不是把它当教条背诵；
- 说清 **mock 的边界**：它隔离的应该是「慢/贵/不稳定」，而不是替你定义依赖的真实行为（两个实测反例）；
- 解释**覆盖率为什么会说谎**（实测 100% 覆盖 + 全绿 + bug 仍在），并用强断言修复它;
- 手写测试框架的三件核心工作（自动发现、隔离运行、失败报告），并说出 Java 与 C++ 发现机制的差异；
- 用**属性测试**验证不变量（实测三层递进抓 bug），并识别**异步假通过**（实测失败被吞）。

## 2. 为什么会出现这个概念

### 一个从未被论证的默认

```text
前 51 章的每个「实测」都在做同一件事: 运行代码 → 检查输出 → 与预期比对
本书的 run-all.sh 本身就是一个测试运行器: 6 通过 0 失败
→ 测试不是新概念，是把「验证」这件事【自动化、可重复、有报告】
```

### 不测试的真实代价

```text
没有测试的代码库里，「改一行」的成本是:
  手工把相关功能全点一遍（每次几分钟到几小时）
  或者——不点，上线赌运气（第 46-51 章实测过各种「赌输了」的形状）
→ 测试的本质是【把验证的成本从每次变更付，变成一次性预付】
→ 预付的回报: 重构、升级依赖、改架构时，有一张安全网告诉你什么被改坏了
```

### 一句话定义

```text
测试 = 可执行的规格说明
     它有两个读者: 机器（每次运行判对错）+ 下一个改代码的人（读它了解行为）
```

> **一句话总结**：测试回答「你怎么知道代码是对的」，而本章实测证明这个问题有三个陷阱——**快的测不出真的**（mock/fake 的保真度边界）、**跑过不等于验证过**（覆盖率与弱断言）、**绿灯可能是假的**（异步假通过）。写测试容易，写**诚实的**测试需要本章的全部内容。

## 3. 底层原理

### 钥匙实验一：金字塔是成本结构，不是教条

**Python 实测三层测试的单次成本**（同样验证「金额解析」这段逻辑）：

| 层 | 验证方式 | 实测单次耗时 | 相对成本 |
|----|---------|------------|---------|
| **单元** | 纯函数进出 | **0.7 μs** | 1x |
| **集成** | 真实 sqlite：建库→写入→查询→删库 | **665 μs** | **1022x** |
| **端到端** | 启动完整进程 | **10157 μs** | **15608x** |

```text
一套 1000 个测试的套件:
  全单元:   1 ms   —— 每次保存都能跑
  全端到端: 10 秒  —— 每次提交勉强能跑；套件涨到一万个就是 100 秒
→ 金字塔的形状（大量单元、适量集成、少量端到端）不是审美偏好
→ 它是「反馈速度」的直接推论: 测试越慢，跑得越少；跑得越少，bug 活得越久
```

**三层各自的职责**（不可互相替代）：

```text
单元:   验证【一段逻辑】——快到可以每次保存都跑
集成:   验证【与真实依赖的契约】——mock 掩盖的缺陷在这层现形（钥匙实验二）
端到端: 验证【整个系统串起来】——最贵，只留关键路径
```

### 钥匙实验二：mock 的两面

**实验设计**：真实支付网关有一条业务规则——「金额必须为正」；业务代码 `checkout()` 有个 bug——没校验 0 元订单。

**mock 版测试**（实测）：

```python
gw = Mock()
gw.charge.return_value = "ok"
assert checkout(gw, "0.00") == "ok"     # 0 元订单——mock 欣然接受
```

```text
mock 版测试「0 元订单结账」: 通过 ✓（57 μs）
真实网关同一个用例        : 失败 ✗ —— 网关拒绝: 金额必须为正
```

**mock 版的绿灯掩盖了业务代码的真实缺陷**：

```text
mock 测的是【你以为依赖会怎样】，集成测试测的是【依赖实际怎样】
→ mock 的正确用途: 隔离【慢/贵/不稳定】的依赖（JS 版的 mock 计时器是完美示范）
→ mock 的错误用途: 替你【定义】依赖的行为——你定义的和真实的迟早分道扬镳
```

**C# 版用 fake 复现了同一教训的另一张面孔**（实测）：

```text
fake 仓储（Dictionary）: 订单号「2026/08/001」照常工作 ✓
真实文件系统           : 同一个用例失败 ✗ —— 斜杠是路径分隔符！
→ fake 复刻了【接口语义】，复刻不了【底层介质的规则】
→ 处方: fake 支撑日常快速反馈，再留【少量集成测试】跑真实介质
```

**替身的速度红利也实测了**（这是它存在的理由）：

```text
2000 个测试用 fake:    0.5 ms
2000 个测试用真实文件: 160.1 ms（慢 333x）
→ 快与真不可兼得——所以金字塔要分层，两种测试都要有
```

### 钥匙实验三：100% 覆盖率下的 bug

**实验设计**：`discount()` 函数埋着 bug（VIP 该打七折写成八折），测试**调用了两个分支**但 VIP 分支的断言是弱断言。

```python
def weak_tests():
    assert discount(100, False) == 95.0   # 非 VIP: 断言正确
    result = discount(100, True)          # VIP: 调用了，但——
    assert result > 0                     # ← 弱断言: 是正数就过
```

**实测结果**（用 `trace` 模块统计覆盖率）：

```text
行覆盖率 100%: True
测试结果: 全部通过 ✓
但 bug 还在: discount(100, True) = 80.0（应该是 70.0）
```

```text
覆盖率度量的是【代码被执行过】，不是【行为被验证过】
→ 弱断言让覆盖率变成假安全感
→ 把覆盖率当目标，团队就会生产「跑过但不验证」的测试——古德哈特定律:
  当一个度量变成目标，它就不再是好度量
```

**强断言立刻抓住它**（实测，unittest 跑出）：

```text
✗ test_vip_discount_correct: AssertionError: 80.0 != 70.0
```

### 测试框架的三件核心工作（手写实测）

**Java 版各用约 10 行实现了 JUnit 的骨架**：

```text
① 自动发现: 反射扫描 @Test 注解（第 30/51 章的同一招）
② 隔离运行: 每个测试方法 new 一个新实例
③ 失败报告: 捕获 AssertionError，汇总通过/失败——失败不中断其他测试
```

**隔离的必要性被实测钉死**：

```text
共享一个实例跑（t1 先跑）: ✓ t1_往购物车加一件  ✗ t2_购物车应当是空的 —— 期望 0，实际 1
每个测试一个新实例:        ✓ ✓  2/2 通过
→ 共享实例时 t2 的成败取决于【t1 是否先跑】——测试顺序耦合
→ JUnit 默认每方法新实例，是用【隔离】买【确定性】
```

**一个实现细节本身就是教训**：`getDeclaredMethods()` 返回顺序不确定——第一版演示恰好 t2 先跑而失效，按名字排序后才可复现。**测试基础设施自己也要可复现。**

### 钥匙实验四：属性测试的三层递进（C++）

```text
第一层: 手挑用例——average(4,6)=5、average(-3,3)=0、二分查找找两端……全部通过 ✓
第二层: 属性测试——「average(a,b) 必须落在 [min,max] 区间内」
        100000 组随机输入 → 12433 个反例！
        第一个反例: average(-1144634710, -1024273349) = 1063029618（均值跑到区间外）
        根因: a+b 溢出 int
第三层: 教科书修法 a+(b-a)/2 —— 仍有 12600 个反例！
        反例: average(-2145984020, 505633457)——异号大数时 b-a 照样溢出
终点:   std::midpoint —— 100000 组全部满足 ✓
        「求两数中点」难到 2019 年才进 C++20 标准库（P0811）
```

```text
手挑用例测的是【你想到的输入】，属性测试测的是【你没想到的】
→ 同一个溢出让二分查找在超大数组上出错——它在 JDK 里潜伏了九年（JDK-5045582）
→ 属性测试连【修复的 bug】都能抓到——这是它相对手挑用例的本质优势
```

### 钥匙实验五：异步假通过（JS）

```javascript
test('坏写法: 忘了 await', () => {
  fetchBalance(1).then((balance) => {
    assert.strictEqual(balance, 100);   // 会失败——但测试已经「通过」了
  });
  // 测试函数同步返回 → 框架判定: 通过 ✓
});
```

**实测**：

```text
测试 1「坏写法」: 框架报告【通过】——但断言根本还没执行
泄漏的断言最终执行了吗: leaked=1，它其实失败了: 「Expected values to be strictly equal:」
→ 这个失败【没有出现在任何测试报告里】——绿灯下埋着一个真实的 bug
```

```text
机制: 测试函数同步返回，Promise 里的断言晚于判定（第 43 章的事件循环在这里变现）
→ 这类测试最危险: 它们【永远是绿的】，删掉都没人发现
→ node:test 会诊断「测试结束后产生了异步活动」——框架在努力抓，但不能根治
→ 解法: async 测试必须 await 每一个异步断言
```

## 4. JavaScript

JS 版承包了测试世界最危险的陷阱与最优雅的工具。

### 异步假通过（实测，见钥匙实验五）

**为什么 JS 特别容易踩**：回调、Promise、async 三代异步模型并存（第 42 章），任何一个「忘了等」都制造假通过。**判断标准只有一条：断言执行时，测试还在被框架监视吗？**

### mock 计时器：时间变成可控输入（实测）

```javascript
mock.timers.enable({ apis: ['setTimeout'] });
const save = debounce((v) => calls.push(v), 1000);
save('a'); save('b'); save('c');            // 连按三次
mock.timers.tick(1000);                     // ← 虚拟时钟拨快 1 秒
assert.deepStrictEqual(calls, ['c']);       // 只有最后一次生效
```

```text
「等待 1000ms」的防抖测试实际耗时: 0.06 ms（真实时间几乎为零）
→ mock.timers 劫持了 setTimeout: 时间成了【可控输入】而不是等待
→ 这是 mock 的【正确】用途: 隔离「慢」，而不是隔离「真」
```

### flaky 测试的两大来源：时间与随机（实测）

```javascript
const pickWinner = (users, rand) => users[Math.floor(rand() * users.length)];
pickWinner(['甲', '乙', '丙'], () => 0.99)   // → '丙'（随机源被注入成常量）
```

```text
坏: Math.random() / new Date() 直接写在业务代码里 —— 没法测
好: 把随机源和时钟作为【参数注入】—— 不确定性变成确定的输入
```

> **注意**：node 18+ 内置 `node:test` + `node:assert`，零依赖可写测试；Vitest/Jest 提供 watch、快照、并行，骨架相同；**快照测试**要警惕「一键更新快照」——它让弱断言问题更隐蔽（覆盖率教训的快照版）。

## 5. Python

Python 版是三大钥匙实验（金字塔成本、mock 两面、覆盖率说谎）的主战场，数据见第 3 节。这里补充它独有的工程细节。

### 实验设计的可复现性

```text
金字塔实测的关键: 单元跑 2000 次取平均、集成跑 20 次、端到端跑 5 次
→ 越贵的测试样本越少——测量本身也遵循成本结构
覆盖率实测的关键: 用标准库 trace 模块数出真实执行的行,
→ 行号动态计算（discount.__code__.co_firstlineno）——第一版硬编码行号翻了车
```

### unittest 的最小可用形态（实测跑出真实失败报告）

```python
class TestParseAmount(unittest.TestCase):
    def test_vip_discount_correct(self):
        self.assertEqual(discount(100, True), 70.0)   # 强断言，抓住 bug
```

```text
跑了 3 个测试: 1 个失败
  ✗ test_vip_discount_correct: AssertionError: 80.0 != 70.0
→ 强断言立刻暴露了覆盖率 100% 也没抓到的 bug
```

### AAA 结构

```text
Arrange（准备）→ Act（执行）→ Assert（断言）
def test_vip_gets_30_percent_off():        # 名字说清「期望的行为」
    price = 100                            # Arrange
    result = discount(price, is_vip=True)  # Act
    assert result == 70.0                  # Assert
→ 一个测试一个行为: 挂了就知道【哪条规则】坏了，不用调试测试本身
```

> **注意**：pytest 是社区事实标准（裸 `assert` + fixture + 参数化），unittest 是标准库零依赖选项；`unittest.mock.Mock` 接受任意调用——`spec=RealGateway` 能让它拒绝不存在的方法，缓解「mock 与真实漂移」；覆盖率工具用 `coverage.py`，但记住本章实测：**它验证不了断言的强度**。

## 6. Java

Java 版手写微型 JUnit——把「框架」还原成三段各 10 行的代码。

### 三件核心工作（实测可用）

```java
// ① 自动发现
for (Method m : methods)
    if (!m.isAnnotationPresent(Test.class)) continue;
// ② 隔离运行
Object instance = freshInstance ? testClass.getDeclaredConstructor().newInstance() : shared;
// ③ 失败报告
catch (InvocationTargetException e) {
    results.add(new TestResult(m.getName(), false, e.getCause().getMessage()));
}
```

```text
跑 CartTest: ✓ 空购物车总价为零  ✓ 加两件商品  ✗ 故意失败的测试 —— 期望 60，实际 50
            2/3 通过
→ 失败没有中断其他测试——每个测试独立成败
```

### 隔离实验（实测，见钥匙实验）

```text
共享实例: 1/2 通过（t2 挂——它看到了 t1 留下的购物车）
新实例:   2/2 通过
```

**但隔离不是万能的**：

```text
不免费: 每个测试 new 实例 + 跑 @Before —— 昂贵的准备用 @BeforeAll 共享
不万能: static 字段、单例、文件、数据库——【实例外】的状态隔离不掉
→ 测试污染的排查套路: 单独跑挂掉的测试——单独过、一起挂 = 有人污染了共享状态
```

### 测试命名：失败信息应该像一句需求

```text
差: test1 / testCart / testTotal   ← 挂了以后你得读代码才知道坏了什么
好: 空购物车总价为零 / VIP享受七折  ← 失败列表本身就是坏掉的需求清单
```

> **注意**：JUnit 5 用 `@Test`/`@BeforeEach`/`@AfterEach`，本例手写的就是它的骨架；AssertJ 的流式断言（`assertThat(x).isEqualTo(y)`）失败信息更好；Testcontainers 在 Docker 里起真数据库，是集成层的现代标配——它存在的理由正是本章实测的「mock 掩盖真实缺陷」。

## 7. C++

C++ 版回答两个问题：没有反射怎么发现测试，以及属性测试为什么强。

### 测试发现：静态注册器（30 行框架）

```cpp
struct Registrar {                            // 全局对象的构造函数在 main 之前跑
    Registrar(const char* name, std::function<void()> fn) { registry().push_back({name, fn}); }
};

#define TEST(name)                                                  \
    static void test_##name();                                      \
    static Registrar reg_##name(#name, test_##name);  /* 自动注册 */ \
    static void test_##name()
```

```text
Java 靠反射扫 @Test；C++ 的类不知道自己有什么方法
→ TEST 宏展开成一个全局 Registrar 对象，构造函数在 main 之前把测试塞进注册表
→ Catch2 / GoogleTest 的 TEST_CASE / TEST 宏就是这么实现的
→ 与第 51 章 ORM 同一个结论: 语言不给反射，就得靠宏/代码生成绕过去
```

### 属性测试三层递进（实测，见钥匙实验四）

```text
手挑用例 4/4 通过 → (a+b)/2 被 12433 个反例击穿 → a+(b-a)/2 被 12600 个反例击穿
→ std::midpoint 100000 组全过
```

### 好用的不变量长什么样

```text
排序:   输出有序 + 长度不变 + 元素多重集相同（三条缺一不可）
编解码: decode(encode(x)) == x（往返性质——序列化/压缩/转义通用）
求逆:   apply(undo(op)) == 原状态（第 48 章 undo log 的正确性就是它）
幂等:   f(f(x)) == f(x)（去重、规范化、重试安全——SQL 版实测了它）
→ 不变量比具体用例【便宜】: 一条性质顶几百个手写断言
```

> **注意**：本例的有符号溢出是**未定义行为**——RapidCheck 是属性测试的工业版（会自动**缩小**反例到最小形态）；`-fsanitize=address,undefined` 是另一类「测试」：UBSan 会直接在运行期抓到 `(a+b)/2` 的溢出。**C++ 的特殊之处：有些 bug（UB）测试框架测不到，要交给编译器插桩。**

## 8. C#

C# 版把「测试替身」这个被混用的词拆成三张面孔。

### 三种替身各验证什么（实测）

| 替身 | 是什么 | 回答的问题 | 本例 |
|------|-------|-----------|------|
| **stub** | 固定返回值 | 「当依赖返回 X 时，我的逻辑对吗」 | `StubRepo.Find` 永远返回 9999 |
| **mock** | 记录交互 | 「我有没有**正确地调用**依赖」 | `MockNotifier.Sent` 列表 |
| **fake** | 能工作的轻量实现 | 「存进去的能**原样取出**吗」 | `FakeRepo`（Dictionary） |

```text
实测: 大额订单发通知 ✓（mock 验证了 1 条、内容含 200.00）
     小额订单不发   ✓（mock 验证了 0 条）
     保存后能读回   ✓（fake 验证了往返）
→ 术语常被混用成「mock」，但选错类型会让测试【验证不到你想验证的】
```

### fake 测不出的 bug（实测，见钥匙实验二）

```text
fake（Dictionary）: 订单号「2026/08/001」照常工作 ✓
真实文件系统:       同一个用例失败 ✗ —— 斜杠是路径分隔符
→ fake 的保真度边界: 它复刻接口语义，复刻不了底层介质的规则
```

### 可测性来自设计

```text
OrderService 依赖的是【接口】IOrderRepo/INotifier，不是具体类
→ 所以才【换得进】替身——这就是依赖注入（第 55 章的主角）
→ 反例: 在方法里 new FileRepo() 或调静态方法 → 什么都换不掉 → 测不了
→ 「难测」几乎总是设计问题的信号: 依赖写死、副作用糊进逻辑、全局状态
```

> **注意**：.NET 生态是 xUnit（框架）+ Moq/NSubstitute（mock 库）+ coverlet（覆盖率）；xUnit 每个测试方法 new 一个测试类实例——与 Java 版实测的隔离策略一致；`[Theory]` + `[InlineData]` 是参数化测试，一份逻辑多组数据。

## 9. SQL

数据库世界有自己的三种「断言」。

### 约束 = 永远在线的断言（实测）

```text
插入 -50 分的订单: changes=0（被 CHECK 拦下）
插入状态 flying:   changes=0（枚举 CHECK 拦下）
→ 单元测试跑一次，约束【每次写入】都跑——数据层的最后防线
→ 应用层校验可以被绕过（新代码、手工 SQL、别的服务），约束不能
```

### 断言查询：找违规行，0 行 = 通过（实测）

```sql
-- 规则写成「找违规行」的查询
SELECT COUNT(*) FROM orders WHERE status NOT IN ('paid','shipped','done','cancelled');
```

```text
规则 A「不允许孤儿状态」: 违规 0 行 → 通过 ✓
→ 这就是 dbt tests 的原理；这类测试跑在【生产数据】上
→ 单元测试测代码，数据测试测数据——两个不同的被测对象
```

### 回滚隔离：数据库测试的标准姿势（实测）

```text
测试前订单数: 2
BEGIN → 造测试数据 + 执行被测操作 → 事务内订单数 3、订单 1 状态 done
ROLLBACK → 订单数 2、订单 1 状态 paid（分毫未动）
→ 每个测试一个事务，结束就 ROLLBACK——不用手写清理，也不会互相污染
→ Django/Rails/Spring 的数据库测试默认就是这么做的
→ 边界: 被测代码自己 COMMIT 或开新连接时失效（得换 truncate/重建）
```

### 幂等性：数据侧最值得测的性质（实测）

```text
UPSERT 设值执行两次后 qty = 8（幂等 ✓——重试安全）
对照: 写成 qty = qty - 2 的累加式，重复执行就是 6（重试不安全）
→ 消息重投、接口重试无处不在（第 48 章的重试逻辑）——幂等是必测性质
```

> **注意**：测试数据的两难——手工造的可控稳定但覆盖不了真实数据的怪状，生产脱敏副本真实但慢且不可复现；常见分工是单元/集成用手工数据、数据质量断言跑生产；**迁移测试**（新 schema 在生产数据副本上演练）是最容易被跳过、事故也最疼的一类。

## 10. 五语言横向对比

### ① 测试设施对照

| 能力 | JavaScript | Python | Java | C++ | C# |
|------|-----------|--------|------|-----|-----|
| 内置测试设施 | ✅ `node:test`（18+） | ✅ `unittest` | ❌（要 JUnit） | ❌（只有 `assert`） | ❌（要 xUnit） |
| 测试发现机制 | 文件约定 | 类/方法名约定 | **反射扫注解** | **静态注册宏** | 反射扫特性 |
| 事实标准框架 | Vitest / Jest | pytest | JUnit 5 | Catch2 / GoogleTest | xUnit |
| mock 库 | 内置 `mock` | 内置 `unittest.mock` | Mockito | 手写/FakeIt | Moq / NSubstitute |
| mock 计时器 | ✅ `mock.timers`（实测） | `freezegun` | — | — | — |
| 属性测试 | fast-check | Hypothesis | jqwik | RapidCheck | FsCheck |
| 特有陷阱 | **异步假通过**（实测） | fixture 作用域 | static 状态穿透隔离 | **UB 测不到**（要 sanitizer） | 同 Java |

### ② 钥匙实验数据汇总

```text
金字塔成本（Python）: 单元 0.7 μs → 集成 665 μs（1022x）→ 端到端 10157 μs（15608x）
mock 两面（Python）:  mock 版 0 元订单通过 ✓（57 μs），真实网关拒绝 ✗
fake 边界（C#）:      斜杠订单号 fake 过、真实文件系统挂；速度红利 333x
覆盖率说谎（Python）: 行覆盖 100% + 全绿 + bug 仍在（80.0 ≠ 70.0）
隔离实验（Java）:     共享实例 1/2，新实例 2/2
属性测试（C++）:      手挑 4/4 过 → 原始 bug 12433 反例 → 修复 bug 12600 反例 → midpoint 全过
假通过（JS）:         泄漏断言 leaked=1，失败没进任何报告
回滚隔离（SQL）:      事务内 3 行 → 回滚后 2 行分毫未动
```

### ③ 发现机制的分野（与第 51 章同构）

```text
Java/C#: 运行时反射扫注解/特性 —— 类知道自己长什么样
Python:  命名约定 + 内省      —— 动态语言的自然路径
JS:      文件约定 + 函数注册   —— test() 调用本身就是注册
C++:     静态注册宏           —— 没有反射，全局对象构造函数替代之
→ 第 51 章 ORM 的映射机制、本章测试的发现机制——同一个语言特性差异的两次投影
```

### ④ 共性与根因

**共性**：所有语言的测试框架都做同样三件事（发现、隔离、报告——Java 版各 10 行手写实现）；所有生态都同时需要「快的替身」和「真的集成」（实测证明两者不可互相替代）；覆盖率工具在所有语言里都测不出断言强度。

**根因**：

- **金字塔的形状由物理决定**：进程启动、磁盘 I/O、网络往返的成本（第 39/46 章实测过）直接决定了每层测试的价格；
- **mock 的风险是结构性的**：替身与真实实现是**两份代码**，没有任何机制强制它们同步——漂移只是时间问题；
- **覆盖率说谎是度量的通病**：它测量执行不测量验证，而古德哈特定律保证被当作目标的度量必然退化；
- **异步假通过是 JS 独重的**，因为它的测试函数边界与异步完成边界天然分离（第 43 章的事件循环）；
- **发现机制的差异**与第 51 章 ORM 完全同构——运行时自省能力决定了框架的形态。

## 11. 底层实现对比

| 框架 | 发现 | 隔离 | 报告 |
|------|------|------|------|
| **JUnit 5** | 反射扫 `@Test` | 每方法新实例 | TestEngine 事件流 |
| **pytest** | 名字约定 `test_*` + 内省 | fixture 作用域管理 | 断言重写（rewrite AST 给出好的失败信息） |
| **node:test** | `test()` 调用注册 | 子测试树 | TAP 协议输出（实测所见） |
| **Catch2** | `TEST_CASE` 宏静态注册 | section 重入执行 | 表达式分解（`REQUIRE(a==b)` 打印 a、b 的值） |
| **xUnit** | 反射扫 `[Fact]`/`[Theory]` | 每测试新类实例 | 并行执行默认开 |

**pytest 的断言重写值得单独说**：

```text
裸 assert a == b 本来只会抛 AssertionError（没有细节）
pytest 在【导入时改写测试文件的 AST】，把 assert 变成能报告两边值的形式
→ 所以 pytest 的失败信息是「assert 80.0 == 70.0」而不是干巴巴的 AssertionError
→ 这是第 30 章「运行时改代码」在测试工具里最成功的应用
```

## 12. 性能分析

### 本章实测数字速查

```text
金字塔:    单元 0.7 μs / 集成 665 μs (1022x) / 端到端 10157 μs (15608x)
套件外推:  1000 个测试全单元 1 ms，全端到端 10 秒
替身红利:  fake vs 真实文件 333x（C#）；mock 计时器让 1 秒等待变 0.06 ms（JS）
属性测试:  100000 组输入几百毫秒——比手写几百个用例便宜得多
覆盖率:    100% 行覆盖与 bug 共存（弱断言）
```

### 测试套件的性能就是团队的反馈速度

```text
套件 10 秒:  每次保存都跑 → bug 活不过一分钟
套件 10 分钟: 每次提交才跑 → bug 活几小时，修复时上下文已冷
套件 1 小时:  每天跑一次 → bug 活几天，谁引入的都要查半天
→ 「测试太慢」不是舒适度问题，是【缺陷存活时间】问题
→ 优化顺序: 下沉到更低层（金字塔）→ 替身换掉慢依赖 → 并行执行 → 只跑受影响的测试
```

> ⚠️ **flaky 测试比慢测试更毒**。一个 1% 概率随机挂的测试，在 100 个测试的套件里让「全绿」概率降到 37%——团队会开始「重跑一次就好」，然后**真正的失败也被重跑掩盖**。flaky 的两大来源（时间、随机）本章都给了注入解法；第三大来源（测试间污染）Java 版给了排查套路。

## 13. 工程实践

| 场景 | ✅ 推荐 | ❌ 避免 | 原因 |
|------|--------|--------|------|
| 分层策略 | 大量单元 + 适量集成 + 少量端到端 | 全部端到端 | 实测每层贵 1~2 个数量级 |
| mock 的对象 | 慢/贵/不稳定的依赖 | 一切依赖都 mock | 实测 mock 掩盖真实网关规则 |
| 替身之外 | 留少量集成测试跑真实介质 | 只有 fake | 实测斜杠订单号只有真实现能抓 |
| 断言 | 精确断言期望值 | `> 0`/`not null` 式弱断言 | 实测弱断言让 100% 覆盖率与 bug 共存 |
| 覆盖率 | 当**探测器**（找没测的区域） | 当 KPI | 古德哈特定律 + 实测 |
| 异步测试 | await 每个异步断言 | fire-and-forget | 实测假通过，失败被吞 |
| 时间/随机 | 注入时钟与随机源 | 直接调 `Date.now`/`random` | flaky 的两大来源 |
| 有算法不变量时 | 属性测试 | 只写手挑用例 | 实测抓出手挑漏掉的两层 bug |
| 数据库测试 | 事务回滚隔离 | 手写清理代码 | 实测回滚后分毫未动 |
| 数据质量 | 断言查询跑生产 | 只测代码不测数据 | 数据也会坏 |
| 测试命名 | 描述行为的句子 | test1/test2 | 失败列表 = 坏掉的需求清单 |
| 顺序耦合排查 | 单独跑挂掉的测试 | 盲目重跑 | 单独过一起挂 = 共享状态污染 |

### 一句话决策

```text
写一个测试前问三件事:
  ① 它验证的是行为还是执行过？        → 断言必须精确到期望值
  ② 它依赖的真实性重要吗？            → 重要就别 mock，进集成层
  ③ 它会因时间/随机/顺序而不稳定吗？  → 会就注入依赖、隔离状态
维护套件时盯一件事: 反馈速度——慢测试下沉，flaky 测试立刻修或删
```

## 14. 最佳实践

- **金字塔按成本分层**：实测单元:集成:端到端 = 1 : 1022 : 15608——快的多写，贵的精写。
- **mock 隔离「慢贵不稳」，不替代「真」**：实测 mock 和 fake 各掩盖了一个真实缺陷；每个被替身覆盖的依赖，都要有至少一条真实路径的集成测试。
- **断言精确到期望值**：实测 `assert result > 0` 让 100% 覆盖率形同虚设；写 `assert result == 70.0`。
- **覆盖率当探测器不当 KPI**：它能告诉你哪里**没**测，不能告诉你哪里测**好**了。
- **异步断言必须被等待**：实测忘 await 的失败被吞、测试永绿——async 测试里不允许 fire-and-forget。
- **时间与随机一律注入**：实测 mock 计时器把 1 秒等待变 0.06 ms，注入随机源让结果可复现。
- **有不变量就上属性测试**：实测它连「修复的 bug」都能抓到——排序、编解码、幂等、求逆都是现成的性质。
- **测试要隔离，且知道隔离的边界**：实测共享实例导致顺序耦合；static/文件/数据库等实例外状态要另行处理（数据库用事务回滚，实测干净）。

## 15. 常见坑

**坑 1 · 异步断言没人等（JS 最常见）**

```javascript
test('...', () => {
  fetchBalance(1).then(b => assert.equal(b, 100));   // ⚠️ 实测: 失败被吞，测试永绿
});
// ✅ test('...', async () => { assert.equal(await fetchBalance(1), 100); });
```

**坑 2 · 弱断言撑高覆盖率**

```python
result = discount(100, True)
assert result > 0            # ⚠️ 实测: 覆盖率 100%，bug 安然无恙
assert result == 70.0        # ✅
```

**坑 3 · mock 定义了依赖的行为**

```python
gw.charge.return_value = "ok"    # ⚠️ 真实网关会拒绝 0 元——mock 不知道
# ✅ mock 之外，留一条真实网关的集成测试
```

**坑 4 · 测试间共享状态**

```java
static List<Order> orders = ...;   // ⚠️ 实测: t2 的成败取决于 t1 是否先跑
// ✅ 每测试新实例（框架默认）+ static 状态在 @BeforeEach 重置
```

**坑 5 · 测试里 sleep 等待异步完成**

```javascript
await sleep(500); assert(...)   // ⚠️ 机器慢就挂（flaky）、机器快就浪费
// ✅ mock 计时器（实测 0.06 ms）或等待明确的完成信号
```

**坑 6 · 数据库测试不清理**

```sql
-- ⚠️ 测试插入的数据留在库里 → 下一个测试的 COUNT 全错
-- ✅ BEGIN → 测试 → ROLLBACK（实测分毫未动）
```

**坑 7 · 只测 happy path**

```text
⚠️ 手挑用例全过 ≠ 没 bug——实测 (a+b)/2 藏着 12433 个反例
✅ 边界值（0/负数/空/溢出）+ 属性测试轰炸
```

7. **复现属性测试三层递进**：对 `(a+b)/2` 跑随机轰炸，验证教科书修法也有反例，再验证标准库版。
8. 在你的 JS 项目里找出所有「then 里断言但没 return/await」的测试（可写 lint 规则），统计有几个假通过。
9. 给一个依赖时间的功能（防抖/重试/超时）写 mock 计时器测试，对比真实等待版的耗时。

## 18. 本章总结

**一句话**：测试是**可执行的规格说明**，本章用五个钥匙实验把「怎么知道代码是对的」这个问题的三个陷阱全部量化——**快的测不出真的**（金字塔三层实测 1x/1022x/15608x 的成本结构决定了必须分层；mock 版 0 元订单绿灯而真实网关拒绝、fake 让斜杠订单号通过而真实文件系统失败，证明替身的保真度有边界）、**跑过不等于验证过**（实测 100% 行覆盖 + 测试全绿 + VIP 折扣 bug 安然无恙——弱断言让覆盖率变成假安全感，把它当 KPI 就触发古德哈特定律）、**绿灯可能是假的**（JS 实测忘 await 的断言在测试判定后才执行、失败被吞，这类测试永远是绿的）；框架本身被手写祛魅——Java 用反射 30 行实现发现/隔离/报告（并实测共享实例导致顺序耦合：1/2 vs 2/2），C++ 没有反射就用静态注册宏（与第 51 章 ORM 同构）；而**属性测试**的三层递进（手挑用例全过 → `(a+b)/2` 被 12433 个反例击穿 → 教科书修法再被 12600 个反例击穿 → `std::midpoint` 全过）证明了它连修复的 bug 都能抓到——「求两数中点」难到 2019 年才进标准库。

**关键要点**

- **金字塔 = 成本结构**（实测）：0.7 μs / 665 μs / 10157 μs——分层不是教条，是反馈速度的推论。
- **mock 两面**（实测）：正确用途是隔离慢/贵/不稳定（mock 计时器 1 秒→0.06 ms）；错误用途是定义依赖行为（0 元订单、斜杠订单号两个反例）。
- **覆盖率说谎**（实测）：100% 覆盖与 bug 共存；它度量执行，不度量验证。
- **框架的三件事**（手写实测）：发现（反射/静态注册）、隔离（每测试新实例，实测 1/2 vs 2/2）、报告（失败不中断）。
- **属性测试**（实测三层）：不变量比用例便宜；连修复的 bug 都能抓；反例要能自动缩小。
- **异步假通过**（实测）：断言晚于判定 → 失败被吞 → 永绿；async 测试必须 await 一切。
- **数据库三断言**（实测）：约束（每次写入都跑）、断言查询（0 行=通过）、回滚隔离（分毫未动）。
- **flaky 三来源**：时间、随机（注入解决）、测试间污染（隔离+排查套路）。

**自查清单**

- [ ] 我能用实测数据解释金字塔为什么分层。
- [ ] 我知道 mock 的边界，且每个替身背后留了真实路径的集成测试。
- [ ] 我的断言精确到期望值，不靠覆盖率数字自我安慰。
- [ ] 我的 async 测试没有 fire-and-forget 的断言。
- [ ] 我能为有不变量的代码写属性测试。

**下一章预告**：测试保证了代码的正确，但代码还依赖着几十上百个别人写的包——它们的版本谁来管？第 53 章讲**包管理**：为什么会有「依赖地狱」、语义化版本的承诺与谎言、锁文件到底锁住了什么、pip/npm/Maven/NuGet/vcpkg 五家解依赖冲突的算法有何不同（npm 允许同一个包多版本共存而 Maven 只留一个，这个差异的后果远比听起来大），以及供应链攻击为什么让「装个包」变成了安全决策。
