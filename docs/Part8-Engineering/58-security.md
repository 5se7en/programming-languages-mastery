# 第 58 章 · 安全

**简体中文** ｜ [English](./58-security.en-US.md)

---

> 第 57 章教你把程序变快。这一章要说的是：**跑得快的错误程序，只是更快地出错**。而安全漏洞是一类特殊的错误——它们**不会让程序崩溃，不会让测试变红，也不会在监控上留下任何异常**。它们安静地待在那里，直到有人来找它们。
>
> 本章的**钥匙实验**只有一行代码的差别。同一个登录查询，输入 `alice` 返回 1 行；输入 `alice' OR '1'='1` 返回 **3 行——整张用户表**。改成参数化查询后，同样的恶意输入返回 **0 行**，而两次执行的 SQL **字符串完全相同**。这个对比揭示了参数化的真正含义：它**不是帮你转义引号**，而是**让 SQL 语句和数据走两条不同的通道**——语句先被解析成执行计划，参数之后才填进去，它从来没有机会变成语法。
>
> 于是就有了「那我自己转义不行吗」。本章实测了一次真实的绕过：防御方把所有输入都过一遍 `escape_quotes()`，但项目里另一处查询的值**没有被引号包住**（数值列），于是输入 `1 OR 1=1` 转义前后**完全没变**，直接拖走了整张表。**转义的前提是「值被引号包住」，而这个前提不写在任何地方。**
>
> XSS 更难缠，因为「转义」在这里根本不是一个动作，而是**六个不同的动作**。本章用同一个 `escapeHtml` 打三种上下文：HTML 文本里 **✅ 有效**；无引号属性里 **❌ 失败**（载荷 `a onmouseover=alert(1)` 里根本没有需要转义的字符）；事件处理属性里 **❌ 失败**，而且失败得最隐蔽——浏览器解析属性值时会**先把 `&#39;` 解码回 `'`** 再交给 JS 引擎，转义反而制造了漏洞。**同一个函数，三种上下文，三种结果。**
>
> 然后是本书唯一一处「性能越差越好」的设计。SHA-256 在单核上跑到 **366 万次/秒**，而 PBKDF2 跑 60 万轮只有 **6.4 次/秒**——猜测速率相差 **56 万倍**（Java 版实测 234 万倍）。密码哈希**故意做慢**，因为攻击者拿到库之后，唯一的成本就是每次猜测的代价。一本一千万条的常见密码字典，用 SHA-256 几秒跑完，用 PBKDF2 要跑几周。
>
> 时序攻击则把第 57 章的直觉整个反过来。逐字节比较令牌时，**第 1 字节就不同耗时 18.5 ms，第 32 字节才不同耗时 237.4 ms（差 12.9 倍）**——耗时随「猜对的前缀长度」增长，这个差距本身就是一条信息泄露通道，能把 32 字节令牌的爆破空间从 256³² 降到 **8192 次**。恒定时间比较把差距压到 **0.99x**，代价是绝对耗时反而更高（453 ms vs 18 ms）：**它永远做满全部工作，拒绝提前返回。**
>
> 最后是内存安全。C++ 版实测一次整数溢出：请求 10.7 亿个 4 字节元素，32 位乘法回绕成 **4 字节**——程序以为自己有 4 GB。而「C++ 不做边界检查是为了性能」这个理由，实测已经基本不成立了：`at()` 相对 `[]` 的开销在 **-O0 是 2.21x，-O1 是 1.05x，-O2 是 1.02x**。**优化器变强，安全的代价就塌缩了。**
>
> 一句话概括本章：**注入类漏洞全都是同一个根因——把不可信数据交给了一个会解析它的东西；而所有防御的共同形状是：别拼字符串，用结构化接口。**

## 1. 学习目标

学完本章，你将能够：

- 解释 SQL 注入的**真正根因**，并说清参数化查询为什么不是「自动转义」；
- 说明为什么**手工转义几乎必然失败**，并复现一次真实的绕过；
- 区分 XSS 的**多种上下文**，并为每种选择正确的编码方式；
- 解释密码哈希为什么**故意做慢**，并量化它与通用哈希的差距；
- 识别**时序攻击**的成因，并知道何时必须使用恒定时间比较；
- 说清**内存安全**消灭了哪一类漏洞、没消灭哪一类，以及边界检查今天的真实代价；
- 用**纵深防御**的思路评估一个系统：第一道防线失守后，还剩下什么。

## 2. 为什么会出现这个概念

### 2.1 安全 bug 与普通 bug 的三个区别

| | 普通 bug | 安全 bug |
|---|---|---|
| **谁来触发** | 用户偶然遇到 | **有人主动寻找** |
| **输入分布** | 正常业务数据 | **专门构造的边界数据** |
| **失败表现** | 报错、结果不对 | **一切正常**（这正是攻击成功的样子） |

第三条是根本性的。一个功能 bug 会自己暴露：页面白屏、接口 500、数据对不上。而一个 SQL 注入漏洞在**功能测试里 100% 通过**——因为正常输入下它工作得完全正确。

本章 C# 版的密码学清单把这一点讲得最直白：ECB 模式加密**不报错**、解密**完全正确**、往返测试**全绿**——它只是把明文的结构原样泄露了出去。**密码学的错误不会让程序崩溃，只会让它安静地不安全。**

### 2.2 一个根因，很多名字

本章覆盖的漏洞看起来五花八门，但注入这一大类**只有一个根因**：

```
SQL 注入   : 数据被拼进【SQL 解析器】的输入
XSS        : 数据被拼进【HTML 解析器】的输入
命令注入   : 数据被拼进【shell 解析器】的输入
路径穿越   : 数据被拼进【路径解析器】的输入
反序列化   : 数据被交给一个【会调用方法】的还原器
模板注入   : 数据被拼进【模板引擎】的输入
```

**把不可信数据交给了一个会解析它的东西。**

于是防御也只有一个形状：**别拼字符串，用结构化接口**。

```
SQL      → 参数化查询（语句与数据分两条通道）
HTML     → textContent / setAttribute（DOM API，不经过 HTML 解析器）
Shell    → execve(["cmd", arg1, arg2])（数组形式，不经过 shell）
路径     → 规范化后校验前缀，或用不含用户输入的映射表
反序列化 → 用 JSON 等纯数据格式
```

这个「同构」不是巧合。它是本章最值得带走的一条认知：**当你发现自己在用字符串拼接构造某种「会被解析的东西」，你就在制造一个注入漏洞**。

### 2.3 为什么「过滤输入」是错误的心智模型

很多人的第一反应是「在入口处过滤掉危险字符」。这个思路有三个致命问题：

**① 危险字符集取决于输出位置，而入口不知道输出在哪。** 同一个用户名，写进 SQL 时危险的是 `'`，写进 HTML 时危险的是 `<`，写进 shell 时危险的是 `;`，写进 LDAP 时危险的是 `(`。入口过滤要么漏掉一种，要么把所有正常内容都毁掉（一个叫 O'Brien 的用户永远无法注册）。

**② 数据会被多次使用。** 一个用户名存进数据库，之后可能出现在 HTML 页面、JSON API、日志文件、CSV 导出、邮件正文里——五种上下文，五套规则。

**③ 过滤是黑名单，而黑名单永远不完整。**

正确的心智模型是：**输入时验证（是不是合法的业务数据），输出时编码（按目标上下文）**。这两件事发生在不同的时间、不同的地点，用不同的规则。

### 2.4 纵深防御：假设第一道会失守

安全设计的基本假设**不是「不会出错」，而是「出错时代价有多大」**。

本章 SQL 版整节都在讲这件事：假设应用层的参数化查询失守了，攻击者能做多少事完全取决于**这个数据库连接的权限**。用超级用户连接？可读全部表、可 DROP、可能可执行命令。用最小权限账号？只能碰它被授权的那几张表的那几列——`pw_hash` 根本不在视图里。

同样的思路贯穿整章：

| 第一道防线 | 失守后的第二道 |
|---|---|
| 参数化查询 | 数据库最小权限、视图、RLS |
| 输出编码 | CSP（内联脚本不执行）、HttpOnly（Cookie 偷不走） |
| 密码哈希 | 加盐（彩虹表失效）、慢哈希（爆破变慢） |
| 内存安全编码 | ASan/UBSan、栈保护、ASLR |
| 授权检查 | 审计日志（事后能回答「发生了什么」） |

## 3. 底层原理

### 3.1 注入的机制：一次解析，两个来源

理解注入的关键是看清**解析器眼里的世界**。

```
你以为的:   SELECT ... WHERE name = [一个字符串值]
                                     ↑ 用户数据

解析器看到的: SELECT ... WHERE name = 'alice' OR '1'='1'
             └────────── 一整串待解析的 SQL ──────────┘
```

解析器**没有能力**区分哪部分是你写的、哪部分是用户填的——它看到的只是一串字符。所谓「注入」，就是用户数据**跨过了数据与代码的边界**。

参数化查询从机制上消灭了这个边界问题：

```
① 客户端发送:  SELECT id FROM users WHERE name = ?
   数据库:      解析 → 生成执行计划（此时 ? 是一个占位的【参数槽】）
② 客户端发送:  参数值 = "alice' OR '1'='1"
   数据库:      把这个值【放进参数槽】——解析早就结束了
```

第二步没有任何解析发生。这就是为什么参数化「不需要转义」：**没有字符串需要被正确转义，因为压根没有拼接出一个字符串。**

顺带一个收益：执行计划可以被复用（第 49 章），所以**参数化通常还更快**。

### 3.2 为什么转义总是输

转义的正确性依赖一串**没有写下来的前提**：

1. 值被引号包住（本章实测的绕过就打在这里）；
2. 转义规则匹配这个数据库的方言；
3. 字符集与数据库一致（历史上 MySQL 的 GBK 编码让 `addslashes()` 整个失效——`0x5c` 被吃进多字节字符的第二字节，反斜杠消失了）；
4. 转义只做一次（多做一次或少做一次都出错）；
5. 项目里**每一处**都记得调用。

第 5 条尤其致命：转义是一个**必须处处正确**的防御，而攻击者只需要找到**一处**遗漏。参数化则是一个**默认正确**的防御。

> 这就是安全工程里反复出现的原则：**优先选择「默认安全」的机制，而不是「正确使用就安全」的机制。**

### 3.3 XSS：六种上下文，六种规则

浏览器不是一个解析器，而是**一串解析器**：HTML 解析器 → 属性值解码 → JS 解析器 / CSS 解析器 / URL 解析器。数据落在哪一层，就要按哪一层的规则编码。

```
<div>       用户数据 </div>          ← HTML 文本: 实体编码 &<>"'
<div class="用户数据">   </div>      ← 属性值: 实体编码 + 【必须有引号】
<div class=用户数据>     </div>      ← 无引号属性: 【无法安全编码】
<a href="用户数据">                  ← URL: 实体编码 + 【协议白名单】
<a onclick="f('用户数据')">          ← 事件处理: 【JS 编码】，实体编码会被二次解码
<script> var x = "用户数据"; </script> ← 原始文本: JSON 编码，实体【不会】被解码
<style> .a { color: 用户数据 } </style> ← CSS: 严格白名单
```

其中**事件处理属性**最容易讲错，也最容易写错。浏览器解析 `onclick="..."` 时会**先把属性值里的字符引用解码**，再把解码结果交给 JS 引擎。本章实测：

```
转义后的 HTML:  <a onclick="greet('&#39;);alert(1);//')">
JS 引擎实际看到: greet('');alert(1);//')
```

`&#39;` 被解回 `'`，字符串被闭合，`alert(1)` 成了独立语句。**HTML 转义在这里不但没用，还正好制造了漏洞**——这就是「双重解码」漏洞。

> 一个常被讲错的对照：`<script>` 标签内部是**原始文本**，字符引用**不会**被解码。所以在 `<script>` 里做 HTML 转义**不是「有漏洞」，而是「数据被损坏」**——用户名会真的显示成 `&#39;`。正确做法是 `JSON.stringify`。

### 3.4 密码哈希：唯一一处「越慢越好」

普通哈希（SHA-256、MD5）的设计目标是**快**——它们要能每秒处理几 GB 数据。这个目标与密码存储**直接冲突**。

攻击者拿到数据库之后，破解流程是：

```
for 候选密码 in 常见密码字典:
    if hash(候选密码 + 盐) == 存储的哈希:
        破解成功
```

**唯一的成本就是 `hash()` 这一次调用的代价。**所以密码哈希函数被设计成故意慢：

| 函数 | 慢的方式 |
|---|---|
| PBKDF2 | 重复迭代 HMAC 数十万次 |
| bcrypt | 迭代 + 需要 4 KB 内存 |
| scrypt | 迭代 + **可配置的大量内存** |
| Argon2id | 迭代 + 大内存 + 抗侧信道 |

「吃内存」这一条很关键：GPU 有几千个核心，但**显存带宽有限**。一个吃 64 MB 内存的哈希函数，让 GPU 的并行度优势直接消失——这就是 scrypt/Argon2 优于 PBKDF2 的原因（PBKDF2 只吃 CPU，可被 GPU 大幅加速）。

**注意这个代价是对称的**：你的登录接口也要付这 150 ms。所以迭代次数是一个**安全 vs 可用性**的权衡，OWASP 会随硬件进步逐年上调建议值。

### 3.5 加盐：让预计算失效

不加盐时，同一个密码在所有系统里产生同一个哈希，于是攻击者可以**预先算好**一张巨表（彩虹表），破解时只需查表。

加盐后，每个用户的盐不同 → 同一个密码产生完全不同的哈希 → **预计算整类失效**，攻击者必须对每个用户单独跑一遍字典。

本章实测三个用户使用同一个弱密码：

```
不加盐:  三个哈希完全相同（一眼看出「这三人密码一样」，且彩虹表一次命中三个）
加盐后:  三个完全不同的结果
```

盐**不需要保密**（它和哈希存在一起），它只需要**唯一且随机**。

### 3.6 时序攻击：耗时也是输出

```java
for (int i = 0; i < a.length; i++)
    if (a[i] != b[i]) return false;      // ⚠️ 一发现不同就返回
```

这个循环的耗时**正比于「前缀猜对了多少字节」**。于是攻击者可以：

```
猜第 1 字节 = 0x00..0xff（256 次），耗时最长的那个就是正确的
猜第 2 字节 = 0x00..0xff（256 次），...
```

32 字节的令牌，从 **256³² 次**降到 **256 × 32 = 8192 次**。

本章 C# 版实测了这个差距：**第 1 字节就不同 18.5 ms，第 32 字节才不同 237.4 ms——12.9 倍**（Java 版实测 5.9 倍）。

恒定时间比较的做法是**不提前返回，用位运算累积差异**：

```java
int diff = a.length ^ b.length;
for (int i = 0; i < a.length; i++) diff |= a[i] ^ b[i];   // 始终扫完
return diff == 0;
```

实测差距被压到 **0.99x**。代价是绝对耗时更高（453 ms vs 18 ms）——**它永远做满全部工作**。

> 这是本章与第 57 章最直接的冲突点：**那里追求「尽早返回」，这里必须「拒绝提前返回」。**

### 3.7 内存安全：一整类漏洞的存在与消失

C/C++ 里的内存安全漏洞有一个共同结构：**长度信息与数据分离**。

```c
char* p;        // 只有地址，没有长度
strcpy(dst, src);   // strcpy 不知道 dst 多大，它只找 '\0'
```

而漏洞往往**不在出事的那一行**。本章实测的整数溢出：

```
请求 1073741825 个元素 × 4 字节 = 期望 4294967300 字节
32 位乘法实际得到: 4 字节  ← 回绕了
```

于是分配了 4 字节，程序却以为自己有 4 GB——**之后每一次写入都越界**。真正的漏洞在那行乘法，可能在崩溃点之前几十行。

微软与 Chromium 各自统计：**约 70% 的高危 CVE 是内存安全问题**。这 70% 在 Java/C#/Python/JS/Rust 里**整类不存在**。

但要说清另一半：**剩下 30% 的逻辑漏洞（注入、认证、越权、密码学误用）每种语言都一个不少**。本章前六节讲的全是这 30%。

**换语言能消灭一类漏洞，不能消灭安全工作本身。**

## 4. JavaScript

JS 版聚焦 XSS——以及一个 JS 独有的注入类别。

### 4.1 同一个 escapeHtml，三种结果

```javascript
function escapeHtml(s) {
  return String(s)
    .replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;').replace(/'/g, '&#39;');
}
```

**上下文 A：HTML 文本** — ✅ 有效

```
未转义:  <div><img src=x onerror=alert(1)></div>
转义后:  <div>&lt;img src=x onerror=alert(1)&gt;</div>
```

**上下文 B：无引号属性** — ❌ 失败

```
未转义:  <div class=a onmouseover=alert(1)>
转义后:  <div class=a onmouseover=alert(1)>     ← 完全相同
```

载荷里**没有一个字符需要转义**。属性没有引号包住，一个空格就足以引入新属性。

**上下文 C：事件处理属性** — ❌ 失败（最隐蔽）

```
转义后的 HTML:  <a onclick="greet('&#39;);alert(1);//')">
JS 引擎实际看到: greet('');alert(1);//')
```

浏览器解析属性值时**先解码字符引用**，`&#39;` 变回 `'`，字符串被闭合。

### 4.2 javascript: 伪协议——转义全对，依然中招

```javascript
const url = 'javascript:alert(document.cookie)';
escapeHtml(url)   // → 完全没变，因为没有任何需要转义的字符
// <a href="javascript:alert(document.cookie)">click</a>
```

正确做法是**协议白名单**：

```
https://ok.example/a     → https://ok.example/a
javascript:alert(1)      → #
DaTa:text/html,x         → #        （大小写绕过被挡住）
//evil.example           → //evil.example   ⚠️ 通过了！
```

最后一条值得注意：`//evil.example` **通过了协议白名单**——它继承当前页面的 `https:`，协议对了，主机却是攻击者的。这是开放重定向，需要**再加一层主机白名单**。

> 教训：一个检查通过 ≠ 安全，**要问清楚它到底检查了什么**。

### 4.3 根本解法：结构化 API

```javascript
el.innerHTML = "<div>" + userInput + "</div>";   // ❌ 经过 HTML 解析器
el.textContent = userInput;                      // ✅ 数据永远是数据
el.setAttribute("class", userInput);             // ✅ 属性值不参与解析
```

**与参数化查询完全同构**：让数据走一条不会被解析的通道。

React/Vue 默认转义 `{expr}`，这就是它们「默认安全」的来源——而 `dangerouslySetInnerHTML` / `v-html` 的名字里就写着代价。

### 4.4 原型链污染：JS 独有的一类注入

```javascript
function unsafeMerge(target, src) {
  for (const k in src) {
    if (typeof src[k] === 'object' && src[k] !== null) {
      target[k] = target[k] || {};
      unsafeMerge(target[k], src[k]);       // ⚠️ 没有过滤 __proto__
    } else target[k] = src[k];
  }
  return target;
}
const evil = JSON.parse('{"__proto__":{"isAdmin":true}}');
unsafeMerge({}, evil);
```

```
合并前，一个【全新的空对象】的 isAdmin: undefined
合并后，一个【全新的空对象】的 isAdmin: true
```

攻击者从未碰过这个对象，却让它有了 `isAdmin === true`。第 26 章讲过原型链：**改 `Object.prototype` 会影响所有对象**——任何 `if (user.isAdmin)` 的检查全部失守。

防御：过滤 `__proto__`/`constructor`/`prototype`，或用 `Object.create(null)`、`Map`。

### 4.5 纵深防御：浏览器给的第二道防线

```
CSP:              script-src 'self' → 即使被注入，内联脚本也不执行
HttpOnly Cookie:  → document.cookie 读不到，XSS 偷不走会话
SameSite=Lax:     → 跨站请求不带 Cookie，挡住大部分 CSRF
SRI:              <script integrity="sha384-..."> → CDN 被攻破也不加载篡改脚本
```

这些都建立在同一个假设上：**第一道防线会失守，但仍然要限制损失**。

## 5. Python

Python 版是本章的主线：SQL 注入与密码存储。

### 5.1 钥匙实验

```python
def login_vulnerable(con, name):
    """⚠️ 拼接字符串——name 里的内容会成为 SQL 语法的一部分"""
    sql = f"SELECT id, name, role FROM users WHERE name = '{name}'"
    return sql, con.execute(sql).fetchall()
```

```
正常输入: name = 'alice'
  实际执行的 SQL: SELECT ... WHERE name = 'alice'
  返回 1 行: ['alice']

恶意输入: name = "alice' OR '1'='1"
  实际执行的 SQL: SELECT ... WHERE name = 'alice' OR '1'='1'
  返回 3 行: ['alice', 'bob', 'root']       ← 整张表
```

参数化之后：

```python
sql = "SELECT id, name, role FROM users WHERE name = ?"
con.execute(sql, (name,))
```

```
name = 'alice'                → 返回 1 行: ['alice']
name = "alice' OR '1'='1"     → 返回 0 行: []
两次执行的 SQL 完全相同: SELECT id, name, role FROM users WHERE name = ?
```

**注意最后一行**：SQL 字符串没有变化，恶意输入被当成了一个（不存在的）用户名。

### 5.2 一次真实的转义绕过

```python
def escape_quotes(s):
    """有人认为「把 ' 换成 '' 就安全了」"""
    return s.replace("'", "''")
```

防御方给所有输入都加了这个函数。但项目里另一处查询的值**没有被引号包住**：

```
输入: '1 OR 1=1'（转义后完全没变: '1 OR 1=1'）
SQL:  SELECT id, name FROM users WHERE id = 1 OR 1=1
→ 返回 3 行: ['alice', 'bob', 'root'] —— 【转义被完整绕过】
```

**转义的前提是「值被引号包住」，而数值列往往不带引号。**防御假设一旦不成立就全盘失效——而这个假设不写在任何地方。

### 5.3 参数化管不到的地方：标识符

`?` 只能替换**值**，不能替换表名/列名/`ORDER BY` 方向：

```
ORDER BY ? → 语法上通过，但它按【常量 'name'】排序，等于没排序
```

动态标识符只有一种安全写法——**白名单映射**：

```python
allowed = {"name", "role"}
col = want if want in allowed else "id"
```

```
请求排序列 'name'                        → 实际使用 'name'
请求排序列 'secret; DROP TABLE users'    → 实际使用 'id'
```

### 5.4 密码哈希：越慢越好

```
SHA-256 直接哈希 200000 次: 55 ms → 约 3.66 M 次/秒（单核）
PBKDF2-SHA256   10000 轮:    2.7 ms → 约   375.2 次/秒
PBKDF2-SHA256  100000 轮:   26.2 ms → 约    38.1 次/秒
PBKDF2-SHA256  600000 轮:  155.5 ms → 约     6.4 次/秒
→ 猜测速率相差 568,411 倍
```

一本一千万条的常见密码字典：**用 SHA-256 几秒跑完，用 PBKDF2 要跑几周。**

### 5.5 加盐

```
不加盐（三个用户同一个弱密码）:
  alice  → f52fbd32b2b3b86ff88ef6c490628285...
  bob    → f52fbd32b2b3b86ff88ef6c490628285...
  carol  → f52fbd32b2b3b86ff88ef6c490628285...

各自随机盐:
  alice  → d0d8eeedb6eca936bc357fff14c726ca...
  bob    → bb58bff0b9c5c487e49c78629d171c1c...
  carol  → 7afefe537e84aad404039da16a82d80d...
```

### 5.6 一个诚实的失败：时序差没测出来

Python 版尝试实测 `==` 与 `hmac.compare_digest` 的时序差，**没有测出来**：单次差异在纳秒级，被 Python 解释器的开销完全淹没。

这一点被如实写进了示例：

> **测不出来 ≠ 不存在** —— 攻击者可以发起百万次请求做统计，把噪声平均掉。这是第 57 章「差距要大于波动」的反面：**攻击者有办法把波动降下去。**

（Java 与 C# 版在编译型运行时上成功测出了 5.9x 与 12.9x 的差距。）

## 6. Java

Java 版测三个「看起来能用、实际上不能用」的 API。

### 6.1 java.util.Random 是可预测的

```java
long serverSeed = 1_700_000_000_123L;         // 攻击者猜到了时间戳种子
Random serverRng = new Random(serverSeed);    // 服务端签发重置令牌
Random attackerRng = new Random(serverSeed);  // 攻击者重放
```

```
服务端签发的 5 个重置令牌: [700288, 997043, 31130, 561012, 185333]
攻击者用同一种子推算:      [700288, 997043, 31130, 561012, 185333]
完全一致: true
```

`java.util.Random` 是**线性同余生成器**：状态只有 48 位，观察到**两个连续输出**就能解出内部状态，然后预测全部后续值。它是为模拟、洗牌、游戏设计的，**不是为安全设计的**。

> 判定标准很简单：**任何与安全相关的随机数，一律用 `SecureRandom`**——令牌、盐、IV、会话 ID、密码重置码、CSRF token，无一例外。

### 6.2 密码哈希（JVM 上的数字）

```
SHA-256 直接哈希 1000000 次: 182 ms → 约 5.49 M 次/秒（单核）
PBKDF2-HmacSHA256  10000 轮:   7.9 ms → 约  126.5 次/秒
PBKDF2-HmacSHA256 100000 轮:  72.4 ms → 约   13.8 次/秒
PBKDF2-HmacSHA256 600000 轮: 425.6 ms → 约    2.3 次/秒
→ 猜测速率相差 2,334,582 倍
```

### 6.3 恒定时间比较（实测出了差别）

```
逐字节比较，第 1 字节就不同:   3.3 ms
逐字节比较，第 32 字节才不同: 19.5 ms（慢 5.9x）

MessageDigest.isEqual 早不同: 43.1 ms
MessageDigest.isEqual 晚不同: 45.4 ms（差 1.05x）
```

耗时**随猜对的前缀长度增长**——这个差距就是一条信息泄露通道。

### 6.4 反序列化：把数据变成代码的另一条路

`ObjectInputStream.readObject()` 会**调用被反序列化类的方法**。攻击者构造一条「gadget 链」，让 JVM 在还原对象的过程中执行任意命令。

**与 SQL 注入完全同构**：不可信数据被交给了一个会「执行」它的东西。

防御顺序：① 别反序列化不可信数据 ② 用 JSON 等纯数据格式 ③ 实在要用就上 `ObjectInputFilter` 白名单（Java 9+）。

### 6.5 内存安全的语言里剩下什么

```
✅ 数组越界抛 ArrayIndexOutOfBoundsException，不会踩到别人的内存
✅ new int[n] 对负数直接抛异常
⚠️ 但整数依然会溢出: Integer.MAX_VALUE + 1 = -2147483648
```

经典漏洞形态：`if (offset + len > size)` 的左边先溢出成负数，检查被绕过。用 `Math.addExact()` 让溢出抛异常，或改写成 `offset > size - len`。

还有：默认的 `ObjectInputStream` 不安全、默认的 XML 解析器允许外部实体（XXE）。

**「内存安全的语言」消灭了一整类漏洞，但逻辑类漏洞一个都没少。**

## 7. C++

C++ 版讲那 70%——以及消除它的代价到底有多大。

### 7.1 整数溢出：分配尺寸悄悄变小

```cpp
static size_t alloc_size_buggy(uint32_t count, uint32_t elem) { return count * elem; }
```

```
请求 1073741825 个元素 × 4 字节 = 期望 4294967300 字节
32 位乘法实际得到: 4 字节  ← 【回绕了】
```

malloc 了 4 字节，程序却以为自己有 4 GB——**之后每一次写入都越界**。

**漏洞不在写入的那一行，而在几十行之前的乘法。**这是 CVE 里最常见的形态之一。

带检查的版本在溢出时抛异常，分配从未发生。

### 7.2 有符号长度：一次「检查通过」的越界

```cpp
if (user_len > BUFSZ) reject();
memcpy(dst, src, user_len);
```

```
攻击者传入 user_len = -1, BUFSZ = 64
上界检查 (-1 > 64): 通过  ← 【放行了】，因为负数当然小于上界
但 memcpy 的第三个参数是 size_t，-1 会被转换成: 18446744073709551615 字节
```

一个**只写了上界**的检查，被一个负数完整绕过。根因是**同一个值，两种含义**：检查时它是有符号的，使用时它是无符号的。

### 7.3 边界检查的代价：这个理由已经过期了

```
operator[]（不检查） 20000000 次:  20.20 ms
at()      （检查）   20000000 次:  44.60 ms（慢 2.21x）     ← -O0
```

但换个优化级别：

| 优化级别 | `at()` 相对 `[]` |
|---|---|
| `-O0` | **2.21x** |
| `-O1` | **1.05x** |
| `-O2` | **1.02x** |

**边界检查的代价随编译器变强而塌缩。**优化器能证明 `i` 永远在范围内，或把检查提到循环外；剩下的分支预测器几乎 100% 猜对（第 57 章）。

> 所以「C++ 不检查是为了性能」在今天基本**不成立**了——这个设计是 1980 年代的取舍，那时候优化器远没有这么强。这也解释了 Rust 为什么敢默认检查还自称「零成本抽象」：**这笔账现在算得过来。**

而 `at()` 与 `[]` 的真正区别是**失败时的行为**：

```
at(N+10) → 抛出 std::out_of_range（越界【被变成了一个可处理的错误】）
v[N+10]  → 未定义行为: 可能崩溃，可能返回垃圾，也可能【看起来一切正常】
```

**最后那种情况最危险：测试全绿，漏洞已经在生产环境里了。**

> 这个实验第一次写的时候测出 `at()` **更快**——因为第一个循环承担了首次触碰 80 MB 内存的缺页开销。加上预热与多轮取最小值才得到上面的数字。**第 57 章的三个陷阱，在这里又踩了一个。**

### 7.4 C 字符串与 std::span

```
目标缓冲区 16 字节，源数据 76 字节
strcpy(dst, src)                → 【溢出】: strcpy 只找 '\0'
snprintf(dst, sizeof(dst), ...) → 截断到 15 字节, 返回值 76（= 本该写入的长度）
```

**返回值 76 > 缓冲区 16**：返回值是检测截断的唯一途径，忽略它就成了静默数据丢失。

根因：`char*` 把「指针」和「长度」拆开了，而**只有指针会被传递**。

```cpp
auto sum_raw = [](const int* p, size_t n) { ... };    // ⚠️ 调用方传错 n 就完了
auto sum_span = [](std::span<const int> sp) { ... };  // ✅ 长度不可能传错
```

**安全 API 设计的核心原则：让错误的用法无法通过编译，而不是写进文档。**

## 8. C#

C# 版讲密码学——一个「能跑通」和「安全」之间隔着好几个不会报错的选择的领域。

### 8.1 ECB 模式：加密了，但什么都没藏住

三条记录，其中第 1 条和第 3 条内容相同：

```
明文  块1: alice:role=user      块2: bob:role=user        块3: alice:role=user

ECB   块1: 77f4a8dddffd1b30...  块2: 48a0cfc601826...  块3: 77f4a8dddffd1b30...
      → 第 1 块与第 3 块的密文相同: True  ← 【明文结构完整泄露】

CBC   块1: f6ed351b2538c3f2...  块2: 1c3b0c8d4e1f8...  块3: f4db96f6f2cca4eb...
      → 第 1 块与第 3 块的密文相同: False
```

ECB 逐块独立加密 → **相同明文块 = 相同密文块**。著名的「ECB 企鹅」图片就是这么来的：加密后还能看出轮廓。

**两次加密都没报错、都能正确解密**——安全性不体现在功能测试里。

### 8.2 同一个 IV 用两次，CBC 也一样泄露

```
明文 A = "transfer 100 to bob"，明文 B = "transfer 100 to eve"
两次加密【同一条】明文 A → 密文完全相同: True
加密 A 与 B → 第 1 块密文相同: True   ← 泄露了「两条消息前 16 字节一样」
              第 2 块密文相同: False  ← 差异从这里开始
```

攻击者由此能**二分定位差异位置**，还能识别重放的请求。

IV 的作用就是**让相同明文每次产生不同密文**，固定它等于取消这个作用。IV 必须每次随机生成（可以公开传输，但不能重复）。

### 8.3 只加密不认证

CBC 不保证完整性：攻击者改一个密文字节，解密仍然「成功」，只是对应明文块变成乱码——而**前一块的对应位会被精确翻转**。

```
AES-GCM 解密被篡改的密文 → 抛出 CryptographicException ✅
```

AEAD（`AES-GCM`、`ChaCha20-Poly1305`）把认证内建进来：密文动了一个 bit，解密就直接失败。

> **永远不要只加密不认证。**

### 8.4 恒定时间比较（实测差距最大）

```
逐字节比较，第 1 字节就不同:   18.5 ms
逐字节比较，第 32 字节才不同: 237.4 ms（慢 12.9x）

FixedTimeEquals，第 1 字节不同:  452.8 ms
FixedTimeEquals，第 32 字节不同: 450.0 ms（差 0.99x）
```

注意 `FixedTimeEquals` 的**绝对耗时更高**（453 ms vs 18 ms）：它永远做满全部工作。

> 这正是本章与第 57 章的分歧点：**那里追求「尽早返回」，这里必须「拒绝提前返回」。**

### 8.5 随机数：命名就是个陷阱

```
Random(12345) 生成: [66746, 70159, 774765, 511139]
同种子重放:        [66746, 70159, 774765, 511139]  → 完全一致: True
RandomNumberGenerator: 8420b04c4c99a0d7ec187fcea9596ca3（不可预测）
```

> `Random` 听起来就够随机了，而它恰恰是不能用的那个。

### 8.6 「不要自己造」清单

```
❌ 自己设计加密算法      → 用 AES-GCM / ChaCha20-Poly1305
❌ 手工组 CBC+HMAC       → 用 AEAD
❌ 用 SHA-256 存密码     → 用 Argon2id / bcrypt / PBKDF2
❌ 用 == 比较密钥        → 用 FixedTimeEquals
❌ 用 Random 生成令牌     → 用 RandomNumberGenerator
❌ 固定或复用 IV/nonce   → 每次随机生成
```

**共同点：上面每一条功能测试都会通过。**

## 9. SQL

SQL 版讲纵深防御：假设应用层已经失守，数据库层还能剩下什么。

### 9.1 最小权限决定损失规模

```
如果应用用超级用户连接: 可读全部表、可 DROP、可读文件、可能可执行命令
如果应用用最小权限账号: 只能碰它被授权的那几张表的那几列
```

```sql
GRANT SELECT, INSERT, UPDATE ON app.orders TO app_user;
-- 不要授予 DROP / CREATE / FILE / SUPERUSER，迁移用另一个账号
```

### 9.2 视图：让敏感列不在可达范围内

```sql
CREATE VIEW users_public AS
  SELECT id, tenant_id, name, role FROM users WHERE deleted_at IS NULL;
```

```
users_public 的列: id, tenant_id, name, role
```

`pw_hash` 和 `email` **不在视图里**——即使这个查询被注入，攻击者也拿不到它们。

### 9.3 越权访问（IDOR）：参数化完全防不住

这是本节最重要的一条。租户 100 的用户请求 `GET /orders/3`（这是租户 200 的订单）：

```
ⓐ 只按 id 查（漏洞写法）  → 返回 1 行，跨租户数据泄露
ⓑ 同时按 tenant_id 过滤   → 返回 0 行
```

**输入是合法的数字 3，没有任何注入。**参数化查询、输入验证、WAF——全都防不住。

> **授权检查必须发生在每一次数据访问上，不能只在路由入口检查一次。**

PostgreSQL 的**行级安全（RLS）**把这个约束下沉到数据库，应用忘写也不会漏：

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY t ON orders USING (tenant_id = current_setting('app.tenant')::int);
```

### 9.4 审计日志

```sql
CREATE TRIGGER audit_role_change AFTER UPDATE OF role ON users
BEGIN
  INSERT INTO audit_log(at, actor, action, target)
  VALUES (..., 'role: '||OLD.role||' → '||NEW.role, NEW.name);
END;
```

```
role: user → admin（目标 bob，时间 2026-08-13T10:00:00）
```

审计日志的价值**不在阻止，而在事后能回答「发生了什么」**。关键：审计表要让应用账号**只能 INSERT，不能 UPDATE/DELETE**，否则可被清理。

### 9.5 软删除的安全含义

```
users 表里 carol 仍然存在: 1 行
users_public 视图里已经看不到: 0 行
```

任何**忘记加 `deleted_at IS NULL`** 的查询都会泄露已删除数据。而 GDPR 的「被遗忘权」要求真删除——软删除会让合规变成一个持续的债务。

### 9.6 数据库侧清单

```
ⓐ 应用账号最小权限，迁移账号分离
ⓑ 敏感列走视图/列级权限
ⓒ 多租户用 RLS 兜底
ⓓ 连接串密码走密钥管理服务
ⓔ 传输加密(TLS) + 静态加密(TDE)，备份同样要加密
ⓕ 审计日志只进不出
```

**注意这六条没有一条是「防注入」**——那是应用层的事。**数据库层的职责是：假设应用层会出错，把损失控制住。**

| **本章主题** | XSS / 原型污染 | SQL 注入 / 密码 | 随机数 / 反序列化 | 内存安全 | 密码学误用 | 纵深防御 |
| **内存安全** | ✅ | ✅ | ✅ | ❌ | ✅（`unsafe` 除外） | ✅ |
| **默认安全的注入防御** | 框架默认转义 | DB-API 参数化 | PreparedStatement | — | 参数化 | — |
| **安全随机数** | `crypto.randomBytes` | `secrets` | `SecureRandom` | `<random>` 无 CSPRNG | `RandomNumberGenerator` | — |
| **恒定时间比较** | `crypto.timingSafeEqual` | `hmac.compare_digest` | `MessageDigest.isEqual` | 需自己写 | `FixedTimeEquals` | — |
| **密码哈希（标准库）** | `crypto.scrypt` | `hashlib.pbkdf2_hmac` | `SecretKeyFactory` | 无 | `Rfc2898DeriveBytes` | — |
| **语言独有的坑** | 原型污染 | `pickle` 反序列化 | `ObjectInputStream` | UB 的整个类别 | `Random` 的命名误导 | 越权（IDOR） |
| **本章实测最大差距** | — | 密码哈希 **56.8 万倍** | 密码哈希 **233 万倍** | 边界检查 **2.21x→1.02x** | 时序 **12.9x** | — |

### 10.1 「默认安全」的差异有多大

同一个需求，六种语言的默认路径安全性差别巨大：

```python
# Python: 标准库的 DB-API 就是参数化的，f-string 拼 SQL 是【明显更麻烦】的路
con.execute("... WHERE name = ?", (name,))
```

```javascript
// React: {expr} 默认转义，要绕过必须显式写 dangerouslySetInnerHTML
<div>{userInput}</div>
```

```java
// Java: PreparedStatement 是标准，但 Statement + 字符串拼接同样是一行代码
stmt.executeQuery("... WHERE name = '" + name + "'");   // 一样容易写出来
```

**默认值决定了大多数代码的样子。**一个「安全用法更麻烦」的 API，一定会在某处被写成不安全的样子。

### 10.2 内存安全语言消灭了什么、没消灭什么

| 漏洞类别 | C/C++ | Java/C#/Python/JS |
|---|---|---|
| 缓冲区溢出 / UAF / 二次释放 | ⚠️ 存在 | ✅ **整类不存在** |
| 整数溢出 | ⚠️ 存在（UB） | ⚠️ **存在**（但不会变成内存破坏） |
| SQL 注入 / XSS / 命令注入 | ⚠️ 存在 | ⚠️ **一样存在** |
| 反序列化 | ⚠️ 存在 | ⚠️ **一样存在**（Java 尤甚） |
| 密码学误用 | ⚠️ 存在 | ⚠️ **一样存在** |
| 越权 / 认证缺陷 | ⚠️ 存在 | ⚠️ **一样存在** |

**约 70% 的高危 CVE 在第一行消失了，剩下六行一个都没少。**

## 11. 底层实现对比

| 机制 | JavaScript | Python | Java | C++ | C# |
|---|---|---|---|---|---|
| **越界访问** | 返回 `undefined` | 抛 `IndexError` | 抛异常 | **未定义行为** | 抛异常 |
| **整数溢出** | 变 `double`（精度丢失） | **自动大整数** | 静默回绕 | **有符号是 UB** | 静默回绕（`checked` 可选） |
| **CSPRNG 来源** | `getrandom`/`BCryptGenRandom` | 同左 | 同左 | 依赖平台 API | 同左 |
| **字符串** | 不可变，带长度 | 不可变，带长度 | 不可变，带长度 | `char*` **不带长度** | 不可变，带长度 |
| **反序列化默认** | `JSON.parse`（纯数据）✅ | `pickle`（可执行）⚠️ | `readObject`（可执行）⚠️ | 无标准 | `BinaryFormatter`（已废弃）⚠️ |

### 11.1 整数溢出的三种处理方式

```
Python:  自动升级为任意精度整数 —— 溢出【不存在】，代价是性能
Java/C#: 静默回绕到负数 —— 定义明确，但检查容易被绕过
C++:     有符号溢出是【未定义行为】—— 编译器可以假设它不发生，
         于是 if (a + b < a) 这种溢出检查【可能被优化掉】
```

最后一条特别值得注意：C++ 里手写的溢出检查**可能被编译器删除**，因为标准允许编译器假设 UB 不会发生。这正是第 57 章「你写的不是运行的」在安全领域的翻版。

### 11.2 为什么反序列化的默认值差别这么大

`JSON.parse` 只能产生**纯数据**（对象、数组、字符串、数字、布尔、null）——它没有能力构造任意类型的实例，更不会调用方法。

`pickle` / `ObjectInputStream` / `BinaryFormatter` 设计目标是**还原任意对象图**，这必然要求它们能构造任意类型、调用构造与回调方法。**能力越强，攻击面越大。**

> 这是一条通用的安全设计原则：**选择能力刚好够用的格式**。

## 12. 性能分析

安全与性能的关系在本章有两个方向，都值得量化。

### 12.1 安全措施的代价（越小越好）

| 措施 | 实测代价 |
|---|---|
| 参数化查询 | **负代价**（执行计划可复用，通常更快） |
| 数组边界检查（C++ `at()`） | -O0 **2.21x** / -O1 **1.05x** / -O2 **1.02x** |
| 输出编码（HTML 转义） | 可忽略（相比网络往返） |
| TLS 握手 | 一次约 1 个额外 RTT（会话复用后≈0） |
| ASan | 约 **2x**（所以只在 CI/测试开，不上生产） |

**边界检查那一行是本章最重要的性能结论**：它证明「安全太贵」这个论据在今天大多已经过期。

### 12.2 故意的慢（越大越好）

| 措施 | 实测 |
|---|---|
| SHA-256（Python） | 366 万次/秒 |
| SHA-256（Java） | 549 万次/秒 |
| PBKDF2 60 万轮（Python） | **6.4 次/秒**（差 **56.8 万倍**） |
| PBKDF2 60 万轮（Java） | **2.3 次/秒**（差 **233 万倍**） |
| 恒定时间比较（C#） | 453 ms vs 18 ms（**慢 24 倍**，但时序差从 12.9x → 0.99x） |

### 12.3 时序泄露的量化

| 语言 | 早不同 vs 晚不同 | 恒定时间版 |
|---|---|---|
| Java | 3.3 ms vs 19.5 ms（**5.9x**） | 1.05x |
| C# | 18.5 ms vs 237.4 ms（**12.9x**） | 0.99x |
| Python | **测不出**（被解释器开销淹没） | — |

Python 那一行是个诚实的失败，也是一课：**测不出来 ≠ 不存在**。攻击者可以发起百万次请求做统计，把噪声平均掉——**这是第 57 章「差距要大于波动」的反面：攻击者有办法把波动降下去。**

### 12.4 从这些数字里读出的三件事

**① 安全措施的代价被系统性高估了。** 参数化查询更快，边界检查在 -O2 下只有 2%，输出编码相比一次网络往返可以忽略。

**② 唯一昂贵的是密码哈希，而那正是它的目的。** 150 ms 的登录延迟换来 56 万倍的破解成本。

**③ 有一处安全与性能真正冲突：恒定时间比较。** 它必须放弃所有提前返回的优化。这也是全书唯一一处「必须写出更慢的代码」。

## 13. 工程实践

### 13.1 威胁建模：在写代码之前问四个问题

```
① 我们在保护什么？        （用户数据？资金？可用性？声誉？）
② 攻击者是谁？            （外部匿名？已登录用户？内部员工？供应链？）
③ 他们能碰到什么？        （攻击面：API、上传、依赖、运维通道）
④ 出事了会怎样？          （数据泄露规模？能否横向移动？能否篡改？）
```

第 ② 条最常被跳过。**大多数越权漏洞（IDOR）的攻击者是「一个已登录的普通用户」**——如果威胁模型里只有「外部黑客」，这类漏洞根本不会被想到。

### 13.2 把安全检查接进 CI

| 层次 | 工具 | 检查什么 |
|---|---|---|
| SAST | CodeQL、Semgrep、Bandit | 代码里的危险模式（字符串拼 SQL） |
| SCA | `npm audit`、Dependabot、Trivy | 依赖里的已知 CVE |
| Secret 扫描 | gitleaks、truffleHog | 提交进仓库的密钥 |
| 动态 | ZAP、Burp | 运行中的应用 |
| 运行时 | ASan/UBSan（C++） | 内存错误 |

关键设计（与第 52 章的测试、第 57 章的性能基准同理）：

- **必须能失败**：一个从不阻断合并的检查等于没有；
- **必须低误报**：误报率高的工具一周内就会被所有人忽略；
- **必须给出修复路径**，而不只是「发现漏洞」。

### 13.3 密钥管理

```
❌ 硬编码在代码里              → git 历史永远删不干净
❌ 明文写在环境变量里          → 进程列表、崩溃转储、日志都可能泄露
❌ 提交 .env 到仓库            → Secret 扫描的头号发现
✅ 密钥管理服务（Vault/KMS/Secrets Manager）
✅ 定期轮换，且【轮换流程要演练过】
```

最后一条常被忽略：一个从没演练过的轮换流程，在真正需要紧急轮换时（密钥泄露了）不会成功。

### 13.4 依赖与供应链

第 53 章实测过：一个 `create-react-app` 装出 1000+ 个传递依赖。**你审计了自己的 200 行代码，但运行的是几十万行别人的代码。**

`event-stream`（2018）是标志性案例：一个每周 200 万下载的包被转手给新维护者，新维护者植入了盗币代码。

防御是**依赖管理问题，不是代码审计问题**：

```
lockfile 锁死版本 + 完整性校验
最小依赖（每个依赖都要问「值不值」）
CI 里跑 SCA
关键依赖考虑 vendoring 或内部镜像
```

### 13.5 事件响应：假设已经发生了

```
① 检测：日志、告警、异常流量（没有日志就没有检测）
② 遏制：吊销密钥、隔离系统、下线受影响功能
③ 取证：审计日志能否回答「谁在什么时候访问了什么」（SQL 版 ⑤）
④ 修复：补漏洞，不只是清痕迹
⑤ 复盘：写下来，改流程，加自动化检查
```

第 ③ 步决定了前四步能不能做。**日志和审计要在事故发生之前就准备好**——这和第 52 章「测试要在 bug 出现之前写好」是同一个道理。

## 14. 最佳实践

- **永远用参数化查询**，不要拼接 SQL。动态标识符用白名单映射。
- **输出时按上下文编码**，不要在输入时「过滤危险字符」。
- **优先用结构化 API**（`textContent`、`execve` 数组、DOM API）而不是字符串拼接。
- **密码用 Argon2id/bcrypt/scrypt**，每个用户独立随机盐，绝不用 SHA/MD5 裸哈希。
- **安全相关的随机数一律用 CSPRNG**（`SecureRandom` / `secrets` / `RandomNumberGenerator`）。
- **比较密钥、令牌、签名一律用恒定时间函数**。
- **加密一律用 AEAD**（AES-GCM / ChaCha20-Poly1305），IV/nonce 每次随机且不重复。
- **授权检查放在每一次数据访问上**，不要只在路由入口检查一次。
- **数据库账号最小权限**，敏感列走视图，多租户用 RLS 兜底。
- **纵深防御**：CSP、HttpOnly、SameSite、SRI——假设第一道会失守。
- **C/C++ 里开满警告并当成错误**，CI 里常开 ASan/UBSan，用 `std::span`/容器代替裸指针。
- **依赖要锁版本、要扫描、要尽量少**。
- **安全检查接进 CI 且必须能阻断合并**。
- **密钥进密钥管理服务，轮换流程要演练过**。

## 15. 常见坑

### 坑 1：以为「转义就够了」

```python
name = user_input.replace("'", "''")
sql = f"SELECT ... WHERE id = {name}"      # ⚠️ 数值列，没有引号
```

**为什么错**：本章实测，输入 `1 OR 1=1` 转义前后完全相同，整张表被拖走。转义的前提是「值被引号包住」，而这个前提不写在任何地方。

**怎么避免**：参数化。它不产生「需要被正确转义的字符串」。

### 坑 2：用一个转义函数打所有上下文

```javascript
el.setAttribute('onclick', `f('${escapeHtml(name)}')`);
```

**为什么错**：事件处理属性会**先解码字符引用**再交给 JS 引擎，`&#39;` 变回 `'`，转义反而制造了漏洞（本章实测）。

**怎么避免**：按上下文选编码方式；更好的是**根本不构造这种字符串**——用 `addEventListener` 传函数。

### 坑 3：用 SHA-256 存密码

**为什么错**：本章实测 SHA-256 每秒 366 万次，PBKDF2 每秒 6.4 次——攻击者的成本差 **56.8 万倍**。

**怎么避免**：Argon2id / bcrypt / scrypt。存储格式要**自带算法与参数**，方便将来平滑升级迭代次数。

### 坑 4：用 `Random` 生成令牌

**为什么错**：本章实测同种子重放得到**完全相同**的序列。`java.util.Random` 状态只有 48 位，观察两个连续输出就能解出内部状态。

**怎么避免**：`SecureRandom` / `secrets` / `RandomNumberGenerator`。**判定标准：只要这个随机数与安全有关，就用 CSPRNG。**

### 坑 5：用 `==` 比较令牌

**为什么错**：本章实测第 1 字节不同 18.5 ms vs 第 32 字节不同 237.4 ms（12.9x）。这个差距把 32 字节令牌的爆破空间从 256³² 降到 8192。

**怎么避免**：恒定时间比较函数。

### 坑 6：只在入口做一次授权检查

```python
@require_login
def get_order(order_id):
    return db.query("SELECT * FROM orders WHERE id = ?", order_id)  # ⚠️ 参数化了，但没查归属
```

**为什么错**：本章 SQL 版实测——输入是合法数字 3，没有任何注入，参数化查询完全防不住。这是 OWASP Top 10 里长期排第一的**越权访问**。

**怎么避免**：每一次数据访问都带上归属条件；用 RLS 在数据库层兜底。

### 坑 7：加密了但没认证

**为什么错**：CBC 不保证完整性，攻击者可以精确翻转明文的位。

**怎么避免**：用 AEAD（AES-GCM / ChaCha20-Poly1305）。本章实测：篡改一个 bit，AES-GCM 解密直接抛异常。

### 坑 8：以为「换了内存安全的语言就安全了」

**为什么错**：内存安全消灭了约 70% 的高危 CVE，但注入、越权、密码学误用、反序列化——**一个都没少**。本章前六节讲的全是这后 30%。

**怎么避免**：把「换语言」当作消灭一类漏洞的手段，而不是安全工作的终点。

### 坑 9：把「测不出来」当成「不存在」

**为什么错**：本章 Python 版没能测出时序差（被解释器开销淹没），但那不代表漏洞不存在——攻击者可以发起百万次请求做统计。

**怎么避免**：安全判断基于**机制**（这段代码会不会提前返回），而不是基于**一次本地测量**。

## 16. 面试题

**Q1：参数化查询为什么能防 SQL 注入？它和「自动转义」有什么区别？**

A：参数化**不是转义**。它让 SQL 语句和数据走两条不同的通道：语句先被发送并解析成执行计划（此时 `?` 只是一个参数槽），参数值之后才被填进槽里——**第二步没有任何解析发生**。所以不存在「需要被正确转义的字符串」。本章实测：同样的恶意输入 `alice' OR '1'='1`，拼接版返回 3 行（整张表），参数化版返回 0 行，而两次执行的 SQL 字符串完全相同。附带收益是执行计划可复用，通常还更快。

**Q2：为什么说「手工转义」几乎必然失败？**

A：转义的正确性依赖一串没写下来的前提：值被引号包住、方言匹配、字符集一致、只转一次、每一处都记得调用。本章实测了第一条的失效——防御方给所有输入加了 `escape_quotes()`，但数值列的查询没有引号包住，输入 `1 OR 1=1` 转义前后完全相同，整张表被拖走。更根本的是**攻击者只需要找到一处遗漏，而防御方必须处处正确**。这就是为什么要优先选「默认安全」的机制。

**Q3：XSS 为什么不能用一个统一的转义函数？**

A：因为浏览器不是一个解析器，而是一串解析器（HTML → 属性解码 → JS/CSS/URL）。本章用同一个 `escapeHtml` 打三种上下文：HTML 文本 ✅ 有效；无引号属性 ❌ 失败（载荷里没有需要转义的字符）；事件处理属性 ❌ 失败——浏览器会**先解码字符引用**再交给 JS 引擎，`&#39;` 变回 `'` 闭合了字符串。另外 `<script>` 内部是原始文本，字符引用**不会**被解码，在那里做 HTML 转义是「损坏数据」而非「有漏洞」。根本解法是别拼字符串，用 `textContent`/`setAttribute` 这类结构化 API。

**Q4：密码哈希为什么要故意做慢？慢多少合适？**

A：攻击者拿到数据库后，破解的唯一成本就是每次 `hash()` 调用的代价。本章实测 SHA-256 每秒 366 万次，PBKDF2 60 万轮每秒 6.4 次——差 **56.8 万倍**。一本千万条的字典，前者几秒跑完，后者要几周。慢多少是**安全 vs 可用性**的权衡：登录接口也要付这个代价，所以 OWASP 会随硬件进步逐年上调建议值。更好的选择是 Argon2id/scrypt，它们还**故意吃内存**，让 GPU 的并行优势失效（PBKDF2 只吃 CPU，能被 GPU 大幅加速）。

**Q5：什么是时序攻击？为什么恒定时间比较能防？**

A：短路比较（一发现不同就返回）的耗时**正比于猜对的前缀长度**，于是攻击者可以逐字节爆破：把 32 字节令牌的空间从 256³² 降到 256×32 = 8192 次。本章 C# 版实测第 1 字节不同 18.5 ms vs 第 32 字节不同 237.4 ms（**12.9x**）。恒定时间比较**不提前返回，用位运算累积差异**，实测把差距压到 0.99x，代价是绝对耗时更高（453 ms vs 18 ms）——它永远做满全部工作。**这是全书唯一一处必须写出更慢的代码。**

**Q6：内存安全的语言解决了什么问题，没解决什么问题？**

A：解决了缓冲区溢出、use-after-free、二次释放这一整类——微软与 Chromium 各自统计约占高危 CVE 的 **70%**。没解决的是另外 30%：SQL 注入、XSS、越权、密码学误用、反序列化——这些**每种语言都一个不少**，本章前六节讲的全是它们。此外整数溢出在 Java/C# 里**依然存在**（只是不会变成内存破坏），经典形态是 `if (offset + len > size)` 的左边先溢出成负数导致检查被绕过。

**Q7：「C++ 不做边界检查是为了性能」——这个说法今天还成立吗？**

A：基本不成立了。本章实测 `at()` 相对 `[]` 的开销：**-O0 是 2.21x，-O1 降到 1.05x，-O2 只有 1.02x**。优化器能证明索引在范围内或把检查提到循环外，剩下的分支预测器几乎 100% 猜对。这个设计是 1980 年代的取舍，当时优化器远没有这么强。这也解释了 Rust 为什么敢默认检查还自称「零成本抽象」。而两者的真正区别是**失败时的行为**：`at()` 抛出可处理的异常，`[]` 是未定义行为——可能崩溃、可能返回垃圾、也可能**看起来一切正常**（最危险的一种：测试全绿，漏洞已经上线）。

**Q8：越权访问（IDOR）为什么参数化查询防不住？**

A：因为它**根本不是注入**。本章 SQL 版实测：租户 100 的用户请求 `GET /orders/3`（属于租户 200），输入是合法数字 3，没有任何特殊字符。只按 `id` 查返回 1 行（跨租户泄露），同时按 `tenant_id` 过滤返回 0 行。参数化、输入验证、WAF 全都防不住——**授权检查必须发生在每一次数据访问上**，不能只在路由入口检查一次。PostgreSQL 的行级安全（RLS）把这个约束下沉到数据库，应用忘写也不会漏。这类漏洞长期占据 OWASP Top 10 第一位，恰恰因为它不需要任何「攻击技巧」。

## 17. 练习

### 练习 1：复现并修复一次注入（基础）

用你熟悉的语言写一个最小的登录查询，先用字符串拼接实现，构造输入让它返回全部用户；再改成参数化，确认同样的输入返回 0 行。

**要求**：打印出**两次实际执行的 SQL 字符串**——参数化那次应该完全没有变化。这一步是理解「两条通道」的关键。

### 练习 2：给三种上下文各写一个正确的编码函数（进阶）

为 HTML 文本、带引号属性、JS 字符串各写一个编码函数，然后：

1. 用同一个载荷 `'"><script>alert(1)</script>` 测试三个函数；
2. 把每个函数用在**错误的**上下文里，说明会发生什么；
3. 解释为什么「无引号属性」这一栏你写不出安全的实现。

### 练习 3：测量你的密码哈希参数（实战）

在你的生产硬件上：

1. 测出 Argon2id/bcrypt/PBKDF2 在当前参数下的单次耗时；
2. 计算你的登录接口能承受的 QPS；
3. 反推：以这个速率，攻击者跑完一本一千万条的字典要多久？
4. 对照 OWASP 的当前建议值，判断你的参数是否需要上调。

**这道题的价值在第 3 步**——把「安全」变成一个可以讨论的数字。

### 练习 4：找出一处越权（实战）

在你正在做的项目里：

1. 列出所有接受资源 ID 的接口；
2. 对每一个，问：如果换成另一个租户/用户的 ID 会怎样？
3. 实际测试其中三个；
4. 对发现的问题，评估「在数据库层用 RLS 兜底」是否可行。

**这道题通常比前三道找出更多真实问题。**

### 练习 5：给项目接一条安全流水线（实战）

选一个仓库，接入 SAST + SCA + secret 扫描：

1. 跑第一次，记录发现数与**误报数**；
2. 调整规则直到误报率可接受；
3. 设置为**阻断合并**；
4. 故意提交一处字符串拼 SQL，确认能被拦住；
5. 故意提交一处无关改动，确认不会误报。

第 5 步最容易被跳过——**一个会误报的安全检查，一周之内就会被所有人加上 `# noqa`。**

## 18. 本章总结

**核心结论**：安全漏洞是一类**不会让测试变红**的错误。注入类漏洞全都是同一个根因——**把不可信数据交给了一个会解析它的东西**；所有防御的共同形状是——**别拼字符串，用结构化接口**。

**关键实测数据**：

| 发现 | 数据 |
|---|---|
| SQL 注入 | 拼接版返回 **3 行（整张表）**，参数化版返回 **0 行** |
| 手工转义的绕过 | 数值列无引号，`1 OR 1=1` 转义前后**完全相同** |
| XSS 三上下文 | HTML 文本 ✅ / 无引号属性 ❌ / 事件处理属性 ❌（双重解码） |
| 密码哈希（Python） | SHA-256 366 万/秒 vs PBKDF2 6.4/秒（**56.8 万倍**） |
| 密码哈希（Java） | SHA-256 549 万/秒 vs PBKDF2 2.3/秒（**233 万倍**） |
| 时序泄露（C#） | 18.5 ms vs 237.4 ms（**12.9x**），恒定时间版 0.99x |
| 时序泄露（Java） | 3.3 ms vs 19.5 ms（**5.9x**），恒定时间版 1.05x |
| 整数溢出 | 10.7 亿 × 4 字节 → 实际分配 **4 字节** |
| 有符号长度 | `-1 > 64` 检查**放行**，memcpy 收到 18446744073709551615 |
| 边界检查代价 | -O0 **2.21x** → -O1 **1.05x** → -O2 **1.02x** |
| ECB 泄露 | 相同明文块 → **相同密文块**（第 1 块 = 第 3 块） |
| 固定 IV | 相同明文 → **完全相同的密文**，前缀差异可被二分定位 |
| `Random` 可预测 | 同种子重放序列**完全一致** |
| 越权（IDOR） | 合法数字 3，无任何注入，**参数化完全防不住** |

**三条能带走的原则**：

```
① 注入的统一形状：把不可信数据交给了一个会解析它的东西
   → 防御的统一形状：别拼字符串，用结构化接口

② 默认安全 > 正确使用才安全
   → 攻击者只需找到一处遗漏，防御方必须处处正确

③ 纵深防御：假设第一道会失守
   → 安全设计的问题不是「会不会出错」，而是「出错时代价有多大」
```

**本章与第 57 章的三处冲突**：

| | 第 57 章（性能） | 第 58 章（安全） |
|---|---|---|
| 哈希 | 越快越好 | **密码哈希越慢越好**（56.8 万倍） |
| 比较 | 尽早返回 | **拒绝提前返回**（恒定时间） |
| 检查 | 能省则省 | **边界检查要留**（且代价已降到 1.02x） |

**自查清单**：

- [ ] 我能解释参数化查询为什么不是「自动转义」。
- [ ] 我知道手工转义失败的至少三个原因。
- [ ] 我能为 HTML 文本、属性、JS 字符串各选出正确的编码方式。
- [ ] 我知道密码哈希为什么故意做慢，并能量化这个差距。
- [ ] 我知道什么时候必须用恒定时间比较，以及它为什么更慢。
- [ ] 我能说清内存安全消灭了哪一类漏洞、没消灭哪一类。
- [ ] 我知道越权（IDOR）为什么参数化防不住，以及 RLS 怎么兜底。
- [ ] 我会用「第一道防线失守后还剩什么」评估一个系统。
- [ ] 我知道安全 bug 在功能测试里 100% 通过，所以需要专门的检查手段。

**下一章预告**：代码写完了、测过了、优化过了、也加固过了——但它还在你的机器上。第 59 章讲**部署**：我们会实测同一份代码在六种语言里从源码到「能在别人机器上跑起来」需要带走什么（这直接决定了容器镜像的大小与启动速度），量化不可变基础设施与配置漂移的差别，复现「在我机器上是好的」这句话背后的三种具体成因，并说清蓝绿、金丝雀、滚动发布各自在**回滚速度**与**资源成本**上的实际代价。这是全书最后一章——它把前 58 章造出来的东西，真正交到用户手里。
