# 第 59 章 · 部署

**简体中文** ｜ [English](./59-deployment.en-US.md)

---

> 这是全书最后一章。前面 58 章造出了一个东西——它类型正确、并发安全、事务一致、测试覆盖、性能达标、漏洞加固。但它还在你的机器上。**这一章负责把它交出去。**
>
> 本章的**钥匙实验**回答一个从没被认真量化过的问题：**「运行它」到底需要带走什么？**同一份「跑一个循环并打印结果」的程序，六种语言的交付物差别是这样的：C++ 产物 **74 KB**；Node 需要一个 **106.5 MB** 的二进制；Python 需要 **50 MB / 1,637 个文件**的标准库；而 JVM 需要 **309 MB / 455 个文件**——其中你自己写的代码只有 **9,759 字节**。**比例是 1 : 33,212，交付物里 0.003% 才是你写的东西。**
>
> 这个比例直接解释了容器时代的一条经验：**基础镜像的选择比业务代码的优化更影响镜像大小**。你把代码从 1 MB 优化到 0.5 MB 毫无意义，而把基础镜像从 `openjdk` 换成 `eclipse-temurin:17-jre-alpine` 能省掉一半。
>
> 第二个被系统性忽略的变量是**启动时间**。实测「进入 main() 之前已经花掉多少」：C++ **1.23 ms**（exec + 动态链接）、Node **7.4 ms**、JVM **28 ms**、.NET **20 ms**。**在长驻服务里这笔钱可以忽略——它被摊薄到几个月的运行时间上；但在 Serverless、CLI、扩容时刻，它就是用户直接感受到的延迟。**判据只有一个：**你的进程启动多少次。**启动一次跑三个月，和每秒启动一百次，答案完全不同。
>
> .NET 的四种发布模式把这笔账算得最清楚（对同一份代码实测）：框架依赖 **1 MB / 5 个文件 / 20.0 ms**，自包含 **77 MB / 187 个文件 / 20.0 ms**，自包含+裁剪 **19 MB / 34 个文件 / 19.9 ms**，Native AOT **15 MB / 4 个文件 / 3.3 ms**。**前三种模式的启动时间几乎完全一样**——自包含和裁剪解决的是可移植性与体积，**不解决启动速度**；只有 AOT 把启动降到 3.3 ms（快 6 倍），因为它没有 CLR 要加载、没有 JIT 要跑。代价写在最后一列：**放弃反射和动态加载**。第 30 章的账单在这里结清。
>
> 第三个发现来自一个刻意设计的对照实验：**总字节数完全相同，只改文件个数**。一个 8 MB 的文件复制耗时 **4.0 ms**；4000 个 2 KB 的文件复制耗时 **319.0 ms——慢 79 倍**。字节数一模一样，慢的部分**全是每个文件的元数据开销**。这就是为什么 Node 生产部署普遍要打包：**打包的意义不是「体积更小」，而是「文件数量少了几个数量级」。**
>
> 最后是那个唯一**无法回滚**的部分：数据库。代码回滚只是换回旧产物，而 `DROP COLUMN` 之后数据已经没了、大表 `ALTER` 回滚也要跑几十分钟、回滚脚本几乎从不被测试——**需要它的时候是你第一次运行它**。所以真正的策略不是「写好回滚脚本」，而是**让变更不需要回滚**：扩展-收缩模式把一次列重命名拆成**四次发布**，每一次的前后两个状态都能同时服务新旧代码。
>
> 一句话概括本章：**部署的全部工作，是减少交付物对环境的假设——假设越少，能跑起来的地方越多，「在我机器上是好的」出现的概率就越低。**

## 1. 学习目标

学完本章，你将能够：

- 说清六种语言**「运行它需要带走什么」**的差别，以及这如何决定镜像大小与构建速度；
- 量化**启动时间**在不同部署形态下的意义，并用「启动次数」作为选型判据；
- 解释**「在我机器上是好的」**的三类具体成因，并逐类给出防御手段；
- 区分**可变基础设施与不可变基础设施**，并说清配置漂移为什么难以察觉；
- 比较**重建/滚动/蓝绿/金丝雀**在回滚速度与资源成本上的取舍；
- 用**扩展-收缩模式**设计一次不需要回滚的数据库变更；
- 说清可观测性三根支柱各自回答什么问题，以及为什么缺一根就无法判断发布是否成功。

## 2. 为什么会出现这个概念

### 2.1 部署是「假设」的对账

一个程序在你机器上能跑，是因为一大堆假设**恰好都成立**：

```
装了对的运行时版本          装了对的系统库
环境变量都设好了            时区是你预期的那个
数据库 schema 是新的        配置文件在你以为的路径
有网络能访问依赖的服务       文件系统可写
CPU 架构一致                字符编码一致
```

这些假设**没有一条写在代码里**。部署的全部工作，就是把这份隐式清单变成显式的、可复现的、能在别人机器上成立的东西。

**「在我机器上是好的」不是一句玩笑，它是一份没写下来的假设清单的名字。**

### 2.2 交付物的边界在哪里

不同语言对「交付物」的定义差别巨大，这直接决定了部署的难度：

| 语言 | 交付物包含 | 依赖目标机器提供 |
|---|---|---|
| C++ | 一个可执行文件（74 KB 实测） | libc、libstdc++、系统库 |
| Java | jar（KB 级） | **整个 JVM（309 MB 实测）** |
| C# | dll（1 MB 实测） | .NET 运行时（74 MB 实测） |
| Python | .py 源码 | **解释器 + 标准库（50 MB 实测）+ 所有第三方包** |
| Node | .js 源码 | **node 二进制（106.5 MB 实测）+ node_modules** |
| Go/Rust | 一个静态二进制 | （几乎什么都不需要） |

注意 C++ 那一行的反直觉之处：**产物最小，但它并不自包含**。实测本章的 C++ 示例依赖：

```
/usr/lib/libc++.1.dylib
/usr/lib/libSystem.B.dylib
```

这些库**不在交付物里**，必须由目标机器提供——缺一个、或版本对不上，程序就启动失败或行为不同。

**容器解决的正是这件事**：镜像 = 应用 + 它需要的整个用户态环境。它把「必须由目标机器提供」的东西变成了交付物的一部分。

### 2.3 三类「在我机器上是好的」

本章把这句话拆成三类可分别防御的成因：

**① 运行时/工具链不匹配**——最容易发现的一类，因为它通常**启动就失败**：

```
用 JDK 17 编译、拿 JDK 11 运行 → UnsupportedClassVersionError
x86 上编译的二进制拿到 ARM 上  → exec format error
在 macOS 上 npm install 含原生模块的包，拷进 Linux 容器 → 直接崩
```

**② 隐式的环境依赖**——最危险的一类，因为它**不报错，只是结果不同**：

```
file.encoding 不同 → 中文乱码，且只在某些环境
时区不同           → 所有日期逻辑的边界都变了（开发机 Asia/Shanghai，容器默认 UTC）
locale 不同        → "I".toLowerCase() 在土耳其 locale 下不是 "i"
```

**③ 外部状态**——最难的一类，因为它**不在你的交付物里**：

```
数据库 schema 版本、配置中心的值、依赖服务的版本、DNS、时钟、证书有效期
```

第 ③ 类正是本章 SQL 版整节要解决的问题。

### 2.4 不可变基础设施：把运维问题变成构建问题

**可变的做法**：ssh 上去 `apt install`、改配置、打补丁。后果是每台机器的状态由**「历史上执行过的所有命令」**决定。几个月后没有人能说清任意两台机器有什么区别——这就是**配置漂移**。

它的典型症状你一定见过：

```
「重启那台机器就好了」
「只有 3 号机有问题」
「我不知道为什么，但把它踢出集群就恢复了」
```

**不可变的做法**：要改就重新构建一个镜像，然后**替换整台机器**。机器的状态**完全由构建产物决定**，与它的历史无关。回滚 = 换回上一个镜像，而不是「把改动反着做一遍」。

> 关键洞察：**不可变基础设施把「运维」问题变成了「构建」问题**——而构建问题是可以版本化、可复现、可测试的（第 54 章）。

## 3. 底层原理

### 3.1 启动时间由什么构成

```
exec()                         ← 内核加载可执行文件
动态链接器解析符号              ← C++ 到此结束（实测 1.23 ms）
初始化语言运行时                ← JVM/CLR/V8 在这里
  ├─ 分配并初始化堆
  ├─ 加载核心类库/内置模块
  └─ JIT 编译启动路径上的代码
执行用户代码的顶层/静态初始化    ← Python 的 import 在这里
进入 main()
```

每一层的代价在本章都有实测：

| 语言 | 进入用户代码前 | 主要开销 |
|---|---|---|
| C++ | **1.23 ms** | exec + 动态链接 |
| Node | **7.4 ms** | 初始化 V8、建立事件循环 |
| .NET | **20.0 ms** | 加载 CLR、JIT 启动路径、初始化 GC 堆 |
| JVM | **28 ms** | 加载 JVM、类加载、JIT |
| .NET AOT | **3.3 ms** | 没有 CLR，没有 JIT |

**这笔开销的性质是「固定成本」**：它不随请求量变化，只随**进程启动次数**变化。

```
长驻服务:   启动一次跑三个月  → 28 ms 分摊到 90 天 = 完全可忽略
CLI 工具:   每次调用启动一次  → 28 ms 是用户每次都感受到的延迟
Serverless: 冷启动           → 28 ms 加上镜像拉取，可能是几百 ms
自动扩容:   突发流量时批量启动 → 启动慢意味着扩容跟不上流量
```

### 3.2 为什么文件数量比体积更重要

本章设计了一个纯净的对照实验：**总字节数完全相同，只改文件个数**。

```javascript
// 8 MB，一个文件  vs  8 MB，4000 个文件
```

```
1 个 8 MB 的文件    → 复制耗时   4.0 ms
4000 个 2 KB 的文件 → 复制耗时 319.0 ms（慢 79x）
```

字节数一模一样，慢的部分**全是每个文件的元数据开销**（`open`/`write`/`close`、目录项更新、inode 分配）。

这解释了三件事：

1. **容器构建慢**：`COPY node_modules` 复制几十万个小文件，比复制一个大文件慢得多；
2. **冷启动慢**：每个 `require()`/`import` 都是一次文件系统查找；
3. **打包的真正意义**：`esbuild`/`webpack`/`ncc` 把几万个文件变成一个——**不是「体积更小」，而是「文件数量少了几个数量级」**。

### 3.3 镜像分层：按变化频率切分

容器镜像是分层的，每一层是一个只读的文件系统差分。**上层变了，下层不用重传**。

一个典型 Java 镜像的分层（从下到上，变化频率递增）：

```
① 基础 OS         ~50 MB   几个月变一次
② JRE            ~200 MB   几个月变一次
③ 第三方依赖 jar   ~50 MB   几周变一次
④ 你的业务代码      ~1 MB   【每天变几十次】
```

如果打成一个 fat jar，改一行代码就要重传**全部 300 MB**。分层之后只重传第 ④ 层的 1 MB。

> 通用原则：**按变化频率分层，稳定的在下，易变的在上。**这和第 54 章的增量构建是同一个思路：**让不变的部分不必重做**。

Dockerfile 里最常见的体现：

```dockerfile
COPY package.json package-lock.json ./   # 变化少
RUN npm ci                               # 依赖层，被缓存
COPY . .                                 # 变化多，放最后
```

反过来写（先 `COPY . .` 再 `npm ci`）会让**每次代码改动都重装全部依赖**。

### 3.4 动态能力与提前编译的根本冲突

本章 C# 版实测的四种发布模式，最后一列揭示了一个贯穿全书的权衡：

```
框架依赖    → 需要目标机装了对应运行时
自包含      → 什么都不用装
自包含+裁剪  → 反射需显式配置
Native AOT  → 放弃反射/动态加载
```

**每一档更好的启动速度，都在放弃一部分动态能力。**

原因是：裁剪和 AOT 都需要**静态分析出「哪些代码会被用到」**。而反射（第 30 章）、动态类加载、运行时代码生成让这个分析**在原理上不可能完成**：

```csharp
Type.GetType(configValue).GetMethod(anotherConfigValue).Invoke(...)
```

编译器无法知道 `configValue` 运行时是什么。所以它只有两个选择：保守地全部保留（裁剪失效），或者要求你**显式声明**（配置文件列出所有反射用到的类型）。

> 这是第 30 章那笔账在部署阶段结清：**运行时越动态，越难提前编译。**

同样的冲突在 Java 侧表现为 `jlink` 裁剪与 GraalVM 原生镜像的反射配置问题——本章 Java 版也实测了模块数（JDK 提供 70 个，本进程解析 62 个）。

### 3.5 发布策略：回滚速度是用资源换来的

| 策略 | 资源 | 停机 | 回滚速度 | 适用 |
|---|---|---|---|---|
| 重建部署 | 1x | 有停机 | 快（重来一次） | 内部工具 |
| 滚动发布 | 1.2x | 无停机 | 慢（要滚回去） | 默认选择 |
| 蓝绿部署 | **2x** | 无停机 | **最快，切流量即可** | 关键系统 |
| 金丝雀发布 | 1.1x | 无停机 | 快（先切 1% 回来） | 高风险变更 |

**核心权衡：回滚速度是用资源换来的。**蓝绿最快，因为它一直养着另一套完整环境。

**金丝雀的独特价值不是回滚快**，而是**故障只影响 1% 的用户**——它把「回滚快慢」问题降级成了「影响面大小」问题。

⚠️ **但所有这些策略都有一个共同前提：新旧版本能同时运行。**

滚动发布期间，集群里同时有 v1 和 v2 的实例；蓝绿切换的瞬间也有短暂重叠；金丝雀更是**长时间**并存。这个前提一旦被打破——最常见的打破方式就是**数据库 schema 变更**——所有策略同时失效。

### 3.6 扩展-收缩：让变更不需要回滚

代码回滚只是换回旧产物。数据库回滚**没有这么便宜**：

```
ⓐ DROP COLUMN 之后，那一列的数据【已经没了】，回滚只能恢复结构，恢复不了内容
ⓑ 大表上的 ALTER 可能跑几十分钟，回滚也要同样久（期间系统处于中间状态）
ⓒ 回滚脚本几乎从不被测试 —— 需要它的时候是你第一次运行它
```

所以真正的策略不是「写好回滚脚本」，而是**让变更不需要回滚**：每一步都同时兼容新旧两个版本的应用代码。

把 `users.name` 改名为 `users.full_name`，安全做法是**四次发布**：

```
发布 1【扩展】 ALTER TABLE users ADD COLUMN full_name TEXT;   -- 可空，旧代码看不见
发布 2【双写】 新代码同时写 name 和 full_name，并回填历史数据
发布 3【切读】 新代码改为只读 full_name（仍然双写，保证可回滚到发布 2）
发布 4【收缩】 确认没有代码再用 name，才 DROP COLUMN name
```

**四次发布，每一次的前后两个状态都能同时服务新旧代码。**代价是慢（要等几个发布周期），收益是**任何一步都可以停下来或回退**。

这个模式适用于一切破坏性变更：改列名、改类型、拆表、改约束。

## 4. JavaScript

Node 版关心的是「几万个小文件」对部署意味着什么。

### 4.1 启动时间

```javascript
// ⚠️ 必须在最前面读: process.uptime() 是「Node 进程启动到现在」的秒数
const startupMs = process.uptime() * 1000;
```

```
Node 启动 → 执行到本文件第 1 行: 7.4 ms
一段 500 万次循环的业务代码:     18.8 ms
```

这段启动时间用来初始化 V8、建立事件循环（第 43 章）、加载内置模块。

### 4.2 运行时：一个 106.5 MB 的二进制

```
process.execPath = .../bin/node
node 可执行文件: 106.5 MB（单个文件，V8 都在里面）
内置模块数量: 68
```

与 Java 版对照：**JVM 运行时是几百个文件、309 MB；node 是一个 106.5 MB 的二进制**。

- 单文件的好处：分发简单，没有「装错版本的运行时」问题；
- 单文件的代价：**无法裁剪**——你用不到的模块也在里面。

### 4.3 文件数量的实测代价

```
1 个 8 MB 的文件    → 复制耗时   4.0 ms
4000 个 2 KB 的文件 → 复制耗时 319.0 ms（慢 79x）
```

> 打包在部署里的意义**不是「体积更小」，而是「文件数量少了几个数量级」**。

### 4.4 Node 的三类「在我机器上是好的」

```
成因一【原生模块】: 含 C++ 扩展的包按本机 ABI 编译
   在 macOS 上 npm install，把 node_modules 拷进 Linux 容器 → 直接崩
   这也是 .dockerignore 必须包含 node_modules 的原因
成因二【lockfile 没用上】: npm install 会按 semver 范围重新解析
   必须用 npm ci（第 53 章）
成因三【隐式全局状态】: 环境变量、时区、locale、可写的临时目录
   实测当前时区 Asia/Shanghai，容器里默认通常是 UTC —— 所有日期逻辑都会变
```

### 4.5 健康检查：三种探针为什么要分开

```
liveness（活着吗）:  挂了就重启。检查项要尽量少——
   如果 liveness 依赖数据库，数据库抖一下会让全部实例被同时重启
readiness（能收流量吗）: 依赖没就绪就先不发流量，但不要重启
startup（还在启动吗）: 给慢启动的应用一个宽限期，避免被 liveness 误杀
```

**把它们混成一个，会让「依赖抖动」升级成「集体重启」。**

优雅关闭同样关键：

```
收到 SIGTERM → readiness 立刻置为 false → 等在途请求处理完 → 退出
```

少了这一步，**每次发布都会丢掉一批请求**。

## 5. Python

Python 版关心的是「依赖在部署那一刻才被解析」。

### 5.1 交付物

```
标准库目录: .../lib/python3.9
  50 MB / 1,637 个文件
解释器可执行文件: 0.1 MB
```

Python 的运行时是**一个小可执行文件 + 一大堆 .py 源码**。后果：容器里光是标准库就要复制 1,637 个文件，加上第三方包就是几万个——和 Node 版 ③ 实测的同一个问题。

### 5.2 导入成本：每次启动都要重新付

```
import json                        2.3 ms
import sqlite3                     2.4 ms
import email                       0.4 ms
import unittest                    6.1 ms
import xml.etree.ElementTree       4.0 ms
五个标准库模块合计: 15.4 ms
```

Python 的 `import` 是**运行时行为**：查找文件 → 编译成字节码 → 执行模块顶层代码。`.pyc` 缓存能省掉编译，但**查找与执行仍在每次启动时发生**。

所以 Python 服务的冷启动优化，第一刀往往是**砍 import**（尤其是顶层的重依赖）。

### 5.3 依赖锁定：可复现构建的最小要求

| 做法 | 结果 | 判定 |
|---|---|---|
| `flask>=2.0` | 今天 2.3.3，下月 2.4.0 | ❌ 不可复现 |
| `flask==2.3.3` | 总是 2.3.3 | ⚠️ 但它的**依赖**仍未锁 |
| `pip freeze` 全量锁定 | 整棵依赖树都固定 | ✅ 可复现 |
| 再加 `--require-hashes` | 内容也被校验 | ✅ 可复现 + 抗篡改 |

第二行是最常见的误解：**锁住直接依赖不等于锁住传递依赖**。第四行防的是第 58 章讲的供应链攻击：**版本号对了，内容也可能被换过**。

### 5.4 配置：三种做法与它们的失败模式

```
ⓐ 硬编码在代码里    → 每个环境一份代码，必然出现「测试环境是对的」
ⓑ 配置文件随镜像打包 → 同一份代码，但每个环境一个镜像 = 测过的不是发出去的
ⓒ 环境变量/配置中心 → 构建一次，到处部署，测过的产物就是发出去的产物
```

**ⓑ 的问题很隐蔽**：它看起来「配置和代码分开了」，但只要产物里含环境信息，你在预发环境测的就**不是**要上生产的那个产物。

> 判据：**同一个构建产物能否原封不动地跑在所有环境。**

## 6. Java

Java 版把「交付物里有多少不是你写的代码」量化到了极致。

### 6.1 启动时间

```java
long beforeMain = ManagementFactory.getRuntimeMXBean().getUptime();
```

```
JVM 启动 → 进入 main(): 28.0 ms
一段 500 万次循环的业务代码: 4.5 ms
```

**还没执行任何业务逻辑，就已经花了 28 ms**——而真正的业务代码只用了 4.5 ms。

### 6.2 1 : 33,212

```
运行时总大小: 324,118,808 字节（309 MB，455 个文件）
你的业务代码（本例编译产物）: 9,759 字节
→ 比例 1 : 33,212 —— 交付物里【0.0030% 才是你写的代码】
```

这就是「基础镜像选择比业务代码优化更影响镜像大小」的实测依据。

### 6.3 模块化：打包的远多于用到的

```
JDK 提供的模块总数: 70
本进程实际解析到的模块: 62
本例真正用到的: java.base, java.management（另加启动时默认解析的若干个）
```

`jlink` 可以按实际用到的模块裁剪运行时。但注意：**裁剪是构建期决定的，运行时才发现少了模块就来不及了**。而反射加载（第 30 章）会让「用到了哪些模块」**无法被静态分析出来**——这是 AOT / 裁剪 / 原生镜像共同的难点。

### 6.4 环境依赖

```
file.encoding    = UTF-8
java.version     = 17.0.18
os.arch          = aarch64
user.timezone / user.language / java.vendor ...
```

三类成因：

- **运行时版本**：用 17 编译、拿 11 运行 → `UnsupportedClassVersionError`。好消息是它**启动就失败**；
- **隐式环境依赖**：`file.encoding` / 时区 / locale——**不报错，只让结果悄悄不同**；
- **外部状态**：数据库 schema、配置、路径、时钟、DNS——**不在你的交付物里**。

> 防御：**显式声明一切**（JDK 版本、编码、时区），别依赖默认值。

### 6.5 四种交付形态

```
ⓐ jar + 系统 JRE:   产物最小（几 MB），但依赖目标机器装了对的 JRE
ⓑ fat jar / 容器:    自带全部依赖，可复现；镜像几百 MB
ⓒ jlink 定制运行时:  裁剪后几十 MB，启动略快
ⓓ GraalVM 原生镜像:  启动降到毫秒级、内存占用大降，
   代价是构建慢、反射需显式配置、失去 JIT 的峰值性能（第 57 章）
```

> 判据是**启动次数**：启动一次跑三个月，和每秒启动一百次，答案完全不同。

## 7. C++

C++ 版的主题是：**产物最小，但它并不自包含**。

### 7.1 74 KB vs 309 MB

```
本程序大小: 74,312 字节（0.07 MB）
```

对照：JVM 运行时约 309 MB、node 二进制约 106.5 MB、Python 标准库约 50 MB。**C++ 的产物小两三个数量级——因为它没有把运行时带上。**

### 7.2 但它依赖目标机器

```
/usr/lib/libc++.1.dylib (compatibility version 1.0.0, current version 1900.180.0)
/usr/lib/libSystem.B.dylib (compatibility version 1.0.0, current version 1351.0.0)
```

这些库**不在交付物里**。静态链接可以把它们打进来（产物变大、更新库要重新编译整个程序），但 glibc 静态链接有已知问题（NSS/dlopen），**musl 才是常见解法**。

### 7.3 编译期烙进二进制的东西

```
目标架构     = aarch64
操作系统     = macOS
C++ 标准     = 202002
标准库       = libc++ 190102
编译器       = clang 17.0
指针宽度     = 64 位
优化         = 开启
断言(NDEBUG) = 仍开启
```

**上面每一行都是构建时决定、运行时无法更改的。**

「在我机器上是好的」在 C++ 里最常见的成因就是这张表对不上：换了架构（x86 → ARM）、换了 libc（glibc → musl）、换了标准库 ABI（`_GLIBCXX_USE_CXX11_ABI` 那次著名的分裂）。

> 所以 C++ 的可复现构建必须**锁定工具链本身**，而不只是锁定依赖版本。

### 7.4 启动开销：1.23 ms

```
启动本程序并立即退出 30 次，平均: 2.04 ms/次
同样次数的 shell 内建 true（基线）:  1.81 ms/次
→ 差值 1.23 ms 就是【exec + 动态链接 + 退出】的成本
```

（差值随运行波动，多次测量在 0.2–1.3 ms 之间。）

对照本章其他语言：JVM 28 ms、Node 7.4 ms、.NET 20 ms。**这就是 CLI 工具和 Serverless 偏爱 C++/Go/Rust 的原因**，也是 GraalVM 原生镜像、.NET AOT 想要达到的目标。

### 7.5 容器为什么解决了 C++ 的部署问题

容器镜像 = **应用 + 它需要的整个用户态环境**（libc、libstdc++、证书、时区库）。它把 7.2 里那些「必须由目标机器提供」的东西变成了交付物的一部分。

多阶段构建是标准做法：

```dockerfile
FROM gcc AS build
...
FROM debian-slim          # 只 COPY 出二进制
```

极端做法是 `FROM scratch`（静态链接，镜像只有几 MB），代价是**没有 shell、没有证书、没有时区库——出事时无法进去看**。

> 又一个熟悉的权衡：**最小化与可诊断性是对立的。**

## 8. C#

C# 版把「发布模式」这笔账算得最清楚——对**同一份代码**实测四种模式。

### 8.1 四种发布模式（实测）

| 模式 | 产物 | 文件数 | 进入 Main() | 前提 |
|---|---|---|---|---|
| 框架依赖（默认） | 1 MB | 5 | 20.0 ms | 目标机装了对应 .NET |
| 自包含 | **77 MB** | 187 | 20.0 ms | 什么都不用装 |
| 自包含 + 裁剪 | 19 MB | 34 | 19.9 ms | 反射需显式配置 |
| **Native AOT** | 15 MB | **4** | **3.3 ms** | 放弃反射/动态加载 |

```bash
dotnet publish -c Release -r osx-arm64 \
  [--self-contained] [-p:PublishTrimmed=true] [-p:PublishAot=true]
```

**三个读法**：

**① 前三种模式的启动时间几乎完全一样**（都是 20 ms）——自包含和裁剪解决的是**可移植性与体积**，**不解决启动速度**。这一点最容易被误解。

**② 只有 AOT 把启动降到 3.3 ms（快 6 倍）**，因为它没有 CLR 要加载、没有 JIT 要跑。

**③ 裁剪把 77 MB 压到 19 MB（省 75%）**，文件数从 187 降到 4——后者对容器构建速度的意义可能比前者更大（见 3.2 节实测的 79 倍）。

### 8.2 运行时占比

```
应用输出目录: 146 KB / 5 个文件
共享框架目录: 74 MB / 184 个文件
→ 比例 1 : 517 —— 和 Java 版是同一个量级的结论
```

### 8.3 按需加载：少了 DLL 可能很久才发现

```
本进程已加载程序集: 11 个
```

.NET 的程序集是**按需加载**的（和第 30 章的反射同源）。后果：少了一个 DLL，可能**跑到那条代码路径时才崩**——一个只在月底结算时才走到的分支，能藏住这个问题一个月。

> 防御：部署后跑一遍冒烟测试，覆盖所有**会加载新程序集**的路径。

### 8.4 配置：一个常见的伪解法

```
配置优先级: 命令行 > 环境变量 > 配置文件 > 默认值
```

⚠️ **「构建时按环境替换配置文件」是个伪解法**——它看起来做到了配置分离，实际上产生了 N 个**互不相同的产物**，于是你在预发测的产物 ≠ 你发到生产的产物。

### 8.5 可观测性三根支柱

```
日志(Logs):    离散事件。回答「那一刻发生了什么」
指标(Metrics): 聚合数值。回答「现在整体健康吗」，成本低、可长期保留
链路(Traces):  一次请求的完整路径。回答「慢在哪一跳」
```

> 三者的关系：**指标告诉你出事了，链路告诉你在哪，日志告诉你为什么。**

部署与可观测性是一件事的两面：**没有可观测性，你无法判断发布是否成功**——而判断不了成功与否，**金丝雀发布就失去了全部意义**。

## 9. SQL

数据库是唯一**无法回滚**的那一部分。

### 9.1 迁移的最小机制

```sql
CREATE TABLE schema_migrations(version TEXT PRIMARY KEY, applied_at TEXT, checksum TEXT);
```

```
已应用 001_create_users @ 2026-08-01T10:00:00
已应用 002_add_email    @ 2026-08-05T14:30:00
```

迁移状态由**数据库自己记录**，而不是由「谁记得跑过」决定。部署时工具比对「文件里有哪些迁移」与「表里记了哪些」，只跑差集。

`checksum` 的作用是检测**已应用的迁移文件被改动过**——那意味着开发机和生产库的 schema 已经悄悄分叉了。

> 这和第 53 章的 lockfile 是同一个思路：**把「当前状态」变成可校验的事实**。

### 9.2 扩展-收缩：一次重命名，四次发布

```sql
-- ❌ 危险
ALTER TABLE users RENAME COLUMN name TO full_name;
-- 滚动发布期间新旧代码同时在跑，旧代码找不到 name 列 → 全部报错
```

```sql
-- ✅ 安全：四次发布
-- 发布 1【扩展】
ALTER TABLE users ADD COLUMN full_name TEXT;        -- 可空，旧代码看不见它
-- 发布 2【双写】
UPDATE users SET full_name = name WHERE full_name IS NULL;   -- 新代码双写 + 回填
-- 发布 3【切读】新代码只读 full_name（仍双写，保证可回滚到发布 2）
-- 发布 4【收缩】
ALTER TABLE users DROP COLUMN name;                 -- 确认无人再用，才删
```

### 9.3 变更的安全等级

```
✅ 安全（旧代码不受影响）: 加可空列、加新表、加索引(并发方式)、放宽约束
⚠️ 危险（旧代码会崩）:    删列、改列名、改类型、收紧约束、加 NOT NULL 无默认值
```

> 判据很简单：**旧版本的代码在变更之后还能不能正常工作？**

加索引也要小心：不带 `CONCURRENTLY` 的 `CREATE INDEX` 会锁表（第 49/50 章）。

### 9.4 schema 迁移与数据迁移是两回事

```
schema 迁移: 快、原子、可以在发布流程里同步跑
数据迁移:   可能要处理上亿行，必须分批、可中断、可重入
```

反例是一条 `UPDATE` 扫全表——锁住整张表几十分钟，等于**计划内的停机**。

正确做法是后台任务按主键分批推进，记录进度，失败可从断点续跑：

```sql
UPDATE orders SET ... WHERE id BETWEEN ? AND ?   -- 每批几千行，跑完记录位置
```

### 9.5 发布顺序与回滚窗口

```
ⓐ 先跑【扩展类】迁移（加列/加表）—— 此时线上还是旧代码，不受影响
ⓑ 再滚动发布新代码 —— 新旧代码此时同时在跑，两者都能工作
ⓒ 观察一段时间（金丝雀/指标），确认没问题
ⓓ 最后才跑【收缩类】迁移（删列），且要在【下一个发布周期】
```

**ⓐ 和 ⓓ 之间隔着至少一个完整的发布周期，这段时间就是你的回滚窗口**——在它关闭之前，随时可以退回旧代码。

⚠️ 最常见的事故：**把 ⓐ 和 ⓓ 合并成一次发布，回滚窗口直接消失。**

### 9.6 备份

> **没有演练过恢复的备份，不叫备份。**

三个要定期回答的问题：

```
RPO（能接受丢多少数据）→ 决定备份频率与是否需要 WAL 归档（第 46 章）
RTO（能接受多久恢复）  → 决定用全量还是增量、要不要热备
恢复演练做过没有       → 决定前两个数字是不是真的
```

与第 58 章的密钥轮换同理：**没演练过的流程，在真正需要时不会成功。**

## 10. 五语言横向对比

| 维度 | JavaScript | Python | Java | C++ | C# | SQL |
|---|---|---|---|---|---|---|
| **交付物** | .js 源码 | .py 源码 | jar | 可执行文件 | dll | 迁移脚本 |
| **必须带走的运行时** | node 二进制 **106.5 MB** | 解释器 + 标准库 **50 MB** | JVM **309 MB** | **无**（依赖系统库） | .NET **74 MB** | — |
| **运行时文件数** | 1 | 1,637 | 455 | — | 184 | — |
| **进入用户代码前** | **7.4 ms** | 见 import 成本 | **28 ms** | **1.23 ms** | **20 ms**（AOT **3.3 ms**） | — |
| **依赖何时解析** | 安装时（锁文件） | **部署时**（除非锁定） | 构建时 | **编译/链接时** | 构建时 + 运行时按需 | — |
| **裁剪运行时** | ❌ 不能 | 部分（删 stdlib） | `jlink` | 天然最小 | `PublishTrimmed` | — |
| **提前编译** | ❌ | ❌ | GraalVM 原生镜像 | 天然 AOT | Native AOT | — |
| **最典型的部署坑** | 原生模块 ABI | 依赖版本漂移 | 运行时版本 / 编码 | libc / ABI 不匹配 | 缺 DLL 延迟暴露 | 破坏性 schema 变更 |

### 10.1 三种「运行时形态」

本章的实测把六种语言归成三类：

**① 无运行时（C++/Go/Rust）**——产物 74 KB，启动 1.23 ms。代价是**必须锁定整条工具链**，且默认不自包含。

**② 单文件运行时（Node）**——106.5 MB 一个二进制。好处是分发简单、不会装错版本；代价是**无法裁剪**。

**③ 多文件运行时（JVM / .NET / Python）**——几百个文件、几十到几百 MB。好处是**可以裁剪**（`jlink`、`PublishTrimmed`）；代价是文件数量带来的构建与冷启动开销（实测 79 倍的复制差距）。

### 10.2 容器把三类拉平了

容器出现之前，这三类的部署难度差别巨大：C++ 要处理 libc 版本，Java 要求目标机装 JRE，Python 要求解释器和一堆包。

容器把「运行环境」也变成了交付物，于是三类都变成了同一件事：**构建一个镜像，替换整台机器**。

**但容器没有消除差别，只是把它换了个位置**：

```
以前的问题: 目标机器上有没有对的运行时？
现在的问题: 镜像多大、构建多久、冷启动多慢？
```

而这三个新问题的答案，恰恰由本章实测的那些数字决定。

## 11. 底层实现对比

| 机制 | JavaScript | Python | Java | C++ | C# |
|---|---|---|---|---|---|
| **代码分发形式** | 源码（可打包） | 源码 + `.pyc` | 字节码（class/jar） | 机器码 | IL（可 AOT） |
| **依赖解析时机** | `npm ci` 时 | `pip install` 时 | 构建时（Maven/Gradle） | 链接时 | 构建时 |
| **运行时缺依赖** | `require` 时抛错 | `import` 时抛错 | `NoClassDefFoundError` | **启动即失败** | **按需加载时才抛错** |
| **版本不匹配** | 语法/API 错误 | 语法/API 错误 | `UnsupportedClassVersionError` | ABI 不匹配（**可能不报错**） | `FileLoadException` |
| **裁剪机制** | 打包器 tree-shaking | 手动删 | `jlink` | 链接器 `--gc-sections` | `PublishTrimmed` |

### 11.1 「缺依赖」的暴露时机决定了排查难度

这一行值得单独看：

```
C++:     启动即失败       → 最容易发现（部署脚本立刻报错）
Node/Python: 首次 require/import 时  → 通常在启动阶段，较容易发现
Java:    首次用到该类时    → 可能很晚
C#:      按需加载程序集时  → 【可能非常晚】
```

本章 C# 版指出了最坏的情况：**一个只在月底结算时才走到的分支，能藏住这个问题一个月**。

> 这解释了为什么部署后的**冒烟测试**必须覆盖「会加载新代码路径」的场景，而不只是「首页能打开」。

### 11.2 静态链接与容器解决的是同一个问题

```
静态链接: 把依赖库打进【可执行文件】
容器镜像: 把依赖库打进【文件系统镜像】
```

两者的目标一致——**消除对目标机器的假设**——只是粒度不同。容器赢在它同时覆盖了配置文件、证书、时区库这些「不是库但同样必需」的东西。

而 `FROM scratch` + 静态链接是两者的叠加：镜像只有几 MB，代价是**完全无法诊断**。

### 12.2 启动时间（实测）

| 形态 | 进入用户代码前 |
|---|---|
| C++（exec + 动态链接） | **1.23 ms** |
| .NET Native AOT | **3.3 ms** |
| Node | **7.4 ms** |
| .NET（框架依赖 / 自包含 / 裁剪） | **20.0 ms** |
| JVM | **28 ms** |

**注意 .NET 三种非 AOT 模式的启动时间完全一样（20.0 / 20.0 / 19.9 ms）**——这是本章最容易反直觉的一条：**体积和可移植性的优化，不会顺带优化启动速度。**

### 12.3 .NET 四种发布模式（同一份代码）

| 模式 | 产物 | 文件数 | 启动 |
|---|---|---|---|
| 框架依赖 | 1 MB | 5 | 20.0 ms |
| 自包含 | 77 MB | 187 | 20.0 ms |
| 自包含 + 裁剪 | 19 MB（**省 75%**） | 34 | 19.9 ms |
| Native AOT | 15 MB | 4 | **3.3 ms（快 6x）** |

### 12.4 文件数量的代价（实测）

| 形态 | 总字节 | 文件数 | 复制耗时 |
|---|---|---|---|
| 一个大文件 | 8 MB | 1 | **4.0 ms** |
| 许多小文件 | 8 MB | 4000 | **319.0 ms（79x）** |

**总字节数完全相同。**慢的部分全是每个文件的元数据开销。

### 12.5 从这些数字里读出的三件事

**① 你写的代码在交付物里几乎不占位置。** 1 : 33,212 意味着优化业务代码体积毫无意义，而换基础镜像能省一半。

**② 「更小」和「更快启动」是两件事。** .NET 裁剪省了 75% 的体积，启动时间**一毫秒都没省**。只有换掉编译模型（AOT）才动得了启动时间。

**③ 文件数量是被系统性忽略的维度。** 79 倍的差距不体现在任何「镜像大小」指标里，但它直接决定容器构建速度和冷启动速度。

## 13. 工程实践

### 13.1 构建一次，到处部署

这是十二要素里最实用的一条，也是最容易在实践中被破坏的一条。

```
✅ 正确: 一个产物 + N 份环境配置
❌ 破坏: 为每个环境单独构建（"生产版" jar / "测试版" 镜像）
```

**破坏它的后果是测试失去意义**：你在预发环境验证过的产物，**不是**要发到生产的那个产物。

自查方法：**同一个构建产物能否原封不动地跑在所有环境？**如果不能，找出是什么把环境信息烙进了产物。

### 13.2 一个可用的 Dockerfile 骨架

```dockerfile
# 构建阶段：带完整工具链
FROM node:22 AS build
WORKDIR /app
COPY package.json package-lock.json ./     # ← 变化少，单独一层
RUN npm ci                                  # ← 依赖层，被缓存
COPY . .
RUN npm run build                           # ← 打包成少量文件（79x 那笔账）

# 运行阶段：只留产物
FROM node:22-slim
WORKDIR /app
COPY --from=build /app/dist ./dist
USER node                                   # ← 不要用 root 跑（第 58 章）
CMD ["node", "dist/main.js"]
```

四个要点：

1. **依赖层与代码层分开**（3.3 节的分层原则）；
2. **多阶段构建**：运行阶段不带编译器；
3. **打包**：把几万个文件变成少量文件；
4. **非 root 用户**：容器逃逸的代价直接相关（第 58 章的最小权限）。

### 13.3 发布检查清单

```
发布前:
  □ 产物是构建流水线产出的，不是本地打的
  □ 扩展类迁移已跑完，且旧代码仍能工作
  □ 回滚方案是「换回上一个产物」，而不是「跑回滚脚本」
  □ 关键指标的告警阈值已就位

发布中:
  □ 先小流量（金丝雀），观察够久再放量
  □ 观察的是【业务指标】（错误率、延迟、转化），不只是「进程活着」

发布后:
  □ 冒烟测试覆盖了会加载新代码路径的场景（第 11.1 节）
  □ 收缩类迁移推迟到下一个周期（回滚窗口）
```

### 13.4 回滚要比发布更容易

一个可靠的判断标准：**回滚的操作步骤，必须比发布更少、更快、更不需要思考。**

如果回滚需要「先停服务、再跑脚本、然后手工改配置」，那么在真正需要回滚的时刻——半夜、告警响个不停、所有人都很紧张——**它不会成功**。

这与第 58 章的密钥轮换、9.6 节的备份恢复是同一条规律：**没演练过的流程，在需要时不会成功。**

### 13.5 部署与可观测性是一件事

```
指标告诉你【出事了】
链路告诉你【在哪】
日志告诉你【为什么】
```

金丝雀发布的全部价值建立在「能判断这 1% 的流量是否正常」之上。**没有可观测性，金丝雀只是把故障拖长了。**

最小可用集合：

```
错误率、P95/P99 延迟、吞吐量  ← 按版本打标签，才能对比新旧
资源使用（CPU/内存/连接数）
业务指标（下单成功率、支付成功率）← 最重要，也最常被漏掉
```

## 14. 最佳实践

- **构建一次，到处部署**：产物里不含任何环境特定的值。
- **配置走环境变量或配置中心**，不随产物打包。
- **不可变基础设施**：要改就重建镜像替换机器，不 ssh 上去改。
- **按变化频率分层**：依赖层与代码层分开，多阶段构建。
- **打包成少量文件**：文件数量的代价实测 79 倍，且不体现在任何体积指标里。
- **按启动次数选择部署形态**：长驻服务不在乎启动，Serverless/CLI 只在乎启动。
- **锁定依赖**（lockfile + 哈希）和**锁定工具链**（C++ 尤其必要）。
- **三种健康探针分开**：liveness 尽量简单，避免依赖抖动引发集体重启。
- **优雅关闭**：SIGTERM → 摘流量 → 等在途请求 → 退出。
- **数据库变更用扩展-收缩**，扩展与收缩分在不同发布周期，留出回滚窗口。
- **数据迁移分批、可中断、可重入**，绝不用一条全表 UPDATE。
- **发布后跑冒烟测试**，覆盖会加载新代码路径的场景。
- **回滚必须比发布更简单**，并且**演练过**。
- **可观测性先于金丝雀**：判断不了成功与否，金丝雀就没有意义。

## 15. 常见坑

### 坑 1：为每个环境单独构建

```
生产环境用 build:prod，测试环境用 build:test
```

**为什么错**：你在预发验证过的产物，不是要发到生产的那个产物——测试失去了意义。

**怎么避免**：一个产物 + N 份配置。自查：同一个产物能否原封不动跑在所有环境？

### 坑 2：Dockerfile 先 COPY 全部代码再装依赖

```dockerfile
COPY . .
RUN npm ci        # ⚠️ 任何代码改动都会让这一层缓存失效
```

**为什么错**：改一行业务代码就重装全部依赖，构建时间从几十秒变成几分钟。

**怎么避免**：先 `COPY package*.json` 再 `npm ci`，最后 `COPY . .`。

### 坑 3：把 node_modules 拷进镜像

**为什么错**：含 C++ 扩展的包按**本机 ABI** 编译。在 macOS 上 `npm install` 再拷进 Linux 容器 → 直接崩。

**怎么避免**：`.dockerignore` 里加上 `node_modules`，在镜像内部 `npm ci`。

### 坑 4：以为「自包含发布」能加快启动

**为什么错**：本章实测框架依赖 20.0 ms、自包含 20.0 ms、裁剪 19.9 ms——**一毫秒都没省**。自包含解决的是可移植性，裁剪解决的是体积。

**怎么避免**：想要更快启动只有一条路——**换编译模型**（AOT / 原生镜像），代价是放弃反射与动态加载。

### 坑 5：liveness 探针检查了数据库

```yaml
livenessProbe:
  httpGet: { path: /health/full }    # ⚠️ 里面查了数据库
```

**为什么错**：数据库抖动 30 秒 → **所有实例同时被判定为「死了」并重启** → 雪崩。

**怎么避免**：liveness 只检查「进程还能响应吗」；依赖检查放 readiness（它只摘流量，不重启）。

### 坑 6：没有优雅关闭

**为什么错**：收到 SIGTERM 立刻退出 → 在途请求全部失败 → **每次发布都丢一批请求**。

**怎么避免**：SIGTERM → readiness 置 false → 等负载均衡摘掉流量 → 等在途请求处理完 → 退出。

### 坑 7：扩展与收缩合并成一次发布

```sql
ALTER TABLE users RENAME COLUMN name TO full_name;   -- ⚠️ 一步到位
```

**为什么错**：滚动发布期间新旧代码同时在跑，旧代码找不到 `name` 列 → **全部报错**。而且此刻**无法回滚**——旧代码已经跑不了了。

**怎么避免**：扩展-收缩四步走，扩展与收缩分在不同的发布周期。

### 坑 8：用一条 UPDATE 做数据迁移

**为什么错**：上亿行的全表 UPDATE 锁表几十分钟，等于**计划外的停机**；中途失败还无法续跑。

**怎么避免**：按主键分批（每批几千行），记录进度，可中断可重入。

### 坑 9：备份没演练过恢复

**为什么错**：备份成功 ≠ 能恢复。备份文件损坏、缺少某张表、恢复流程缺一个步骤——这些**只有真正恢复一次才知道**。

**怎么避免**：定期演练恢复，并用演练结果校准 RPO/RTO 这两个数字。

### 坑 10：优化了业务代码的体积

**为什么错**：本章实测交付物里 **0.003% 才是你写的代码**。把 1 MB 优化到 0.5 MB 改变不了 309 MB 的总量。

**怎么避免**：先看基础镜像和运行时——换 `-slim`/`-alpine`、用 `jlink`/`PublishTrimmed`，收益是几百 MB 级的。

## 16. 面试题

**Q1：为什么容器镜像要分层？怎么分才对？**

A：镜像层是只读的文件系统差分，**上层变了下层不用重传**。分层的原则是**按变化频率**：稳定的在下（基础 OS、运行时），易变的在上（业务代码）。一个典型 Java 镜像里 OS ~50 MB 和 JRE ~200 MB 几个月才变一次，而业务代码 ~1 MB 每天变几十次——如果打成一个 fat jar，改一行代码要重传全部 300 MB；分层后只传 1 MB。Dockerfile 的具体体现是先 `COPY package.json` 再 `npm ci`，最后才 `COPY . .`。这和第 54 章的增量构建是同一个思路：**让不变的部分不必重做**。

**Q2：「在我机器上是好的」有哪几类成因？各自怎么防？**

A：三类。① **运行时/工具链不匹配**（JDK 版本、CPU 架构、原生模块 ABI）——最容易发现，因为通常启动就失败；防御是显式声明版本 + 在与生产一致的环境里构建。② **隐式环境依赖**（编码、时区、locale）——最危险，因为**不报错，只是结果悄悄不同**；防御是显式设置，不依赖默认值。③ **外部状态**（数据库 schema、配置、DNS、时钟）——最难，因为它**不在你的交付物里**；防御是版本化迁移 + 配置外置 + 契约测试。

**Q3：为什么说「文件数量」比「镜像体积」更值得关注？**

A：本章做了一个总字节数完全相同、只改文件个数的对照实验：一个 8 MB 文件复制耗时 4.0 ms，4000 个 2 KB 文件复制耗时 319.0 ms——**慢 79 倍**。差距全部来自每个文件的元数据开销。这直接影响容器构建速度（`COPY node_modules` 复制几十万个小文件）和冷启动速度（每个 `require` 是一次文件系统查找）。而这个维度**不体现在任何「镜像大小」指标里**——两个都是 8 MB，但一个慢 79 倍。这也是生产部署要打包的真正原因：**不是体积更小，而是文件数量少了几个数量级**。

**Q4：自包含发布、裁剪、AOT 分别解决什么问题？**

A：本章对同一份 C# 代码实测四种模式：框架依赖 1 MB/20.0 ms、自包含 77 MB/20.0 ms、裁剪 19 MB/19.9 ms、Native AOT 15 MB/**3.3 ms**。读法是：**自包含解决可移植性**（不需要目标机装运行时），**裁剪解决体积**（省 75%），**只有 AOT 解决启动速度**（快 6 倍）——前三种模式的启动时间几乎完全一样。代价在于动态能力：裁剪需要显式配置反射，AOT 直接放弃反射和动态加载。这是第 30 章那笔账在部署阶段结清——**运行时越动态，越难提前编译**。

**Q5：蓝绿、金丝雀、滚动发布各自的取舍是什么？**

A：核心权衡是**回滚速度用资源换**。蓝绿要 2 倍资源，因为它一直养着另一套完整环境，回滚就是切流量——最快。滚动只要 1.2 倍资源，但回滚需要反向再滚一遍——最慢。金丝雀 1.1 倍资源，**它的独特价值不是回滚快，而是故障只影响 1% 的用户**——它把「回滚快慢」问题降级成了「影响面大小」问题。但要注意：**所有策略都有一个共同前提——新旧版本能同时运行**。数据库 schema 变更会打破这个前提，让所有策略同时失效。另外金丝雀的价值完全建立在可观测性之上：判断不了这 1% 是否正常，金丝雀只是把故障拖长了。

**Q6：为什么数据库变更不能像代码那样回滚？正确做法是什么？**

A：三个原因：① `DROP COLUMN` 之后数据**已经没了**，回滚只能恢复结构不能恢复内容；② 大表 `ALTER` 可能跑几十分钟，回滚也要同样久，期间系统处于中间状态；③ **回滚脚本几乎从不被测试**——需要它的时候是你第一次运行它。所以正确策略不是「写好回滚脚本」，而是**让变更不需要回滚**：用扩展-收缩模式，把一次列重命名拆成四次发布（扩展加列 → 双写回填 → 切读 → 收缩删列），**每一次的前后两个状态都能同时服务新旧代码**。关键是扩展与收缩要分在不同的发布周期，中间那段时间就是**回滚窗口**。

**Q7：liveness 和 readiness 探针为什么必须分开？**

A：因为它们的失败动作完全不同：liveness 失败会**重启**容器，readiness 失败只是**摘掉流量**。如果把依赖检查（比如查数据库）放进 liveness，数据库抖动 30 秒会导致**所有实例被同时判定为死亡并重启**——把一次依赖抖动升级成一次集体重启，通常还会因为大量实例同时重连而让数据库彻底崩掉。正确做法是 liveness 只检查「进程还能响应吗」，依赖检查放 readiness，慢启动的应用另配 startup 探针避免被 liveness 误杀。

**Q8：不可变基础设施解决了什么问题？**

A：解决**配置漂移**。可变的做法（ssh 上去 apt install、改配置、打补丁）让每台机器的状态由「历史上执行过的所有命令」决定，几个月后没人能说清任意两台机器的区别——症状是「重启那台就好了」「只有 3 号机有问题」。不可变的做法是要改就重建镜像替换整台机器，机器状态**完全由构建产物决定，与它的历史无关**，回滚就是换回上一个镜像。更本质地说：**它把运维问题变成了构建问题**——而构建问题是可以版本化、可复现、可测试的（第 54 章）。

## 17. 练习

### 练习 1：量一量你的交付物（基础）

对你正在做的项目：

1. 测出运行时（JRE / node / 解释器 / .NET）的大小与文件数；
2. 测出你自己代码的大小；
3. 算出比例；
4. 据此判断：镜像瘦身应该从哪里下手？

**如果比例超过 1:100，任何针对业务代码体积的优化都是浪费时间。**

### 练习 2：测出你的启动时间构成（进阶）

1. 测「进程启动 → 进入 main/第一行代码」的时间；
2. 测「进入 main → 能对外服务（readiness 通过）」的时间；
3. 找出第 2 步里最耗时的三件事（通常是：加载配置、建连接池、预热缓存）；
4. 估算：如果实例数在流量高峰翻倍，扩容需要多久才能生效？

### 练习 3：复现文件数量的代价（基础）

写一个脚本，生成两个总字节数相同的目录（一个大文件 vs N 个小文件），分别测量：

1. 复制耗时；
2. 打成 tar 的耗时；
3. 构建成容器镜像的耗时（如果有 Docker）。

**要求**：报告 N = 100 / 1000 / 10000 三档，并画出趋势。

### 练习 4：设计一次不需要回滚的 schema 变更（实战）

选一个你项目里的破坏性变更（改列名/改类型/拆表），写出扩展-收缩的完整四步：

1. 每一步的 SQL；
2. 每一步之后，**旧代码**是否仍能工作？
3. 每一步之后，**新代码**是否仍能工作？
4. 回滚窗口从哪一步开始、到哪一步结束？

**第 2、3 两问必须逐步骤回答「是」——只要有一个「否」，方案就是错的。**

### 练习 5：演练一次回滚（实战）

在预发环境：

1. 部署一个版本，记录时间；
2. 部署下一个版本，记录时间；
3. **回滚到上一个版本，记录时间和步骤数**；
4. 对比：回滚是否比发布更快、步骤更少？
5. 如果不是，重新设计部署流程。

**这道题的价值全在第 4 问。**一个比发布还复杂的回滚流程，在真正需要的时刻不会成功。

## 18. 本章总结

**核心结论**：部署的全部工作，是**减少交付物对环境的假设**。假设越少，能跑起来的地方越多，「在我机器上是好的」出现的概率就越低。

**关键实测数据**：

| 发现 | 数据 |
|---|---|
| 交付物里你的代码占多少 | JVM 比例 **1 : 33,212**（0.003%）；.NET **1 : 517** |
| 必须带走的运行时 | JVM **309 MB**/455 文件、node **106.5 MB**/1 文件、Python **50 MB**/1,637 文件、C++ **0** |
| 进入用户代码前的耗时 | C++ **1.23 ms** / AOT **3.3 ms** / Node **7.4 ms** / .NET **20 ms** / JVM **28 ms** |
| .NET 四种发布模式 | 1 MB·20.0ms / 77 MB·20.0ms / 19 MB·19.9ms / **15 MB·3.3ms** |
| 文件数量的代价 | 同样 8 MB：1 个文件 **4.0 ms** vs 4000 个文件 **319.0 ms（79x）** |
| Python 导入成本 | 五个标准库模块 **15.4 ms**，每次启动都要重新付 |
| C++ 的动态依赖 | 产物 74 KB，但依赖 `libc++`、`libSystem` —— **并不自包含** |

**三条最反直觉的结论**：

```
① 你写的代码在交付物里几乎不占位置（0.003%）
   → 优化业务代码体积毫无意义，换基础镜像能省一半

② 「更小」和「更快启动」是两件不同的事
   → .NET 裁剪省了 75% 体积，启动时间一毫秒都没省
     只有换掉编译模型（AOT）才动得了启动时间

③ 文件数量是被系统性忽略的维度
   → 79 倍的差距不体现在任何「镜像大小」指标里
```

**四条能带走的原则**：

```
① 构建一次，到处部署    产物里不含任何环境特定的值
② 不可变基础设施       把运维问题变成构建问题
③ 按启动次数选形态     长驻服务不在乎启动，Serverless 只在乎启动
④ 让变更不需要回滚     扩展-收缩，留出回滚窗口
```

**自查清单**：

- [ ] 我知道我的交付物里运行时占多少、我的代码占多少。
- [ ] 我测过「进程启动到能对外服务」需要多久。
- [ ] 我能说出「在我机器上是好的」的三类成因，并知道各自怎么防。
- [ ] 我的镜像按变化频率分层，依赖层和代码层是分开的。
- [ ] 我知道自包含/裁剪/AOT 各自解决什么问题、不解决什么问题。
- [ ] 我的 liveness 探针不依赖外部服务。
- [ ] 我的应用处理 SIGTERM 并优雅关闭。
- [ ] 我的数据库变更是扩展-收缩式的，且留出了回滚窗口。
- [ ] 我的回滚流程比发布更简单，并且演练过。
- [ ] 我有能判断「这次发布是否成功」的指标。

## 🎓 全书结语

到这里，59 章走完了。

回头看这条路线：从**第 1 章**的「机器码为什么演进成高级语言」，到**第 7 章**的类型系统、**第 20 章**的哈希表、**第 27 章**的虚函数表、**第 36 章**的垃圾回收、**第 41 章**的内存模型、**第 49 章**的 B+ 树、**第 57 章**的缓存局部性、**第 58 章**的注入防御，最后到这一章的**交付**。

如果说这本书有一条真正的主线，那就是它反复在做的同一件事：**把「它是怎么工作的」变成一个可以当场验证的问题。**

书里的每一个论断都配着一段能跑的代码，而**其中相当一部分实验并没有得出预期的结果**：

- Node 和 .NET 悄悄把 `fsync` 升级成了 `F_FULLFSYNC`（第 46 章）；
- sqlite 的优化器在低选择性索引上**选错了**（第 49 章）；
- 「乐观锁在低竞争下更快」这条教科书规则**没能复现**（第 48 章）；
- 二分查找的经典修复方式**本身也是错的**（第 21 章）；
- 编译器把 StackOverflow 最高票的分支预测实验**优化没了**（第 57 章）；
- V8 的多态内联缓存让「属性顺序影响性能」这条广为流传的建议**过期了**（第 57 章）；
- 「C++ 不做边界检查是为了性能」这个理由，在 -O2 下只剩 **1.02 倍**（第 58 章）。

这些失败的实验，最后成了全书最有价值的部分。它们共同说明一件事：**关于软件的常识会过期，而验证它的方法不会。**

所以如果只能从这 59 章里带走一样东西，希望是这个习惯：

> **当你不确定某件事时，写一段代码去问它。**

六门语言、59 个概念、几百个实测数字——它们都会过期。但「不确定就去测」这件事不会。

**祝你写出更好的代码。** 🚀
