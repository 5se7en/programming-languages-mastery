# 第 55 章 · 依赖注入

**简体中文** ｜ [English](./55-di.en-US.md)

---

> 第 52 章讲测试时反复出现一句话——「难测几乎总是设计问题的信号」，而那一章的 C# 版之所以能把 `FakeRepo` 塞进 `OrderService`，是因为它依赖的是**接口**而不是具体类。这一章正面回答那个被推迟的问题：**为什么要把依赖「交出去」**。
>
> 答案的内核只有一句：**不要自己找依赖，让依赖被送进来**。类自己 `new SqlRepo()` 时，「用哪个实现」的控制权在类手里；改成构造器参数后，控制权交给了调用方——这就是**控制反转**。
>
> 本章的**钥匙实验**是手写一个 DI 容器：反射找构造器 → 递归解析每个参数类型 → `newInstance` 装配，**40 行就是 Spring 的骨架**（第 30 章的反射 + 第 51 章的对象图构建在这里合流）。它还实测了容器的另外两项核心职责：**生命周期**（`@Singleton` 的 `SqlRepo` 被三处注入却只造了 1 个实例）和**循环依赖检测**（A 需要 B、B 需要 A → 容器精确报出 `循环依赖: A → B → A`）。
>
> 而循环依赖那个实验揭示了一条重要判据：**构造器注入让循环依赖在构造期就无法成立**，容器立刻报错；换成字段注入（`@Autowired` 打在字段上）则是先 `new` 空对象再塞字段——循环依赖能「成功」启动，但对象在某一刻是**半成品**，问题被推迟到运行时。**构造器注入把设计问题变成了启动失败**。
>
> C# 版实测了 DI 最经典的生产事故——**被俘获的依赖**：一个 `Singleton` 服务依赖了 `Scoped` 的仓储，结果第 2 次请求仍然用着**第 1 次请求的 `RequestContext`**（实测两次都是 `Request#4`）。真实后果是数据库连接、事务、当前用户跨请求泄漏——安全与正确性双重事故。规则很硬：**长生命周期不能依赖短生命周期**。
>
> Python 版则给出了一个反向视角：动态语言里依赖**写死也能换掉**——直接改实例属性、或用 `mock.patch` 换掉模块命名空间里的名字绑定（实测两种都成功）。这解释了「Python 不太需要 DI 容器」的技术根源，但也点明了它的代价：**patch 的字符串路径写死了「谁在哪里 new 了什么」**，测试因此耦合到了实现细节。
>
> C++ 版量出了另一条路的价格：运行时多态（虚函数）1.60 ns/次 vs 编译期注入（模板）0.48 ns/次——**快 3.3 倍，差距全部来自能不能内联**。而 C++ 几乎没有 DI 容器的原因，与第 51 章 ORM 完全相同：**没有运行时反射**。

## 1. 学习目标

学完本章，你将能够：

- 用一句话说清**控制反转**与**依赖注入**的关系，并区分 **DI** 与 **DI 容器**；
- 手写一个 DI 容器（反射构造 + 自动装配 + 生命周期 + 循环依赖检测）；
- 比较**构造器/属性/方法**三种注入方式的取舍（实测各自的失败形态）；
- 识别**被俘获的依赖**（实测跨请求状态泄漏）并说出生命周期的硬规则；
- 解释为什么**服务定位器被视为反模式**——它与 DI 只差一个方向。

## 2. 为什么会出现这个概念

### 第 52 章留下的问题

```text
第 52 章实测: OrderService 依赖【接口】才换得进测试替身
              「难测几乎总是设计问题的信号」
→ 但为什么依赖接口就能换？谁来决定用哪个实现？—— 这一章的主题
```

### 依赖写死时发生了什么

```java
class UserService {
    private Repo repo = new SqlRepo();        // ⚠️ 依赖写死在内部
    private Mailer mailer = new SmtpMailer(); // ⚠️ 测试时换不掉
}
```

```text
谁来决定用哪个实现？【类自己】—— 控制权在类手里
后果: 测试换不进替身（第 52 章实测）、换数据库要改业务代码、并发下无法隔离
```

### 控制反转：把决定权交出去

```java
class UserService {
    UserService(Repo repo, Mailer mailer) { ... }   // 只声明【需要什么】
}
```

```text
谁来决定用哪个实现？【调用方/容器】—— 控制【反转】了
→ 「依赖注入」是实现控制反转的一种手法: 通过参数把依赖【递进来】
→ 其他手法还有: 模板方法、事件回调、服务定位器（本章 ⑧ 会说它为什么是反模式）
```

### 一句话定义

```text
依赖注入 = 不要自己找依赖，让依赖被送进来
它把「用哪个实现」这个决定，从【使用者】手里挪到了【组装者】手里
```

> **一句话总结**：DI 的价值不在「用了个框架」，而在于**依赖变成了公开的、编译期可见的契约**——写在构造器签名里，测试时必须传、看代码时一眼可知。本章会实测：这个简单的转变同时买到了可测性、可替换性和**启动期的错误暴露**。

## 3. 底层原理

### DI 不等于 DI 容器（先破除最大的误解）

**手工注入（Poor Man's DI）就是最纯粹的依赖注入**（Java 实测）：

```java
Repo repo = new SqlRepo();
FakeMailer mailer = new FakeMailer();
UserService svc = new UserService(repo, mailer);
System.out.println(svc.notify(42));   // → 用户42，邮件记录: [用户42: 你好]
```

```text
→ 没有任何框架，这就是 DI
→ 容器解决的是「对象图太大时手工装配太啰嗦」，不是 DI 本身
→ 小项目/库【不该】引入容器；C++ 更是几乎只有这一条路（C++ 版 ⑥）
```

### 钥匙实验一：手写 DI 容器（Java，约 40 行）

**容器只做三件事**：

```java
<T> T get(Class<T> type) {
    Class<?> impl = bindings.getOrDefault(type, type);
    if (singletons.containsKey(impl)) return (T) singletons.get(impl);
    if (!building.add(impl)) throw new IllegalStateException("循环依赖: ...");  // ③ 查环
    Constructor<?> ctor = impl.getDeclaredConstructors()[0];                   // ① 找构造器
    Object[] args = new Object[ctor.getParameterCount()];
    for (int i = 0; i < args.length; i++)
        args[i] = get(ctor.getParameterTypes()[i]);                            // ② 递归解析
    Object instance = ctor.newInstance(args);
    if (impl.isAnnotationPresent(Singleton.class)) singletons.put(impl, instance);
    return (T) instance;
}
```

**实测运行**：

```text
container.get(UserService.class) —— 容器做了三件事:
  ① 反射找到构造器 UserService(Repo, Mailer)
  ② 递归解析每个参数类型（Repo→SqlRepo，Mailer→FakeMailer）
  ③ newInstance 把它们装配起来
结果: notify(7) → 用户7
```

**这就是 Spring/Guice 的骨架**——第 30 章的反射（问类要构造器）加第 51 章的对象图构建（递归装配），在这里合流。

### 钥匙实验二：生命周期（Java + C# 实测）

**Java 版实测单例共享**：

```text
SqlRepo 标了 @Singleton，被 UserService/ReportService 共用
SqlRepo 实例数: 1（三次注入只造了一个）
ReportService 未标注 → 每次新建: r1 == r2 ? false
```

**C# 版实测三种生命周期的完整语义**：

```text
同一个 scope 内两次解析 IRepo: 同一实例? True
不同 scope 解析 IRepo:        同一实例? False
  scope1 → 用户1（来自 Request#2）
  scope2 → 用户1（来自 Request#3）      ← 各自持有自己的 RequestContext
Singleton 的 IClock: 跨 scope 同一实例? True
```

```text
Transient  每次新建     —— 无状态的小对象
Scoped     每请求一个   —— 连接、事务、当前用户（Web 里 scope = 一次 HTTP 请求）
Singleton  全局一个     —— 配置、连接池、缓存
```

### 钥匙实验三：被俘获的依赖（C# 实测，DI 最经典的事故）

**一个 `Singleton` 服务依赖了 `Scoped` 的仓储**：

```text
第 1 次请求解析 SingletonService → 用户1（来自 Request#4）
第 2 次请求解析 SingletonService → 用户1（来自 Request#4）   ← 还是 #4！
两次拿到的是同一个 SingletonService? True
```

```text
⚠️ 第 2 次请求【用着第 1 次请求的 RequestContext】——它被单例俘获了
→ 真实后果: 数据库连接/事务/当前用户跨请求泄漏——安全与正确性双重事故
→ 规则: 长生命周期【不能】依赖短生命周期（Singleton ⊅ Scoped ⊅ Transient）
→ ASP.NET Core 的 ValidateScopes 会在启动时把这种组合直接【报错】
→ 必须这么用时: 注入 IServiceScopeFactory，用时现开一个 scope
```

### 钥匙实验四：循环依赖与三种注入方式

**构造器注入让循环依赖在构造期就无法成立**（Java 实测）：

```text
container.get(A.class) → ✗ 循环依赖: A → B → A
→ A 需要 B，B 又需要 A —— 构造器注入下【根本造不出来】，容器立刻报错
```

**对比字段注入**：

```text
字段注入(@Autowired 打在字段上): 先 new 空对象再塞字段
→ 循环依赖能「成功」启动，但对象在某一刻是【半成品】——问题推迟到运行时
→ 这是构造器注入相对字段注入的最大优势: 把【设计问题】变成【启动失败】
```

**三种注入方式的失败形态**（C# 实测）：

| 方式 | 写法 | 失败形态（实测） | 取舍 |
|------|------|----------------|------|
| **构造器** | `Svc(IRepo repo)` | 忘了传 → **构造时**抛异常 ✓ | 依赖必填且不可变——**推荐默认** |
| **属性** | `svc.Repo = ...` | 忘了设 → **用时** NullReference | 依赖可选可换，代价是对象可能半成品 |
| **方法** | `Run(IRepo repo)` | 签名强制传 | 只服务单个方法的临时依赖 |

### 容器的代价（C# 实测）

```text
容器解析 200000 次:  71.5 ms（0.36 μs/次）
手工 new 200000 次:   1.5 ms（0.01 μs/次）
→ 慢 48x —— 反射查构造器 + 递归解析的开销
→ 但注意分母: 每次几微秒，而一次 HTTP 请求是毫秒级——通常可忽略
→ 真实容器会【缓存编译好的构造委托】（表达式树，第 51 章），比本例快得多
→ 编译期 DI（Dagger/Micronaut/源生成器）干脆把装配代码生成出来: 零反射
```

### DI 与服务定位器：只差一个方向

```text
DI:        UserService(Repo repo)                    —— 依赖【被推进来】
服务定位器: Repo repo = Locator.get(Repo.class);      —— 依赖【被拉出来】

表面上都实现了「不 new 具体类」，但:
  DI 的依赖写在【构造器签名】里 —— 编译期可见，测试时必须传
  定位器的依赖藏在【方法体】里 —— 看签名不知道它要什么，测试时会漏
→ 后者被视为反模式的原因: 它把依赖【隐藏】了，而 DI 把依赖【公开】了
```

## 4. JavaScript

JS 版展示了**函数式 DI**——闭包就是最轻的容器。

### 闭包工厂：装配与使用分离（实测）

```javascript
function makeGreeter({ clock, mailer }) {
  // 依赖被【闭包捕获】，返回的函数签名里再也看不到它们
  return function greet(user) {
    const stamp = clock();
    mailer.send(user, `你好 @${stamp}`);
    return stamp;
  };
}
```

```text
组装期: makeGreeter({...}) —— 只做一次（相当于容器的 Resolve）
使用期: greet('甲') → 1000000，greet('乙') → 1000000
→ greet 的签名是 (user) —— 调用方【完全不知道】它依赖时钟和邮件
→ 这就是构造器注入的函数式版本: 闭包环境 = 对象的字段
→ 第 13 章讲闭包时说「函数 + 它捕获的环境」——这里那个环境就是【依赖容器】
```

### 部分应用：DI 的另一个名字（实测）

```javascript
const report = partial(sendReport, frozenClock(2_000_000), fakeMailer());
report('日报') → 日报@2000000
report('周报') → 周报@2000000
```

```text
「把依赖绑定好，返回一个更简单的函数」——这与 DI 容器做的事完全同构
→ 函数式世界里 DI 不需要专门的名字，它就是【部分应用】
```

### 组装根：整个应用只有一处知道真实依赖

```javascript
function buildApp(env) {
  const deps = env === 'test'
    ? { clock: frozenClock(3_000_000), mailer: fakeMailer() }
    : { clock: realClock, mailer: realMailer };
  return { greet: makeGreeter(deps), deps };
}
```

```text
→ 组装根应该在【程序最外层】（main/入口），业务代码一律只接收依赖
→ 判断 DI 做得好不好的一个信号: 全项目搜 `new Xxx()`，应该只在组装根出现
```

### 为什么 JS 生态很少用 DI 容器

```text
① 模块本身就是单例容器: import { db } from "./db.js" —— 天然的全局装配
② 函数是一等公民: 传函数比传对象轻得多
③ 但代价是: import 的依赖【换不掉】——测试里只能用 jest.mock 改模块
→ 实践是: 业务逻辑写成【接收依赖的纯函数/工厂】，只在组装根 import 真实实现
→ 例外: Angular（完整 DI 容器）、NestJS（照搬 Spring 的装饰器 + 容器）
```

> **注意**：`jest.mock`/`vi.mock` 与 Python 的 `mock.patch` 有同样的问题——测试耦合到「谁在哪里 import 了什么」；React 的 Context 是 UI 层的 DI（跨组件层级传递依赖而不逐层 props）；依赖注入在 JS 里最常见的失败形态是「模块顶层就 `new` 了数据库连接」——那让整个模块都无法在测试中加载。

## 5. Python

Python 版给出了动态语言的反向视角。

### 依赖写死也能换掉（实测两种手法）

**手法一：直接改实例属性**：

```text
改完实例属性后 greet('甲') → 1000000，邮件: [('甲', '你好 @1000000')]
→ 静态语言里这一步做不到（private final 字段），所以【必须】先做好 DI
→ 这就是「Python 不太需要 DI 容器」的技术根源: 一切都是可写的属性
```

**手法二：`mock.patch` 换掉模块命名空间里的名字绑定**：

```python
with mock.patch(__name__ + ".SystemClock", lambda: FrozenClock(2_000_000)), \
     mock.patch(__name__ + ".Mailer", FakeMailer):
    svc2 = HardCodedService()      # 内部 new 的是被替换后的类
```

```text
patch 期间内部 new 出来的是替身: greet → 2000000，mailer 类型: FakeMailer
退出 with 之后恢复原状 ✓
→ 直接改【模块命名空间里的名字绑定】（第 13 章作用域）
⚠️ 但这不是「更好的 DI」，而是【测试对实现细节的耦合】:
   patch 的字符串路径写死了「谁在哪里 new 了什么」——重构一下测试就红
```

### 构造器注入在 Python 里同样是首选（实测）

```text
InjectedService(FrozenClock, FakeMailer).greet('丙') → 3000000
→ 不需要 patch，不需要知道内部实现——测试只依赖【构造器签名】这个公开契约
→ 猴子补丁能救你，但不该成为设计的替代品
```

### 默认参数注入：Python 特有的轻量方案（实测）

```python
def greet_with_defaults(user, clock=None, mailer=None):
    clock = clock or SystemClock()      # ← 必须在函数体里兜底
    mailer = mailer or Mailer()
```

```text
生产: greet_with_defaults('丁')                          用真实依赖
测试: greet_with_defaults('丁', FrozenClock(4e6), fake)  → 4000000
→ 一个函数就是一个「注入点」，不需要类、不需要容器
⚠️ 陷阱: 别写 def f(mailer=Mailer())——默认值在【定义时】求值一次，全局共享
```

### Protocol：静态检查 + 鸭子类型

```text
SystemClock 和 FrozenClock 都没有 implements 任何接口，但都满足 Clock 协议
→ Protocol 是【结构化类型】: mypy 静态检查它，运行时不强制（第 28 章接口的第三条路）
→ 于是 Python 得到了「有类型提示的 DI」而不必引入接口继承的仪式
```

> **注意**：需要容器的场景仍然存在——对象图很深、需要统一生命周期、Web 框架的请求作用域（FastAPI 的 `Depends()` 就是一个轻量 DI 容器）；`functools.partial` 是 JS 版部分应用的 Python 等价物；**DI 是设计原则，容器是规模到了才需要的工具**。

## 6. Java

Java 版是钥匙实验的主场（数据见第 3 节），这里补充 Spring 生态的两个高频困惑。

### 为什么 `@Transactional` 自调用不生效（实测代理机制）

```text
容器注入给你的往往不是原对象，而是一个【代理】:
  直接调 raw.find(1)     → 用户1
  调代理 proxied.find(1) → 【代理拦截】用户1
```

```text
事务/日志/缓存这些横切能力，就是代理在方法前后插入的
但类【内部】的 this.method() 走的是原对象，绕过了代理
→ 第 48 章说的「@Transactional 自调用不生效」不是 bug，是代理的必然
→ 解法: 拆成两个 bean 互相注入，或注入自己的代理（AopContext）
```

### 构造器注入 vs 字段注入（Spring 官方也推荐前者）

```java
// ✅ 构造器注入: 依赖必填、可 final、循环依赖启动即报错（实测）
public UserService(Repo repo, Mailer mailer) { ... }

// ⚠️ 字段注入: 字段不能 final、循环依赖能启动、测试必须用反射或容器
@Autowired private Repo repo;
```

```text
Spring 4.3+ 单构造器可省略 @Autowired —— 官方在用默认值引导你走构造器注入
```

> **注意**：`@Component`/`@Service`/`@Repository` 只是语义化的 `@Component`，扫描机制相同；`@Lazy` 可以打破循环依赖但只是把问题藏起来；Guice/Dagger 是 Spring 之外的两条路——Dagger 用**注解处理器在编译期生成装配代码**（零反射、启动快，Android 生态的主流）。

## 7. C++

C++ 版量出了两条路的价格。

### 运行时多态 vs 编译期注入（实测）

```cpp
// 路线一: 虚函数（Java/C# 风格）
class RuntimeService { std::shared_ptr<IClock> clock_; };

// 路线二: 模板参数（依赖是【类型】）
template <typename ClockT>
class CompileTimeService { ClockT clock_; };   // 值持有，无指针、无虚表
```

```text
运行时多态 20000000 次: 31.9 ms（1.60 ns/次）
编译期注入 20000000 次:  9.6 ms（0.48 ns/次）
→ 编译期版快 3.3x —— 差距全部来自「能不能内联」
→ 零开销哲学（第 29/38 章）在 DI 上的又一次体现
```

### 但编译期注入有三个代价

```text
① 类型爆炸: Service<A,B> 与 Service<A,C> 是【两个无关的类型】
② 无法运行时切换: 读配置文件决定用哪个实现？做不到
③ 编译变慢 + 报错难读（第 54 章实测头文件展开 8286x）
→ 真实项目常常混用: 稳定的高频依赖用模板，可配置的用虚函数
```

### 为什么 C++ 几乎没有 DI 容器

```text
与第 51 章 ORM 完全同一个原因: 【没有运行时反射】
→ Java 容器能 getDeclaredConstructors() 问类要构造器（Java 版实测）
→ C++ 的类不知道自己有哪些构造器、参数是什么类型——容器无从下手
→ 于是 C++ 的答案是【手工组装根】: 在 main() 里把对象图一层层构造出来
   这正是 Java 版说的 Poor Man's DI —— 对 C++ 而言它不是「穷人版」，是唯一版
```

> **注意**：Boost.DI 用模板元编程模拟自动装配，代价是编译期魔法与报错地狱；`std::function` 是「注入一个行为」的轻量方式（不需要接口继承）；C++20 concepts 让模板参数也能声明契约——相当于编译期版的 Protocol（第 28 章）。

## 8. C#

C# 版承包了生命周期的完整实测（数据见钥匙实验二、三），这里补充实践判据。

### 什么该注入，什么不该

```text
该注入:   有【外部副作用】或【多实现】的东西
          —— 数据库、HTTP 客户端、时钟、随机源、文件系统、当前用户
          （第 52 章实测: 时间与随机是 flaky 测试的两大来源，注入即驯服）
不该注入: 纯数据结构、值对象、纯函数工具类 —— 它们没有替换的必要
→ 判据: 「测试时我需要换掉它吗？」——不需要就别为它加一层间接
→ 过度 DI 的味道: 每个类都有接口、接口只有一个实现、名字叫 IFooService/FooService
```

### ASP.NET Core 的生命周期约定

```text
AddSingleton  —— 配置、连接池、内存缓存
AddScoped     —— DbContext、当前用户、请求级事务（scope = 一次 HTTP 请求）
AddTransient  —— 无状态的小服务
→ ValidateScopes（开发环境默认开）会在启动时抓出「Singleton 依赖 Scoped」（③ 实测的事故）
```

> **注意**：`IServiceScopeFactory` 是在单例里安全使用 scoped 服务的唯一正道；`IOptions<T>` 是配置注入的标准形态（支持热重载）；源生成器版的 DI（如 Jab、StrongInject）把装配代码生成出来，兼得容器的便利与手工的性能。

## 9. SQL

数据库侧也有「可替换实现」的问题，而答案同样是**依赖契约而非实现**。

### 视图 = 数据库层的接口（实测）

```text
应用查 users 视图，不直接碰 users_v1 表:
  查询 users: 张三@北京, 李四@上海
底层列名从 full_name 改成 name_text 后，同样的查询: 张三@北京, 李四@上海
```

```text
→ 与第 28 章「依赖接口而非实现」完全同构: 视图就是那个接口
→ 依赖倒置原则的数据库版: 应用不依赖表，表也不依赖应用，两者都依赖【视图契约】
```

### CTE 参数化数据源：SQL 版的依赖注入（实测）

```sql
WITH source_orders(id, user_id, amount) AS (
  VALUES (101, 1, 99), (102, 1, 1)          -- ← 注入进来的「测试替身」
)
SELECT u.name, COUNT(s.id), SUM(s.amount)
FROM users u LEFT JOIN source_orders s ON s.user_id = u.id GROUP BY u.id;
```

```text
真实数据源: 张三: 2 单, 共 8000   李四: 1 单, 共 100
替身数据源: 张三: 2 单, 共 100    李四: 0 单, 共 0
→ 同一段统计逻辑，喂给它不同的数据源——逻辑与数据源解耦
→ dbt 的 ref()/source() 宏把这件事做成了工程实践（第 54 章提过）
```

### 更多可替换点

```text
PRAGMA/SET 参数 → 运行时配置注入（第 46 章 synchronous、第 48 章隔离级别）
自定义函数(UDF) → 应用把函数【注册】进数据库（sqlite3 的 create_function）
外部表/FDW      → 让「表」背后其实是另一个数据库或 API
→ 共同点: 让【契约】固定，让【实现】可换
```

> **注意**：抽象也有代价——多层视图嵌套会让优化器难以下推谓词（第 47 章）；Repository 抽象过度会把 SQL 的 JOIN/窗口函数能力抽没（第 47 章）；判据与应用层完全一致：**只有一个实现的接口，在哪一层都是过度设计**。

## 10. 五语言横向对比

### ① DI 机制对照

| 维度 | Java | C# | Python | JavaScript | C++ |
|------|------|-----|--------|-----------|-----|
| 主流容器 | Spring/Guice/Dagger | 内置 `IServiceCollection` | 通常不用（FastAPI `Depends`） | 通常不用（Angular/NestJS 例外） | **几乎没有** |
| 装配机制 | **运行时反射** | 运行时反射 + 表达式树 | 一切可写 | 闭包/工厂 | **模板或手工** |
| 主流注入方式 | 构造器（官方推荐） | 构造器 | 构造器/默认参数 | 闭包捕获/部分应用 | 构造器（手工） |
| 生命周期 | singleton/prototype/request | Singleton/Scoped/Transient | 自管 | 自管 | 自管 |
| 特色手法 | AOP 代理（实测） | ValidateScopes | **猴子补丁**（实测） | **部分应用**（实测） | **编译期注入**（实测 3.3x） |
| 无容器时的做法 | 手工装配 | 手工装配 | 默认参数 | 组装根 | **组装根（唯一路）** |

### ② 钥匙实验数据汇总

```text
手写容器:     反射找构造器 → 递归解析 → newInstance，40 行 = Spring 骨架
单例共享:     @Singleton 的 SqlRepo 三处注入只造 1 个实例
生命周期:     同 scope 内 IRepo 同一实例 True；跨 scope False；Singleton 跨 scope True
被俘获依赖:   Singleton 依赖 Scoped → 第 2 次请求仍用 Request#4（跨请求泄漏）
循环依赖:     构造器注入 → 容器报出「循环依赖: A → B → A」
三种注入:     构造器忘传→构造时抛异常；属性忘设→用时 NullReference
容器代价:     解析 0.36 μs/次 vs 手工 new 0.01 μs/次（慢 48x，但绝对值可忽略）
C++ 两条路:   虚函数 1.60 ns/次 vs 模板 0.48 ns/次（快 3.3x）
Python 补丁:  改实例属性 ✓；mock.patch 换模块名字绑定 ✓（但耦合实现细节）
SQL 视图:     底层列改名，调用方查询结果不变
```

### ③ 共性与根因

**共性**：所有语言的 DI 内核完全相同——**不要自己找依赖，让依赖被送进来**；所有生态都推荐构造器注入（依赖必填、不可变、循环依赖启动即暴露）；所有语言都存在「组装根」概念（唯一知道真实实现的地方）。

**根因**：

- **容器的有无由反射能力决定**：Java/C# 有运行时反射 → 容器强大；C++ 没有 → 只能手工组装（与第 51 章 ORM 完全同构）；
- **动态语言的 DI 更轻**：Python 一切可写、JS 函数是一等公民——它们不需要「先设计好才能替换」；
- **生命周期是容器独有的复杂度**：手工装配时对象的生死由你控制，交给容器后就必须显式声明——**被俘获的依赖是这份复杂度的账单**；
- **代理是 AOP 的实现基础**，也是 Spring 各种「不生效」困惑的统一解释（自调用绕过代理）；
- **注入的边界由「是否需要替换」决定**：这与第 52 章「该 mock 什么」是同一条判据的两次出现。

## 11. 底层实现对比

| 容器 | 装配时机 | 机制 | 特点 |
|------|---------|------|------|
| **Spring** | 运行时 | 反射 + CGLIB/JDK 动态代理 | 功能最全；代理带来自调用陷阱（实测） |
| **Guice** | 运行时 | 反射 + 显式 Module 绑定 | 无 XML、无扫描，绑定代码即文档 |
| **Dagger** | **编译期** | 注解处理器生成装配代码 | 零反射、启动快、错误在编译期（Android 主流） |
| **ASP.NET Core** | 运行时 | 反射 + 表达式树缓存 | 内置；ValidateScopes 抓被俘获依赖 |
| **FastAPI `Depends`** | 运行时 | 函数签名内省 | 依赖就是函数，天然支持嵌套与缓存 |

**Dagger 的编译期路线值得单独说**：

```text
它在编译期【生成】出与手工装配一模一样的代码
→ 运行时零反射（C# 版实测反射解析慢 48x，这里直接消除）
→ 依赖缺失/循环依赖在【编译期】报错（比启动期更早）
→ 代价: 构建变慢（第 54 章的注解处理器）、生成代码需要调试时理解
→ 这与第 51 章 ORM 的「C++ 靠代码生成绕过反射缺失」是同一个思路
```

## 12. 性能分析

### 本章实测数字速查

```text
容器解析:     0.36 μs/次 vs 手工 new 0.01 μs/次（慢 48x）
C++ 两条路:   虚函数 1.60 ns/次 vs 模板 0.48 ns/次（快 3.3x）
单例:         三处注入 1 个实例（生命周期正确时的收益）
```

### 什么时候容器的开销要紧

```text
不要紧: Web 请求（毫秒级）里解析几十个对象——0.36 μs × 50 = 18 μs，可忽略
要紧:   ① 每次循环都 Resolve（应该在循环外解析一次）
        ② 启动时间敏感（Serverless 冷启动、Android 应用启动）→ 用编译期 DI
        ③ 热路径上的虚函数调用（C++ 实测 3.3x）→ 用模板
```

> ⚠️ **DI 的真正代价不是性能，是间接层**。每加一个接口就多一次「跳转去看实现」的认知成本；只有一个实现的接口既没买到可替换性，又付出了理解成本——第 52 章说的「该 mock 什么」在这里变成「该抽象什么」，判据完全相同：**测试时我需要换掉它吗？**

## 13. 工程实践

| 场景 | ✅ 推荐 | ❌ 避免 | 原因 |
|------|--------|--------|------|
| 默认注入方式 | 构造器注入 | 字段注入 | 实测循环依赖启动即报错、依赖可 final |
| 小项目/库 | 手工装配（Poor Man's DI） | 引入容器 | DI ≠ 容器；库引容器会强加给使用者 |
| 生命周期 | 短依赖不被长依赖持有 | Singleton 依赖 Scoped | 实测跨请求状态泄漏 |
| 单例里用 scoped | `IServiceScopeFactory` 现开 scope | 直接注入 | 同上 |
| 该注入什么 | 外部世界（DB/HTTP/时钟/随机） | 纯数据结构、值对象 | 判据: 测试时需要换吗 |
| 接口数量 | 有多实现或需替换时才建接口 | 每个类配一个接口 | 只有一个实现 = 纯粹的间接层 |
| 组装位置 | 组装根（main/入口）唯一 | 业务代码里 `new` | 全项目搜 `new`，应只在组装根 |
| Spring 横切失效 | 拆 bean 或注入自身代理 | 疑惑「为什么没生效」 | 实测代理绕过是自调用的必然 |
| Python 测试 | 构造器注入 | 大量 `mock.patch` | patch 耦合「谁在哪 new 了什么」 |
| C++ 热路径 | 模板编译期注入 | 虚函数 | 实测 3.3x |
| 启动敏感场景 | 编译期 DI（Dagger/源生成器） | 运行时反射容器 | 零反射 + 编译期报错 |

### 一句话决策

```text
写一个类时问三件事:
  ① 它自己 new 了什么？        → 那就是它无法被替换的部分
  ② 那些东西测试时要换掉吗？   → 要 → 提到构造器参数上
  ③ 需要容器吗？               → 对象图小就手工装配，大了再上容器
```

## 14. 最佳实践

- **默认用构造器注入**：实测它让循环依赖在启动期就报错、让依赖可 `final`、让测试必须显式传参。
- **区分 DI 与 DI 容器**：实测手工装配就是纯粹的 DI；小项目和库不该引入容器。
- **长生命周期绝不依赖短生命周期**：实测被俘获的依赖让第 2 次请求用着第 1 次的上下文——这是安全事故不只是 bug。
- **只为「需要替换的东西」建接口**：判据与第 52 章的「该 mock 什么」完全相同；只有一个实现的接口是纯粹的间接层。
- **把 `new` 收敛到组装根**：全项目搜 `new Xxx()`/`make_shared`，应该只在入口附近出现。
- **Python/JS 里优先构造器或工厂，而非猴子补丁**：实测 patch 能用，但它把测试耦合到了「谁在哪里 new 了什么」。
- **C++ 热路径用模板注入**：实测比虚函数快 3.3x；可配置的部分再用虚函数。
- **启动敏感场景用编译期 DI**：Dagger/源生成器把装配代码生成出来，零反射且错误提前到编译期。

## 15. 常见坑

**坑 1 · Singleton 依赖 Scoped（被俘获的依赖）**

```csharp
services.AddSingleton<MyService>();   // ⚠️ 它依赖 Scoped 的 DbContext
// 实测: 第 2 次请求仍用着第 1 次的 RequestContext
// ✅ 注入 IServiceScopeFactory，用时现开 scope
```

**坑 2 · 字段注入掩盖循环依赖**

```java
@Autowired private B b;    // ⚠️ 循环依赖能「成功」启动，对象一度是半成品
// ✅ 构造器注入 —— 实测容器直接报「循环依赖: A → B → A」
```

**坑 3 · Spring 自调用导致横切失效**

```java
public void outer() { this.inner(); }        // ⚠️ 绕过代理，@Transactional 不生效
@Transactional public void inner() { ... }
// ✅ 拆成两个 bean，或注入自身代理
```

**坑 4 · 每个类都配一个接口**

```text
⚠️ IUserService/UserService、IOrderService/OrderService …… 接口只有一个实现
✅ 只在「有多实现」或「测试需替换」时建接口
```

**坑 5 · 在循环里 Resolve**

```csharp
for (int i = 0; i < 100000; i++) container.Resolve<IRepo>();   // ⚠️ 实测 0.36 μs × 10 万
// ✅ 循环外解析一次
```

**坑 6 · Python 的可变默认参数**

```python
def f(mailer=Mailer()):    # ⚠️ 默认值在【定义时】求值一次，全局共享
def f(mailer=None):        # ✅ 函数体里兜底
```

**坑 7 · 库里引入 DI 容器**

```text
⚠️ 库依赖某个容器 → 使用者被迫接受你的容器选择（第 53 章依赖冲突的常见来源）
✅ 库暴露构造器/工厂函数，让使用者自己决定怎么装配
```

## 18. 本章总结

**一句话**：依赖注入的内核只有一句——**不要自己找依赖，让依赖被送进来**——它把「用哪个实现」的决定权从使用者挪到组装者手里（**控制反转**），而这个简单转变同时买到了可测性（第 52 章实测的替身得以塞入）、可替换性和**启动期的错误暴露**；本章手写的 DI 容器揭示了它只做三件事——**反射找构造器 → 递归解析参数 → 装配实例**（40 行即 Spring 骨架，是第 30 章反射与第 51 章对象图构建的合流），另加两项职责：**生命周期**（实测 `@Singleton` 三处注入只造 1 个实例）与**循环依赖检测**（实测精确报出 `A → B → A`，而这正是**构造器注入优于字段注入的最大理由**——它把设计问题变成启动失败，而非运行时的半成品对象）；C# 版实测了 DI 最经典的生产事故 **被俘获的依赖**（`Singleton` 持有 `Scoped` 仓储 → 第 2 次请求仍用着第 1 次的 `RequestContext`，真实后果是连接/事务/用户身份跨请求泄漏），并量出容器的代价（解析 0.36 μs/次 vs 手工 new 0.01 μs，慢 48x 但绝对值在毫秒级请求前可忽略）；Python 版给出反向视角——动态语言里依赖写死也能换掉（改实例属性、`mock.patch` 换模块名字绑定均实测成功），这解释了「Python 不太需要容器」，但也点破了代价：**patch 把测试耦合到了「谁在哪里 new 了什么」**；JS 版展示了函数式 DI（闭包即容器、部分应用即注入）；C++ 版量出编译期注入比虚函数快 **3.3x**，并指出它几乎没有 DI 容器的原因与第 51 章 ORM 完全相同——**没有运行时反射**；最后，DI 与**服务定位器**只差一个方向：前者把依赖写进构造器签名（公开、编译期可见、测试必须传），后者藏在方法体里（隐藏、看签名不知道要什么）——**这就是后者被视为反模式的全部理由**。

**关键要点**

- **内核一句话**：不要自己找依赖，让依赖被送进来；DI ≠ DI 容器（手工装配就是纯粹的 DI）。
- **容器只做三件事**（手写实测）：反射找构造器、递归解析参数、装配实例；外加生命周期与查环。
- **构造器注入优于字段注入**（实测）：循环依赖启动即报错，而非运行时的半成品对象。
- **生命周期硬规则**（实测）：长生命周期不能依赖短生命周期——否则就是被俘获的依赖。
- **被俘获的依赖是安全事故**（实测跨请求复用 `Request#4`）：连接、事务、用户身份都会泄漏。
- **容器的代价可忽略但间接层不可忽略**（实测慢 48x，绝对值 0.36 μs）：真正的成本是认知负担。
- **动态语言的 DI 更轻**（实测猴子补丁可行），但补丁会让测试耦合实现细节。
- **DI vs 服务定位器**：推 vs 拉、公开 vs 隐藏——这是「反模式」判定的唯一依据。

**自查清单**

- [ ] 我能区分控制反转、依赖注入、DI 容器三个概念。
- [ ] 我能手写一个支持自动装配与查环的最小容器。
- [ ] 我知道三种注入方式的失败形态，并默认使用构造器注入。
- [ ] 我能识别被俘获的依赖，并说出生命周期的硬规则。
- [ ] 我用「测试时需要换掉它吗」判断该不该抽象与注入。

**下一章预告**：DI 解决的是「依赖从哪来」，但依赖之间怎么组织、对象怎么创建、行为怎么扩展——这些反复出现的问题各自都有被验证过的解法。第 56 章讲**设计模式**：我们会实测**策略模式与函数指针的等价性**（在函数是一等公民的语言里，一半的经典模式退化成一个函数）、观察者模式与事件循环的关系（第 43 章）、单例在多线程下的正确实现（第 41 章的双重检查锁定为何一度是错的），以及最重要的——**为什么「模式」在不同语言里的必要性天差地别**：C++ 需要三十行的策略模式，在 Python 里就是传一个函数。
