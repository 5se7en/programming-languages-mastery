# 第 57 章 · 性能优化

**简体中文** ｜ [English](./57-performance.en-US.md)

---

> 性能优化是本书最容易被直觉带偏的一章。前面 56 章里，你的直觉大体是可靠的——类型系统怎么设计、并发怎么同步、事务怎么隔离，想清楚了就基本对了。**性能不是这样的**：它取决于缓存层级、编译器改写、JIT 状态、分支预测器、GC 的分代结构——这些东西没有一个写在你的源代码里。
>
> 本章的**钥匙实验**在 Python 里放了两个函数：一个是三层循环里做字符串拼接（`slow_looking`），一个是一行成员判断（`actually_slow`）。凭感觉，几乎所有人都会去优化前者。实测：`slow_looking` **5.0 ms（占 1%）**，`actually_slow` **426.2 ms（占 99%）**。把「看起来最可疑」的那个优化到极致，整体最多快 **1.01x**。而真正的瓶颈只需要把一个 `[]` 换成 `set()`——**快 191 倍，改动两行**。
>
> 这个 1% vs 99% 不是精心构造的极端案例，而是真实项目里的常态。**阿姆达尔定律**给出了它的数学形式：优化占比 p 的部分，加速比的天花板是 `1/(1-p)`。一个占 1% 的热点，哪怕加速一千倍，整体也只快 1.01 倍。所以性能工作的第一步永远不是「怎么优化」，而是**「该优化哪里」**——而回答这个问题唯一可靠的方法是 profiler，不是读代码。
>
> C++ 版量化了「大 O 之外」的那个变量。`vector` 和 `list` 遍历都是 O(n)，教科书说它们复杂度相同——实测 **0.3 ms vs 3.6 ms，差 12.8 倍**。更纯净的对照是同一个数组、同样多的元素、只改访问顺序：顺序 **0.6 ms**，乱序 **4.0 ms**，**差 7.0 倍**。指令数完全一样，内存总量完全一样，差距 100% 来自**缓存与硬件预取**。这就是第 16 章缓存局部性在真实数据结构上的分量。
>
> 但本章最有价值的实验是**失败的那些**。C++ 里那个 StackOverflow 史上最高票问题「为什么处理有序数组更快」（分支预测），在今天的编译器下**复现不出来了**——实测差距仅 **1.0x**。原因不是分支预测不重要，而是编译器把 `if` 编译成了**条件移动指令**（`csel`/`cmov`），根本没有分支可预测。加上内存屏障强行保留真实分支后，差距才回到 **11.0 倍**。同样地，JavaScript 里流传甚广的「对象属性顺序不同会变慢」，实测 **4 种形状只慢 3%**——V8 的多态内联缓存早已能高效处理少数几种形状，真正的悬崖在 **30 种形状（慢 2.87x）**。
>
> Java 版则展示了微基准最危险的假象：同一个函数调用两千万次，**丢弃返回值 0.0 ms，累加返回值 4.5 ms，相差 4547 倍**。不是优化让它快了 4547 倍，而是 C2 编译器判定「结果没人用」，**把整个两千万次循环删掉了**。而 C# 版修正了「堆分配很贵」这个粗糙说法：分配 **305 MB** 纯垃圾、触发 38 次 Gen0 回收，代价只有 **1.2x**；真正决定 GC 成本的是**存活量**——实测一次完整回收在存活 0 / 100 万 / 400 万个对象时分别耗时 **1.0 / 3.8 / 13.6 ms**。
>
> 一句话概括本章：**关于性能的常识会过期，唯一不会过期的是「当场测量」。**

## 1. 学习目标

学完本章，你将能够：

- 用**阿姆达尔定律**在动手之前算出一个优化的**收益上限**，并解释为什么「找对地方」比「优化得多彻底」重要得多；
- 使用六种语言各自的 profiler 定位热点，并说清为什么**读代码猜热点的失败率极高**（实测 1% vs 99%）；
- 量化**缓存局部性**对性能的影响，并解释为什么同样 O(n) 的两段代码能差一个数量级；
- 识别微基准的三大陷阱——**没预热、被死代码消除、只测一次**——并写出不会自欺的测量代码；
- 说清**分配量 vs 存活量**在 GC 语言里的不同代价，以及为什么「分配量」是比「耗时」更好的指标；
- 判断一条流传的性能「常识」是否已经过期，并知道**怎么当场验证它**。

## 2. 为什么会出现这个概念

### 2.1 一个真实的场景

一个接口慢了。你打开代码，看到这样一段：

```python
def build_report(orders):
    lines = []
    for o in orders:                      # 一万条订单
        for item in o.items:              # 每条平均 5 个商品
            lines.append(format_line(item))   # 三层嵌套，看起来很可疑
    return "\n".join(lines)
```

三层嵌套、五万次字符串格式化——「瓶颈肯定在这」。于是你花两天把 `format_line` 改写成模板预编译，本地测出这一段快了 3 倍。上线后**接口耗时几乎没变**。

原因是：这段代码只占总耗时的 4%。剩下 96% 在一个你没看的地方——`o.items` 是 ORM 的懒加载属性，每次访问都发一条 SQL（第 51 章实测过：**201 条 SQL vs 1 条**）。

这不是编造的故事，它是性能工作中最常见的失败模式。而它的根因只有一个：**在测量之前就开始优化**。

### 2.2 直觉为什么在性能上特别不可靠

前面 56 章里，你的直觉建立在**源代码的语义**上——这段代码做了什么、调用了谁、状态怎么变。这套直觉在讨论正确性时基本够用。

但性能不由源代码语义决定，它由**执行时的物理现实**决定：

| 你看到的 | 实际发生的 | 差距来源 |
|---|---|---|
| `for x : list` 和 `for x : vector` 都是 O(n) | 一个顺序读内存，一个每次跳到堆上随机位置 | **缓存**（实测 12.8x） |
| `if (x >= 128)` 是一个分支 | 编译器可能把它变成无分支的条件移动 | **编译器改写**（实测差距从 11x 塌到 1x） |
| `pure(i)` 被调用了两千万次 | JIT 发现结果没人用，整个循环被删掉 | **死代码消除**（实测 4547x 的假象） |
| `new Point(...)` 是一次堆分配 | JIT 做了标量替换，根本没分配 | **逃逸分析**（实测单次成本差 11.6x） |
| `obj.x` 是一次属性读取 | 可能是一条机器指令，也可能是一次哈希查找 | **内联缓存状态**（实测 2.87x） |
| `alloc 305 MB` 听起来很贵 | 全是垃圾的话，GC 根本不用碰它们 | **分代假说**（实测代价仅 1.2x） |

**这六行里没有一行能从源代码看出来。**它们全都要测。

### 2.3 阿姆达尔定律：优化的天花板

1967 年 Gene Amdahl 提出了一个关于并行加速的公式，但它对任何局部优化都成立：

```
                    1
加速比上限 = ───────────────────
             (1 - p) + p / s
```

其中 `p` 是被优化部分占总耗时的比例，`s` 是这一部分的加速倍数。令 `s → ∞`：

```
加速比上限 = 1 / (1 - p)
```

Python 版对这个公式做了实测验算：

```
把「字符串拼接」（占 1%）加速    2x → 总耗时 431 → 429 ms（整体快 1.01x）
把「字符串拼接」（占 1%）加速   10x → 总耗时 431 → 427 ms（整体快 1.01x）
把「字符串拼接」（占 1%）加速 1000x → 总耗时 431 → 426 ms（整体快 1.01x）
把「成员判断」  （占 99%）加速   2x → 总耗时 431 → 218 ms（整体快 1.98x）
把「成员判断」  （占 99%）加速  10x → 总耗时 431 →  48 ms（整体快 8.94x）
把「成员判断」  （占 99%）加速 1000x → 总耗时 431 →   5 ms（整体快 79.9x）
```

**占 1% 的那块哪怕加速一千倍，整体也只快 1.01 倍。**这就是为什么「先 profile」不是一句客套的忠告，而是一道**数学上的闸门**：不知道 p，你根本不知道值不值得动手。

## 3. 底层原理

### 3.1 延迟的数量级：一张必须刻在脑子里的表

性能直觉的地基是**知道各种操作差几个数量级**。下面是一组广为流传的量级（具体数字随硬件变化，但**相对关系**极其稳定）：

```
L1 缓存命中                    ~1 ns        ┐
L2 缓存命中                    ~4 ns        │ 差 100 倍
主存访问（缓存缺失）            ~100 ns      ┘
                                            
分支预测失败                   ~10-20 ns
系统调用                       ~100 ns - 1 μs
SSD 随机读                     ~100 μs      ┐
                                            │ 差 100 倍
机械硬盘寻道                   ~10 ms       ┘
同机房网络往返                 ~0.5 ms
跨大洲网络往返                 ~150 ms
```

关键不是记住绝对值，而是记住**台阶**：缓存缺失比命中贵约 100 倍，磁盘比内存贵约 1000 倍，跨洲网络比同机房贵约 300 倍。

这张表直接解释了本章的实验结果。C++ 版的 vector vs list：两者指令数相同，但 list 每个节点都是一次可能的缓存缺失。**12.8 倍的差距 = 100 倍的单次代价 × 有多少比例真的缺失。**

### 3.2 缓存局部性：为什么「同样的 O(n)」能差一个数量级

CPU 不是按字节读内存的，它按**缓存行**（cache line，通常 64 字节）读。这意味着：

```
读 vec[0] → 硬件把 vec[0..15] 整条缓存行拉进 L1（16 个 int）
读 vec[1] → 已经在 L1 里，几乎免费
...
读 vec[15] → 已经在 L1 里
读 vec[16] → 新的缓存行，但硬件预取器早就预判到了，已经在路上
```

而链表：

```
读 node1->val → 一次缓存缺失（~100 ns）
node1->next   → 指向堆上某个随机地址
读 node2->val → 又一次缓存缺失（预取器无法预判随机地址）
```

**大 O 只数「操作次数」，不数「每次操作有多贵」。**这是算法课留下的最大盲区。

C++ 版做了一个更纯净的实验来隔离这个变量——**同一个数组、同样多的元素、只改访问顺序**：

```cpp
for (int i : idxSeq)  a1 += vec[i];   // 顺序: 0,1,2,3,...
for (int i : idxRand) a2 += vec[i];   // 乱序: 同样的下标，只是洗过牌
```

指令数完全相同、访问的内存总量完全相同、结果完全相同。实测 **0.6 ms vs 4.0 ms（7.0 倍）**——差距 100% 来自缓存与预取。

### 3.3 编译器：你写的不是运行的

现代编译器会大幅改写你的代码。三个与性能测量直接相关的改写：

**① 死代码消除（DCE）**——如果一个计算的结果没人用，整个计算可以被删除。

**② 条件移动（conditional move）**——`if (c) x = a;` 可以编译成「两边都算，按条件选」的无分支指令（x86 的 `cmov`、ARM 的 `csel`）。这消除了分支预测失败的代价，但也**消除了分支预测实验**。

**③ 标量替换（scalar replacement）**——如果一个对象不逃逸出当前方法，JIT 可以把它的字段直接放进寄存器，**根本不分配**。

这三条的共同后果是：**微基准里测到的可能不是你以为在测的东西**。本章的 C++ 和 Java 实验各踩了一次这个坑，并且都保留在了示例里——因为踩坑本身就是这一课。

### 3.4 JIT：同一段代码有多个速度

在 JVM、CLR、V8 上，一段代码的执行速度取决于它**已经跑了多少次**：

```
第 1~N 次:   解释执行字节码            （慢）
计数器达标:   C1/基线编译器编译为机器码   （中）
继续变热:     C2/优化编译器，激进优化    （快）
假设失效:     去优化（deoptimize），退回解释执行
```

Java 版实测同一个 `compute(2_000_000)` 连跑 8 次：

```
1.7  1.2  1.0  0.9  0.9  0.9  0.9  0.9  ms
第 1 次 1.7 ms → 第 8 次 0.9 ms（快 2.0x）
```

**不预热就计时，你测到的是解释器的速度**——与生产环境毫无关系。第 52 章实测过它的后果：不预热让一个并行加速比从 5.78x 掉到 1.92x。

而 CPython 没有 JIT，Python 版实测预热效应**小到测不出来**（相差 ±2%，落在噪声范围内）。**「要不要预热」本身就是语言相关的**——这是本章最容易被跨语言照搬害到的一条。

### 3.5 GC：分配便宜，存活才贵

第 33 章讲过现代分配器的指针碰撞：分配一个对象往往只是 `ptr += size`，几纳秒。第 36 章讲过分代假说：**绝大多数对象在年轻时就死了**。

把这两条合起来，就得到一个反直觉的结论：**扔掉的垃圾几乎是免费的**。分代 GC 的标记-复制过程只遍历**存活**对象，然后把它们搬到新区域——**死对象从头到尾没有被访问过一次**。

C# 版直接测了这个因果：

```
存活        0 个对象时，一次 Gen2 完整回收:    1.0 ms
存活  1000000 个对象时，一次 Gen2 完整回收:    3.8 ms
存活  4000000 个对象时，一次 Gen2 完整回收:   13.6 ms
```

耗时随**存活对象数**单调增长，与已经死掉的垃圾量几乎无关。所以准确的原则不是「别分配」，而是：

> **别让短命对象活过 Gen0。**真正该警惕的是缓存和静态集合——它们把对象钉在老年代，每次完整回收都要重新遍历一遍。

### 3.6 动态语言的形状假设：内联缓存

V8、CLR、JVM 都用同一个思路加速动态派发：**假设下次和上次一样**。

```
obj.x 第一次执行   → 查找 x 的偏移量，把「隐藏类 H → 偏移 8」缓存在这个访问点
obj.x 再次执行     → 如果对象还是 H，直接读偏移 8（一条指令）
                    如果不是 H，缓存里再加一条（多态）
                    形状太多（>4~8 种）→ 放弃缓存，退化成哈希查找（超多态）
```

JavaScript 版实测了这三档：

```
单态（1 种形状）:    18.0 ms
多态（4 种形状）:    18.5 ms（1.03x）
超多态（30 种形状）: 51.5 ms（2.87x）
```

**关键发现：几种形状几乎没有代价。**这直接推翻了流传很广的「对象属性顺序不同就会变慢」——多态内联缓存能高效处理少数几种形状。真正的悬崖在超多态：一个通用函数处理来自十几个不同 API 的对象，那才是问题。

## 4. JavaScript

JS 版聚焦 V8 的**对象形状**——这是 JS 性能里最大的隐形变量。

### 4.1 内联缓存的三档

```javascript
/** 造一个数组，其中的对象共有 shapes 种不同的「形状」 */
function buildShapes(shapes) {
  const arr = [];
  for (let i = 0; i < N; i++) {
    const o = { x: i };                                   // 每个对象都有 x
    for (let k = 0; k < i % shapes; k++) o['f' + k] = k;  // 额外字段数不同 → 不同隐藏类
    arr.push(o);
  }
  return arr;
}

// 关键: 每次都【新建一个函数】，让它有自己独立的内联缓存
const freshSum = () => new Function('arr', 'let s=0;for(const o of arr)s+=o.x;return s;');
```

那个 `new Function` 不是装饰。这个实验**第一次写的时候测反了**：三个数组共用同一个求和函数，那个函数的内联缓存同时见过全部三种情况，于是三档一样慢。**测量代码本身成了被测系统的一部分**——这是微基准最隐蔽的坑。

```
单态（1 种形状）:    18.0 ms
多态（4 种形状）:    18.5 ms（1.03x）
超多态（30 种形状）: 51.5 ms（2.87x）
```

### 4.2 数组的元素种类

V8 的数组有**元素种类**（elements kind）：SMI（小整数）→ DOUBLE → 通用。它只能**单向降级，永不回升**。

```javascript
const mixed = new Array(M);
for (let i = 0; i < M; i++) mixed[i] = i;
mixed[Math.floor(M / 2)] = 'oops';             // ⚠️ 一个字符串，让整个数组降级
```

```
全小整数数组求和:  2.1 ms
全浮点数组求和:    1.8 ms
混入一个字符串后:  3.7 ms（比小整数慢 1.7x）
```

**一个字符串就能让整个数组从紧凑存储降级为装箱的通用数组。**要极致性能就用 `TypedArray`（`Float64Array`），它在类型上根本不允许降级。

### 4.3 delete 的代价

```javascript
const o = { x: i, tmp: 0, y: i };
delete o.tmp;                                  // ⚠️ 破坏隐藏类链 → 字典模式
```

```
保留 tmp 字段的 1000000 个对象求和: 5.9 ms
delete o.tmp 之后:              10.7 ms（慢 1.8x）
改成 o.tmp = null:              7.7 ms（慢 1.3x）
```

`delete` 让 V8 把对象转成**字典模式**（用哈希表存属性）。想清空一个字段就赋 `null`——实测比 `delete` 快，但仍不如一开始就别留这个字段。

### 4.4 但先别急着优化这些

```
前端: 网络往返 > 主线程阻塞 > 重排重绘 >> 这里说的 JS 执行细节
Node: I/O 等待 > 序列化(JSON) > 数据库查询 >> JS 细节
```

上面三个实验的差距虽然是几倍，但它们作用的时间在真实应用里通常只占几个百分点。**阿姆达尔定律永远是第一道闸门。**

## 5. Python

Python 版是本章的方法论主线：**先猜，再测，看猜得对不对**。

### 5.1 钥匙实验

```python
def slow_looking(n):
    """看起来最可疑: 循环里做字符串拼接"""
    parts = []
    for i in range(n):
        parts.append(str(i))
    return "".join(parts)


def actually_slow(n):
    """看起来无辜: 一行成员判断——但 seen 是 list，每次都要 O(len) 线性扫描"""
    seen = []                                    # ⚠️ 用 list 做去重
    for i in range(n):
        key = i % 3000                           # 3000 个不同值 → list 最终长 3000
        if key not in seen:                      # ⚠️ 这一行是 O(len(seen))
            seen.append(key)
    return len(seen)
```

```
slow_looking:       5.0 ms（占比 1%）
actually_slow:    426.2 ms（占比 99%）
```

`key not in seen` 是**一行代码**，读起来像一次查找，实际是一次线性扫描——而且随着 `seen` 变长，扫描越来越慢。这个 O(n²) 藏在一个 `in` 里。

### 5.2 profiler 直接指出来

```
   ncalls  tottime  percall  cumtime  percall filename:lineno(function)
        1    0.427    0.427    0.427    0.427 main.py:18(actually_slow)
        1    0.006    0.006    0.008    0.008 main.py:10(slow_looking)
        1    0.000    0.000    0.435    0.435 main.py:36(workload)
```

按 `tottime` 排序，**第一行就是答案**。这一步的成本是一分钟，而猜错的成本是几天的无效优化。

> `tottime`（函数自身耗时）与 `cumtime`（含子调用）的区别很关键：找热点看 `tottime`，找「哪条调用链最贵」看 `cumtime`。

### 5.3 修复往往很小

```python
def fast_version(n):
    seen = set()          # 就这一处
    for i in range(n):
        seen.add(i % 3000)
    return len(seen)
```

```
用 list 做成员判断:    413.1 ms
换成 set:               2.2 ms（快 191x）
```

**改动量：一个 `[]` 换成 `set()`。**收益：O(n) 的成员判断变成 O(1)（第 20 章哈希表）。

性能优化绝大多数时候不是精雕细琢，而是**找到那个用错的数据结构**。

### 5.4 三个微基准陷阱

```
陷阱一 —— 测了个空循环:
  timed(lambda: None) 单次 0.028 μs —— 这是【测量本身】的开销
  → 被测代码若比这还快，你测到的全是噪声

陷阱二 —— 忘了预热:
  第一次 9.6 ms vs 预热后平均 9.8 ms（相差 -2%，落在波动范围内）
  → Python 没有 JIT，预热效应【小到测不出来】

陷阱三 —— 只测了一次:
  同一段代码跑 7 次: min 9.4 / 中位数 9.5 / max 9.7 ms（波动 1.03x）
  → 判断一个优化是否真实有效，前提是差距【大于这个波动】
```

第三条是最常被忽略的：**如果你的优化只带来 5% 的改善，而测量波动是 10%，你什么都没证明。**

## 6. Java

Java 版专门测「为什么 JVM 上的微基准这么难写」。

### 6.1 死代码消除：4547 倍的假象

```java
/** 一个纯函数——极易被内联，因而也极易被死代码消除 */
static int pure(int x) { return x * 31 + 7; }

/** 把循环放进【独立方法】，才能被 C2 正常编译（写在 main 里只能走 OSR 编译） */
static void discardLoop(int n) { for (int i = 0; i < n; i++) pure(i); }
static long accumulateLoop(int n) {
    long s = 0;
    for (int i = 0; i < n; i++) s += pure(i);
    return s;
}
```

```
调用 pure() 20000000 次，【丢弃】返回值:     0.0 ms
调用 pure() 20000000 次，【累加】返回值:     4.5 ms
差距 4547x（累加结果 6199999830000000，证明它真的算了）
```

丢弃版耗时归零：C2 判定「结果没人用」，**把整个两千万次循环删掉了**。

这是微基准最常见的假象：你以为测出了「优化后快 100 倍」，实际上是**被优化的那份代码根本没运行**。

> 注释里那句「循环必须放进独立方法」是踩坑踩出来的：最初把循环写在 `main` 里，两个版本测出 324 ms vs 183 ms——差距只有 1.8x，与隔离测试的结果完全对不上。根因是 `main` 里的循环只能走 **OSR（栈上替换）编译**，优化程度与标准 C2 编译不同。**基准代码放在哪个方法里，会改变测量结果。**

### 6.2 逃逸分析

```java
for (int i = 0; i < M; i++) {
    int[] pair = {i, i + 1};        // 局部数组，不逃逸 → 标量替换，根本不分配
    sumA += pair[0] + pair[1];
}
```

```
不逃逸的对象 20000000 次:    11.1 ms（0.55 ns/次）
逃逸的对象   1000000 次:      6.4 ms（6.42 ns/次）
单次成本差 11.6x
```

不逃逸的对象被**标量替换**：字段直接放寄存器，没有堆分配。这是「Java 对象分配很贵」这个说法过时的原因之一。

但反过来说：**你的微基准里如果对象不逃逸，测的就不是真实场景的分配成本。**

### 6.3 字符串拼接：少数「凭经验就能判断」的优化

```
循环里 s += "x" 20000 次:         14.7 ms
StringBuilder.append 20000 次:     2.3 ms（快 6x）
```

`String` 不可变（第 9 章）→ 每次 `+=` 复制整个字符串 → O(n²)。

注意边界：**单条语句里的 `a + b + c` 会被编译器优化成 `StringBuilder`，但跨循环迭代的累加优化不掉。**

## 7. C++

C++ 版量化第 16 章的缓存局部性——以及编译器如何毁掉一个经典实验。

### 7.1 四组缓存实验

```
vector 遍历 4000000 个元素:     0.3 ms
list   遍历 4000000 个元素:     3.6 ms（慢 12.8x）

顺序访问 4000000 个元素:        0.6 ms
乱序访问【同样的】元素:         4.0 ms（慢 7.0x）

行优先遍历 2000x2000:           0.3 ms
列优先遍历 2000x2000:           1.1 ms（慢 4.1x）

AoS（结构体数组，每个 64 字节）只求和 x:  1.1 ms
SoA（分离的 x 数组）             求和 x:  0.5 ms（快 2.2x）
```

四个实验，四种形态，同一个原因：**数据在内存里是不是连着的**。

AoS vs SoA（Array of Structs vs Struct of Arrays）值得单说：

```cpp
struct Particle { float x, y, z, vx, vy, vz; char pad[40]; };  // 64 字节
std::vector<Particle> aos;      // 只求和 x，却把整个 64 字节拉进缓存
std::vector<float>    soaX;     // 只拉 x 的那个数组，一条缓存行装 16 个
```

游戏引擎和数值计算大量使用 SoA，正是这个原因（**数据导向设计**）。

### 7.2 那个失败的分支预测实验

「为什么处理有序数组更快」是 StackOverflow 史上最高票的问题之一。本章想复现它，结果**复现不出来**：

```
版本 A（编译器自由优化）:
  已排序    0.3 ms   未排序    0.3 ms   → 差距仅 1.0x
```

诊断过程：用 `-O0` 重新编译，差距回到 2.3x；再 `objdump | grep csel`，找到了一条 `csel` 指令。**编译器把 `if` 编译成了条件移动**——「两条路都算，按条件选结果」，根本没有分支，自然无所谓预测。

于是改成两版对照，用内存屏障强制保留真实分支：

```cpp
// 版本 A: 让编译器自由发挥
for (int x : sorted_) if (x >= 128) c1 += x;

// 版本 B: 用内存屏障【强制保留真实分支】（屏障只能在分支成立时执行，编译器无法条件移动）
for (int x : sorted_) if (x >= 128) { __asm__ volatile("" ::: "memory"); c3 += x; }
```

```
版本 A（编译器自由优化）: 已排序 0.3 ms   未排序  0.3 ms   → 差距仅 1.0x
版本 B（屏障强制保留分支）: 已排序 0.9 ms   未排序 10.2 ms   → 差距 11.0x
```

**分支预测依然重要（11 倍），但那个经典实验已经测不出它了。**这是本章的核心论点：关于性能的常识会过期。

### 7.3 构建配置：一个足以颠倒结论的变量

本仓库的 `run-all.sh` 为了让所有章节可复现，统一用**不带 `-O` 的默认编译**（即 `-O0`）。于是同一份代码：

| | `-O0`（harness 默认） | `-O2` |
|---|---|---|
| vector 遍历 4M | 11.4 ms | **0.3 ms** |
| vector vs list | 1.7x | **12.8x** |
| 分支预测版本 A | 2.4x（有分支） | **1.0x（被改成 csel）** |

**同一段基准代码，在两个优化级别下能得出完全相反的结论。**所以示例本身会打印它的构建配置：

```cpp
#ifdef __OPTIMIZE__
    printf("【构建配置】开启了优化（-O2 或更高）——这是性能测量应有的配置\n");
#else
    printf("⚠️【构建配置】未开启优化（-O0）——本章测得的所有数字都会因此偏离真实性能\n");
#endif
```

**任何性能数字都必须注明构建配置**，否则它不可复现，也就不构成证据。

## 8. C#

C# 版聚焦 GC 语言里最常见的那笔开销——**热路径上的内存分配**——并修正了一个流传很广的粗糙说法。

### 8.1 「堆分配很贵」到底有多贵

```csharp
record Point(double X, double Y);                 // 引用类型: 每次 new 都在堆上
readonly record struct PointS(double X, double Y); // 值类型: 栈上，无 GC
```

```
record class（每次都在堆上 new）:   163.2 ms，分配  305 MB，Gen0 38 次
record struct（栈上，零分配）:       77.7 ms，分配    0 MB，Gen0  0 次
→ 只快 2.1x —— 【远小于直觉预期】
```

分配了 **305 MB**、触发了 **38 次** Gen0 回收，代价只有约 2 倍（重复运行在 1.2x~2.1x 之间浮动）。

那 GC 的成本到底由什么决定？直接测：

```
存活        0 个对象时，一次 Gen2 完整回收:    1.0 ms
存活  1000000 个对象时，一次 Gen2 完整回收:    3.8 ms
存活  4000000 个对象时，一次 Gen2 完整回收:   13.6 ms
```

**回收耗时随存活对象数增长，与已经死掉的垃圾量几乎无关。**

### 8.2 分配量才是稳定的指标

写作本章时，同一份代码重复运行，耗时在 1.2x~2.1x 之间浮动，而**分配量每一次都完全相同**（305 MB / 859.1 MB / 427 MB / 114 MB）。

这就是 C# 版的核心方法论建议：

> **在 GC 语言里，先看分配量再看耗时。**分配量是确定性的，耗时受 GC 触发时机影响会抖动。

`GC.GetTotalAllocatedBytes()` 是本例用的接口；BenchmarkDotNet 默认就会报告它。

### 8.3 三笔典型的隐形分配

```
① 字符串拼接
  循环里 s += "x" 30000 次:      76.290 ms，分配  859.1 MB
  StringBuilder.Append 30000 次:  0.040 ms，分配   61.0 KB
  → 分配量差 14417x

② Substring vs Span
  Substring(50,100) 2000000 次:  25.7 ms，分配  427 MB，Gen0 54 次
  AsSpan(50,100)    2000000 次:   4.7 ms，分配    0 KB，Gen0  0 次
  → 快 6x，几乎零分配

③ 装箱
  装箱成 object  5000000 次:  18.9 ms，分配  114 MB
  泛型 List<int> 5000000 次:  10.1 ms，分配    8 KB
  → 快 1.9x
```

`Span<T>` 是一个**指向已有内存的视图**（第 34 章的指针，被类型系统管住了）——现代解析器和序列化器都建立在它之上，避免为「看一眼」而复制。

装箱那一条呼应第 29 章：**C# 泛型是真泛型**（运行时特化），Java 是类型擦除必须装箱——所以 Java 的 `List<Integer>` 无法避免这笔开销。这是两种泛型设计的直接性能后果。

### 8.4 构建配置（又一次）

示例会检测并打印：

```
⚠️ 本次运行在【Debug】配置下（dotnet run 的默认值）——
   Debug 关闭了 JIT 的大部分优化，上面所有数字在 Release 下都会不同
```

BenchmarkDotNet **会拒绝在 Debug 配置下运行**，就是为了防止这个错误。

## 9. SQL

数据库侧的性能诊断有自己的一套流程，但第一步和其他语言完全一致：**先看事实，不要猜**。

### 9.1 EXPLAIN 是数据库的 profiler

```sql
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE user_id = 42;
```

```
`--SCAN orders                                    ← 全表扫描 20 万行
```

建索引后：

```
`--SEARCH orders USING INDEX idx_user (user_id=?)  ← 走索引
```

**这一行就是诊断结论。**不需要读应用代码，不需要猜。

### 9.2 索引被写法「废掉」的三种形态

```sql
-- ⓐ 列上套函数/表达式
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE user_id + 0 = 42;   → SCAN

-- ⓑ 前导通配的 LIKE
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE status LIKE '%ped'; → SCAN

-- ⓒ 低选择性列
status='paid' 命中 50000 / 200000 行 —— 第 49 章实测过这时全表扫更快
```

**建完索引一定要再 EXPLAIN 一次确认它被用上了。**「加了索引还是慢」十有八九是这三种之一。

### 9.3 覆盖索引与聚合下推

```
`--SEARCH orders USING COVERING INDEX idx_user_amount (user_id=?)
```

计划里出现 `COVERING INDEX` = 需要的列全在索引里，不用回表——而 `SELECT *` 保证了这个优化**永远用不上**（第 47 章）。

聚合下推同理：

```
ⓐ 拉回全部行，应用里循环求和 → 传输 200000 行
ⓑ SUM(amount) 下推给数据库    → 传输 1 行
```

第 51 章实测过这笔账：传输 5 行 vs 100000 行，**慢 86 倍**。

### 9.4 深分页

```sql
SELECT * FROM orders ORDER BY id LIMIT 10 OFFSET 100000;  -- 先扫过并丢弃前十万行
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 10;  -- 键集分页，直接定位
```

`OFFSET` 越翻越慢；键集分页与页码无关。

### 9.5 诊断顺序

```
ⓐ 查询条数: 是不是 N+1？（第 51 章实测 201 条 SQL vs 1 条）
ⓑ 执行计划: SCAN 还是 SEARCH？
ⓒ 返回数据量: SELECT * 拉了多少用不上的列？
ⓓ 锁与事务: 是不是在等锁？事务是不是太长？（第 48/50 章）
ⓔ 最后才是: 加索引、改 schema、加缓存
```

**注意 ⓐ~ⓒ 都不需要改数据库**——绝大多数「数据库慢」其实是查询写法问题。

生产环境用 `pg_stat_statements`（PostgreSQL）或 `performance_schema`（MySQL）找慢查询。关键是它们按**总耗时**排序，而不是单次耗时：**一条 1 ms 但每秒跑一万次的查询，比一条 3 秒但每天跑一次的更值得优化。**这正是阿姆达尔定律在数据库侧的形态。

## 10. 五语言横向对比

| 维度 | JavaScript | Python | Java | C++ | C# | SQL |
|---|---|---|---|---|---|---|
| **主要性能变量** | 对象形状 | 数据结构选择 | JIT 状态 + GC | 缓存局部性 | 分配与存活 | 执行计划 |
| **需要预热** | 是（V8 JIT） | **否**（实测 ±2%） | 是（实测 2.0x） | 否（AOT） | 是（CLR JIT） | 是（缓冲池） |
| **主力 profiler** | `--cpu-prof` / DevTools | `cProfile` | async-profiler / JFR | `perf` / Instruments | dotnet-trace | `EXPLAIN` |
| **微基准框架** | 无标准（自己写） | `timeit` | **JMH** | Google Benchmark | **BenchmarkDotNet** | — |
| **最大的坑** | IC 被测量代码污染 | 测量开销比被测代码大 | **死代码消除** | **编译器改写实验** | Debug/Release 配置 | 索引没被用上 |
| **最稳定的指标** | 多轮最小值 | 多轮中位数 | JMH 的分叉平均 | 多轮最小值 | **分配量** | 逻辑读次数 |
| **本章实测最大差距** | 2.87x（超多态） | **191x**（list→set） | **4547x**（死代码假象） | **12.8x**（vector/list） | 14417x（分配量） | 551x（第 49 章索引） |

### 10.1 三条跨语言通用的规则

本章测了六种语言，真正**跨语言通用**的规则只有三条：

1. **先 profile，再优化**（阿姆达尔定律对所有语言成立）；
2. **循环里的字符串累加是 O(n²)**（Java 实测 6x，C# 实测分配量 14417x）；
3. **用错数据结构的代价远大于任何微优化**（Python 实测 191x）。

其余的一切——预热、逃逸分析、内联缓存、条件移动——**全是语言相关的**。

### 10.2 「怎么测」本身就是语言相关的

这是本章最容易被忽略的一课。同一套微基准方法论：

- 在 **C++** 上要防**编译器**优化掉（`volatile`、内存屏障、`DoNotOptimize`）；
- 在 **JVM/CLR** 上要防 **JIT** 优化掉（预热、Blackhole、逃逸）；
- 在 **Python** 上几乎不用防（没有 JIT），但要防**测量开销**淹没被测代码；
- 在 **JS** 上要防**测量代码自己**污染内联缓存；
- 在 **SQL** 上要防**缓存**（第二次查询命中缓冲池，快得没有意义）。

把一种语言的测量习惯照搬到另一种语言，是本章列出的所有陷阱里最常见的一个。

## 11. 底层实现对比

| 机制 | JavaScript (V8) | Python (CPython) | Java (HotSpot) | C++ | C# (CoreCLR) |
|---|---|---|---|---|---|
| **对象布局** | 隐藏类 + 属性数组 | `dict` / `__slots__` | 对象头 + 字段 | 内存布局即声明顺序 | 对象头 + 字段 |
| **属性/字段访问** | 内联缓存（3 档） | 哈希查找 | 固定偏移 | **编译期偏移** | 固定偏移 |
| **方法派发** | 内联缓存 + 内联 | 字典查找 | vtable + 内联 | vtable / 静态 / 模板 | vtable + 内联 |
| **分配** | 半空间新生代 | 引用计数 + arena | TLAB 指针碰撞 | `malloc` / 栈 / 池 | 指针碰撞 |
| **回收成本** | 与存活量成正比 | 引用计数即时 + 循环检测 | 与存活量成正比 | **无 GC** | 与存活量成正比（实测 1.0/3.8/13.6 ms） |
| **优化编译器** | TurboFan | 无（3.11+ 有专用解释器） | C1 + C2 | GCC/Clang/MSVC | RyuJIT |
| **去优化** | 有 | 无 | 有 | 无 | 有（有限） |

### 11.1 为什么 C++ 不需要预热，也没有去优化

C++ 在编译期就把一切定死：字段偏移、函数地址（除了虚函数）、循环展开、向量化。代价是**没有运行时信息可用**——编译器不知道哪个分支实际更常走，不知道虚函数实际只有一个实现。

JIT 语言反过来：**用运行时信息做更激进的优化**（比如把只有一个实现的虚函数直接内联），代价是这些优化建立在**假设**上，假设失效就要去优化退回。

这个取舍直接决定了两边测量方法的差异。C++ 的数字一测就准；JIT 语言的数字必须**测足够多轮**才有意义。

### 11.2 profile-guided optimization：两边的收敛

现代 C++ 编译器支持 **PGO**：先用插桩版跑一遍真实负载，收集分支频率，再用这些数据重新编译。这本质上是**把 JIT 的运行时信息搬到编译期**。

反过来，JVM 的 AOT（GraalVM Native Image）、.NET 的 ReadyToRun 是**把编译搬到运行前**。

两边在向中间收敛——但**它们收敛不掉的那件事，是测量本身**。

## 12. 性能分析

本节汇总本章全部实测数据。所有数字在 Apple Silicon / macOS 上测得，C++ 为 `-O2`、C# 为 Debug（harness 默认），**相对关系比绝对值重要**。

### 12.1 缓存与内存（C++，`-O2`）

| 实验 | 快的一方 | 慢的一方 | 倍数 |
|---|---|---|---|
| vector vs list 遍历 4M | 0.3 ms | 3.6 ms | **12.8x** |
| 顺序 vs 乱序访问同一数组 | 0.6 ms | 4.0 ms | **7.0x** |
| 行优先 vs 列优先 2000×2000 | 0.3 ms | 1.1 ms | **4.1x** |
| SoA vs AoS（64 字节结构体） | 0.5 ms | 1.1 ms | **2.2x** |
| 分支预测（编译器自由） | 0.3 ms | 0.3 ms | **1.0x** ⚠️ |
| 分支预测（屏障强制保留） | 0.9 ms | 10.2 ms | **11.0x** |

### 12.2 JIT 与运行时（Java）

| 实验 | 数值 |
|---|---|
| JIT 预热（第 1 次 vs 第 8 次） | 1.7 ms → 0.9 ms（**2.0x**） |
| 死代码消除（丢弃 vs 累加返回值） | 0.0 ms vs 4.5 ms（**4547x** 假象） |
| 逃逸分析（不逃逸 vs 逃逸，单次成本） | 0.55 ns vs 6.42 ns（**11.6x**） |
| 字符串拼接 vs StringBuilder（20000 次） | 14.7 ms vs 2.3 ms（**6x**） |

### 12.3 动态语言（JavaScript / Python）

| 实验 | 数值 |
|---|---|
| 内联缓存：单态 / 多态(4) / 超多态(30) | 18.0 / 18.5 / 51.5 ms（**1.03x / 2.87x**） |
| 数组元素种类：SMI vs 混入字符串 | 2.1 ms vs 3.7 ms（**1.7x**） |
| `delete` vs 保留 vs 赋 null | 5.9 / 10.7 / 7.7 ms（**1.8x / 1.3x**） |
| Python 热点占比（猜 vs 实测） | 1% vs **99%** |
| Python list → set 成员判断 | 413.1 ms → 2.2 ms（**191x**） |
| Python 测量开销 | 0.028 μs/次 |
| Python 预热效应 | ±2%（**测不出来**） |
| Python 运行间波动 | 1.03x |

### 12.4 分配与 GC（C#，Debug）

| 实验 | 耗时 | 分配量 |
|---|---|---|
| record class vs struct（5M 次） | 163.2 vs 77.7 ms（1.2~2.1x，浮动） | 305 MB vs **0 MB** |
| Gen2 完整回收（存活 0 / 1M / 4M） | **1.0 / 3.8 / 13.6 ms** | — |
| 字符串 `+=` vs StringBuilder（30000 次） | 76.3 vs 0.040 ms | 859.1 MB vs 61.0 KB（**14417x**） |
| Substring vs AsSpan（2M 次） | 25.7 vs 4.7 ms（**6x**） | 427 MB vs **0 KB** |
| 装箱 vs 泛型（5M 次） | 18.9 vs 10.1 ms（**1.9x**） | 114 MB vs 8 KB |

**注意最后一列**：耗时列在重复运行中浮动，分配量列**每次完全相同**。这就是「先看分配量」的实证依据。

### 12.5 从这些数字里读出的三件事

**① 最大的差距来自数据结构，不是微优化。** 191x（list→set）和 12.8x（vector/list）都是「换个数据结构」，而所有微优化加起来不到 3x。

**② 最大的数字往往是假的。** 4547x 是死代码消除的假象，14417x 是分配量而非耗时。**看到惊人的数字，先怀疑测量方法。**

**③ 有些数字比另一些更值得相信。** 分配量、缓存缺失次数、SQL 逻辑读次数——这些是**计数**，确定性强；耗时是**测量**，受一切干扰。能用计数说明问题时，别用耗时。

## 13. 工程实践

### 13.1 性能预算：把目标写下来

没有目标就没有「优化完成」。性能工作必须从一个**可证伪的数字**开始：

```
首页 P95 < 200 ms
搜索接口 P99 < 500 ms
构建时间 < 90 s
App 冷启动 < 1.5 s
```

注意用 **P95/P99 而不是平均值**：平均值会被大量快请求稀释，而用户感受到的是慢的那部分。一个平均 50 ms、P99 3 s 的接口，意味着**每 100 个用户里有 1 个等了 3 秒**。

### 13.2 USE 方法：从系统层面切入

Brendan Gregg 的 USE 方法给出了一个系统性的检查顺序，对每个资源（CPU、内存、磁盘、网络）检查三件事：

- **U**tilization（使用率）：忙了多少比例的时间？
- **S**aturation（饱和度）：有多少工作在排队？
- **E**rrors（错误）：有没有报错/重试？

这套方法的价值在于**它先排除整类可能**。如果 CPU 使用率只有 5%，那所有 CPU 侧的微优化都不用看了——瓶颈在 I/O 或锁等待。

### 13.3 火焰图：把 profiler 输出变成可读的

采样式 profiler 的输出是几十万条调用栈。火焰图把它们聚合成一张图：

- **横轴是样本数占比**（不是时间轴），越宽的函数占用越多 CPU；
- **纵轴是调用栈深度**；
- **看「平顶」**：宽而平的顶部就是热点。

配合 `perf` / async-profiler / `--cpu-prof` 使用，几乎是定位 CPU 热点最快的方式。

### 13.4 把性能测试放进 CI

第 52 章讲过：**没有回归测试的修复会被改回去**。性能同理。

```yaml
# 一个可行的最小形态
- run: ./bench.sh > current.json
- run: python compare.py baseline.json current.json --threshold 10%
```

关键设计：

- **比较相对值而非绝对值**——CI 机器的性能天天在变；
- **阈值要大于噪声**（本章 Python 实测波动 1.03x，那阈值至少 10%）；
- **失败时给出可复现的命令**，而不只是「变慢了」。

### 13.5 生产环境的持续 profiling

开发机上的 profile 与生产环境的差距可能很大（数据量、并发度、缓存命中率全不同）。现代做法是**在生产环境一直开着低开销采样**：

| 语言 | 工具 |
|---|---|
| Java | async-profiler、JFR（开销 < 2%） |
| .NET | dotnet-trace、dotnet-counters |
| Go | 内置 `net/http/pprof` |
| Node | `--cpu-prof`、Clinic.js |
| Python | py-spy（**不需要改代码，可 attach 到运行中的进程**） |
| 数据库 | `pg_stat_statements`、`performance_schema` |

py-spy 值得单独提：它从外部读进程内存，**不需要修改代码、不需要重启**——这让「线上突然变慢」有了当场诊断的可能。

## 14. 最佳实践

- **先定目标，再测现状，最后才优化。**没有目标的优化没有终点。
- **用 profiler 找热点，不要读代码猜**（本章实测猜错的代价：优化了占 1% 的部分）。
- **算阿姆达尔上限再动手**：占比 < 5% 的部分，通常不值得优化。
- **优先检查数据结构和算法**：本章最大的两个差距（191x、12.8x）都来自这里。
- **一次只改一个变量**，否则不知道是哪一处起了作用，也无法回退。
- **报告多轮的最小值或中位数**，永远不要报告随手跑的那一次。
- **确认差距大于测量波动**：本章 Python 实测波动 1.03x，那么 5% 的「改善」毫无意义。
- **在 GC 语言里先看分配量**：它是确定性的，耗时不是。
- **注明构建配置**（`-O2`/Release）——否则数字不可复现，就不构成证据。
- **用成熟的基准框架**（JMH、BenchmarkDotNet、Google Benchmark），它们替你处理预热和死代码消除。
- **把基准加进 CI**，阈值设在噪声之上。
- **怀疑任何惊人的数字**：4547x 是假象，14417x 是分配量不是耗时。

## 15. 常见坑

### 坑 1：优化了占比很小的部分

```python
# 花两天优化 slow_looking，从 5.0 ms 优化到 0.5 ms
# 总耗时 431 ms → 427 ms
```

**为什么错**：阿姆达尔定律的天花板是 `1/(1-0.01) = 1.01x`。

**怎么避免**：动手前先算 p。占比小于 5% 的部分，除非能顺手改，否则不要碰。

### 坑 2：微基准被死代码消除

```java
for (int i = 0; i < 20_000_000; i++) pure(i);   // 返回值没人用
// 实测 0.0 ms —— 整个循环被 C2 删掉了
```

**为什么错**：编译器/JIT 判定结果无用，删除整段代码。

**怎么避免**：把结果累加到逃逸的变量，或用 JMH 的 `Blackhole` / BenchmarkDotNet 的 `Consumer` / Google Benchmark 的 `DoNotOptimize`。

### 坑 3：没预热就在 JIT 语言上计时

```java
long t0 = System.nanoTime();
compute(N);                    // 第一次: 解释执行
```

**为什么错**：实测第 1 次 1.7 ms vs 第 8 次 0.9 ms（2.0x），测到的是解释器速度。

**怎么避免**：先跑够轮次让 C2/TurboFan 接管，再开始计时。但注意**这条规则在 Python 上不适用**（实测预热效应 ±2%）。

### 坑 4：测量代码污染了被测系统

```javascript
const sumX = (arr) => { let s = 0; for (const o of arr) s += o.x; return s; };
sumX(monoArray);      // 这个函数的内联缓存现在见过形状 A
sumX(megaArray);      // ...又见过 30 种形状 → 两次测量都变成超多态
```

**为什么错**：JS 的内联缓存挂在**代码位置**上，共用函数就共用缓存。本章的 ① 和 ③ **各踩了一次这个坑**。

**怎么避免**：每个被测对象配一个**全新的函数**（`new Function(...)`）。

### 坑 5：只测一次就下结论

```
第一次跑: 优化前 100 ms, 优化后 92 ms → 「快了 8%！」
```

**为什么错**：如果测量波动是 ±10%，这 8% 什么都没证明。

**怎么避免**：跑 5~7 轮，报告最小值或中位数，并**报告波动范围**。

### 坑 6：忘了注明构建配置

**为什么错**：本章实测同一份 C++ 代码，`-O0` 下 vector vs list 是 1.7x，`-O2` 下是 12.8x；分支预测实验的结论在两个级别下**完全相反**。

**怎么避免**：性能数据必须带上编译/运行配置。BenchmarkDotNet 直接**拒绝在 Debug 下运行**就是这个道理。

### 坑 7：相信过期的性能常识

```
「处理有序数组更快」    → 实测 1.0x（编译器用了条件移动）
「对象属性顺序要一致」   → 实测 4 种形状只慢 3%
「Java 对象分配很贵」   → 实测不逃逸的对象根本不分配
「堆分配很贵」          → 实测 305 MB 纯垃圾只慢 1.2x
```

**为什么错**：这些说法在提出时都是对的，但编译器、JIT 和 GC 一直在进步。

**怎么避免**：**当场测**。本章每一个「⚠️」标记的地方，都是一条曾经正确、现在已经不成立的常识。

### 坑 8：在开发机上 profile 生产问题

**为什么错**：数据量、并发度、缓存命中率、网络延迟全都不同。开发机上 100 行的表，生产上是 2 亿行——热点完全不在一处。

**怎么避免**：用生产环境的持续 profiling（py-spy、async-profiler、`pg_stat_statements`），或至少用生产规模的数据复现。

## 16. 面试题

**Q1：阿姆达尔定律是什么？它对日常优化有什么指导意义？**

A：加速比上限 = `1 / ((1-p) + p/s)`，其中 p 是被优化部分的耗时占比，s 是这部分的加速倍数。令 s→∞ 得到天花板 `1/(1-p)`。指导意义是：**动手之前先算 p**。本章实测一个占 1% 的部分，哪怕加速 1000 倍整体也只快 1.01 倍；而占 99% 的部分加速 10 倍就能整体快 8.94 倍。所以「找对地方」比「优化得多彻底」重要一个数量级。

**Q2：为什么 vector 和 list 的遍历都是 O(n)，实测却差十几倍？**

A：大 O 只数**操作次数**，不数**每次操作有多贵**。vector 元素连续，一条 64 字节缓存行装 16 个 int，且硬件预取器能预判下一条；list 的每个节点在堆上随机位置，每次都可能是缓存缺失（约 100 ns，比 L1 命中贵 100 倍）。本章实测 12.8x。更纯净的对照是同一个数组只改访问顺序：顺序 vs 乱序 7.0x。

**Q3：写 JVM 微基准时最常见的三个错误是什么？**

A：① **没预热**——测到的是解释器速度（实测 2.0x 差距）；② **被死代码消除**——结果没人用时 C2 会删掉整个循环（实测「快 4547 倍」的假象）；③ **对象不逃逸**——JIT 做标量替换，测不到真实的分配成本（实测单次成本差 11.6x）。补充一条更隐蔽的：把循环写在 `main` 里只能走 OSR 编译，与标准 C2 编译的优化程度不同——**基准代码放在哪个方法里会改变结果**。用 JMH 可以规避前三条。

**Q4：「为什么处理有序数组比无序数组快」这个经典问题，今天还成立吗？**

A：**在那个经典的例子上已经不成立了。**本章实测差距仅 1.0x，因为编译器把 `if` 编译成了条件移动指令（`csel`/`cmov`）——两条路都算、按条件选结果，根本没有分支可预测。但分支预测本身依然重要：用内存屏障强制保留真实分支后，差距回到 11.0x。这个例子说明：**关于性能的常识会过期，验证的方法是看汇编（`objdump | grep csel`）或换优化级别对照。**

**Q5：在 GC 语言里，「减少内存分配」这个建议准确吗？**

A：不够准确。本章实测分配 305 MB 纯垃圾、触发 38 次 Gen0 回收，代价只有约 1.2 倍。原因是分代 GC 只遍历**存活**对象——死对象从头到尾没被访问过。真正决定成本的是**存活量**：实测一次 Gen2 完整回收在存活 0 / 100 万 / 400 万个对象时分别耗时 1.0 / 3.8 / 13.6 ms。所以准确的说法是「**别让短命对象活过 Gen0**」，真正该警惕的是缓存和静态集合——它们把对象钉在老年代。

**Q6：为什么说「分配量」是比「耗时」更好的性能指标？**

A：因为它是**确定性的**。本章写作时同一份代码重复运行，耗时在 1.2x~2.1x 之间浮动，而分配量每次都完全相同（305 MB / 859.1 MB / 427 MB / 114 MB）。耗时受 GC 触发时机、CPU 频率、OS 调度、其他进程影响；分配量只取决于代码本身。同类的「计数型」指标还有缓存缺失次数、分支预测失败次数、SQL 逻辑读次数——**能用计数说明问题时，别用耗时**。

**Q7：一个接口变慢了，你的诊断顺序是什么？**

A：① 先确认**目标和现状**（P95/P99 是多少，目标是多少）；② 用 **USE 方法**排除整类可能（CPU 使用率低 → 瓶颈在 I/O 或锁）；③ 数据库侧先看**查询条数**（N+1？实测 201 条 vs 1 条）再看**执行计划**（SCAN 还是 SEARCH）；④ 应用侧用 profiler 看**火焰图**找平顶；⑤ 算**阿姆达尔上限**决定值不值得优化；⑥ 一次只改一个变量，改完**再测**；⑦ 把基准加进 CI 防回归。注意前四步都是**测量**。

**Q8：JS 里「对象属性顺序要保持一致」这条建议还有效吗？**

A：**大幅过时了。**本章实测 4 种不同形状只慢 3%——V8 的多态内联缓存能高效处理少数几种形状。真正的悬崖在**超多态**：30 种形状慢 2.87 倍，此时 V8 放弃缓存退化成哈希查找。所以准确的建议不是「形状必须完全一致」，而是「**别让一个访问点见到几十种形状**」——典型反例是一个通用函数处理来自十几个不同 API 的对象。

## 17. 练习

### 练习 1：验证阿姆达尔定律（基础）

写一个程序，包含两个函数：A 占总耗时约 10%，B 占约 90%。分别把 A 和 B 加速 10 倍，实测总耗时的变化，并与 `1/((1-p)+p/s)` 的预测值对比。

**要求**：误差应在 5% 以内。若不在，找出原因（提示：检查你的「加速 10 倍」是否真的做到了 10 倍）。

### 练习 2：复现死代码消除（进阶）

在你熟悉的 JIT 语言里写一个微基准，让它测出「优化后快 100 倍以上」的假结果，然后：

1. 用 profiler 或 `-XX:+PrintCompilation` / `--trace-opt` 证明代码被删掉了；
2. 加上正确的防御（Blackhole / Consumer），给出真实数字；
3. 写下这两个数字的比值——那就是你差点写进报告里的谎言的大小。

### 练习 3：找出你项目里的真实热点（实战）

在你正在做的项目上：

1. 先**写下你猜的**前三个热点（不许看代码）；
2. 用 profiler 实测，列出真实的前三；
3. 对比：你猜对了几个？
4. 对真实的第一名，算出阿姆达尔上限，判断值不值得优化。

**这道题的价值不在优化，而在第 3 步的那个数字。**

### 练习 4：把经典结论重新验证一遍（进阶）

选一条你听过的性能「常识」（例如「`i++` 比 `++i` 慢」「异常比返回码慢」「虚函数调用很贵」），设计实验验证它在**你当前的语言和编译器版本**下是否还成立。

**要求**：如果测不出差距，必须找出原因（编译器改写？被内联？测量精度不够？），而不是简单地说「不成立」。本章的 C++ 分支预测实验就是这个流程的完整示范。

### 练习 5：给项目加一个性能回归测试（实战）

选一个关键路径，写一个基准，接进 CI：

1. 跑 7 轮，记录中位数与波动范围；
2. 阈值设为「波动范围的 2 倍」；
3. 故意提交一个会变慢 30% 的改动，确认 CI 能拦住；
4. 故意提交一个无关改动，确认 CI **不会**误报。

第 4 步是最容易被跳过、也最重要的一步——一个会误报的性能测试，一周之内就会被所有人忽略。

## 18. 本章总结

**核心结论**：性能优化是一门**测量的学问**，不是猜测的学问。本章六种语言的实验反复证明同一件事：**关于性能的直觉和常识都会过期，唯一不会过期的是当场测量。**

**关键实测数据**：

| 发现 | 数据 |
|---|---|
| 凭感觉找热点会错 | 猜的那个占 **1%**，真正的占 **99%** |
| 修复往往很小 | `[]` 换成 `set()`，**191x** |
| 缓存局部性的分量 | 同样 O(n)，vector vs list **12.8x** |
| 纯净的缓存实验 | 同一数组，只改访问顺序 **7.0x** |
| 死代码消除的假象 | 丢弃 vs 累加返回值 **4547x** |
| JIT 预热 | 第 1 次 vs 第 8 次 **2.0x** |
| 逃逸分析 | 不逃逸的对象根本不分配，单次成本差 **11.6x** |
| 内联缓存 | 4 种形状 **1.03x**，30 种形状 **2.87x** |
| 分配 vs 存活 | 305 MB 垃圾只慢 **1.2x**；GC 停顿随存活量 **1.0→13.6 ms** |
| 分支预测的经典实验 | 编译器自由优化 **1.0x**，屏障强制保留 **11.0x** |

**四条会过期的「常识」**（本章逐条实测推翻）：

1. ~~处理有序数组更快~~ → 编译器用条件移动消除了分支（实测 1.0x）；
2. ~~对象属性顺序不同会变慢~~ → 4 种形状只慢 3%，问题在超多态（实测 2.87x）；
3. ~~Java 对象分配很贵~~ → 不逃逸的对象被标量替换，根本不分配；
4. ~~堆分配很贵~~ → 决定成本的是存活量，不是分配量。

**六步性能工作流**：

```
① 定目标   「首页 P95 < 200 ms」——没有目标就没有「优化完成」
② 测现状   profiler 找热点，不要猜
③ 算上限   阿姆达尔定律——值不值得优化，先算再动手
④ 改一处   一次只改一个变量
⑤ 再测量   确认真的变快了，且差距大于噪声
⑥ 定回归   把基准加进 CI（第 52 章的思路）
```

**六步里有三步是测量**——这就是本章唯一真正的纪律。

**自查清单**：

- [ ] 我能用阿姆达尔定律在动手前算出一个优化的收益上限。
- [ ] 我会先用 profiler 找热点，而不是读代码猜。
- [ ] 我知道同样 O(n) 的两段代码为什么能差一个数量级。
- [ ] 我能说出微基准的三大陷阱，并知道各自的防御方法。
- [ ] 我知道「要不要预热」是语言相关的，不能跨语言照搬。
- [ ] 我在 GC 语言里会先看分配量再看耗时，并知道为什么。
- [ ] 我报告性能数字时会注明构建配置和测量方法。
- [ ] 我在看到惊人的倍数时，第一反应是怀疑测量方法。
- [ ] 我知道怎么当场验证一条流传的性能常识是否已经过期。

**下一章预告**：性能优化让程序跑得更快，但**跑得快的错误程序只是更快地出错**。第 58 章讲**安全**——我们会实测 SQL 注入如何在参数化查询前后表现完全不同、复现 XSS 的三种上下文（HTML/属性/JS）为何需要三种不同的转义、量化密码哈希算法「故意做慢」的设计（本章刚学的「越快越好」在这里**整个反过来**），并说清为什么六种语言的安全默认值差异巨大——以及那些差异如何变成真实的漏洞。
