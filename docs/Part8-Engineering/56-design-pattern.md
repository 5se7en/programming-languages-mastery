# 第 56 章 · 设计模式

**简体中文** ｜ [English](./56-design-pattern.en-US.md)

---

> 1994 年的《设计模式》给出了 23 个「反复出现的问题的通用解法」，此后三十年被无数团队奉为圭臬——也被无数团队误用成「每个类都要配一个接口」。这一章不复述那 23 个模式，而是回答一个更根本的问题：**为什么同一个模式在不同语言里的分量天差地别**。
>
> 本章的**钥匙实验**把同一个需求——「把行为参数化」——在六种语言里各实现一遍。GoF 的策略模式需要**一个接口 + N 个实现类 + 一个上下文类**（约 25 行）；Python 里是 `sorted(items, key=len)`（**零额外结构**）；Java 8 之后是 `Comparator.comparingInt(String::length)`（一行）。三者结果完全一致。**GoF 的一半模式，本质上是在没有一等函数的语言里模拟一等函数。**
>
> 但「传函数」在不同语言里的**代价**并不相同。C++ 版实测了三种策略写法：虚函数 **1.33 ns/次**、`std::function` **0.76 ns/次**、模板 **0.36 ns/次**——**模板比虚函数快 3.7 倍**。而 C# 版实测同样的对比：接口 9.76 ns vs 委托 9.98 ns，**差距 1.02x，基本等价**。这两组数字放在一起才是完整结论：**在 C++ 里选哪种模式是性能决策，在有 JIT 的语言里纯粹是可读性决策。**
>
> Java 版则挖出了模式史上最著名的一次翻车。懒汉单例的线程不安全被实测复现（16 个线程同时调用 `getInstance()`，构造器执行了 **16 次**，拿到 **16 个不同实例**）；而它的标准解法**双重检查锁定，在 Java 5 之前是错的**——`instance = new Singleton()` 不是原子操作，JVM 允许把「赋引用」重排到「调构造器」之前，于是另一个线程可能拿到**尚未初始化完的半成品对象**。`volatile` 的真正作用不只是可见性，更是**禁止这个重排序**。这是「模式本身是对的，但语言的内存模型让它错了十年」的经典案例——而 C++11 之后 `static Config c;` 一行就线程安全了（Meyers 单例，实测 16 线程只构造 1 次）。
>
> 更大的图景是：**模式有三种命运**。被语言吸收的（迭代器→`yield return`、观察者→`event`、策略→lambda、访问者→模式匹配、单例→magic static），仍然必要的（适配器、外观、仓储——它们组织的是**架构边界**而非语言缺陷），以及语言特有的（RAII、Pimpl、CRTP——**GoF 书里一个都没有**，因为它们是 C++ 自己的问题催生的）。
>
> 最后 SQL 版提醒了另一半事实：**每个领域都会长出自己的模式语言**。软删除、乐观锁（实测「影响 0 行」即冲突信号）、事件溯源（实测重放得到余额 400）、闭包表——GoF 书里同样一个都没有，因为它们解决的是数据与持久化的问题。

## 1. 学习目标

学完本章，你将能够：

- 解释**为什么 GoF 的一半模式在现代语言里「消失」了**（实测策略模式的三种写法）；
- 用实测数据说明**模式的选择在 C++ 里是性能决策、在 JIT 语言里是可读性决策**；
- 复现**单例的线程安全陷阱**，并说清双重检查锁定为何一度是错的（第 41 章的内存模型）；
- 区分模式的**三种命运**（被吸收 / 仍必要 / 语言特有），并用它判断一个模式值不值得学；
- 认识到**每个领域都有自己的模式语言**（数据库、前端、并发各有各的）。

## 2. 为什么会出现这个概念

### 模式是什么

```text
模式 = 【反复出现的问题】+【被验证过的解法】+【一个便于沟通的名字】
```

**第三项常被低估**：模式最大的日常价值往往是**沟通效率**——「这里用闭包表」代替十分钟的白板讲解。

### 但 GoF 反映的是 1994 年的语言

```text
《设计模式》成书时，主流语言是 C++ 与 Smalltalk:
  · 函数不是一等公民 → 想传递行为，只能包成对象
  · 没有 lambda → 每个策略都要一个具名类
  · 没有泛型（C++ 模板刚起步）→ 类型复用靠继承
→ 于是「用只有一个方法的对象来模拟函数」成了一批模式的共同骨架
```

### 一句话定义

```text
一个模式的必要性 = 它解决的问题【是否仍然存在于你的语言里】
→ 解决【语言缺陷】的模式，会随语言进化而消失
→ 解决【领域复杂度】的模式，永远存在
```

> **一句话总结**：读 GoF 时最该问的不是「这个模式怎么用」，而是**「这个模式在我的语言里还是问题吗」**——本章会用六种语言的实测回答这个问题，并给出一条清晰的分界：**模拟语言缺失特性的模式会消失，组织系统边界的模式会留下。**

## 3. 底层原理

### 钥匙实验一：同一个需求，六种语言的分量

**需求**：把「排序的比较规则」参数化。

**GoF 版**（Python 实测，同样适用于 Java 7 / C++98）：

```python
class SortStrategy:                       # 抽象策略
    def compare(self, a, b): raise NotImplementedError
class ByLength(SortStrategy): ...         # 具体策略 ×3
class Sorter:                             # 上下文
    def __init__(self, strategy): self.strategy = strategy
    def sort(self, items): ...
```

**语言内建版**：

```text
GoF 版（接口+3个类+上下文，约 25 行）: ['fig', 'kiwi', 'apple', 'banana']
Python 版 sort_with(words, key=len):    ['fig', 'kiwi', 'apple', 'banana']
结果一致: True
换策略——Python: 甚至可以现写 lambda → sort_with(words, lambda w: w[-1])
```

```text
→ 「策略模式」的本质是【把行为参数化】——而函数就是参数化的行为
→ 在函数不是一等公民的语言里，你必须用「只有一个方法的对象」来模拟函数
→ 于是 GoF 的一半模式，本质上是【在没有一等函数的语言里模拟一等函数】
```

**Java 8 之后也退化了**（Java 实测）：

```text
GoF 版（接口 + 实现类）:                        [fig, kiwi, apple, banana]
Java 8 版 Comparator.comparingInt(String::length): [fig, kiwi, apple, banana]
→ 但注意 Java 的函数【仍然是对象】: lambda 编译成函数式接口的实例
→ 所以 Java 是「用语法糖模拟一等函数」，与 Python 的原生一等函数仍有差别
```

### 钥匙实验二：但「传函数」的代价因语言而异

**C++ 三种写法的性能**（实测 5000 万次调用）：

| 写法 | 耗时 | 每次 | 能否运行时替换 |
|------|------|------|--------------|
| 虚函数（GoF 原版） | 66.4 ms | **1.33 ns** | ✓ |
| `std::function` | 38.1 ms | **0.76 ns** | ✓ |
| 模板（编译期） | 18.2 ms | **0.36 ns** | ✗ |

```text
→ 模板比虚函数快 3.7x，比 std::function 快 2.1x
→ 差距来自【能否内联】: 模板在编译期就知道调谁，另两者都要间接跳转
```

**C# 同样的对比**（实测 5000 万次）：

```text
接口调用: 487.9 ms（9.76 ns/次）
委托调用: 499.2 ms（9.98 ns/次）
→ 差距 1.02x —— 基本等价
```

**两组数字合起来才是完整结论**：

```text
C++（无 JIT，编译期定死）: 3.7x 差距 → 选哪种模式是【性能决策】
C#/Java（有 JIT）:        1.02x     → 选哪种模式是【可读性决策】
Python/JS（解释执行）:     函数本来就是一等公民 → 根本没有「选择」这回事
→ 这就是同一个模式在不同语言里分量不同的根源
```

### 钥匙实验三：单例——模式对了，语言错了十年

**懒汉单例的线程不安全**（Java 实测，三次运行结果一致）：

```java
static UnsafeLazySingleton getInstance() {
    if (instance == null) instance = new UnsafeLazySingleton();  // ⚠️ 检查-创建不原子
    return instance;
}
```

```text
16 个线程同时调 getInstance(): 构造器执行了 16 次，拿到 16 个不同实例
→ 第 46/48 章的读-改-写在这里换了个形状: 竞态条件依然是同一个问题
```

**双重检查锁定：正确版需要 `volatile`**（Java 实测）：

```java
private static volatile DclSingleton instance;      // ← volatile 是必须的
static DclSingleton getInstance() {
    if (instance == null) {                          // 第一次检查: 不加锁，快路径
        synchronized (DclSingleton.class) {
            if (instance == null) instance = new DclSingleton();   // 第二次检查
        }
    }
    return instance;
}
```

```text
16 个线程同时调: 构造器执行了 1 次，拿到 1 个不同实例 ✓
```

**但这个写法在 Java 5 之前是错的，而且错得极其隐蔽**：

```text
instance = new DclSingleton() 不是原子操作，它是三步:
  ① 分配内存  ② 调用构造器  ③ 把引用赋给 instance
JVM/CPU 允许把 ②③【重排序】（第 41 章的内存模型）→ 于是可能:
  线程 A 执行到 ③ 但还没执行 ②（instance 非空，但对象没初始化完）
  线程 B 的第一次检查看到 instance != null → 直接返回【半成品对象】
→ volatile 的作用不只是「保证可见性」，它还【禁止这个重排序】
→ Java 5 (JSR-133) 修订内存模型后，volatile 才真正让 DCL 正确
```

**而语言进化后，这个复杂度被吸收了**：

```text
Java 的最佳写法——静态内部类（实测 16 线程构造 1 次）:
  内部类只在首次访问时加载 → JVM 保证【类初始化】线程安全（JLS 12.4.2）
  → 天然懒加载 + 天然线程安全 + 零锁

C++11 的 Meyers 单例（实测 16 线程构造 1 次）:
  static Config c;   // 就这一行
  → C++11 标准【要求】静态局部变量的初始化线程安全（magic static）
  → C++11 之前，这里也要写 DCL，也踩过同款重排序坑
```

**这是本章最好的注脚**：**模式的复杂度会随语言进化被吸收进语言本身**。

### 单例本身是个可疑的模式

```text
它同时做了两件事: ① 保证只有一个实例  ② 提供【全局访问点】
② 才是问题所在: 全局访问 = 隐藏的依赖（第 55 章服务定位器同款批评）
  · 测试时换不掉（第 52 章实测过依赖写死的后果）
  · 谁用了它，从签名上完全看不出来
→ 现代做法: 让容器管理【生命周期为单例】，通过构造器注入（第 55 章实测）
→ 「我需要唯一实例」是合理需求，「我要全局静态访问」不是
```

### 钥匙实验四：模式的三种命运

**命运一：被语言吸收**（各语言实测汇总）：

| GoF 模式 | Python | JavaScript | C# | C++ |
|---------|--------|-----------|-----|-----|
| 策略 | 传函数 | 传函数 | `Func<T,R>` | lambda/模板 |
| 命令 | `partial` | 闭包/`bind` | `Action` | lambda |
| 观察者 | 函数列表 | `EventEmitter`/Promise | **`event` 关键字** | 信号槽库 |
| 迭代器 | 生成器（第 44 章） | `for...of` | **`yield return`** | 范围 for |
| 装饰器 | **`@` 语法** | 高阶函数 | 扩展方法 | — |
| 单例 | 模块即单例 | ES 模块即单例 | — | **magic static** |
| 访问者 | — | — | **模式匹配** | `std::visit` |
| 代理 | `__getattr__` | **内建 `Proxy`** | `DispatchProxy` | — |

**命运二：仍然必要**（与语言无关）：

```text
适配器 / 外观 / 仓储 / 状态机
→ 它们组织的是【架构边界】与【领域复杂度】，不是语言缺陷
→ 第 51 章实测过仓储的职责，第 55 章实测过适配器式的接口隔离
```

**命运三：语言特有**（C++ 实测清单）：

```text
RAII（第 37 章）    —— C++ 独有、其他语言羡慕的「模式」，已内建为语言机制
Pimpl（第 53 章）  —— 隔离 ABI 与编译依赖，C++ 特有问题的特有解法
CRTP              —— 用模板实现静态多态（避免虚函数开销）
类型擦除           —— std::function/std::any 的实现手法
→ 注意这四个【GoF 书里一个都没有】: 它们是 C++ 自己的问题催生的
```

## 4. JavaScript

JS 版揭示了观察者模式与整个 JS 异步世界的血缘。

### 手写观察者：30 行就是 EventEmitter（实测）

```javascript
class MiniEmitter {
  constructor() { this.handlers = new Map(); }        // 事件名 → 回调列表
  on(event, fn) { /* ... */ return () => this.off(event, fn); }   // 返回退订闭包
  emit(event, ...args) { for (const fn of [...this.handlers.get(event) || []]) fn(...args); }
}
```

```text
两个订阅者 → emit(A1) → 退订一个 → emit(A2)
["库存服务处理 A1","邮件服务处理 A1","邮件服务处理 A2"]
与 Node 内建 EventEmitter 行为一致 ✓
→ 「观察者模式」= 一个 Map<事件名, 回调数组> + 遍历调用
→ 它解耦的是【谁产生事件】和【谁关心事件】
```

### 观察者的三代演化（实测）

```text
一代 回调:       readCallback(cb)          —— 观察者的最朴素形态
二代 Promise:    只会触发【一次】的观察者   —— resolve 就是 emit，then 就是 on
三代 异步迭代器: 触发多次且【可背压】       —— 第 44 章的协程
→ 三代都是同一个模式，语言把它一层层内建、标准化
→ 第 43 章的事件循环是【运行时层】的观察者，EventEmitter 是【用户态】的同一模式
```

### 「代理模式」变成了内建对象

```text
GoF 的代理模式需要手写一个同接口的包装类
JS: new Proxy(target, handler) —— 语言把模式做成了 API
→ 这是「模式被吸收」的最极端形态: 连名字都保留了，但它不再是你写的代码
```

### 装饰器 = 高阶函数（实测）

```javascript
const withRetry = (fn, times) => async (...args) => { /* 重试逻辑 */ };
withRetry(flaky, 5)() → 成功（尝试了 3 次）
```

```text
→ 一个高阶函数就实现了 GoF 需要四个类的装饰器模式
→ 而且可以任意组合: withLog(withRetry(withTimeout(fn)))
```

> **注意**：JS 里真正还活跃的模式是**中间件/管道**（Express/Koa 的核心，本质是责任链）与**状态机**（XState）——前者是框架生态的新生，后者是领域复杂度的必然；`export const db = new Database()` 是 JS 的单例惯用法，但代价与第 55 章一致：**测试时换不掉**。

## 5. Python

Python 版实测了「模式被语言吸收」最彻底的一种情况。

### 九个 GoF 模式在 Python 里的对应物（实测表）

```text
策略 Strategy     → 传一个函数
命令 Command      → 函数 / functools.partial（第 55 章的部分应用）
模板方法          → 传一个函数进去，或用默认参数
工厂方法          → 类本身就是可调用对象——直接传类名
抽象工厂          → 一个返回构造函数的函数
单例 Singleton    → 模块本身就是单例（import 只执行一次）
迭代器 Iterator   → 语言内建（第 44 章的生成器）
装饰器 Decorator  → 语法糖 @
观察者 Observer   → 一个函数列表
```

```text
→ 不是「Python 不需要设计」，而是【这些设计已经被语言内建了】
```

### 装饰器：GoF 模式变成了语言语法（实测）

```text
@log_calls 包装后调用两次: 记录 = [('甲',), ('乙',)]
@memoize 调用 5 次（只有 2 个不同参数）: 缓存 2 项，实际计算 2 次
→ GoF 的装饰器模式需要 4 个类；Python 只要一个高阶函数 + 一个 @
```

### 单例：模块就是单例（实测）

```text
两次拿到本模块对象: 同一个吗 True
→ import 只执行一次模块代码（第 14 章 sys.modules 缓存）→ 模块级变量天然是单例
→ Python 的惯用法是模块里写 `_instance = Thing()`，而不是 getInstance()
```

> **注意**：Python 里仍然需要的是**仓储/适配器**（架构边界）、**状态机**（领域复杂度）；建造者模式常被关键字参数 + `dataclass` 代替；判据始终是**「这个模式解决的是语言的缺陷还是领域的复杂度」**。

## 6. Java

Java 版承包了单例的完整实测（数据见钥匙实验三），这里补充它的历史意义。

### 单例四种写法的取舍

| 写法 | 线程安全 | 懒加载 | 锁开销 | 备注 |
|------|---------|--------|--------|------|
| 饿汉 | ✓（JVM 保证类初始化） | ✗ | 无 | 简单；实例可能白造 |
| 懒汉无同步 | **✗**（实测 16 个实例） | ✓ | 无 | 错误写法 |
| DCL + `volatile` | ✓（实测 1 个） | ✓ | 首次有 | **Java 5 之前是错的** |
| **静态内部类** | ✓（实测 1 个） | ✓ | **无** | Java 最佳实践 |

**更彻底的是枚举单例**（《Effective Java》推荐）：还能防反射与序列化破坏。

### DCL 的教训超出了单例本身

```text
「一行赋值语句不是原子的」这个事实，影响的远不止单例:
  · 第 41 章的 volatile ≠ 原子（实测 volatile int 仍然丢更新）
  · 第 41 章的内存模型与重排序
  · 无锁数据结构里的发布安全（safe publication）
→ DCL 是这些概念最著名的一个演示场
```

> **注意**：Java 8 的 lambda 让策略/命令/模板方法都退化成函数式接口，但 lambda 仍然编译成对象；`Optional` 是空对象模式的语言化；`record` + `sealed interface` + `switch` 模式匹配让 Java 也拿到了 C# 的访问者替代方案。

## 7. C++

C++ 版的核心是：**在这里选模式是性能决策**（数据见钥匙实验二）。

### 三种写法的适用场景

```text
虚函数:        策略在【运行时由配置/用户】决定，且调用不在热路径
std::function: 需要装各种可调用对象（lambda 捕获了状态时尤其方便）
模板:          策略在【编译期】就确定，且在热路径上
→ std::sort 的比较器是模板参数，qsort 的是函数指针——这是 std::sort 更快的原因之一
```

### C++ 特有的四个模式（GoF 书里都没有）

```text
RAII（第 37 章）  —— 已内建为语言机制，其他语言用 try-with-resources/using 模仿
Pimpl（第 53 章） —— 隔离 ABI 与编译依赖（第 54 章实测头文件扇出的代价）
CRTP             —— 模板实现静态多态，是钥匙实验二「模板版」的泛化
类型擦除          —— std::function/std::any 的实现手法
→ 它们由 C++ 的独特约束催生: 手动内存管理、ABI、编译模型、零开销哲学
```

> **注意**：Meyers 单例（`static Config c;`）是 C++11 起的标准做法，实测 16 线程只构造 1 次；C++11 之前这里同样要写 DCL 并踩重排序坑；`std::visit` + `std::variant` 是 C++ 的模式匹配式访问者。

## 8. C#

C# 版实测了「一部把设计模式吸收进语言的演化史」。

### C# 吃掉的模式清单（实测）

```text
策略 Strategy     → Func<T,R> / 委托（实测与接口性能等价 1.02x）
命令 Command      → Action / 委托 + 闭包
观察者 Observer   → event 关键字（实测 += 订阅、-= 退订）
迭代器 Iterator   → yield return（实测 Fibonacci(10)）
访问者 Visitor    → switch 模式匹配（实测与访问者版结果一致）
装饰器 Decorator  → 扩展方法 / 高阶函数
适配器 Adapter    → 扩展方法（给别人的类型加方法）
空对象            → 可空引用类型 + ?? 运算符
原型 Prototype    → record 的 with 表达式
```

### `event`：语言内建的观察者（实测）

```text
两个订阅者 → Place(A1) → 退订一个 → Place(A2)
库存服务处理 A1 | 邮件服务处理 A1 | 邮件服务处理 A2
→ event 甚至比手写更安全: event 字段【只能】在声明类内部 Invoke
⚠️ 但有个经典内存泄漏: 订阅者不退订，发布者就一直持有它的引用（第 36 章 GC）
```

### 访问者 vs 模式匹配：表达式问题

```text
GoF 访问者: 1 个 IVisitor 接口 + 每个类型一个 Visit + 每个类型实现 Accept
模式匹配版: 一个 switch 表达式（实测结果一致）
→ 访问者解决的是「在不改类的前提下加操作」——即所谓【表达式问题】
→ 函数式语言用代数数据类型 + 模式匹配天然解决它
   （record + sealed + switch 就是它的 C# 化）
```

> **注意**：`IObservable<T>`/`IObserver<T>` 是 .NET 把观察者做成的标准接口（Rx 的基础）；扩展方法让适配器模式几乎消失；源生成器正在吃掉更多模式（如第 55 章的编译期 DI）。

## 9. SQL

数据库世界有**自己的模式语言**——GoF 书里一个都没有。

### 软删除（实测）

```text
物理行 3 行，视图里可见 2 行
→ 好处: 可恢复、可审计、外键不会断
→ 代价: 每个查询都要记得加 deleted_at IS NULL（漏一次就是数据泄漏）
→ 配套做法是【视图即接口】（第 55 章）: 应用只查 active_users，永不碰底表
→ 索引也要配合: 第 49 章的部分索引 WHERE deleted_at IS NULL 更小更快
```

### 乐观锁（实测，第 48 章的模式化）

```sql
UPDATE docs SET content='...', version=version+1 WHERE id=1 AND version=1;
```

```text
甲提交（持 version=1）影响 1 行 ✓
乙提交（同样持 version=1）影响 0 行 → 【被拒绝】
当前内容: 甲的修改，version=2
→ 「影响 0 行」就是冲突信号（第 48 章 C# 版实测过它的 ORM 形态）
→ 这是【模式】而非语言特性: 任何数据库、任何语言都是这一套
```

### 事件溯源与快照（实测）

```text
事件流: 开户0 → 存入500 → 取出200 → 存入100
重放得到余额: 400
快照: 余额 400，已覆盖到 seq=4
新事件到达后，当前余额 = 快照 + 增量重放 = 450
→ 与第 46 章的 WAL、第 54 章的迁移脚本是【同一个思想】: 状态 = 事件的折叠
→ 快照模式与第 54 章增量构建完全同构: 快照=构建产物，upto_seq=已应用到哪
```

### 树形结构的两种建模

```text
邻接表(parent_id): 写简单，查子孙要递归 CTE
  递归查「电子」的所有子孙: 电子 → 手机 → 安卓机
闭包表: 额外存下【所有祖先-后代对】——查询变成一次 JOIN，代价是写入要维护
→ 经典的读写权衡（第 49 章索引的同一笔账）: 为读优化就要在写时付出
```

> **注意**：这些模式 GoF 书里一个都没有，因为它们解决的是**数据与持久化**的问题——**每个领域都会长出自己的模式语言**：GoF 是面向对象领域的，Fowler 的 PoEAA 是企业应用的，这些是数据领域的。

## 10. 五语言横向对比

### ① 同一个模式在六种语言里的形态

| GoF 模式 | C++ | Java | C# | Python | JavaScript |
|---------|-----|------|-----|--------|-----------|
| **策略** | 虚函数/`std::function`/模板 | lambda（Java 8+） | `Func<T,R>` | 传函数 | 传函数 |
| **观察者** | 信号槽库（Qt/Boost） | 监听器接口 | **`event` 关键字** | 函数列表 | `EventEmitter`/Promise |
| **迭代器** | 范围 for + 迭代器 | `Iterable` | **`yield return`** | 生成器 | `for...of` |
| **单例** | **magic static** | 静态内部类/枚举 | — | 模块即单例 | ES 模块即单例 |
| **装饰器** | — | 注解 + 代理 | 扩展方法 | **`@` 语法** | 高阶函数 |
| **访问者** | `std::visit` | `sealed` + `switch` | **模式匹配** | — | — |
| **代理** | — | 动态代理（第 55 章） | `DispatchProxy` | `__getattr__` | **内建 `Proxy`** |

### ② 钥匙实验数据汇总

```text
策略模式:     GoF 约 25 行 vs Python 一个函数 vs Java 8 一行 —— 结果完全一致
C++ 三写法:   虚函数 1.33 ns / std::function 0.76 ns / 模板 0.36 ns（模板快 3.7x）
C# 两写法:    接口 9.76 ns / 委托 9.98 ns（差距 1.02x，基本等价）
懒汉单例:     16 线程 → 构造 16 次，16 个不同实例（三次运行一致）
DCL+volatile: 16 线程 → 构造 1 次 ✓（但 Java 5 前因重排序而错）
静态内部类:   16 线程 → 构造 1 次 ✓（零锁）
Meyers 单例:  16 线程 → 构造 1 次 ✓（C++11 magic static）
装饰器:       @memoize 5 次调用 2 个不同参数 → 缓存 2 项，实际计算 2 次
观察者:       手写 30 行与 Node 内建 EventEmitter 行为一致
SQL 乐观锁:   甲影响 1 行 ✓，乙影响 0 行（冲突信号）
SQL 事件溯源: 重放余额 400；快照 + 增量 = 450
```

### ③ 共性与根因

**共性**：所有语言都在把模式吸收进语言本身（迭代器、观察者、策略最先被吃掉）；所有语言都保留了组织架构边界的模式（适配器、外观、仓储）；所有领域都会长出自己的模式语言。

**根因**：

- **一等函数是最大的分水岭**：策略、命令、模板方法、装饰器都是「模拟一等函数」——语言有了它，这些模式就消失；
- **性能模型决定选择的分量**：C++ 无 JIT，编译期定死（实测 3.7x 差距）→ 选模式即选性能；JIT 语言两种写法趋同（实测 1.02x）→ 选模式即选可读性；
- **内存模型能让正确的模式变错**：DCL 是最著名的案例，`volatile` 的语义修订（JSR-133）才让它成立；
- **语言进化会吸收模式的复杂度**：Java 静态内部类、C++11 magic static 都让单例的同步细节消失；
- **模式的领域性**：GoF 覆盖面向对象，PoEAA 覆盖企业应用，数据库/前端/并发各有各的模式语言——**没有放之四海的模式清单**。

## 11. 底层实现对比

| 语言机制 | 吸收了哪个模式 | 实现原理 |
|---------|--------------|---------|
| **`yield return`**（C#） | 迭代器 | 编译器生成状态机（第 44 章实测 `<Counter>d__0`） |
| **`event`**（C#） | 观察者 | 多播委托（invocation list）+ 访问限制 |
| **`@` 装饰器**（Python） | 装饰器 | 语法糖：`f = deco(f)` |
| **magic static**（C++11） | 单例 | 编译器插入一次性 guard 变量与同步 |
| **静态内部类**（Java） | 单例 | JVM 保证类初始化线程安全（JLS 12.4.2） |
| **`Proxy`**（JS） | 代理 | 引擎级的属性访问拦截 |
| **模块缓存**（Python/JS） | 单例 | `sys.modules` / ESM 模块图只求值一次（第 14 章） |

**一个规律**：

```text
被吸收的模式，最终都变成了【编译器生成的代码】或【运行时的内建机制】
→ 你不再写它，但它仍然在运行——模式没有消失，只是换了实现者
→ 第 44 章的协程状态机、第 51 章 ORM 的对象图、第 55 章 DI 的装配代码，都是同一个规律
```

## 12. 性能分析

### 本章实测数字速查

```text
C++ 策略三写法: 虚函数 1.33 ns / std::function 0.76 ns / 模板 0.36 ns（3.7x）
C# 策略两写法:  接口 9.76 ns / 委托 9.98 ns（1.02x）
单例线程安全:   懒汉 16 实例 vs DCL/静态内部类/magic static 各 1 实例
```

### 模式的性能代价从哪来

```text
间接跳转: 虚函数、std::function、委托 —— 编译器无法内联
对象分配: GoF 版策略要 new 一个策略对象（第 33 章的分配成本）
额外层次: 装饰器套三层 = 三次函数调用 + 三个闭包对象
→ 在 C++ 里这些都要认真掂量；在 JIT 语言里绝大多数会被优化掉
→ 但【所有语言】共有的代价不是性能，是【认知负担】（见下）
```

> ⚠️ **模式最大的代价是抽象层次**。每一层间接都是读代码时的一次跳转；GoF 版策略模式的三个类，在 Python 里对应的是一个 `key=len`——**多出来的两个类不产生任何领域信息**。第 55 章说「只有一个实现的接口是纯粹的间接层」，这里是同一条判据：**这个模式带来的灵活性，你真的用得上吗？**

## 13. 工程实践

| 场景 | ✅ 推荐 | ❌ 避免 | 原因 |
|------|--------|--------|------|
| 需要参数化行为 | 传函数/lambda | 写一套策略类 | 实测结果一致，代码少 20+ 行 |
| C++ 热路径的策略 | 模板 | 虚函数 | 实测 3.7x |
| C++ 需运行时切换 | 虚函数/`std::function` | 强行用模板 | 模板做不到运行时替换 |
| JIT 语言选写法 | 按可读性选 | 按性能猜 | 实测 1.02x，性能不是因素 |
| 需要唯一实例 | 容器管理生命周期 + 注入 | 手写 `getInstance()` | 第 55 章实测；全局访问隐藏依赖 |
| 必须手写单例（Java） | 静态内部类/枚举 | DCL | 实测同样正确但更简单 |
| 必须手写单例（C++11+） | `static T& instance()` | DCL | magic static 已线程安全 |
| 需要「加操作不改类」 | 模式匹配（有的话） | 访问者模式 | 实测结果一致，代码少一半 |
| 事件通知 | 语言内建（`event`/EventEmitter） | 手写观察者 | 内建版更安全（限制 Invoke） |
| 数据可恢复/可审计 | 软删除 + 视图 | 物理删除 | 实测配套视图避免遗漏过滤 |
| 跨请求编辑 | 乐观锁（version 列） | 悲观锁 | 第 48 章实测过它的适用边界 |
| 学一个新模式前 | 问「我的语言里还是问题吗」 | 照搬 GoF | 一半模式已被语言吸收 |

### 一句话决策

```text
看到一个模式时问三件事:
  ① 它解决的是【语言缺陷】还是【领域复杂度】？ → 前者可能已被你的语言吸收
  ② 我的语言有没有内建的对应物？               → 有就用内建的（更安全更短）
  ③ 它带来的灵活性我真的用得上吗？             → 用不上就是纯粹的间接层
```

## 14. 最佳实践

- **先问「我的语言里还是问题吗」**：实测九个 GoF 模式在 Python 里已被语言内建；照搬只会制造噪音。
- **优先用语言内建的机制**：`event`、`yield return`、`@` 装饰器、magic static——它们更短、更安全（如 `event` 限制 Invoke 者）。
- **C++ 里把模式选择当性能决策**：实测模板比虚函数快 3.7x；热路径用模板，需运行时替换才用虚函数。
- **JIT 语言里按可读性选**：实测接口与委托差 1.02x——性能不该参与这个决定。
- **手写单例用语言机制而非手写同步**：实测静态内部类（Java）与 magic static（C++11）都线程安全且零锁。
- **区分「唯一实例」与「全局访问」**：前者合理，后者是隐藏依赖——交给容器 + 构造器注入（第 55 章）。
- **认识到每个领域有自己的模式语言**：软删除、乐观锁、事件溯源在 GoF 书里一个都没有，但同样是模式。
- **把模式当沟通词汇而非实现清单**：模式最大的日常价值是让「用闭包表」代替十分钟白板讲解。

## 18. 本章总结

**一句话**：设计模式是「反复出现的问题 + 被验证的解法 + 便于沟通的名字」，但 GoF 反映的是 1994 年 C++/Smalltalk 的语言短板——本章用六种语言的实测证明，**它的一半模式本质上是在模拟一等函数**：同一个「把行为参数化」的需求，GoF 版需要接口加三个实现类加上下文（约 25 行），Python 里是 `sorted(items, key=len)`（零额外结构），Java 8 之后是一行 lambda，三者结果完全一致；而「传函数」的**代价因语言而异**——C++ 实测三种写法（虚函数 1.33 ns / `std::function` 0.76 ns / 模板 0.36 ns，**模板快 3.7 倍**）说明在这里选模式是**性能决策**，C# 实测接口与委托 9.76 vs 9.98 ns（**差距 1.02x**）说明在 JIT 语言里纯粹是**可读性决策**；Java 版还挖出了模式史上最著名的翻车——懒汉单例实测 16 线程造出 **16 个实例**，而它的标准解法**双重检查锁定在 Java 5 之前是错的**（`instance = new Singleton()` 的三步可被重排序，另一线程会拿到半成品对象，`volatile` 的真正作用是**禁止这个重排序**），但语言进化把这份复杂度吸收了——Java 的静态内部类与 C++11 的 magic static 实测都是 16 线程构造 1 次且零锁；由此浮现出**模式的三种命运**：被语言吸收的（迭代器→`yield return`、观察者→`event`、访问者→模式匹配、代理→内建 `Proxy`）、仍然必要的（适配器/外观/仓储——组织的是**架构边界**）、语言特有的（RAII/Pimpl/CRTP——**GoF 书里一个都没有**）；最后 SQL 版提醒**每个领域都会长出自己的模式语言**（软删除、乐观锁实测「影响 0 行」即冲突、事件溯源实测重放余额 400），而模式最大的日常价值往往是第三要素——**让「用闭包表吧」代替十分钟的白板讲解**。

**关键要点**

- **一半 GoF 模式在模拟一等函数**（实测）：策略、命令、模板方法、装饰器——语言有了 lambda，它们就消失。
- **模式的分量由语言决定**（实测）：C++ 3.7x 是性能决策，C# 1.02x 是可读性决策，Python 根本无需选择。
- **单例的线程陷阱**（实测）：懒汉 16 实例；DCL 需 `volatile` 且 Java 5 前因重排序而错。
- **语言进化吸收模式的复杂度**（实测）：静态内部类、magic static 都做到线程安全且零锁。
- **单例真正的问题是全局访问**：它隐藏依赖——现代做法是容器管理生命周期 + 构造器注入（第 55 章）。
- **模式的三种命运**：被吸收 / 仍必要（架构边界）/ 语言特有（RAII、Pimpl）。
- **每个领域有自己的模式语言**（SQL 实测）：软删除、乐观锁、事件溯源、闭包表。
- **模式最大的代价是认知负担**：多出来的抽象层若不产生领域信息，就是纯粹的间接层。

**下一章预告**：模式让代码更好组织，但它跑得够快吗？第 57 章讲**性能优化**——一个从头到尾都在与直觉作对的主题。我们会实测「凭感觉优化」的失败率、量化第 16 章缓存局部性在真实数据结构上的威力（同样的算法复杂度，数组比链表快一个数量级）、复现第 33 章内存分配在热路径上的代价，以及最重要的一课：**先测量，再优化**——本章所有前置章节积累的实测方法，将在这里汇成一套完整的性能诊断流程。
