# 第 48 章 · 事务

**简体中文** ｜ [English](./48-transaction.en-US.md)

---

> 第 46 章实测过一次转账崩在半路的后果——文件里留下 `'id=1,balance=40\nid=2,bal'`，钱凭空消失。那只是 ACID 里的 **A**。本章把四个字母全部拆开，并回答一个更难的问题：**当很多人同时读写同一份数据，怎么让每个人都像在独占它一样**。
>
> 本章的**钥匙实验**用两个真实的数据库连接复现了「隔离」的分野。没有事务包裹时，A 连着读两次同一行得到 **100 → 777**——这就是**不可重复读**；用 `BEGIN` 包起来后，即使 B 在中间把值改成 999 并**已经提交**，A 第二次读到的**仍然是 100**，直到 A 自己提交才看见 999。范围查询同理：事务内两次 `COUNT` 都是 3，事务外立刻变 4——**幻读**也被挡住了。这就是**快照隔离**：你看到的是「事务开始那一刻」的整个数据库。
>
> 快照隔离是怎么做到的？C++ 版**手写了一个 MVCC 引擎**给出答案，而答案短得惊人——**可见性规则只有三行**：版本比我新的看不见、在我开始前就死掉的看不见、其余的可见。这三行判断替代了整套读锁，所以**读永远不会被写阻塞**（Python 实测：B 持有写锁未提交时，A 读同一行耗时 **0.05 ms，零等待**）。代价也实测出来了：连写 100 次后版本链堆到 **102 个**——旧版本不能立刻删，这就是 PostgreSQL 要 `VACUUM`、长事务是 MVCC 天敌的原因。
>
> 但快照隔离有个**挡不住的异常**，而且它专挑「看起来完全正确」的代码下手：**写偏斜**（write skew）。JS 版用医院排班演示——两个医生同时请假，各自都读到「还有 2 人值班」于是判断通过，合起来变成 0 人值班。**两个事务没有写同一行**，所以写-写冲突检测抓不到它。sqlite 因为只有 SERIALIZABLE 挡住了（实测 B 被直接拒绝），但 PostgreSQL 和 MySQL 的默认级别都挡不住。
>
> 最后是一次**对流行说法的实测检验**。「乐观锁在低冲突时更快，悲观锁在高冲突时更快」——C# 版在四档冲突强度下对撞，结果只有热点行那一档稳定可复现（**悲观锁快 1.5~1.9x**，乐观锁做了五万次无用功），其余三档反复跑**连方向都会变**，那是噪声不是规律。原因是内存里加锁只要几十纳秒，乐观锁没什么可省。**乐观锁真正的价值根本不是快**——而是它能跨越**无法持锁的边界**：用户打开编辑表单思考五分钟再提交，你不可能持有数据库锁五分钟，版本号是唯一的办法。

## 1. 学习目标

学完本章，你将能够：

- 说出 ACID 四个字母**各自靠什么机制实现**，并指出哪一个需要你参与；
- 复现并区分三种读异常（**脏读、不可重复读、幻读**），说清它们的差别；
- 用三行可见性规则解释 **MVCC** 为什么能让读写互不阻塞，以及它的代价（版本堆积）；
- 识别**写偏斜**——快照隔离挡不住、且专挑「看起来正确」的代码下手的异常；
- 判断该用**悲观锁还是乐观锁**——依据不是「哪个快」，而是「能不能持锁」。

## 2. 为什么会出现这个概念

### 第 46 章留下的半个答案

```text
第 46 章实测: 文件版转账崩在半路 → 'id=1,balance=40\nid=2,bal'（钱消失+格式毁）
              数据库版同样崩溃    → 自动回滚，两人余额都是 100
→ 那一章证明了【原子性】有多重要，但只讲了 ACID 的 A
```

**真正的难题在并发**：

```text
一个人用数据库时，只需要 A（崩溃能回滚）和 D（写了不丢）
一万个人同时用时，还需要 I（隔离）——否则每个人看到的都是别人做到一半的中间状态
```

### 事务的定义：一组操作的四个承诺

```text
A 原子性 Atomicity   —— 要么全做，要么全不做（Java 版手写 undo log 实现）
C 一致性 Consistency —— 不变量不被打破（第 46 章实测 CHECK 拦下 -999）
I 隔离性 Isolation   —— 并发执行的结果，等同于某种串行执行的结果
D 持久性 Durability  —— 提交了就不会丢（第 46 章实测三档: 1.86/26/4399 μs）
```

**只有 C 有你的份**：

```text
A/I/D 是数据库的工作，你只要 BEGIN/COMMIT
C 是你的工作: 数据库只能执行【你声明的】约束——它不知道「余额不能为负」，除非你写 CHECK
→ 这也是为什么 ACID 里 C 最常被误解: 它不是数据库送你的，是你自己定义的
```

> **一句话总结**：事务把「一组操作」变成一个不可分割的单位，让并发与崩溃这两件最难的事，从**每个应用各自处理**变成**数据库统一处理**——而本章会证明，它处理得比你手写好得多，但**并非没有漏洞**。

## 3. 底层原理

### 钥匙实验一：三种读异常与快照隔离

**Python 用两个真实连接复现了它们**（sqlite WAL 模式）：

**① 不可重复读**（没有事务包裹时）

```text
A 第一次读: 100   B 提交修改后 A 第二次读: 777
→ 同一段逻辑里两次读到不同的值
→ 后果: 「先查余额够不够，再扣款」——中间余额被人改了，你的判断已经过期
```

**② 用事务包裹 → 快照隔离**

```text
事务内第一次读: 100
B 提交 999 后，事务内第二次读: 100   ← 仍是旧值！
A 提交后再读: 999
→ 事务里两次读一致 = 【快照隔离】(snapshot isolation)
```

**A 看到的是「事务开始那一刻」的整个数据库快照**，B 的提交对它完全不可见。

**③ 幻读也被一并挡住**

```text
事务内两次 COUNT: 3 → 3（一致）；事务外再查: 4
```

**三种异常的准确区分**（很多人混淆）：

| 异常 | 读到了什么 | 例子 |
|------|-----------|------|
| **脏读** | 别人**未提交**的数据 | 读到一笔可能被回滚的转账 |
| **不可重复读** | **既有行**被改了 | 同一行两次读到 100 和 777 |
| **幻读** | **新行**凭空出现 | 同一范围两次 COUNT 得到 3 和 4 |

```text
不可重复读 vs 幻读的关键差别: 前者是【行内容变了】，后者是【行集合变了】
→ 这个差别决定了实现难度: 锁住既有行容易，锁住「还不存在的行」难（要间隙锁）
```

### 钥匙实验二：手写 MVCC——可见性规则只有三行

**读为什么能不被写阻塞？C++ 版手写引擎给出了答案。**

**核心数据结构**：每行数据不是一个值，而是一条**版本链**：

```cpp
struct Version {
    int value;
    uint64_t created_by;    // 哪个事务创建了它
    uint64_t deleted_by;    // 哪个事务删除了它（0 = 还活着）
};
```

**写操作从不原地修改**：

```cpp
void write(const std::string& key, int value, uint64_t txn) {
    for (auto& v : versions)
        if (v.deleted_by == 0) v.deleted_by = txn;   // 旧版本标记为「死于本事务」
    versions.push_back({value, txn, 0});             // 追加新版本
}
```

**可见性规则——MVCC 的全部秘密**：

```cpp
if (v.created_by > snapshot)                     return false;  // 未来的版本，看不见
if (v.deleted_by != 0 && v.deleted_by <= snapshot) return false;  // 已成过去的版本，看不见
return true;                                                    // 恰好属于我这个快照
```

**实测的版本链演变**：

```text
T1 写入 100:  [值=100 生于T1 死于T-]
T2 开始（快照=2），读到 100
T3 写入 999:  [值=100 生于T1 死于T3] [值=999 生于T3 死于T-]
T2 再读: 100   ← 新版本 created_by=T3 > 快照 T2，被规则挡住
T4 开始，读到: 999   ← 新事务才看得见
```

**这三行判断替代了整套读锁**：

```text
读者要的旧版本【还在版本链里】，写者追加的新版本不碰它
→ 读操作全程【不需要任何锁】: 只做版本链遍历 + 可见性判断
→ 对照两阶段锁(2PL): 读者拿共享锁、写者拿排他锁，二者互斥 → 读写互相阻塞
```

**Python 实测印证了它**：

```text
B 持有写锁未提交时，A 读同一行: 100（耗时 0.052 ms，没有等待）
```

### MVCC 的代价：版本堆积

**C++ 实测**：

```text
再写 100 次之后，版本链长度: 102
```

```text
旧版本不能立刻删: 只要还有事务的快照【可能看见】它，就得留着
→ PostgreSQL 靠 VACUUM 清理死版本；不清理会「表膨胀」(table bloat)
→ MySQL/InnoDB 把旧版本放在 undo log 里，由 purge 线程回收
→ 长事务是 MVCC 的天敌: 一个开了几小时的事务，会卡住这几小时里所有的版本回收
```

**与第 36 章的呼应**：「还有人引用就不能回收」——**MVCC 的旧版本回收和 GC 是同一个判定问题**。

### 原子性怎么实现：undo log

**Java 版手写了它**，机制朴素得出乎意料：

```java
void put(String k, int v) {
    if (inTxn) undoLog.push(new Undo(k, data.get(k)));   // 先记下旧值，再改
    data.put(k, v);
}
int rollback() {
    while (!undoLog.isEmpty()) applyUndo(undoLog.pop());  // 逆序重放
}
```

```text
实测: 事务中转账一半 甲=40，undo log 里有 1 条记录
     ROLLBACK 撤销 1 条 → 甲=100 乙=100
```

**必须逆序重放**（实测证明）：

```text
同一个键连改三次: 甲=3，undo 里存着三条旧值 [100, 1, 2]
逆序重放 → 甲=100 ✓
顺序重放 → 甲=2   ✗（错的）
```

**与第 46 章 WAL 的关系**：

```text
WAL（redo log）: 存【新值】，用于「提交了但还没写进数据文件」时重做
undo log:        存【旧值】，用于「没提交就崩溃/回滚」时撤销
→ 一体两面: 一个负责「已承诺的必须兑现」，一个负责「没承诺的不留痕迹」
→ MVCC 的旧版本其实就是 undo log 的另一种组织方式（InnoDB 里两者是同一份数据）
```

### 保存点：事务内的部分回滚

```text
Java 实测: sp1 之后改了两处 → ROLLBACK TO sp1 撤销 2 条
          甲=50（sp1 之前，保留）乙=100（sp1 之后，撤销）丙=null（被删回「不存在」）
Python 实测: 提交后 [(1, 1), (2, 100)] —— 同样的行为
```

**实现只是记住「保存点时 undo log 有多深」，回滚到那个深度为止**——ORM 的「嵌套事务」多半就是它（第 51 章）。

## 4. JavaScript

JS 版承包了本章最重要的反例：**快照隔离挡不住的那个异常**。

### 写偏斜：两个事务各自都对，合起来却错了

**场景**：医院排班，规则是「任何时刻至少有一名医生在值班」。Alice 和 Bob 都在值班，两人**同时**点了「我要请假」。

**应用层代码看起来完全正确**：

```text
BEGIN; if (在值班人数 >= 2) { 把自己设为不值班 } COMMIT;
```

**在快照隔离下会发生什么**：

```text
T1 读到「2 人在值班」→ 判断通过 → 把 Alice 设为不值班
T2 读到「2 人在值班」→ 判断通过 → 把 Bob 设为不值班   ← 它读的是快照，看不到 T1
两个事务都提交 → 【0 人值班】，规则被破坏
```

**⚠️ 关键在于：两个事务没有写同一行**——所以写-写冲突检测完全抓不到它。这也是写偏斜最阴险的地方：所有基于「检测同一行冲突」的机制在它面前都失效。

### sqlite 挡住了，但代价是写并发度为 1（实测）

```text
结果: B 被数据库【拒绝】——database is locked
最终在值班人数: 1  ✓ 规则保住了
```

```text
sqlite 只允许【一个写事务】同时存在，等于强制串行化——写偏斜无从发生
代价: 写并发度 = 1（第 46 章实测过它靠排队而非并行取得正确性）
```

**但在 PostgreSQL / MySQL 的默认级别下，写偏斜是真的会发生的**：

```text
PostgreSQL 默认 READ COMMITTED，可选 REPEATABLE READ（实为快照隔离）——两者都挡不住
MySQL 的 REPEATABLE READ 也挡不住，需要 SELECT ... FOR UPDATE 手工加锁
→ 这是「隔离级别」这套术语最危险的地方: 名字听起来够用，实际未必
```

### 三种防御手段

```text
① 提升到 SERIALIZABLE   → 数据库检测冲突并让一方回滚，你要写重试逻辑
② SELECT ... FOR UPDATE → 读的时候就加锁，把「读-判断-写」串行化
③ 改造数据模型          → 加一行「值班人数」计数器，让两个事务写【同一行】
```

**手段 ③ 最快也最稳**：把「约束」变成一个**可以被并发控制看见的具体的行**——写同一行就变成了普通的写-写冲突，现成的锁和冲突检测就能抓住。

### 事务管不了外部世界（实测）

```text
假设事务里做了三件事: ① 改数据库 ② 发邮件 ③ 扣第三方支付
ROLLBACK 后数据库回滚了，但是——
→ 邮件【已经发出去了】，支付【已经扣了】
```

**正确做法**：事务里只做数据库操作，副作用记进「待办表」，提交后再由后台执行——这就是 **outbox 模式**，它把「分布式一致」退化成「本地事务 + 幂等重试」。

> **注意**：`node:sqlite`/better-sqlite3 是同步 API，事务里不会出现 `await`（这是好事）；异步驱动（pg/mysql2）的经典事故是**事务里 await 了另一个连接的查询**——那个查询不在这个事务里，回滚时不会被撤销；事务与连接绑定（第 45 章实测：事务期间连接不能还给池）。

## 5. Python

Python 版是三种读异常的复现主战场，用的是两个**真实的数据库连接**而非模拟。

### 实验设计的关键：WAL 模式

```python
con.execute("PRAGMA journal_mode=WAL")   # WAL 才有真正的快照隔离
con = sqlite3.connect(DB, isolation_level=None)   # None = 我们自己发 BEGIN/COMMIT
```

**没有 WAL 就做不了这个实验**：传统回滚日志模式下，B 的写会被 A 的读锁阻塞，根本走不到「B 提交后 A 还读到旧值」这一步。

### 写-写冲突：数据库如何阻止丢失更新（实测）

```text
A 持写锁期间 B 尝试写: OperationalError: database is locked
（B 等了 235 ms 才放弃——本例把 timeout 设成 0.2 秒，默认是 5 秒）
```

```text
sqlite 用【库级写锁】串行化写者: 同一时刻只有一个写事务
PostgreSQL/MySQL 用【行级锁】: 只有改同一行才互斥，粒度细得多（第 50 章）
```

**`timeout` 参数值得单独说**：它决定「数据库被别人锁着时等多久」，默认 5 秒。生产里这个值设得太大，会让请求线程被长时间占住（第 45 章的线程池饥饿）；设得太小，正常的锁等待也会失败。

### 事务的完整生命周期

```text
BEGIN        → 拿到一个【快照】（读什么版本从此确定）
执行读写      → 写操作先进 WAL，读操作按快照过滤版本
COMMIT       → 日志 fsync（第 46 章实测三档价格）→ 此刻才对别人可见
ROLLBACK/崩溃 → 丢弃未提交的日志记录，别人从头到尾什么都没看见
```

**「原子」不是「不会失败」，而是「失败也不留痕迹」**。

> **注意**：`isolation_level=None` 才能手工控制事务，默认值会让 Python 在某些语句前自动 `BEGIN`（行为反直觉，是历史包袱）；`BEGIN` 是延迟的（第一次读时才取快照），`BEGIN IMMEDIATE` 立刻取写锁——需要「读后写」的事务应该用后者，否则可能在写的时候才发现冲突，此时已经读了旧数据；Python 3.12+ 的 `autocommit` 属性语义更清晰。

## 6. Java

Java 版手写 undo log，把「原子性」这个抽象概念变成了三十行可运行的代码。

### undo log 的实现（实测可用）

```java
record Undo(String key, Integer oldValue) {}   // oldValue 为 null 表示「原本不存在」

void put(String k, int v) {
    if (inTxn) undoLog.push(new Undo(k, data.get(k)));   // 先记旧值，再改
    data.put(k, v);
}
```

```text
实测: 事务中转账一半 甲=40，undo log 里有 1 条记录
     ROLLBACK 撤销了 1 条: 甲=100 乙=100
```

### 逆序重放是必须的（实测）

```text
同一个键连改三次: 甲=3，undo 里 3 条旧值 [100, 1, 2]
逆序重放 → 甲=100 ✓（若顺序重放会得到 2，错的）
```

**这是手写事务最容易踩的坑**：`undoLog` 必须是**栈**而不是队列。

### 保存点的实现（实测）

```java
void savepoint(String name) { savepoints.put(name, undoLog.size()); }   // 记住深度

int rollbackTo(String name) {
    while (undoLog.size() > mark) applyUndo(undoLog.pop());               // 回滚到那个深度
}
```

```text
实测: sp1 之后改了两处 → ROLLBACK TO sp1 撤销 2 条
     甲=50（保留）乙=100（撤销）丙=null（被删回「不存在」）
```

**注意 `丙=null`**：它原本不存在，undo 记录里 `oldValue` 是 `null`，回滚时执行的是 `remove` 而非 `put`——**「不存在」也是一种需要被恢复的状态**。

### 四个隔离级别与它们放过的异常

| 级别 | 脏读 | 不可重复读 | 幻读 | 写偏斜 |
|------|------|-----------|------|--------|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | 可能 |
| READ COMMITTED | 不会 | 可能 | 可能 | 可能 |
| REPEATABLE READ | 不会 | 不会 | 标准允许* | 可能 |
| SERIALIZABLE | 不会 | 不会 | 不会 | 不会 |

```text
* SQL 标准允许 RR 出现幻读，但 MySQL/InnoDB 的 RR 用间隙锁挡住了幻读
  而 PostgreSQL 的 RR 其实是【快照隔离】，也挡住了幻读
→ 同一个名字「REPEATABLE READ」，三家的实际行为各不相同
→ 写偏斜【只有】SERIALIZABLE 挡得住
```

### JDBC 的对应 API

```java
conn.setAutoCommit(false);                    // ← 关掉自动提交才叫开事务
conn.setTransactionIsolation(Connection.TRANSACTION_REPEATABLE_READ);
Savepoint sp = conn.setSavepoint("sp1"); conn.rollback(sp);
conn.commit();  /  conn.rollback();           // ← 必须放在 finally
```

> **注意**：最常见的事故是**忘了 `setAutoCommit(false)`**——每条语句自成一个事务，转账的两步之间没有任何保护，和第 46 章实测的文件版一样脆；Spring 的 `@Transactional` 是这段样板的注解版，但**自调用不生效**（走的是代理，`this.method()` 绕过了代理）；连接归还给池之前必须恢复 `autoCommit`，否则污染下一个使用者。

## 7. C++

C++ 版手写 MVCC 引擎——**本章最有价值的一段代码**，因为它把「读不阻塞写」从一个说法变成了三行可验证的判断。

### 完整的可见性规则

```cpp
bool visible(const Version& v, uint64_t snapshot) const {
    if (v.created_by > snapshot) return false;
    if (v.deleted_by != 0 && v.deleted_by <= snapshot) return false;
    return true;
}
```

**读操作就是「从新到旧找第一个对我可见的版本」**：

```cpp
for (auto rit = versions.rbegin(); rit != versions.rend(); ++rit)
    if (visible(*rit, snapshot)) return rit->value;
```

**全程没有任何锁**——这是 MVCC 与两阶段锁的根本分野。

### 写-写冲突 MVCC 挡不住（实测）

```text
T105 和 T106 都写了 seat，版本链长度 2 —— 【后写的赢，前一个悄悄没了】
→ 本例的玩具引擎没有冲突检测，所以丢失更新真的发生了
```

**真实数据库的两种解法**：

```text
悲观: 写之前加行锁，第二个写者【等待】（MySQL 默认，第 50 章）
乐观: 提交时检查「我读到的版本还是最新的吗」，不是就【报错回滚】（PostgreSQL SI）
```

**所以 MVCC 只解决了「读写并发」，写写并发仍然需要锁或冲突检测**——这是理解数据库并发控制最重要的一条分界线。

### 与前面章节的三处呼应

```text
第 36 章 GC:   「还有人引用就不能回收」——MVCC 的旧版本回收是同一个判定问题
第 46 章 WAL:  「从不原地修改，只追加」——MVCC 的版本链是同一个思想
第 41 章 无锁: 「读路径不加锁」——MVCC 是数据库版的读-拷贝-更新(RCU)
```

**MVCC 不是数据库独有的发明**，而是「多版本 + 快照读」这个通用模式在存储层的应用；Linux 内核的 RCU、Clojure 的持久化数据结构、Git 的对象模型，都是同一个思想的不同形态。

> **注意**：真实 MVCC 比本例复杂得多——要处理事务的**提交状态**（版本可见还需要它的创建事务已提交）、快照要记录「哪些事务正在运行」（PostgreSQL 的 `xmin/xmax/xip_list`）、以及版本链过长时的性能退化（InnoDB 的 undo 链太长会让老快照的读变慢）。

## 8. C#

C# 版做了一次**对流行说法的实测检验**，结果值得单独讲。

### 实测给「乐观 vs 悲观」的教科书规律打了折扣

**实验**：8 个线程共做 16000 次「读-改-写」，在四档冲突强度下对撞。

```text
行数  冲突强度        悲观锁      乐观锁    乐观重试次数   差距
   1  极高(热点行)     14.0 ms     21.5 ms       49256   悲观快 1.54x
   8  高                3.0 ms      3.8 ms        4454   悲观快 1.25x
  64  中                2.6 ms      3.5 ms        1988   悲观快 1.34x
 512  低(分散)          3.0 ms      2.6 ms        1078   乐观快 1.13x
```

**反复运行后的诚实结论**：

```text
唯一【稳定可复现】的只有第一行: 热点行上悲观锁快 1.5~1.9x
（乐观锁在那里做了五万次无用功——读完发现版本变了，全部重来）
其余三档反复跑会在 1.0~1.6x 之间【方向都会变】—— 那是噪声，不是规律
```

**原因**：

```text
内存里加一次锁只要几十纳秒，乐观锁根本没有多少东西可省
那条规律的前提是【持锁的代价很大】——而在数据库里代价大是因为
锁被持有【跨越了网络往返】甚至【跨越了用户思考时间】，不是因为锁指令本身
```

### 乐观锁真正的价值：跨越无法持锁的边界（实测）

**场景**：用户打开编辑表单 → 思考 5 分钟 → 点保存。**你不可能持有数据库锁 5 分钟。**

```text
用户甲、乙同时打开编辑页，都读到 值=100 版本=1
甲改成 110 并保存: 成功（现在 值=110 版本=2）
乙改成 120 并保存: 【被拒绝】（他手里的版本 1 ≠ 当前版本 2）
最终 值=110 —— 乙的修改没有【悄悄覆盖】甲的
```

```text
若无版本号: 乙的保存会直接覆盖甲的改动，甲永远不知道（丢失更新）
→ 乐观锁不是「更快的锁」，而是
  【唯一能跨越无状态请求边界的并发控制】——HTTP 请求之间没法持锁
```

**这才是选型的真正分界线**：不是「哪个快」，而是「**你能不能持锁**」。

### 乐观锁在 ORM 里的样子

```text
EF Core:   [Timestamp] byte[] RowVersion;  → 自动加 WHERE RowVersion = ?
           提交时行数为 0 就抛 DbUpdateConcurrencyException
Hibernate: @Version int version;           → 同样的机制（第 51 章 ORM）
→ 「更新了 0 行」这个信号就是冲突检测: 版本号对不上 → WHERE 匹配不到
```

### 重试逻辑必须知道的两件事

```text
① 只重试【可重试的错误】: 序列化冲突/死锁可以重试，约束违规重试一万次也没用
② 必须【指数退避 + 上限】: 无退避的重试会在冲突时把系统推向雪崩（第 45 章）
→ 且重试的是【整个事务】——包括第一次读，因为快照要重新取
```

> **注意**：`cmd.Transaction = tx` 这行忘了写，命令就**不在事务里**（.NET 最常见的事务坑）；`TransactionScope` 是环境事务，能跨多个连接，但会升级成分布式事务（MSDTC），慎用；`IsolationLevel.Snapshot` 需要数据库先开 `ALLOW_SNAPSHOT_ISOLATION`。

## 9. SQL

本节从数据库一侧看事务的四个字母。

### A 原子性（实测）

```text
① 转账 60 成功后: 甲=40 乙=160，总额=200
   崩溃回滚后: 甲=40，总额仍是 200（一分没少）
```

### C 一致性——约束是不变量的守门员（实测）

```sql
CREATE TABLE account (
  balance INTEGER NOT NULL CHECK (balance >= 0)   -- 声明不变量
);
```

```text
② 试图透支 999: 影响行数=0（CHECK 拦下）
→ C 是唯一需要【你】参与的字母: 数据库只能执行你声明的规则
```

### 四个隔离级别（SQL 标准）

```text
READ UNCOMMITTED : 脏读✗ 不可重复读✗ 幻读✗ 写偏斜✗（几乎没人用）
READ COMMITTED   : 脏读✓ 不可重复读✗ 幻读✗ 写偏斜✗（PostgreSQL/Oracle 默认）
REPEATABLE READ  : 脏读✓ 不可重复读✓ 幻读~ 写偏斜✗（MySQL 默认）
SERIALIZABLE     : 全部✓（sqlite 只有这一级）
```

### 同名不同义：三家的 REPEATABLE READ 是三种东西

```text
SQL 标准    : 允许幻读（只保证既有行不变）
MySQL/InnoDB: 用【间隙锁】额外挡住了幻读，但挡不住写偏斜
PostgreSQL  : 实际是【快照隔离】，幻读也挡住了，仍挡不住写偏斜
→ 所以「我用了 RR 所以安全」是句危险的话——要问的是「哪家的 RR」
```

**这是本章最实用的一条知识**：隔离级别的**名字是标准的，行为不是**。迁移数据库时，同一个级别名下的行为可能完全改变，而这类 bug 极难复现。

### sqlite 的选择

```text
隔离级别: 永远是 SERIALIZABLE
实现方式: 同一时刻只允许【一个写事务】（库级写锁）
PRAGMA journal_mode=WAL 后读者不再被写者阻塞（Python 版实测 0.05 ms 无等待）
→ 正确性拉满，写并发度为 1 —— 嵌入式场景的合理取舍
```

### 三条实务纪律

```text
① 事务要短: 长事务卡住 MVCC 的版本回收（C++ 版实测版本链堆到 102 个）
② 事务里别做 I/O: 发邮件/调支付回滚不掉（JS 版演示）
③ 按固定顺序访问行: 顺序不一致 → 死锁（第 41 章四个必要条件，第 50 章展开）
```

> **注意**：sqlite 的 `BEGIN` 是延迟的，需要「读后写」时用 `BEGIN IMMEDIATE`；`SAVEPOINT` 可以嵌套，名字相同会覆盖；`PRAGMA foreign_keys=ON` 在 sqlite 里**默认是关的**——外键约束不生效是新手最常见的困惑。

## 10. 五语言横向对比

### ① 事务能力对照

| 能力 | SQL | Python | Java | C# | JavaScript |
|------|-----|--------|------|-----|-----------|
| 开启事务 | `BEGIN` | `con.execute("BEGIN")` | `setAutoCommit(false)` | `BeginTransaction()` | `db.exec('BEGIN')` |
| 隔离级别设置 | `SET TRANSACTION` | 驱动参数 | `setTransactionIsolation` | `IsolationLevel` 枚举 | 驱动参数 |
| 保存点 | `SAVEPOINT` | ✅ | `setSavepoint()` | `tx.Save()` | ✅ |
| 声明式事务 | — | 装饰器（框架） | **`@Transactional`** | `TransactionScope` | 框架各异 |
| 乐观锁支持 | 手写 version 列 | 手写 | **`@Version`**（JPA） | **`[Timestamp]`**（EF） | 框架各异 |
| 自动提交默认 | 开 | **开**（要 `isolation_level=None` 关） | **开**（要显式关） | 开 | 开 |

### ② 钥匙实验一：三种读异常（Python 实测）

```text
无事务:   A 读 100 → B 提交 777 → A 读 777        【不可重复读】
有事务:   A 读 100 → B 提交 999 → A 读 100        【快照隔离挡住了】
范围查询: 事务内 COUNT 3 → 3；事务外 4            【幻读也挡住了】
写锁期间: B 未提交时 A 读同一行 0.05 ms 零等待     【读不被写阻塞】
```

### ③ 钥匙实验二：MVCC 三行规则（C++ 实测）

```text
版本链: [值=100 生于T1 死于T3] [值=999 生于T3 死于T-]
T2（快照=2）读到 100；T4（快照=4）读到 999
可见性规则三行 → 替代整套读锁
代价: 连写 100 次后版本链长度 102（旧版本不能立刻删）
```

### ④ 钥匙实验三：写偏斜（JS 实测）

```text
两个事务各自读到「2 人值班」→ 各自判断通过 → 合起来 0 人值班
关键: 两个事务【没有写同一行】→ 写-写冲突检测抓不到
sqlite（SERIALIZABLE）挡住了: B 被拒绝 database is locked
PostgreSQL/MySQL 的默认级别【挡不住】
```

### ⑤ 钥匙实验四：乐观 vs 悲观（C# 实测）

```text
四档冲突强度对撞: 只有热点行那档稳定（悲观快 1.5~1.9x，乐观重试 5 万次）
其余三档方向都会变 → 噪声，不是规律
真正的分界: 能不能持锁（用户思考 5 分钟 → 只能用版本号）
```

### ⑥ 共性与根因

**共性**：所有语言的默认都是**自动提交**（每条语句一个事务）——这个默认值保护了新手，也让「忘了开事务」成为最常见的事故；所有语言的事务都**绑定在连接上**（第 45 章：事务期间连接不能还给池）；所有语言都无法让事务管住**外部副作用**。

**根因**：

- **Java/C# 提供声明式事务**（`@Transactional` / `TransactionScope`）——企业级语言的传统：把横切关注点从业务代码里抽出来；代价是**边界变隐式**（Spring 自调用不生效是经典事故）；
- **Python/JS 保持显式**——脚本语言的传统，事务边界肉眼可见，但样板代码多；
- **JPA/EF Core 都内建了乐观锁**（`@Version` / `[Timestamp]`）——因为 ORM 的典型场景正是「跨 HTTP 请求编辑」，那里根本无法持锁（C# 版实测的分界线）；
- **sqlite 只有 SERIALIZABLE**——嵌入式场景写并发本来就低，用「写者串行」换「零并发 bug」是合理取舍；
- **服务器数据库提供四级**——因为吞吐是刚需，而降低隔离级别是最直接的提速手段（代价是把并发 bug 的责任转给了应用）。

## 11. 底层实现对比

| 数据库 | 隔离实现 | 关键细节 |
|--------|---------|---------|
| **SQLite** | 库级写锁 + WAL 快照读 | 只有 SERIALIZABLE；写并发度 1；读者永不阻塞 |
| **PostgreSQL** | MVCC（元组带 `xmin`/`xmax`） | RR = 快照隔离；SERIALIZABLE = SSI（检测读写依赖环） |
| **MySQL/InnoDB** | MVCC（undo log 链）+ 间隙锁 | RR 用间隙锁挡幻读；死锁自动检测并回滚代价小的一方 |
| **Oracle** | MVCC（回滚段） | 无脏读级别；RR 靠快照；历史最悠久的 MVCC 实现 |
| **SQL Server** | 默认锁；可选 Snapshot | `READ_COMMITTED_SNAPSHOT` 打开后才是 MVCC |

**PostgreSQL 的 SSI 值得单独说**（可串行化快照隔离）：

```text
它不用锁，而是在快照隔离之上【检测危险结构】:
  一个事务读了另一个事务将要写的数据，且形成了特定的依赖环
→ 检测到就让一方回滚（报 serialization_failure）
→ 所以它能挡住写偏斜，且读依然不加锁
→ 代价: 你【必须】写重试逻辑，因为事务会被无辜地回滚
```

## 12. 性能分析

### 隔离级别的代价梯度

```text
READ COMMITTED  → 每条语句一个新快照，版本回收快
REPEATABLE READ → 整个事务一个快照，长事务会拖住版本回收
SERIALIZABLE    → 额外的冲突检测（SSI）或更多的锁（2PL）+ 回滚重试
→ 隔离级别越高，吞吐越低——这是一条真实的、需要你做取舍的曲线
```

### 本章实测数字速查

```text
快照隔离:     事务内两次读 100/100（B 已提交 999 也看不见）
读不被写阻塞: 0.05 ms 零等待（B 持写锁未提交时）
MVCC 版本堆积: 连写 100 次 → 版本链长度 102
写锁冲突:     B 等待 235 ms 后放弃（timeout=0.2s）
悲观 vs 乐观:  热点行悲观快 1.5~1.9x（乐观重试 5 万次）；其余三档是噪声
undo log:     逆序重放正确（甲=100），顺序重放错误（甲=2）
```

### 长事务的真实代价

```text
① 卡住 MVCC 版本回收 → 表膨胀（C++ 版实测版本链只增不减）
② 长期占用连接      → 连接池耗尽（第 45 章实测过池耗尽的雪崩）
③ 持锁时间变长      → 其他事务等待，死锁概率上升
→ 「事务要短」不是一条风格建议，而是三个具体故障的预防措施
```

> ⚠️ 提高隔离级别**不是免费的正确性**。SERIALIZABLE 下事务会因冲突被回滚，**你必须写重试逻辑**——否则用户看到的不是「数据不一致」而是「操作失败」，只是把问题换了个形式。

## 13. 工程实践

| 场景 | ✅ 推荐 | ❌ 避免 | 原因 |
|------|--------|--------|------|
| 转账类多步操作 | 一个事务包住 | 多条独立语句 | 第 46 章实测崩溃留半条 |
| 读后写（扣库存） | `BEGIN IMMEDIATE` / `FOR UPDATE` | 先读再写不加锁 | 实测丢失更新 |
| 跨 HTTP 请求编辑 | 乐观锁（version 列） | 持有数据库锁 | 无法持锁 5 分钟 |
| 检查后行动的约束 | SERIALIZABLE 或改数据模型 | 依赖 RR | 实测写偏斜穿透 RR |
| 事务里发邮件/调支付 | 写 outbox 表，提交后异步做 | 直接在事务里做 | 回滚不掉外部副作用 |
| 长时间的批处理 | 拆成多个小事务 | 一个大事务 | 卡住版本回收 + 占用连接 |
| Java 事务边界 | `@Transactional` 放在服务层入口 | 类内自调用 | 代理机制导致不生效 |
| .NET 命令入事务 | `cmd.Transaction = tx` | 忘了赋值 | 命令根本不在事务里 |
| Python 手工控制 | `isolation_level=None` | 依赖默认行为 | 默认会自动 BEGIN，反直觉 |
| 并发冲突 | 指数退避重试 | 立即无限重试 | 冲突时会雪崩（第 45 章） |
| 迁移数据库 | 逐条核对隔离级别的**实际行为** | 假设同名同义 | 三家的 RR 是三种东西 |

### 一句话决策

```text
① 这组操作要不要「全有或全无」？→ 要 → 包进事务
② 中间有没有「先读后写」？      → 有 → 加锁或用乐观锁（否则丢失更新）
③ 有没有「检查后行动」的约束？  → 有 → 写偏斜风险，上 SERIALIZABLE 或改数据模型
④ 事务里有没有外部 I/O？        → 有 → 挪出去（outbox）
```

## 14. 最佳实践

- **事务要短**：实测三个具体后果——卡住版本回收（版本链堆到 102）、占用连接（第 45 章的池耗尽）、拉长持锁时间。
- **明确知道你的隔离级别叫什么、又实际做什么**：同名不同义是本章最实用的一条——「我用了 RR 所以安全」要先问「哪家的 RR」。
- **「检查后行动」的约束要当心写偏斜**：实测它专挑看起来正确的代码；最稳的解法是**把约束变成一个具体的行**，让并发控制看得见。
- **跨请求的编辑一律用乐观锁**：不是因为它快（实测没有量级优势），而是因为**HTTP 请求之间没法持锁**。
- **事务里绝不做外部 I/O**：邮件发出去就收不回来了；用 outbox 模式把副作用变成「提交后的本地待办」。
- **重试逻辑要判断错误类型 + 指数退避**：只有序列化冲突和死锁值得重试，且要重试**整个事务**（快照要重新取）。
- **显式关掉自动提交**：Java 的 `setAutoCommit(false)`、Python 的 `isolation_level=None`——忘了这一步，你以为的事务根本不存在。
- **别忘了 `cmd.Transaction = tx`**（.NET）和 `@Transactional` 的自调用陷阱（Java）：这两个是各自生态最高频的「事务没生效」原因。

## 15. 常见坑

**坑 1 · 忘了关自动提交**

```java
conn.createStatement().execute("UPDATE ...");   // ⚠️ 每条语句自成事务，两步之间毫无保护
// 正确: conn.setAutoCommit(false); ... conn.commit();
```

**坑 2 · 先读后写不加锁**

```sql
SELECT stock FROM item WHERE id = 1;    -- ⚠️ 读到 1
-- 另一个事务也读到 1 并卖掉了
UPDATE item SET stock = 0 WHERE id = 1; -- 超卖
-- 正确: SELECT ... FOR UPDATE，或 UPDATE ... WHERE stock > 0
```

**坑 3 · 以为 REPEATABLE READ 挡得住写偏斜**

```text
⚠️ 实测: 两个事务各自检查通过，合起来违反约束——RR 完全挡不住
正确: SERIALIZABLE，或 SELECT ... FOR UPDATE，或改数据模型
```

**坑 4 · 事务里做外部 I/O**

```javascript
await db.exec('BEGIN');
await sendEmail(user);        // ⚠️ 回滚不掉
await chargePayment(user);    // ⚠️ 更回滚不掉
```

**坑 5 · Spring `@Transactional` 自调用**

```java
public void outer() { this.inner(); }        // ⚠️ 绕过代理，@Transactional 不生效
@Transactional public void inner() { ... }
```

**坑 6 · 长事务**

```python
con.execute("BEGIN")
for row in huge_list:          # ⚠️ 跑几小时 → 版本回收全卡住 + 连接被占
    process(row)
con.execute("COMMIT")
```

**坑 7 · 重试没有退避**

```python
while True:
    try: do_txn(); break
    except SerializationFailure: pass    # ⚠️ 立即重试 → 冲突时把数据库推向雪崩
```

## 18. 本章总结

**一句话**：事务把一组操作变成不可分割的单位，用四个字母承诺了原子（Java 版手写 undo log，实测逆序重放才正确）、一致（约束守门，唯一需要你参与的字母）、隔离（本章主角）和持久（第 46 章实测的三档 fsync）；其中**隔离**最难也最有料——Python 用两个真实连接实测出快照隔离的分野（无事务时两次读 100→777 是**不可重复读**，包进事务后即使别人已提交 999 也仍读到 100），C++ 手写 MVCC 引擎揭示了它的实现**只有三行可见性规则**（因此读不被写阻塞，实测 **0.05 ms 零等待**；代价是版本堆积到 **102 个**，这正是 VACUUM 与「长事务是天敌」的由来）；但快照隔离有个专挑「看起来正确的代码」下手的漏洞——**写偏斜**（JS 版医院排班：两个事务各自检查通过，合起来违反约束，且**因为没写同一行而躲过所有冲突检测**）；最后 C# 版实测**推翻了「乐观锁低冲突时更快」的流行说法**（四档强度里只有热点行那档稳定，其余是噪声），指出真正的分界不是性能而是**能不能持锁**——用户思考五分钟再提交时，版本号是唯一的办法。

**关键要点**

- **ACID 各自的实现**：A=undo log，C=约束（你的份），I=MVCC+锁，D=WAL+fsync。
- **三种读异常**：脏读（未提交）、不可重复读（行内容变）、幻读（行集合变）——后两者的区别决定了实现难度。
- **快照隔离**（实测）：事务内两次读必然一致，看到的是「事务开始那一刻」的整个数据库。
- **MVCC 三行规则**：新于我的看不见、我开始前就死的看不见、其余可见——替代整套读锁。
- **MVCC 的代价**（实测 102 个版本）：旧版本不能立刻删 → VACUUM、表膨胀、长事务是天敌。
- **写偏斜**：快照隔离挡不住，因为两个事务不写同一行；只有 SERIALIZABLE 或改数据模型能解。
- **同名不同义**：MySQL 的 RR、PostgreSQL 的 RR、SQL 标准的 RR 是三种行为。
- **乐观锁的真正价值**（实测）：不是快，而是**能跨越无法持锁的边界**。

- [ ] 我能区分三种读异常，并解释幻读为什么更难挡。
