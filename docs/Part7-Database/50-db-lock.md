# 第 50 章 · 数据库锁

**简体中文** ｜ [English](./50-db-lock.en-US.md)

---

> 第 48 章反复提到「行级锁」「间隙锁」「写偏斜要 `SELECT ... FOR UPDATE`」，但都没有展开。第 49 章末尾说「索引还决定锁的范围」，也留了个尾巴。这一章把它们全部兑现。
>
> 本章的**钥匙实验**是手写一个锁管理器——把 MySQL 每天在做的三件事实现一遍：**相容性判断、等待图找环、选受害者**。相容矩阵只有一条规则（读读相容，其余三种组合互斥）；死锁检测就是在等待图上做一次 DFS 找环；选受害者则是挑持锁最少的那个。实测输出完整地演了一遍：两个事务以相反顺序加锁 → 等待图出现 `T1 → T2 → T1` → **检测到环** → 回滚持锁最少的 T1 → 另一个事务立刻推进。
>
> Java 版把同样的死锁造在真线程上，让 JVM 用 `findDeadlockedThreads()` 自己抓——**它抓到了**（两个 `WAITING` 线程，各自等着对方持有的锁）。这构成一个重要对照：第 45 章的**线程饥饿死锁**和第 48 章的**写偏斜**，同样的工具**都检测不到**。「数据库能自动处理死锁」这句话，只覆盖等待图有环的那一种。
>
> 锁粒度决定并发上限，C# 版把它量化了：4096 行数据、8 个线程，**表锁（1 把）80 ms、条带锁（16 把）17 ms、行锁（4096 把）13 ms——行锁比表锁快 6.25 倍**；而单线程时三者几乎一样（7 ms），因为没有竞争时加锁只是几十纳秒。但粒度细不是免费的——千万行的表若每行一把锁，光锁对象就要几百 MB，这正是**锁升级**存在的原因，也是「批量 UPDATE 突然把系统卡死」的常见成因。
>
> Python 版揭开了 sqlite 最隐蔽的一个坑：用默认的 `BEGIN`（延迟事务）先读后写，**升级写锁时会失败**——因为快照已经过期。数据库拒绝这次升级，正是在阻止丢失更新；解法是「读后写」的事务一开始就用 `BEGIN IMMEDIATE`。
>
> 最后是 JS 版对「拿到 BUSY 之后该怎么办」的实测：面对同一个持锁 120 ms 的障碍，**立刻重试尝试了 17641 次，指数退避只尝试 8 次，而两者总耗时几乎相同（120 ms vs 127 ms）**。**两千倍的无效锁申请没有换来任何速度**——它只是在高并发下把「一个慢事务」放大成全站雪崩。

## 1. 学习目标

学完本章，你将能够：

- 写出 **S/X 锁的相容矩阵**，并用一条规则推出全部锁行为；
- 复述**死锁检测**的完整算法（等待图 → 找环 → 选受害者），并解释数据库为什么敢让死锁发生；
- 说清哪三种「卡住」能被工具检测、哪些不能（本章 vs 第 45 章 vs 第 48 章）；
- 量化**锁粒度**对并发的影响（实测 6.25x），并解释锁升级为什么是把双刃剑；
- 正确处理锁冲突：**固定加锁顺序**预防死锁，**指数退避重试**兜底（实测 2205 倍无效请求的教训）。

## 2. 为什么会出现这个概念

### 前两章留下的三个尾巴

```text
第 48 章: 「写偏斜要用 SELECT ... FOR UPDATE」——但它到底加了什么锁？
第 48 章: 「MySQL 的 RR 用间隙锁挡幻读」——间隙锁是什么？为什么会制造死锁？
第 49 章: 「索引还决定锁的范围」——怎么决定的？
```

### 锁要解决的问题：MVCC 解决不了的那一半

```text
第 48 章实测: MVCC 让【读】完全不加锁，读写互不阻塞（0.05 ms 零等待）
但 MVCC 挡不住【写写冲突】——C++ 版实测过: 两个事务都写 seat，后写的赢，前一个悄悄没了
→ 所以锁并没有被 MVCC 淘汰，只是【退守到了写这一侧】
```

**这一章讨论的锁，几乎全是围绕「写」的**：

| 场景 | 需要锁吗 | 为什么 |
|------|---------|--------|
| 纯读 | ❌ | MVCC 给你一个快照（第 48 章） |
| 纯写（原子语句） | 数据库内部加 | `UPDATE ... SET v = v + 1` 你无需操心 |
| **读后写** | ✅ **要** | 读到的值是写入的依据，中途被改就错了 |
| **检查后行动** | ✅ **要** | 写偏斜（第 48 章），MVCC 挡不住 |

> **一句话总结**：MVCC 把「读」从锁里解放了出来，剩下的问题——**谁能写、写的顺序、以及互相等待时怎么办**——就是这一章的全部内容。

## 3. 底层原理

### 钥匙实验一：相容矩阵——一条规则推出全部行为

```text
┌──────────────┬────────┬────────┐
│ 已持有 \ 想要 │   S    │   X    │
├──────────────┼────────┼────────┤
│      S       │ ✓相容  │ ✗互斥  │
│      X       │ ✗互斥  │ ✗互斥  │
└──────────────┴────────┴────────┘
```

```text
S = 共享锁（读）  X = 排他锁（写）
一条规则: 「读读不冲突，只要沾上写就冲突」
→ 四种组合里只有 S+S 能共存，其余三种全部互斥
```

**⚠️ 但现代数据库里 S 锁比你想象的少见**：

```text
MVCC（第 48 章）让普通 SELECT 【根本不加锁】——它读快照
S 锁主要出现在: SELECT ... FOR SHARE、外键检查、以及不支持 MVCC 的旧引擎
→ 所以日常遇到的锁冲突，绝大多数是 X 锁之间的（写写冲突）
```

**C++ 实测的正常流程**：

```text
T1 请求 行A 的 S 锁: ✓ 成功
T2 请求 行A 的 S 锁: ✓ 成功   ← 读读并发
T3 请求 行A 的 X 锁: ✗ 阻塞   ← 写要等读完
T1、T2 提交释放锁后，T3 重试: ✓ 成功
```

### 钥匙实验二：死锁检测的完整算法

**造一个死锁**（两个事务以相反顺序访问同一批行——死锁的经典配方）：

```text
T1 acquire(行A, X): ✓
T2 acquire(行B, X): ✓
T1 acquire(行B, X): ✗ 阻塞   ← 行B 被 T2 占着
T2 acquire(行A, X): ✗ 阻塞   ← 行A 被 T1 占着
    锁表: 行A{T1:X} 行B{T2:X}
```

**第一步：构建等待图**（事务 A 等资源 R，而 R 被 B 持有 → 边 `A→B`）：

```cpp
std::map<int, std::set<int>> wait_for_graph() const {
    std::map<int, std::set<int>> g;
    for (const auto& [txn, res] : waits_for_res_) {      // 我在等哪个资源
        for (const auto& h : holders_.at(res))            // 那个资源被谁持有
            if (h.txn != txn) g[txn].insert(h.txn);       // 就连一条边过去
    }
    return g;
}
```

```text
实测输出:
  T1 ──等待──> T2
  T2 ──等待──> T1
```

**第二步：找环**（DFS，回到「正在访问」的节点就是环）：

```cpp
if (visiting.count(v)) {                    // 回到了正在访问的节点 = 有环
    auto pos = std::find(path.begin(), path.end(), v);
    cycle.assign(pos, path.end());
    return true;
}
```

```text
实测: ⚠️ 检测到【环】: T1 → T2 → T1  = 死锁
```

**第三步：选受害者**（持锁最少的那个，回滚代价最小——InnoDB 的策略同源）：

```text
实测: → 选受害者: T1（持锁最少，回滚代价最小）
     → 回滚 T1 释放它的锁后，另一个事务立刻能推进: ✓ 成功
```

### 数据库与你的进程：对死锁的态度完全不同

**第 41 章的四个必要条件在数据库里原样成立**：

```text
① 互斥       —— X 锁天然互斥
② 持有并等待 —— 事务持有 行A 的同时去等 行B
③ 不可剥夺   —— 锁只能由持有者提交/回滚时释放
④ 循环等待   —— T1→T2→T1
```

**但处理策略截然不同**：

```text
你的进程内（第 41 章）: 没有回滚机制 → 死锁只能【预防】，发生了就是永久挂起
数据库:                 能回滚 → 敢让死锁【发生】，然后检测并回滚一方
→ 这是数据库比进程内锁强大的根本原因: 它有「后悔药」
→ 代价转嫁给了你: 你必须【捕获错误并重试整个事务】
```

**Java 版实测 JVM 也能检测**（`findDeadlockedThreads()`）：

```text
⚠️ 检测到 2 个线程互相死锁:
  事务-T1 状态=WAITING
    正在等待: ReentrantLock$NonfairSync@24d46ca6
    被谁持有: 事务-T2
  事务-T2 状态=WAITING
    正在等待: ReentrantLock$NonfairSync@36baf30c
    被谁持有: 事务-T1
```

**但它只能检测这一种「卡住」**——这是本章最重要的对照：

| 现象 | 机制 | 工具能检测吗 |
|------|------|-------------|
| **本章的死锁** | 两个线程各持一把锁，互等对方 → 等待图**有环** | ✅ 能 |
| 第 45 章的**线程饥饿死锁** | 线程在等任务，任务在等线程 → 没有锁的环 | ❌ 不能 |
| 第 48 章的**写偏斜** | 两个事务根本不冲突，只是逻辑上违反约束 | ❌ 更不能 |

```text
→ 「数据库能自动处理死锁」这句话【只覆盖第一种】
→ 后两种要靠你自己: 前者靠拆池（第 45 章），后者靠 SERIALIZABLE 或改数据模型（第 48 章）
```

### 钥匙实验三：锁粒度决定并发上限

**C# 实测**（4096 行数据，每线程 20000 次「读-改-写」）：

| 线程数 | 表锁（1 把） | 条带锁（16 把） | 行锁（4096 把） | 行锁 vs 表锁 |
|--------|------------|---------------|---------------|-------------|
| 1 | 7 ms | 7 ms | 7 ms | 0.98x |
| 2 | 17 ms | 8 ms | 8 ms | 2.23x |
| 4 | 38 ms | 14 ms | 12 ms | 3.23x |
| **8** | **80 ms** | **17 ms** | **13 ms** | **6.25x** |

```text
① 单线程时三者几乎一样 —— 没有竞争时，加锁只是几十纳秒的开销
② 线程越多，粗粒度锁的劣势越明显 —— 表锁把所有并发【强制串行化】
③ 条带锁只用 1/256 的内存，并发度已接近行锁
→ 粒度是并发度的【上限】: 这就是数据库拼命做行级锁的原因
```

### 但粒度细不是免费的：锁升级

```text
4096 行 → 4096 把锁，仅引用就要 32 KB
一张千万行的表若每行一把锁 → 锁对象本身就要几百 MB
```

```text
→ 所以数据库有【锁升级】(lock escalation):
  一个事务锁的行太多时，自动把成千上万把行锁替换成【一把表锁】
  省内存，但并发瞬间归零
→ SQL Server 的阈值约 5000 行；InnoDB 不做升级，改用位图压缩锁信息
→ 「批量 UPDATE 突然把整个系统卡死」的常见原因就是它
```

### 锁与索引：第 49 章在这里收口

```text
行锁是加在【索引条目】上的，不是加在「行」这个抽象概念上
→ 没有合适索引时，数据库只能【扫描并锁住扫过的每一行】
```

**SQL 版实测**：

```text
UPDATE seat SET taken=1 WHERE row_no = 3  （有 idx_row）
  → EXPLAIN: SEARCH ... USING INDEX idx_row
  → 只锁命中的 10 行

UPDATE seat SET taken=1 WHERE taken = 0  （taken 无索引）
  → EXPLAIN: SCAN seat
  → 锁住【扫过的全部 100 行】
```

**这就是「没有索引的 UPDATE 把整张表锁住」的真正机制**——第 49 章的索引不只决定查询快慢，**还直接决定锁的范围和并发上限**。

## 4. JavaScript

JS 版回答了最实际的一个问题：**拿到 `SQLITE_BUSY` 之后该怎么办**。

### busy_timeout：等多久才放弃（实测）

```text
busy_timeout=  0ms: 失败，实际等了   0 ms
busy_timeout= 50ms: 失败，实际等了  62 ms
busy_timeout=200ms: 失败，实际等了 234 ms
```

```text
→ busy_timeout=0 时立刻失败；设了值就会在 sqlite 内部【自旋等待】到超时
→ ⚠️ 这个等待发生在 sqlite 内部，你的线程是被【阻塞】的
  （第 45 章: 会占住线程池里的位置；Node 里更糟——阻塞整个事件循环）
```

### 立刻重试 vs 指数退避（实测——本节的核心）

面对同一个持锁 120 ms 的障碍：

```text
立刻重试（无退避）: 尝试 17641 次，总耗时 120 ms
指数退避:          尝试     8 次，总耗时 127 ms（累计退避 127 ms）
→ 尝试次数相差 2205 倍，总耗时却几乎相同
```

**这个对比揭示了一件反直觉的事**：

```text
无退避的 17641 次尝试【没有换来任何速度】——因为瓶颈是「锁什么时候释放」，不是「你问得多勤」
它唯一的效果是: 用两千倍的无效锁申请持续冲击数据库
→ 单个客户端时只是浪费 CPU
→ 高并发时，N 个客户端一起这么干 = 把「一个慢事务」放大成全站雪崩（第 45 章）
```

### 单写者模型不会死锁，但会「饿死」

```text
sqlite 同时只有一个写事务 → 没有循环等待 → 【不可能死锁】（C++ 版的环不存在）
但会出现另一种问题: 写者排队时【谁先拿到锁没有公平性保证】
→ 高频短事务可能一直插队，让某个长事务反复 BUSY 超时（写者饥饿）
→ 解法: 应用层排队（单一写入通道），而不是让 N 个线程抢同一把写锁
```

### 什么时候需要显式加锁（MVCC 之外的场景）

```text
MVCC 让【读】不需要锁，但下面三种情况仍要显式锁:
  ① 读后写: 读到的值要作为写入的依据 → BEGIN IMMEDIATE / SELECT FOR UPDATE
  ② 检查后行动: 「至少保留一个管理员」这类约束 → 防写偏斜（第 48 章）
  ③ 唯一性生成: 「取号 + 加一」→ 用数据库序列或原子 UPDATE 代替
→ 判据很简单: 你读到的东西会不会【影响你接下来要写什么】？会 → 需要锁
```

> **注意**：`PRAGMA busy_timeout` 是**每连接**设置，不是全局的；better-sqlite3 的 `db.transaction(fn)` 会自动包 `BEGIN/COMMIT` 但**不会自动重试**；`node:sqlite` 与 better-sqlite3 都是同步 API，锁等待会**阻塞整个事件循环**（第 43 章实测过这个后果），写密集的 Node 服务应该把写操作收敛到单一队列。

## 5. Python

Python 版揭开了 sqlite 最隐蔽的一个坑。

### sqlite 的锁模型：一个写者，多个读者（实测）

```text
A 持有写锁期间，B 尝试开写事务: ✗ 被拒绝（等了 236 ms）→ database is locked
但 B 读同一行: 100（耗时 0.178 ms，零等待）← WAL 下读不被写阻塞
```

```text
sqlite 的粒度是【整个数据库】: 写锁只有一把，写者严格排队
对照 PostgreSQL/MySQL 的【行级锁】: 只有改同一行才互斥（C++ 版实现的就是行锁）
→ 这是嵌入式数据库的合理取舍: 用写并发换实现简单和零配置
```

### 最隐蔽的坑：延迟事务的锁升级失败（实测）

```python
A.execute("BEGIN")                       # DEFERRED：此刻【不拿任何锁】
v = A.execute("SELECT balance ...").fetchone()[0]     # 读到 100
# B 趁机改成 999 并提交
A.execute(f"UPDATE ... SET balance = {v - 10} ...")   # ✗ 失败
```

```text
A: BEGIN（延迟）→ 读到 balance = 100   ← 此刻 A 只有【读锁】
B: 趁机改成 999 并提交
A: 现在想把读到的值 -10 写回去: ✗ 失败 —— database is locked
```

```text
底层原因: A 的快照已经过期——它看到的 100 早就不是最新值了
（sqlite 的 C API 返回扩展码 SQLITE_BUSY_SNAPSHOT，Python 只暴露为 database is locked）
→ 数据库拒绝这次升级，正是在【阻止丢失更新】（第 46 章实测过它的后果）
```

**解法：需要「读后写」的事务，一开始就用 `BEGIN IMMEDIATE`**（实测）：

```text
A: BEGIN IMMEDIATE → 读到 999；此时 B 想开写事务: ✗ 被挡在门外
A 的写入: ✓ 成功，最终 balance = 989
→ 代价: B 从头到尾被挡住（并发更低）
→ 收益: A 的「读-改-写」不会中途失效
→ 这就是【悲观锁】: 先占住位置再干活（第 48 章 C# 版量过它与乐观锁的分界）
```

### busy_timeout 的取舍（实测）

```text
timeout=0.05s: 等了  63 ms 后放弃
timeout=0.2s : 等了 230 ms 后放弃
timeout=0.5s : 等了 570 ms 后放弃
```

```text
设太小: 正常的锁等待也会失败
设太大: 请求线程被长时间占住（第 45 章的池饥饿）
→ 生产经验: 设成「你能容忍的最长响应时间」，并配合重试
```

> **注意**：`isolation_level=None` 才能手工控制事务；`BEGIN` 是延迟的（第一次读时才取快照），`BEGIN IMMEDIATE` 立刻取写锁——**这两个词的差别就是本节整个坑的来源**；重试时只重试「可重试」的错误（`database is locked` / `busy`），约束违规重试一万次也没用。

## 6. Java

Java 版把死锁造在真线程上，并对比了三种「卡住」。

### JVM 的死锁检测（实测）

```java
long[] ids = mx.findDeadlockedThreads();
for (ThreadInfo info : mx.getThreadInfo(ids, true, true)) { ... }
```

```text
⚠️ 检测到 2 个线程互相死锁:
  事务-T1 状态=WAITING  正在等待: ReentrantLock@24d46ca6  被谁持有: 事务-T2
  事务-T2 状态=WAITING  正在等待: ReentrantLock@36baf30c  被谁持有: 事务-T1
→ 等待图里有环 → 死锁成立。这正是 C++ 版手写的那个算法
```

### 三种「卡住」的对照（本章最重要的一张表）

```text
本章的死锁     : 两个线程各持一把锁，互等对方 → 等待图【有环】→ 可检测 ✓
第 45 章的饥饿 : 线程在等【任务】，任务在等【线程】→ 没有锁的环 → 检测不到 ✗
第 48 章的写偏斜: 两个事务根本没冲突，只是逻辑上违反了约束 → 更不可检测 ✗
→ 「数据库能自动处理死锁」这句话只覆盖第一种；后两种要靠你自己
```

### 破坏循环等待：固定加锁顺序（实测无死锁）

```java
rowC.lock();                      // ← 所有线程都【先 C 后 D】
try { rowD.lock(); try { ... } finally { rowD.unlock(); } }
finally { rowC.unlock(); }
```

```text
两线程各做 20000 次「双行加锁」，固定顺序: 7 ms，完成 40000 次
期间新增死锁: ✓ 无（顺序一致就不可能有环）
```

**转账场景的正确写法**：

```text
✓ 永远【按账号 id 从小到大】加锁
✗ 「先扣款方，后收款方」——后者的顺序取决于数据，必然出现相反的组合
  （甲转乙 锁 1→2；乙转甲 锁 2→1，两者相遇就是死锁）
```

### 超时退出：另一条活路（实测）

```text
tryLock(200ms) 结果: ✓ 超时放弃（不会永久卡住）
→ 对应数据库的 innodb_lock_wait_timeout（MySQL 默认 50 秒）
→ 超时后你会收到一个【可重试】的错误，而不是永久挂起
```

> **注意**：`SELECT ... FOR UPDATE` / `FOR SHARE` **必须在事务里**用，否则语句一结束锁就没了；`Statement.setQueryTimeout(n)` 是语句级超时，与锁超时是两回事；捕获死锁看 `SQLException.getSQLState() == "40001"`（序列化失败，可重试）；本例把死锁线程设成守护线程，否则 JVM 永远无法退出——**这本身就是「进程内死锁不可恢复」的证据**。

## 7. C++

C++ 版是本章的钥匙实验：**一个完整的锁管理器**。

### 三个组成部分

```cpp
/// ① 相容矩阵：只有「读读」相容
static bool compatible(Mode held, Mode want) {
    return held == Mode::S && want == Mode::S;
}

/// ② 加锁：不相容就记入等待图
bool acquire(int txn, const std::string& res, Mode want) {
    for (const auto& h : holders_[res])
        if (!compatible(h.mode, want)) {
            waits_for_res_[txn] = res;              // 记录「我在等哪个资源」
            return false;
        }
    holders_[res].push_back({txn, want});
    return true;
}

/// ③ 选受害者：持锁最少的那个（回滚代价最小）
int pick_victim(const std::vector<int>& cycle) const;
```

**这三段就是 InnoDB 锁模块的教学版**——真实实现还要处理锁升级、意向锁、间隙锁、以及等待队列的公平性，但**核心结构一模一样**。

### 为什么数据库选择「检测」而不是「预防」

```text
预防死锁要破坏四个条件之一:
  ① 互斥      → 不可能，X 锁的存在就是为了互斥
  ② 持有并等待 → 要求事务【一次性申请所有锁】，但事务要锁哪些行往往运行时才知道
  ③ 不可剥夺   → 允许抢锁 = 允许破坏隔离性
  ④ 循环等待   → 要求全局固定顺序，数据库无法强制应用这么做
→ 前三个都不可行，第四个只能靠【你】配合
→ 所以数据库选择: 接受死锁发生，然后检测 + 回滚（它有回滚能力，这是它的底气）
```

### 破坏循环等待（实测）

```text
同样两个事务，但都按【行A → 行B】的固定顺序访问:
  T1 acquire(行A): ✓
  T2 acquire(行A): ✗ 阻塞   ← T2 在第一步就等待，还没持有任何锁
  T1 acquire(行B): ✓
  检测死锁: ✓ 无环——不可能死锁
```

**关键在于「T2 在还没持有任何锁时就开始等」**——这同时破坏了「持有并等待」和「循环等待」两个条件。

> **注意**：真实锁管理器还有**意向锁**（IS/IX）——在表级标记「我在表里某些行上有锁」，让「要加表锁的事务」不必逐行检查；间隙锁与 Next-Key 锁是 InnoDB 挡幻读的手段；等待队列通常是 FIFO 的，以避免饥饿（本例的玩具实现没有队列）。

## 8. C#

C# 版量化了**锁粒度**这个最影响并发的设计选择。

### 三种粒度的吞吐对比（实测）

| 线程数 | 表锁（1 把） | 条带锁（16 把） | 行锁（4096 把） | 行锁 vs 表锁 |
|--------|------------|---------------|---------------|-------------|
| 1 | 7 ms | 7 ms | 7 ms | 0.98x |
| 2 | 17 ms | 8 ms | 8 ms | 2.23x |
| 4 | 38 ms | 14 ms | 12 ms | 3.23x |
| **8** | **80 ms** | **17 ms** | **13 ms** | **6.25x** |

**注意单线程那一行**：三者几乎一样。**锁的开销不在「加锁」这个动作，而在「等待」**——没有竞争时，加解锁只是几十纳秒。

### 条带锁：工程上的折中

```text
16 把锁覆盖 4096 行，靠 hash(rowId) % 16 分配
→ 内存只有行锁的 1/256，并发度却已接近行锁（17 ms vs 13 ms）
→ 代价: 【假冲突】——两行碰巧落在同一条带上就会互相等待
→ Java 的 ConcurrentHashMap(JDK7)、各类分片计数器用的都是这个思路
```

### 读写锁：一个诚实的反直觉结果（实测）

```text
8 线程 × 20000 次操作（90% 读 / 10% 写）:
  普通互斥锁: 3 ms
  读写锁:     5 ms（慢 1.42x）
```

**读写锁竟然更慢**：

```text
理论上读读相容，读多写少时读写锁应该赢
但读写锁自身的【记账开销】不小（要维护读者计数、处理写者优先级等）
临界区极短时，这些开销超过了并发带来的收益
→ 数据库绕开了这个问题: MVCC 让读【根本不加锁】（第 48 章），比读写锁更彻底
```

**这也解释了一个历史脉络**：早期数据库靠 S 锁做读并发，现代数据库几乎全部转向 MVCC——**因为「不加锁」永远比「加一把更聪明的锁」快**。

### 四种系统对死锁的处理（对照表）

| 系统 | 死锁怎么办 | 你需要做什么 |
|------|-----------|-------------|
| 你的进程内 | 永久挂起（第 41 章） | 自己保证加锁顺序 |
| InnoDB | 自动检测 + 回滚一方 | 捕获错误并**重试整个事务** |
| PostgreSQL | 自动检测 + 回滚一方 | 同上（`deadlock_timeout`） |
| SQLite | 不会死锁（单写者） | 处理 `SQLITE_BUSY` 并重试 |

> **注意**：EF Core 加锁只能走原生 SQL（`FromSqlRaw("SELECT ... FOR UPDATE")`）；捕获死锁看 `SqlException.Number == 1205`（SQL Server）或 `PostgresException.SqlState == "40P01"`；重试必须重试**整个事务**（包括第一次读，因为快照要重新取）。

## 9. SQL

### 显式加锁的语法（跨数据库对照）

```sql
SELECT ... FOR UPDATE              -- 加 X 锁（PostgreSQL / MySQL / Oracle）
SELECT ... FOR SHARE               -- 加 S 锁（MySQL 8；旧版是 LOCK IN SHARE MODE）
SELECT ... FOR UPDATE NOWAIT       -- 拿不到就【立刻报错】，不等待
SELECT ... FOR UPDATE SKIP LOCKED  -- 跳过被锁的行（任务队列的标准写法）
-- sqlite: 没有这些语法，用 BEGIN IMMEDIATE 代替（Python 版实测）
```

### `SKIP LOCKED`：任务队列的正确姿势

```text
N 个 worker 同时抢任务，若用普通 FOR UPDATE:
  worker 2..N 全都【排队等 worker 1】→ 并发度退化成 1
用 FOR UPDATE SKIP LOCKED:
  每个 worker 自动跳过别人锁住的行，各拿各的 → 真并发
```

```sql
SELECT id FROM job WHERE state='pending'
ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED;
```

**这是「用数据库当任务队列」唯一正确的写法**——没有它，多个消费者会互相排队而不是并行消费。

### 间隙锁：挡住幻读的代价（第 48 章的伏笔）

```text
普通行锁只能锁住【已存在的行】，挡不住别人【插入新行】（幻读）
间隙锁锁住行【之间的空隙】: 锁了 (10, 20) 这个区间，就没人能插入 15

代价一: 锁的范围远大于你实际读到的行
代价二: 【极易制造意料之外的死锁】——两个事务锁了互相重叠的区间
→ PostgreSQL 不用间隙锁，靠 MVCC 快照挡幻读
  （第 48 章实测两家 RR 行为不同的根源就在这里）
```

### 读后写为什么必须加锁

```sql
-- ⚠️ 危险写法
SELECT balance FROM account WHERE id=1;    -- 读到 100
-- 此刻别的事务可能已经把它改了
UPDATE account SET balance = 90 WHERE id=1;  -- 用的是【过期的值】

-- ✓ 正确写法一: 让数据库自己算（原子，无需读）
UPDATE account SET balance = balance - 10 WHERE id = 1;
-- ✓ 正确写法二: 读的时候就锁住
SELECT balance FROM account WHERE id=1 FOR UPDATE;
```

### 三种锁策略的选择

```text
悲观锁(FOR UPDATE): 冲突多、事务短、必须成功 → 库存扣减、座位预订
乐观锁(version 列) : 冲突少、或【跨请求】编辑 → 表单保存（第 48 章实测的分界）
无锁(原子语句)     : 能写成一条 UPDATE 就别读 → SET balance = balance - 10
→ 优先级: 无锁 > 乐观 > 悲观。能不加锁就不加，这是并发设计的第一原则
```

> **注意**：`FOR UPDATE` 在 `LEFT JOIN` 的右表上行为各家不同（PostgreSQL 需要 `OF table_name` 指定）；`NOWAIT` 和 `SKIP LOCKED` 是 SQL:2016 标准，MySQL 8.0+ 和 PostgreSQL 9.5+ 都支持；死锁错误码：MySQL 1213、PostgreSQL 40P01、SQLSTATE 40001。

## 10. 五语言横向对比

### ① 锁相关能力对照

| 能力 | SQL | Java | C# | Python | JavaScript |
|------|-----|------|-----|--------|-----------|
| 显式行锁 | `FOR UPDATE` | 走 SQL | 走原生 SQL | `BEGIN IMMEDIATE`（sqlite） | 同左 |
| 死锁检测 | 数据库自动 | **`findDeadlockedThreads()`** | 无内建 | 无内建 | 无内建 |
| 锁超时 | `innodb_lock_wait_timeout` | `tryLock(t)` | `Monitor.TryEnter(t)` | `timeout=` 参数 | `PRAGMA busy_timeout` |
| 读写锁 | S/X 锁 | `ReentrantReadWriteLock` | `ReaderWriterLockSlim` | `threading` 无内建 | 无 |
| 跳过锁定行 | **`SKIP LOCKED`** | — | — | — | — |
| 死锁错误码 | 40001 / 1213 / 40P01 | `SQLState` | `SqlException.Number` | `OperationalError` | 异常消息 |

### ② 钥匙实验一：死锁检测算法（C++ 实测）

```text
等待图: T1 ──等待──> T2 ──等待──> T1
检测: DFS 找到环 T1 → T2 → T1 = 死锁
选受害者: T1（持锁最少）→ 回滚 → 另一方立刻推进 ✓
```

### ③ 钥匙实验二：三种「卡住」只有一种可检测（Java 实测）

```text
本章死锁（等待图有环）     → findDeadlockedThreads() ✓ 抓到 2 个 WAITING 线程
第 45 章线程饥饿死锁       → ✗ 检测不到（没有锁的环）
第 48 章写偏斜             → ✗ 检测不到（根本没有冲突）
```

### ④ 钥匙实验三：锁粒度决定并发（C# 实测）

```text
8 线程: 表锁 80 ms / 条带锁 17 ms / 行锁 13 ms → 行锁快 6.25x
1 线程: 三者都是 7 ms → 锁的开销不在加锁，而在【等待】
条带锁: 1/256 的内存，接近行锁的并发 —— 工程上的最优折中
```

### ⑤ 钥匙实验四：退避的价值（JS 实测）

```text
同一个 120ms 障碍:
  立刻重试: 17641 次尝试，120 ms
  指数退避:     8 次尝试，127 ms
→ 2205 倍的无效请求换来 0 速度提升
```

### ⑥ 共性与根因

**共性**：所有语言都提供互斥锁与超时获取；**只有 Java 内建死锁检测**（`findDeadlockedThreads()`）；所有语言的进程内锁都**没有回滚能力**——所以死锁只能预防，不能恢复。

**根因**：

- **数据库敢让死锁发生，是因为它能回滚**——事务是它的底气，而进程内的锁没有「后悔药」；
- **Java 内建死锁检测**是因为 JVM 掌握全部锁信息（`synchronized` 和 `java.util.concurrent` 的锁都注册在 JVM 里），其他语言的锁是库级实现，运行时看不见；
- **只有 SQL 有 `SKIP LOCKED`**——因为只有数据库同时管理「数据」和「谁在锁它」，能在扫描时跳过；
- **现代数据库转向 MVCC 而非更聪明的读写锁**——C# 实测印证了原因：读写锁的记账开销在短临界区下反而更慢，**「不加锁」永远比「加一把聪明的锁」快**；
- **sqlite 选择单写者**是嵌入式场景的合理取舍：牺牲写并发，换来「不可能死锁」和零配置。

## 11. 底层实现对比

| 数据库 | 锁粒度 | 死锁处理 | 关键细节 |
|--------|--------|---------|---------|
| **SQLite** | 整库写锁 | 不会死锁 | 单写者；WAL 下读者不阻塞 |
| **MySQL/InnoDB** | 行锁 + 间隙锁 + 意向锁 | 等待图检测，回滚**修改行数少**的一方 | 锁加在索引条目上；无索引则锁全部扫过的行 |
| **PostgreSQL** | 行锁 + 表级意向锁 | `deadlock_timeout`（默认 1s）后才检测 | 不用间隙锁；靠 MVCC 挡幻读 |
| **SQL Server** | 行/页/表，**会锁升级** | 检测 + 回滚代价小的一方 | 约 5000 行触发升级 |
| **Oracle** | 行锁 | 立即检测 | 读永不加锁（最早的 MVCC 实现之一） |

**PostgreSQL 的「延迟检测」值得一提**：

```text
它不是每次锁等待都跑一遍找环算法（那太贵）
而是先等 deadlock_timeout（默认 1 秒），超时后才构建等待图检测
→ 因为绝大多数锁等待都是【正常的短暂等待】，不值得为它做全图扫描
→ 代价: 真死锁要多卡 1 秒才被解除
```

## 12. 性能分析

### 本章实测数字速查

```text
锁粒度（8 线程）: 表锁 80 ms / 条带锁 17 ms / 行锁 13 ms → 6.25x
锁粒度（1 线程）: 三者都是 7 ms → 无竞争时加锁成本可忽略
条带锁内存:      1/256 的行锁内存，接近行锁的并发
读写锁:          3 ms（互斥）vs 5 ms（读写锁）→ 短临界区下读写锁【更慢】1.42x
退避:            17641 次 vs 8 次尝试，耗时相同（120 vs 127 ms）
busy_timeout:    0/50/200ms 设置 → 实际等待 0/62/234 ms
WAL 读不阻塞:    写者持锁未提交时，读者 0.037 ms 零等待
固定顺序:        2 线程 × 20000 次双行加锁，7 ms，零死锁
```

### 锁竞争的三个层次

```text
① 无竞争    → 加锁开销几十纳秒，可忽略（实测 1 线程时三种粒度一样快）
② 轻度竞争  → 短暂等待，吞吐略降（实测 2~4 线程）
③ 重度竞争  → 【串行化】，吞吐随线程数增加而【恶化】（实测表锁 8 线程 80 ms）
→ 优化锁的第一步永远是: 先确认你真的处在第 ③ 层
```

> ⚠️ **锁优化最常见的错误是在第 ① 层做优化**。没有竞争时，把互斥锁换成读写锁、无锁结构、更细的粒度，全都只会**增加**开销——C# 实测的读写锁反而慢 1.42x 就是活例。**先测量竞争程度，再决定要不要动锁。**

## 13. 工程实践

| 场景 | ✅ 推荐 | ❌ 避免 | 原因 |
|------|--------|--------|------|
| 计数器/余额更新 | 原子 `UPDATE ... SET v = v + 1` | 读到内存改完写回 | 无锁最快，且不会丢更新 |
| 读后写（扣库存） | `SELECT ... FOR UPDATE` | 先读再写不加锁 | 中途被改就错了 |
| 跨请求编辑 | 乐观锁（version 列） | 持有数据库锁 | 无法持锁 5 分钟（第 48 章） |
| 多行事务 | **按固定顺序（如 id 升序）加锁** | 按业务顺序（先扣款方） | 实测顺序一致就不可能死锁 |
| 任务队列 | `FOR UPDATE SKIP LOCKED` | 普通 `FOR UPDATE` | 后者让消费者退化成串行 |
| 批量更新 | 分批提交（每批几百行） | 一次更新百万行 | 触发锁升级，并发归零 |
| `UPDATE`/`DELETE` 的条件列 | **确保有索引** | 无索引的条件 | 实测会锁住扫过的所有行 |
| 锁等待超时 | 设成「可容忍的最长响应时间」 | 用默认值（可能 50 秒） | 太长会耗尽连接池（第 45 章） |
| 重试 | **指数退避 + 次数上限** | 立刻无限重试 | 实测 2205 倍无效请求，0 收益 |
| 重试范围 | 重试**整个事务** | 只重试失败的那条语句 | 快照要重新取（第 48 章） |
| sqlite 读后写 | `BEGIN IMMEDIATE` | 默认的 `BEGIN` | 实测升级写锁会失败 |
| 排查锁问题 | 看数据库的锁视图 | 猜 | `pg_locks` / `sys.innodb_lock_waits` |

### 一句话决策

```text
① 能写成一条原子 UPDATE 吗？ → 能 → 不用锁（最优）
② 必须先读再写吗？           → 是 → FOR UPDATE 或 BEGIN IMMEDIATE
③ 要动多行吗？               → 是 → 按固定顺序（id 升序）加锁
④ 条件列有索引吗？           → 没有 → 先建索引，否则会锁全表
⑤ 冲突了怎么办？             → 捕获 + 指数退避 + 重试整个事务
```

## 14. 最佳实践

- **能不加锁就不加**：优先级永远是「无锁原子语句 > 乐观锁 > 悲观锁」——实测读写锁在短临界区下反而更慢 1.42x。
- **多行操作按固定顺序加锁**：这是唯一实用的死锁预防手段（实测顺序一致就不可能有环）；转账要按 `id` 升序，而不是「先扣款方」。
- **确保 `UPDATE`/`DELETE` 的条件列有索引**：实测无索引会锁住扫过的所有行——第 49 章的索引**同时决定查询速度和锁范围**。
- **重试必须指数退避**：实测无退避的 17641 次尝试与退避的 8 次耗时相同，**两千倍的无效请求换来零收益**，还会在高并发下引发雪崩。
- **重试整个事务而非单条语句**：快照要重新取，否则你会基于过期数据重做一遍。
- **sqlite 的「读后写」用 `BEGIN IMMEDIATE`**：默认的延迟事务在升级写锁时会失败（实测），且这个失败很难在测试环境复现。
- **批量更新分批提交**：一次锁太多行会触发锁升级（SQL Server 约 5000 行），并发瞬间归零。
- **先测量竞争，再优化锁**：无竞争时加锁只要几十纳秒（实测单线程三种粒度一样快），此时任何「锁优化」都是净开销。

## 15. 常见坑

**坑 1 · 按业务顺序加锁导致死锁**

```sql
-- ⚠️ 甲转乙锁 1→2，乙转甲锁 2→1，两者相遇即死锁
UPDATE account SET balance = balance - 10 WHERE id = :from;
UPDATE account SET balance = balance + 10 WHERE id = :to;
-- ✅ 先锁 min(from,to)，再锁 max(from,to)
```

**坑 2 · 无索引的 UPDATE 锁住全表**

```sql
UPDATE seat SET taken = 1 WHERE taken = 0;   -- ⚠️ taken 无索引 → 锁住扫过的全部行
-- ✅ 先给条件列建索引（第 49 章）
```

**坑 3 · 无退避的重试**

```python
while True:
    try: do_txn(); break
    except OperationalError: pass    # ⚠️ 实测 17641 次无效尝试，0 收益
```

**坑 4 · sqlite 用默认 `BEGIN` 做读后写**

```python
con.execute("BEGIN")                 # ⚠️ 延迟事务，只拿读锁
v = con.execute("SELECT ...").fetchone()[0]
con.execute(f"UPDATE ... {v-10} ...")  # ⚠️ 升级写锁失败: database is locked
# ✅ con.execute("BEGIN IMMEDIATE")
```

**坑 5 · 任务队列用普通 `FOR UPDATE`**

```sql
SELECT id FROM job WHERE state='pending' LIMIT 1 FOR UPDATE;  -- ⚠️ N 个消费者排队
-- ✅ ... FOR UPDATE SKIP LOCKED
```

**坑 6 · 只重试失败的语句**

```python
except Deadlock:
    cur.execute(failed_sql)      # ⚠️ 事务已回滚，基于过期快照重做
# ✅ 重试整个事务，从 BEGIN 开始
```

**坑 7 · 锁等待超时设得过长**

```text
innodb_lock_wait_timeout = 50   # ⚠️ 请求线程被占 50 秒 → 连接池耗尽（第 45 章）
```

## 18. 本章总结

**一句话**：MVCC 把「读」从锁里解放了出来（第 48 章），剩下的**写写冲突**就是这一章的全部战场——手写的锁管理器把数据库每天做的三件事拆开了：**相容矩阵**只有一条规则（读读相容，其余互斥）、**死锁检测**就是在等待图上 DFS 找环（实测 `T1 → T2 → T1`）、**选受害者**是挑持锁最少的那个；Java 版让 JVM 用 `findDeadlockedThreads()` 抓到了同样的死锁，并由此给出本章最重要的对照——**第 45 章的线程饥饿和第 48 章的写偏斜，同样的工具都检测不到**，「数据库自动处理死锁」只覆盖等待图有环的那一种；C# 版量化了**锁粒度即并发上限**（8 线程下行锁比表锁快 **6.25x**，而单线程时三者一样快——**锁的开销不在加锁而在等待**），也解释了锁升级为什么是双刃剑；Python 版揭开了 sqlite 延迟事务**升级写锁必然失败**的隐蔽坑；而 JS 版给出了最实用的一条教训——面对同一个障碍，**立刻重试 17641 次与指数退避 8 次耗时相同**，两千倍的无效请求换来零收益，只会在高并发下把一个慢事务放大成雪崩。

**关键要点**

- **相容矩阵一条规则**：读读不冲突，只要沾上写就冲突；但 MVCC 下 S 锁已很少见。
- **死锁检测三步**（实测）：建等待图 → DFS 找环 → 选持锁最少者回滚。
- **数据库敢让死锁发生**：因为它能回滚；进程内的锁没有后悔药，只能预防。
- **三种「卡住」只有一种可检测**：等待图有环 ✓；线程饥饿 ✗；写偏斜 ✗。
- **锁粒度决定并发上限**（实测 6.25x）；但细粒度要付内存，故有锁升级。
- **锁的开销不在加锁而在等待**（实测单线程三种粒度一样快 7 ms）。
- **锁加在索引条目上**（实测）：条件列无索引 → 锁住扫过的所有行。
- **退避的价值**（实测）：17641 次 vs 8 次尝试，耗时相同——无退避纯属浪费且危险。
