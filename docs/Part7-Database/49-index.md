# 第 49 章 · 索引

**简体中文** ｜ [English](./49-index.en-US.md)

---

> 第 46 章实测过十万行里找一行，文件扫描比 sqlite 主键查询慢 **551 倍**；第 47 章实测过加一个索引让执行计划从 `SCAN` 变成 `SEARCH`，而 SQL 一个字都没改。但索引**到底是什么**、为什么能快几百倍、代价又在哪？这一章把它拆开。
>
> 本章的**钥匙实验**是手写一棵 B+ 树，并测出那个决定一切的量——**扇出如何决定树高**。同样一百万个键：扇出 2（就是教科书里的二叉树）树高 **20**，每次查询访问 20 个节点；扇出 128（典型数据库页）树高 **3**，只访问 3 个节点。内存里这没什么了不起，但**每个节点 = 一次磁盘页读取**时，20 次和 3 次就是 2ms 和 0.3ms 的差别。更惊人的是它的增长速度：键从 1000 涨到 1000 万（一万倍），树高只从 **2 涨到 4**。
>
> 那为什么不用哈希索引？实测给出了答案：内存里哈希点查确实最快，但范围查询 `1000 <= key <= 3000` 上，B+ 树 **0.40 ms**、哈希 **757.9 ms——慢 1892 倍**，因为哈希把顺序彻底打乱了，只能全部扫一遍。Java 版用 `HashMap` 与 `TreeMap` 复现了同一个结论（范围查询 **533x**）。**B+ 树用一种结构覆盖了等值、范围、排序、前缀四类查询**，这就是它成为默认选择的原因。
>
> 但索引不是免费的加速器，它是**一份需要同步维护的数据副本**。Python 实测：从 0 个索引加到 4 个，插入 20 万行从 106 ms 变成 **337 ms（3.18x）**，文件从 5.2 MB 涨到 **15.9 MB（3.06x）**；JS 实测三种写操作全部变慢，其中 `DELETE` 最惨——**6.75x**。
>
> 还有两个反直觉的实测。其一，**索引不是永远更快**：命中 4 行时走索引比全表扫快 **180 倍**，而命中 33% 时全表扫反而快 **1.6 倍**——因为回表是随机 I/O，扫表是顺序 I/O（C# 版用 61 MB 的宽行表量出了这个交叉点，并测出打乱访问顺序会慢 **3.1 倍**）。其二，**sqlite 在这个低选择性查询上选错了**——它仍然用了索引。「优化器会自动选最优」是有前提的。
>
> 最后是**最左前缀原则**：复合索引 `(a, b, c)` 能服务 `WHERE a`、`WHERE a AND b`、`WHERE a AND b AND c`，也能服务 `WHERE a AND c`（但**只用上 a 那一列**）；而 `WHERE b` 和 `WHERE b AND c` **一列都用不上**。索引的列顺序就是它的能力边界——**建错顺序等于白建**。

## 1. 学习目标

学完本章，你将能够：

- 解释**扇出如何决定树高**，并说清为什么磁盘索引用 B+ 树而不用二叉树（实测 20 vs 3 个节点）；
- 说出 B+ 树相对哈希索引的决定性优势（实测范围查询快 **1892x**），以及三个专为磁盘做的设计决策；
- 量化索引的代价：**写放大**（实测插入 3.18x、删除 6.75x）与**空间**（3.06x）；
- 用**选择性**判断一个索引值不值得建，并解释「回表是随机 I/O」为什么让高命中率查询更适合全表扫描；
- 应用**最左前缀原则**设计复合索引，并用 `EXPLAIN` 验证它真的被用上了。

## 2. 为什么会出现这个概念

### 前两章留下的问题

```text
第 46 章实测: 十万行里查 20 次，文件扫描 399.8ms vs sqlite 主键 0.726ms → 551x
第 47 章实测: 加索引让计划从 SCAN 变 SEARCH，SQL 一个字没改
→ 但「索引」这个黑盒里到底是什么？
```

### 问题的本质：磁盘上的数据没有顺序可言

```text
第 20 章的哈希表 O(1) 查找、第 21 章的二叉树 O(log n)——它们都活在【内存】里
磁盘上的一张表就是一堆按插入顺序排列的行，要找某一行只能【从头看到尾】: O(n)
→ 索引就是「在数据之外，额外维护一份【有序的】结构，用它来定位」
```

**一句话定义**：

```text
索引 = 一份【额外的、有序的、需要同步维护的】数据副本，
      用空间和写入速度，换查询速度
```

**这个定义的每个修饰词后面都有一笔账**，本章会把它们逐一量出来：

| 修饰词 | 代价 | 本章实测 |
|--------|------|---------|
| 额外的 | 占磁盘 | 4 个索引 → 文件 3.06x |
| 有序的 | 插入要维护顺序 | 插入 3.18x、删除 6.75x |
| 需要同步维护 | 每次写都要改 | UPDATE 也慢 2.97x |

> **一句话总结**：索引不是「让数据库变快的开关」，而是一笔**用写入速度和存储空间购买查询速度的交易**——这一章的全部内容就是把交易的两边都称一称。

## 3. 底层原理

### 钥匙实验一：扇出决定树高

**为什么数据库用 B+ 树而不用教科书里的二叉搜索树？** C++ 版手写 B+ 树给出了答案（100 万个键）：

| 扇出 | 树高 | 节点总数 | 每次点查 | 相当于 |
|------|------|---------|---------|--------|
| **2** | **20** | 1,000,007 | 访问 20 节点 | 二叉树（教科书里的树） |
| 8 | 7 | 142,860 | 访问 7 节点 | |
| **128** | **3** | 7,876 | **访问 3 节点** | 典型数据库页（4KB / 32B 每键） |
| 512 | 3 | 1,959 | 访问 3 节点 | 大页或窄键的索引 |

```text
内存里 20 次 vs 3 次节点访问算不上什么
但每个节点 = 【一次磁盘页读取】(~100μs) 时:
  20 页 = 2ms    3 页 = 0.3ms    → 快 6.7x
→ 这就是 B+ 树存在的全部理由: 把树压扁，让每次 I/O 都读回尽可能多的信息
```

### 树高增长得有多慢（B+ 树最反直觉的性质）

```text
      1000 个键，扇出 128 → 树高 2
    100000 个键，扇出 128 → 树高 3
  10000000 个键，扇出 128 → 树高 4
```

**数据量涨一万倍，树高只从 2 涨到 4**——查询成本几乎不变。这就是索引能「一次建好、一直有效」的数学基础：`log_128(N)` 增长得极慢。

### B+ 树的三个设计决策（每一个都为磁盘服务）

```text
① 数据【只放叶子】，内部节点只放分隔键
   → 内部节点能塞下更多键 → 扇出更大 → 树更矮

② 叶子之间【串成链表】
   → 范围扫描不用回到根节点，直接顺着链表顺序读

③ 节点大小 = 【磁盘页大小】（通常 4KB/8KB/16KB）
   → 一次 I/O 读回一个完整节点，不浪费任何一次读
```

**对比第 21 章的二叉搜索树**：它为**内存**设计，每节点 1 个键、树高 `log₂ n`；B+ 树为**磁盘**设计，每节点上百个键、树高 `log_f n`。**同一个问题，因为存储介质不同而有了不同的最优解。**

### 钥匙实验二：哈希索引的死穴

**内存里的点查对决**（100 万行，2 万次查询，C++ 实测）：

```text
全表扫描    : 2286.5 ms  O(n)
有序数组二分:    0.8 ms  O(log n)，快 2838x
B+ 树       :    1.2 ms  O(log_f n)，3 次节点访问
哈希表      :    0.6 ms  O(1)，快 3567x
```

**注意 B+ 树并没有比二分查找快**——内存里两者都是 `O(log n)` 而二分更省指针跳转。**B+ 树的优势不在内存**：有序数组无法高效插入，而 B+ 树可以，且它为磁盘优化。

**但范围查询彻底改变了排名**：

```text
查询「1000 <= key <= 3000」1000 次（命中 1001 行）:
  B+ 树: 0.40 ms（下钻到起点叶子，然后沿叶子链表走，共访问 11 个节点）
  哈希 : 757.9 ms（慢 1892x —— 哈希打乱了顺序，只能【全部扫一遍】）
```

**Java 版用 `HashMap` / `TreeMap` 复现了同一结论**：

```text
点查 20 万次: HashMap 12.8 ms，TreeMap 70.7 ms（哈希快 5.5x）
范围查询 2000 次: HashMap 全扫 7279.6 ms，TreeMap 区间 13.7 ms（有序快 533x）
```

**结论**：

```text
哈希索引: 只能回答「等于」
B+ 树   : 等于 / 大于 / 小于 / BETWEEN / 前缀 LIKE / ORDER BY / MIN / MAX 全部能答
→ 一种结构覆盖绝大多数查询形态 —— 这就是数据库默认建 B+ 树索引的原因
```

**有序结构白送的三个能力**（Java 实测）：

```text
最小/最大: firstKey/lastKey  → SQL 的 MIN()/MAX() 走索引是 O(log n) 而非 O(n)
前驱/后继: floorKey/ceilingKey → SQL 的 >= / <= / BETWEEN
天然有序:  叶子本来就排好序   → SQL 的 ORDER BY 免排序（实测快 1652x）
```

### 钥匙实验三：索引的代价

**Python 实测**（20 万行，逐步增加索引数量）：

| 索引数 | 插入耗时 | 倍数 | 文件大小 | 倍数 |
|--------|---------|------|---------|------|
| 0（只有主键） | 106 ms | 1.00x | 5.2 MB | 1.00x |
| 1 | 152 ms | 1.44x | 7.5 MB | 1.46x |
| 2 | 211 ms | 1.99x | 9.8 MB | 1.89x |
| 3 | 262 ms | 2.47x | 11.8 MB | 2.28x |
| **4** | **337 ms** | **3.18x** | **15.9 MB** | **3.06x** |

**JS 实测三种写操作全都变慢**：

```text
操作                无索引        1 个索引      3 个索引
INSERT 150000 行     90 ms       125 ms(1.40x)  212 ms(2.36x)
UPDATE 30000 行       9 ms        26 ms(2.97x)   26 ms(2.95x)
DELETE 30000 行       5 ms        19 ms(4.15x)   31 ms(6.75x)
```

```text
→ UPDATE 尤其贵: 改一个被索引的列 = 索引里【先删旧位置，再插新位置】两次操作
→ DELETE 最惨（6.75x）: 每个索引里都要找到并删掉对应的条目
→ 索引加速的是【读】，它拖慢的是【所有的写】
```

### 钥匙实验四：索引不是永远更快

**Python 用 `INDEXED BY` / `NOT INDEXED` 强制两种执行方式，直接对比**：

```text
高选择性 a=5   命中      4 行（ 0.00%）: 走索引  0.06 ms   全表扫 10.13 ms → 索引快 180x
低选择性 c=1   命中  66667 行（33.33%）: 走索引 23.81 ms   全表扫 14.94 ms → 【全表扫快 1.6x】
```

**为什么会反转？因为访问模式不同**：

```text
走索引: 在 B+ 树里定位 → 拿到一堆行号 → 【逐个回表】= 随机访问
全表扫: 从第一页读到最后一页          = 顺序访问
→ 命中行数少时，随机访问几次就够了，完胜
→ 命中行数多时，成千上万次随机访问 > 一次顺序扫描
```

**C# 用 61 MB 的宽行表量出了这个交叉点**：

```text
命中    1000 行（  0.1%）: 回表 0.0 ms   全表扫 1.9 ms → 索引更快
命中   10000 行（  1.0%）: 回表 0.1 ms   全表扫 1.9 ms → 索引更快
命中  100000 行（ 10.0%）: 回表 0.7 ms   全表扫 2.3 ms → 索引更快
命中  300000 行（ 30.0%）: 回表 2.0 ms   全表扫 2.3 ms → 索引更快
命中  500000 行（ 50.0%）: 回表 3.3 ms   全表扫 1.8 ms → 【全表扫更快】
命中 1000000 行（100.0%）: 回表 6.4 ms   全表扫 2.3 ms → 【全表扫更快】
```

**并且直接测出了随机与顺序的差距来源**：

```text
读【同样的 100 万行】: 顺序 2.0 ms，打乱顺序 6.3 ms（慢 3.1x）
→ 行数完全一样，只是【访问顺序】不同——差距全部来自 CPU 缓存行与硬件预取
```

**⚠️ 但要注意本例的交叉点很高（约 30~50%）**，因为内存里随机只比顺序慢约 3 倍。**磁盘上随机 I/O 比顺序慢一到两个数量级**，所以真实数据库的交叉点低得多——常见经验值是**命中超过 5%~20% 就该放弃索引走全表扫**。

### 一个诚实的发现：sqlite 在这里选错了

```text
Python 实测: 低选择性查询下全表扫快 1.6x
但 sqlite 实际选了: SEARCH t USING INDEX idx_c (c=?)
→ 它【仍然用了索引】——本例中它选错了
→ sqlite 的代价模型比 PostgreSQL 简单得多
```

**「优化器会自动选最优」是有前提的**：它依赖统计信息的准确性和代价模型的精细度。低选择性列上的索引往往是净负担——建了它，优化器还可能被它误导。

## 4. JavaScript

JS 版承包了索引代价的完整账单。

### 三种写操作全都变慢（实测）

```text
操作                无索引        1 个索引      3 个索引
INSERT 150000 行     90 ms       125 ms(1.40x)  212 ms(2.36x)
UPDATE 30000 行       9 ms        26 ms(2.97x)   26 ms(2.95x)
DELETE 30000 行       5 ms        19 ms(4.15x)   31 ms(6.75x)
文件大小             15.4 MB      17.1 MB(1.11x) 21.7 MB(1.40x)
```

**注意 UPDATE 的特殊之处**：改一个被索引的列，索引里要做**两次**操作——在旧位置删除、在新位置插入（因为 B+ 树按值排序，值变了位置就要变）。所以**「频繁更新的列不适合建索引」**不是玄学。

### 选择性：同样是索引，价值天差地别（实测）

```text
列 a: 30000 个不同值，选择性 0.20000，查一个值命中     5 行（ 0.0%）
列 b:     7 个不同值，选择性 0.00005，查一个值命中 21429 行（14.3%）
```

```text
选择性 = 不同值个数 / 总行数，越接近 1 越值得建索引
→ 性别、状态、布尔这类列【单独】建索引几乎总是浪费: 命中太多，回表比扫表还慢
→ 但它们放进【复合索引的后面几列】仍然有用（配合前面高选择性的列）
```

### 索引也需要维护：碎片与统计信息（实测）

```text
删掉一半行后页数 4699 → VACUUM 后 2351（回收 50%）
```

```text
删除不会立刻把空间还给操作系统: 页里留下空洞（第 33 章的内存碎片，磁盘版）
统计信息也会过期: ANALYZE 之后优化器才知道「这个值大概命中多少行」
→ PostgreSQL 的 autovacuum 同时做这两件事（第 48 章 MVCC 的版本回收也靠它）
```

### 什么时候【不】该建索引

```text
① 小表: 几百行全扫只要几微秒，索引下钻反而是净开销
② 低选择性列: 见上——性别/布尔/状态
③ 写多读少的表: 日志/流水表，写放大直接吃掉全部收益（实测 6.75x）
④ 从来没出现在 WHERE/ORDER BY/JOIN 里的列: 建了也不会被用上
→ 建索引的正确触发条件是【一条具体的慢查询】，而不是「这列看起来会被查」
```

> **注意**：批量导入时**先删索引 → 导入 → 再建索引**比边插边维护快得多，因为 `CREATE INDEX` 是**批量排序构建**（C++ 版就是这么建树的），而逐行插入是随机写；用 `SELECT name, sql FROM sqlite_master WHERE type='index'` 查看已有索引；永远用 `EXPLAIN QUERY PLAN` 确认索引真的被用上了。

## 5. Python

Python 版是索引行为的主战场——最左前缀、选择性交叉点、覆盖索引、免排序全部实测。

### 最左前缀原则（实测，强制使用 `idx_abc`）

复合索引 `(a, b, c)`：

| 查询条件 | 用上了几列 | 计划 |
|---------|-----------|------|
| `WHERE a = 5` | 前 **1** 列 | `SEARCH ... COVERING INDEX idx_abc (a=?)` |
| `WHERE a = 5 AND b = 7` | 前 **2** 列 | `SEARCH ... (a=? AND b=?)` |
| `WHERE a = 5 AND b = 7 AND c = 1` | 前 **3** 列 | `SEARCH ... (a=? AND b=? AND c=?)` |
| `WHERE a = 5 AND c = 1` | 前 **1** 列 | `SEARCH ... (a=?)` ← c 用不上 |
| `WHERE b = 7` | **0** 列 | `SCAN t USING COVERING INDEX idx_abc` |
| `WHERE b = 7 AND c = 1` | **0** 列 | `SCAN t USING COVERING INDEX idx_abc` |

**为什么？把复合索引想成按「省-市-街道」排序的电话簿**：

```text
知道省份 → 能定位到一段
知道省份和城市 → 能定位到更小的一段
只知道街道 → 无从下手，因为街道只在【每个「省-市」分组内部】有序
→ 「a AND c」只能用上 a 那一段: c 在每个 (a,b) 分组内才有序，跨分组是乱的
→ 所以复合索引的【列顺序】就是它的能力边界，建错顺序等于白建
```

### 覆盖索引：连表都不用回（实测）

```text
SELECT a, b   （列全在索引里）: 0.125 ms  SEARCH ... USING COVERING INDEX idx_abc (a<?)
SELECT a, name（name 要回表）: 0.240 ms  SEARCH ... USING INDEX idx_abc (a<?)
→ 慢 1.9x
```

**计划里 `COVERING` 一词消失，就意味着每命中一行都要回表一次**。这也是第 47 章「别写 `SELECT *`」的根因：**它保证了覆盖索引永远用不上**。

### 索引的第二个用途：替代排序（实测）

```text
ORDER BY a   （有索引）:  0.006 ms   SCAN t USING COVERING INDEX idx_abc
ORDER BY name（无索引）:    9.4 ms   SCAN t | USE TEMP B-TREE FOR ORDER BY
→ 快 1652x
```

**B+ 树的叶子本来就有序**，`ORDER BY` 直接顺着叶子链表走即可，无需排序。**看到 `USE TEMP B-TREE FOR ORDER BY` 就说明数据库在临时排序**——这是建索引的明确信号。

> **注意**：`INDEXED BY` / `NOT INDEXED` 是 sqlite 的强制提示，用来做对比实验很好用，但**不该写进生产代码**（数据分布变了它就成了枷锁）；`ANALYZE` 之后优化器才有统计信息；sqlite 的 `EXPLAIN QUERY PLAN` 只返回计划树，`EXPLAIN` 返回字节码（很少需要看）。

## 6. Java

Java 版把「哈希 vs 有序树」这道选择题搬回内存，证明它和数据库面对的是同一个问题。

### 对应关系

```text
HashMap         ←→ 哈希索引（MySQL MEMORY 引擎、PostgreSQL HASH 索引）
                    只能等值，不能范围/排序
TreeMap（红黑树）←→ B+ 树索引（几乎所有数据库的默认）
                    等值/范围/排序全支持
→ 区别在【扇出】: 红黑树每节点 1 个键（树高 log₂ n），
  B+ 树每节点上百个键（C++ 版实测树高 3）——因为红黑树为内存设计，B+ 树为磁盘设计
```

### 实测数据

```text
① 点查 20 万次:      HashMap 12.8 ms，TreeMap 70.7 ms（哈希快 5.5x）
② 范围查询 2000 次:  HashMap 全扫 7279.6 ms，TreeMap 区间 13.7 ms（有序快 533x）
④ 插入 20 万条:      HashMap 26 ms，TreeMap 53 ms（有序慢 2.1x）
```

**这三行数字完整概括了这道选择题**：哈希点查快、有序范围快、有序插入慢。数据库选了后者，因为**范围查询和排序太常见了**，而点查那 5.5 倍的差距在磁盘 I/O 面前微不足道。

### 有序结构白送的能力（实测）

```text
firstKey=0  lastKey=1999998           → MIN()/MAX() 走索引是 O(log n) 而非 O(n)
floorKey(1001)=1000  ceilingKey(1001)=1002  → >= / <= / BETWEEN
前几个键 [0, 2, 4, 6, ...]            → ORDER BY 免排序
```

> **注意**：想同时要「有序 + O(1) 点查」就两个结构一起维护——**数据库正是这么干的**：主键 B+ 树存数据，二级索引 B+ 树存「列值 → 主键」，取完整数据时回表再查一次；JDBC 侧用 `DatabaseMetaData.getIndexInfo()` 可以列出表上的索引；别在 Java 里手工缓存整表来「代替索引」——第 46 章实测过它的内存代价（46 MB 堆）。

## 7. C++

C++ 版是本章的钥匙实验：**手写一棵 B+ 树**。

### 批量构建（真实数据库 `CREATE INDEX` 也是这么建的）

```cpp
// ① 先把有序键切成叶子
for (size_t i = 0; i < sorted.size(); i += fanout) { /* 一个叶子装 fanout 个键 */ }
// 串起叶子链表（范围扫描靠它）
for (size_t i = 0; i + 1 < level.size(); ++i) nodes_[level[i]].next = level[i + 1];
// ② 自底向上建内部层，直到只剩一个根
while (level.size() > 1) { /* 每 fanout 个节点归到一个父节点 */ }
```

**为什么批量构建比逐行插入快得多**：逐行插入是**随机写 + 频繁的节点分裂**；批量构建是**排一次序然后顺序填充**。所以大批量导入数据时，**先删索引、导完再建**是标准做法。

### 点查：数节点访问次数（= 磁盘页读取次数）

```cpp
bool find(int key, int& visits) const {
    int cur = root_;
    while (true) {
        ++visits;                                    // 每访问一个节点 = 一次磁盘页读
        const Node& n = nodes_[cur];
        if (n.leaf) return std::binary_search(n.keys.begin(), n.keys.end(), key);
        size_t idx = std::upper_bound(n.keys.begin(), n.keys.end(), key) - n.keys.begin();
        cur = n.children[idx];
    }
}
```

**`visits` 是这个实验的灵魂**：在内存里测时间意义有限，但**数节点访问次数**直接对应真实数据库的磁盘 I/O 次数。

### 范围扫描：沿叶子链表走

```cpp
while (!nodes_[cur].leaf) { /* 先下钻到 lo 所在的叶子 */ }
while (cur != -1) {                                  // 然后顺着叶子链表扫
    for (int k : nodes_[cur].keys) { if (k > hi) return cnt; if (k >= lo) ++cnt; }
    cur = nodes_[cur].next;
}
```

**这几行就是 B+ 树打败哈希的全部原因**（实测 1892x）：找到起点后，**顺序读**即可，不用回到根节点。

### 索引也是数据，也要占空间（实测）

```text
100 万个键的 B+ 树: 7876 个节点（其中叶子 7813 个）
若每节点 = 一个 4KB 页 → 索引占 30.8 MB
```

**注意叶子占了 99.2%**——内部节点只有 63 个。这印证了设计决策 ①：**内部节点只放分隔键，所以极少；数据都在叶子**。

> **注意**：真实 B+ 树还要处理**插入时的节点分裂**与**删除时的节点合并**（本例是批量构建，回避了这部分）；节点内部通常还做**前缀压缩**（相邻键共享前缀，进一步提升扇出）；InnoDB 的页是 16KB，PostgreSQL 是 8KB。

## 8. C#

C# 版回答了一个更底层的问题：**「回表」为什么这么贵**。

### 随机访问 vs 顺序访问的交叉点（实测，61 MB 宽行表）

```text
命中    1000 行（  0.1%）: 回表 0.0 ms   全表扫 1.9 ms → 索引更快
命中   10000 行（  1.0%）: 回表 0.1 ms   全表扫 1.9 ms → 索引更快
命中  100000 行（ 10.0%）: 回表 0.7 ms   全表扫 2.3 ms → 索引更快
命中  300000 行（ 30.0%）: 回表 2.0 ms   全表扫 2.3 ms → 索引更快
命中  500000 行（ 50.0%）: 回表 3.3 ms   全表扫 1.8 ms → 【全表扫更快】
命中 1000000 行（100.0%）: 回表 6.4 ms   全表扫 2.3 ms → 【全表扫更快】
```

### 差距的来源：缓存局部性（实测）

```text
读【同样的 100 万行】: 顺序 2.0 ms，打乱顺序 6.3 ms（慢 3.1x）
→ 行数完全一样，只是【访问顺序】不同
→ 差距全部来自 CPU 缓存行与硬件预取
```

**磁盘上同一个道理，只是量级从「缓存行」变成「4KB 页 + 寻道」**——所以真实数据库的交叉点比本例低得多（经验值 5%~20%）。

### 聚簇索引 vs 非聚簇索引

```text
聚簇(clustered):   表数据【本身】就按索引顺序物理排列
  → InnoDB 的主键、SQL Server 的聚簇索引；每张表只能有一个
  → 主键范围查询是顺序 I/O（极快）

非聚簇(secondary): 索引里只存「列值 → 主键」，取完整数据要回表
  → 所以 InnoDB 的二级索引查询是【两次 B+ 树下钻】: 先查索引拿主键，再用主键查数据
```

**「自增主键比随机 UUID 快」的根因就在这里**：

```text
自增主键: 新行总是追加在【最后一页】→ 顺序写，页利用率高
随机 UUID: 新行落在【随机页】→ 每次插入都可能触发页分裂 + 随机写
→ 不是玄学，是聚簇索引的物理布局决定的
```

> **注意**：EF Core 用 `[Index(nameof(Prop))]` 或 `modelBuilder.HasIndex(...)` 声明索引，`.HasIndex(x => new { x.A, x.B })` 建复合索引（**注意列顺序**），`.IncludeProperties(...)` 对应 SQL Server 的 `INCLUDE`（做覆盖索引而不增加索引键宽度）；EF Core 的迁移**不会替你判断索引是否值得建**——那是你的工作。

## 9. SQL

本节从 `EXPLAIN` 的视角看索引什么时候被用上、什么时候被放弃。

### 索引能服务的四种条件形态（实测）

```text
等值 amount = 500:                SEARCH ... COVERING INDEX idx_amount (amount=?)
范围 amount > 900:                SEARCH ... COVERING INDEX idx_amount (amount>?)
区间 amount BETWEEN 100 AND 200:  SEARCH ... COVERING INDEX idx_amount (amount>? AND amount<?)
排序 ORDER BY amount LIMIT 10:    SCAN ... COVERING INDEX idx_amount（无需临时排序）
→ 等值/范围/区间/排序全能服务——因为 B+ 树的叶子是【有序链表】
```

### 用不上索引的三种写法（实测）

```text
列上有表达式 amount + 0 = 500:   SCAN
前导通配 status LIKE '%ped':      SCAN
否定条件 amount != 500:           SCAN
```

**前两种第 47 章实测过**（慢 1283x / 420x）。**第三种是新的**：「不等于」意味着要取几乎所有行，走索引反而更慢——**这次优化器主动放弃是对的**。

### 部分索引：只索引你真正查的那部分行（实测）

```sql
CREATE INDEX idx_active ON orders(user_id) WHERE status != 'cancelled';
```

```text
索引只覆盖 75000 / 100000 行
→ 体积更小、维护更便宜
→ 「软删除」表的标配: 大量 deleted=1 的行根本不必进索引
```

### 表达式索引：给「列上有函数」的查询一条活路（实测）

```sql
CREATE INDEX idx_month ON orders(substr(created, 6, 2));
```

```text
EXPLAIN: SEARCH orders USING INDEX idx_month (<expr>=?)
→ 把表达式本身建成索引，SCAN 又变回 SEARCH
→ PostgreSQL 同款: CREATE INDEX ON t (lower(email))
```

**这是「列上不能套函数」这条规则的正式解药**：如果某个函数表达式是你的高频查询条件，就为它本身建一个索引。

### 索引的元信息

```sql
SELECT name FROM sqlite_master WHERE type = 'index' AND tbl_name = 'orders';
```

```text
→ 每一个索引都在拖慢 INSERT（Python 版实测 4 个索引 → 插入慢 3.18x）
→ 定期检查「哪些索引从来没被用过」:
  PostgreSQL 查 pg_stat_user_indexes.idx_scan，MySQL 查 sys.schema_unused_indexes
```

> **注意**：sqlite 的部分索引要求 `WHERE` 子句是确定性表达式；表达式索引在查询里必须**原样写出同一个表达式**才能命中；`REINDEX` 可以重建索引（碎片严重时）；主键在 sqlite 里是 `rowid` 的别名，天然聚簇。

## 10. 五语言横向对比

### ① 索引相关能力对照

| 能力 | SQL | C++ | Java | C# | JavaScript / Python |
|------|-----|-----|------|-----|--------------------|
| 有序结构 | B+ 树索引 | `std::map`（红黑树） | `TreeMap` | `SortedDictionary` | JS 无内建 / Python `bisect` |
| 哈希结构 | 哈希索引（少数） | `unordered_map` | `HashMap` | `Dictionary` | `Object`/`Map` / `dict` |
| 范围查询 | ✅ `BETWEEN` | `lower_bound` | `subMap` | `GetViewBetween` | 手写 / `bisect` |
| 复合键 | ✅ 复合索引 | `std::tuple` 作键 | 记录类作键 | 元组作键 | 拼接字符串 |

| 覆盖索引 | ✅ | — | — | — | — |
| ORM 侧声明 | — | — | JPA `@Index` | EF `[Index]` | Prisma `@@index` |

### ② 钥匙实验一：扇出决定树高（C++ 实测）

```text
100 万个键: 扇出 2 → 树高 20（访问 20 节点）  扇出 128 → 树高 3（访问 3 节点）
树高增长: 1000 键 → 2；10 万键 → 3；1000 万键 → 4
→ 每个节点 = 一次磁盘页读取(~100μs) → 2ms vs 0.3ms
```

### ③ 钥匙实验二：B+ 树 vs 哈希（C++ / Java 实测）

```text
点查:     哈希更快（C++ 0.6 vs 1.2 ms；Java HashMap 快 5.5x）
范围查询: B+ 树碾压（C++ 1892x；Java TreeMap 快 533x）
→ 数据库选 B+ 树: 一种结构覆盖等值/范围/排序/前缀四类查询
```

### ④ 钥匙实验三：索引的代价（Python / JS 实测）

```text
Python: 0→4 个索引，插入 106→337 ms（3.18x），文件 5.2→15.9 MB（3.06x）
JS:     INSERT 2.36x、UPDATE 2.97x、DELETE 6.75x（全都变慢）
```

### ⑤ 钥匙实验四：索引不是永远更快（Python / C# 实测）

```text
Python: 命中 0.00% → 索引快 180x；命中 33% → 全表扫快 1.6x
C#:     交叉点在 30%~50% 之间（内存）；磁盘上经验值 5%~20%
差距来源: 顺序 2.0 ms vs 打乱顺序 6.3 ms（3.1x，缓存行与预取）
⚠️ sqlite 在低选择性查询上【仍然用了索引】——它选错了
```

### ⑥ 共性与根因

**共性**：所有语言都提供「哈希 + 有序」两种结构，面对的是与数据库完全相同的选择题；所有有序结构的插入都比哈希贵（Java 实测 2.1x）；**没有任何语言的内存结构能替代数据库索引**——因为它们不持久、不支持并发事务、且要先把全表读进内存（第 46 章实测 46 MB 堆）。

**根因**：

- **数据库选 B+ 树而非二叉树**——因为瓶颈是**磁盘 I/O 次数**而不是比较次数，扇出把树压扁（实测 20 → 3）；
- **数据库选 B+ 树而非哈希**——因为范围查询和排序太常见（实测 1892x / 533x），一种结构覆盖四类查询比两种结构各管一半更划算；
- **只有 SQL 有部分索引和表达式索引**——因为只有数据库同时掌握「数据」和「查询」，能为特定查询形态定制索引；
- **内存语言不需要「覆盖索引」的概念**——因为内存里没有「回表」这回事，数据和索引本来就在同一个地址空间；
- **索引的所有代价都源于同一件事**：它是数据的**副本**，副本必须与原本保持同步（实测写放大 2~7 倍）。

## 11. 底层实现对比

| 数据库/引擎 | 索引结构 | 关键细节 |
|------------|---------|---------|
| **SQLite** | B 树（表与索引都是） | 页 4KB；表本身是按 rowid 组织的 B 树 |
| **MySQL/InnoDB** | B+ 树 | 页 16KB；**主键聚簇**，二级索引存主键 → 回表两次下钻 |
| **PostgreSQL** | B 树（默认）+ Hash/GiST/GIN/BRIN | 页 8KB；表是堆（heap），**所有索引都是二级索引** |
| **SQL Server** | B+ 树 | 聚簇索引可选；`INCLUDE` 列做覆盖而不进索引键 |
| **LSM 树**（RocksDB/Cassandra） | 有序字符串表 + 内存表 | **写优化**：顺序追加，后台合并；读要查多层 |

**PostgreSQL 与 InnoDB 的关键差异**：

```text
InnoDB:     数据【就存在主键 B+ 树的叶子里】→ 主键查询一次下钻直达
            二级索引叶子存主键 → 要完整数据得【再下钻一次主键树】
PostgreSQL: 表是无序的堆，主键也是二级索引 → 任何索引查询都要回堆取数据
            但它有 index-only scan: 若列全在索引里且可见性位图允许，就不回堆
→ 这解释了为什么 InnoDB 特别强调「主键要短」（每个二级索引都存了它一份）
```

**LSM 树是另一条路**（第 46 章追加日志的极致版本）：

```text
B+ 树: 原地更新 → 读快，写要随机 I/O
LSM 树: 只追加 + 后台合并 → 写极快（顺序 I/O），读要查多层（有布隆过滤器缓解）
→ 写多读少选 LSM，读多写少选 B+ 树——又一次「用一边换另一边」
```

## 12. 性能分析

### 本章实测数字速查

```text
扇出与树高:   扇出 2 → 树高 20；扇出 128 → 树高 3（100 万键）
树高增长:     1000 键 2 层；10 万键 3 层；1000 万键 4 层
范围查询:     B+ 树 0.40 ms vs 哈希 757.9 ms（1892x）
点查（内存）: 哈希 0.6 ms < 二分 0.8 ms < B+ 树 1.2 ms << 全扫 2286 ms
写放大:       插入 3.18x（4 个索引）、UPDATE 2.97x、DELETE 6.75x
空间:         4 个索引 → 文件 3.06x；100 万键的 B+ 树 ≈ 30.8 MB
选择性交叉点: 命中 0.00% 索引快 180x；命中 33% 全表扫快 1.6x
覆盖索引:     1.9x（内存中；磁盘上更大）
免排序:       1652x（ORDER BY 有索引 vs 无索引）
随机 vs 顺序: 3.1x（同样 100 万行，只是访问顺序不同）
```

### 索引优化的优先级

```text
① 先找到【具体的慢查询】——没有慢查询就不要建索引
② EXPLAIN 看它是 SCAN 还是 SEARCH
③ 是 SCAN → 检查条件能否被索引服务（列上有表达式？前导 %？）
④ 能服务 → 建索引，选择性高的列放复合索引前面
⑤ 建完再 EXPLAIN 确认真的用上了
⑥ 定期清理【从来没被用过】的索引（它们只有代价没有收益）
```

> ⚠️ **索引的收益是非线性的，代价是线性的**。第一个索引可能带来 100 倍加速，第十个索引大概率一次都用不上——但它照样让每次写入多付一份钱。**索引数量应该由慢查询驱动，而不是由表的列数驱动。**

## 13. 工程实践

| 场景 | ✅ 推荐 | ❌ 避免 | 原因 |
|------|--------|--------|------|
| 决定建不建索引 | 由具体慢查询驱动 | 「这列可能会查」就建 | 实测每个索引写入 +40% 起 |
| 复合索引列顺序 | 高选择性、等值查询的列在前 | 随手写 | 实测跳过第 1 列则一列都用不上 |
| 低选择性列（状态/性别） | 放进复合索引的后几列 | 单独建索引 | 命中太多，回表比扫表慢 |
| 只查部分行（软删除表） | 部分索引 `WHERE deleted = 0` | 全表索引 | 实测只覆盖 75% 的行，更小更快 |
| 查询里列上有函数 | 表达式索引 | 放弃索引 | `SCAN` 能变回 `SEARCH` |
| 高频查询的少数列 | 覆盖索引 | `SELECT *` | 实测 1.9x，且 `SELECT *` 永远用不上 |
| `ORDER BY` 慢 | 给排序列建索引 | 加内存/换机器 | 实测 1652x |
| 批量导入 | 先删索引 → 导入 → 再建 | 边插边维护 | 批量构建是排序填充，逐行插入是随机写 |
| 主键选择 | 自增/有序 ID | 随机 UUID | 聚簇索引下随机主键引发页分裂 |
| 频繁更新的列 | 慎重建索引 | 无脑建 | 实测 UPDATE 慢 2.97x（删+插两次） |
| 索引治理 | 定期查未使用的索引并删除 | 只增不减 | 只有代价没有收益 |
| 验证 | 每次都 `EXPLAIN` | 相信「应该会用上」 | 实测 sqlite 也会选错 |

### 一句话决策

```text
建索引前问三件事:
  ① 有【具体的】慢查询吗？        → 没有就别建
  ② 这一列的选择性够高吗？        → 不同值 / 总行数，太低就别单独建
  ③ 这张表写多还是读多？          → 写多读少时，写放大会吃掉收益
建完必做一件事: EXPLAIN 确认它真的被用上了
```

## 14. 最佳实践

- **索引由慢查询驱动，不由列数驱动**：实测每加一个索引，插入 +40%、删除最高 +575%——而多数「预防性」索引一次都用不上。
- **复合索引的列顺序就是它的能力边界**：实测跳过第 1 列则一列都用不上；把**高选择性、等值查询**的列放最前面。
- **低选择性列不要单独建索引**：实测 33% 命中率时全表扫反而快 1.6 倍——它们只适合做复合索引的后缀列。
- **只查部分行就用部分索引**：软删除表的标配，实测能把索引缩到 75%。
- **列上有函数时用表达式索引**：这是第 47 章「不能在列上套函数」的正式解药。
- **批量导入先删索引后重建**：`CREATE INDEX` 是批量排序构建（C++ 版的建树方式），比逐行维护快得多。
- **主键用自增而非随机 UUID**：聚簇索引下随机主键会让每次插入落在随机页，引发页分裂和随机写。
- **永远用 `EXPLAIN` 验证**：实测 sqlite 在低选择性查询上**也会选错**——「优化器会自动选最优」是有前提的。

## 15. 常见坑

**坑 1 · 给每一列都建索引**

```sql
CREATE INDEX i1 ON t(a); CREATE INDEX i2 ON t(b); ...   -- ⚠️ 实测插入慢 3.18x，文件涨 3.06x
```

**避免**：由慢查询驱动；定期用 `pg_stat_user_indexes.idx_scan` 找出从没被用过的索引并删掉。

**坑 2 · 复合索引列顺序建反**

```sql
CREATE INDEX idx ON t(status, user_id);   -- ⚠️ 若查询总是 WHERE user_id = ?，这个索引用不上
CREATE INDEX idx ON t(user_id, status);   -- ✅ 高选择性的列在前
```

**坑 3 · 给布尔/状态列单独建索引**

```sql
CREATE INDEX idx ON orders(is_paid);   -- ⚠️ 只有 2 个值，命中 50%，实测全表扫更快
```

**坑 4 · 以为建了索引就一定被用上**

```sql
-- ⚠️ 实测 sqlite 在低选择性查询上选了索引（错的），而列上套函数时又完全用不上
EXPLAIN QUERY PLAN SELECT ...;   -- ✅ 每次都验证
```

**坑 5 · 随机 UUID 做聚簇主键**

```sql
id UUID PRIMARY KEY DEFAULT gen_random_uuid()   -- ⚠️ InnoDB 下每次插入落在随机页
-- ✅ 用自增 ID，或有序 UUID（UUIDv7 / ULID）
```

**坑 6 · 批量导入时保留索引**

```python
for row in ten_million_rows:      # ⚠️ 每行都要维护所有索引的 B+ 树
    conn.execute("INSERT ...")
# ✅ DROP INDEX → 导入 → CREATE INDEX（批量排序构建）
```

**坑 7 · 忘了索引也会碎片化**

```text
⚠️ 实测删掉一半行后，页数没变（4699），VACUUM 后才降到 2351
✅ PostgreSQL 靠 autovacuum；必要时 REINDEX
```

## 18. 本章总结

**一句话**：索引是一份**额外的、有序的、需要同步维护的数据副本**——它用写入速度和存储空间购买查询速度，而本章把这笔交易的两边都称了一遍：收益侧，手写 B+ 树实测出决定一切的那个量——**扇出决定树高**（100 万个键，扇出 2 树高 **20**、扇出 128 树高 **3**；且数据涨一万倍树高只从 2 到 4），因为每个节点就是一次磁盘页读取，这直接决定了查询要做几次 I/O；而 B+ 树打败哈希索引靠的是**范围查询**（实测 **1892x**，Java 的 `TreeMap` vs `HashMap` 复现为 **533x**），它用一种结构覆盖了等值/范围/排序/前缀四类查询；代价侧，实测从 0 到 4 个索引让插入慢 **3.18x**、文件涨 **3.06x**，而 `DELETE` 最惨达 **6.75x**；更重要的是**索引并不总是更快**——命中 4 行时索引快 **180x**，命中 33% 时全表扫反而快 **1.6x**，因为回表是随机 I/O 而扫表是顺序 I/O（C# 实测同样的行数只因访问顺序不同就差 **3.1x**），而且实测发现 **sqlite 在这个查询上选错了**；最后是**最左前缀原则**——复合索引 `(a,b,c)` 服务 `WHERE b` 时**一列都用不上**，**列顺序就是索引的能力边界**。

**关键要点**

- **扇出决定树高**（实测）：扇出 2 → 20 层，扇出 128 → 3 层；每层 = 一次磁盘 I/O。
- **树高增长极慢**：1000 键 2 层，1000 万键 4 层——索引「一次建好、一直有效」的数学基础。
- **B+ 树 vs 哈希**（实测 1892x / 533x）：哈希只能等值，B+ 树覆盖等值/范围/排序/前缀。
- **三个磁盘导向的设计**：数据只放叶子、叶子串成链表、节点大小 = 页大小。
- **写放大**（实测）：4 个索引 → 插入 3.18x、空间 3.06x；`UPDATE` 2.97x、`DELETE` 6.75x。
- **选择性交叉点**（实测）：命中 0.00% 索引快 180x，命中 33% 全表扫快 1.6x；磁盘上经验值 5%~20%。
- **最左前缀**（实测）：`(a,b,c)` 能服务 `a` / `a,b` / `a,b,c` / `a`（跳过 b 时只用 a）；`b` 与 `b,c` 完全用不上。
- **覆盖索引免回表**（实测 1.9x）与**索引免排序**（实测 1652x）是两个常被忽略的收益。
